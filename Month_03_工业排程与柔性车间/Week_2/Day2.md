## 2. 为什么 Day 2 要单独谈「合法解怎么构造」

Day 1 把决策拆成了两维，但还留着一个更基础的问题没回答：

```text
给定一个 assignment（每道工序一台机器）与一个 order（工序的先后顺序），
怎么把它变成一个**排程**？而且怎么保证这个排程一定合法？
```

这不是形式问题。`order` 是一个长度 `n` 的工序排列，而排程要求每条工艺路线上的先后
必须成立。随手给一个排列，很可能让后道工序排在前道之前 —— 这种「排程」在车间里意味着
零件还没加工就先装配，是**非法解**。M1 与 M2 的教训是：非法解必须在构造阶段就被挡住，
而不是留给最后的目标函数去发现（那时它已经被当成一个合法的候选解参与比较了）。

所以解码器要同时做三件事：

```text
1. 构造：把 (assignment, order) 变成每道工序的 (机器, 开工, 完工)
2. 把关：检查输入是否合法（顺序是不是拓扑序、机器是不是合格、有没有漏工序）
3. 复核：产物交给**独立**验证器再验一遍，不自己给自己发合格证
```

第 3 条是 M1 与 M2 留下来的纪律：`fjsp_core.schedule_validation` 里的 `validate_schedule`
不经过本模块的任何代码，它重新查机器重叠、工艺路线、机器资格与释放时间。
解码器自己说「我构造得对」不算证据。

另外，解码策略的选择直接决定解的质量上限。今天要对比的两种解码器，
在同一个输入上会给出不同长度的时间线 —— 这就是「合法性」之外的第二个问题。

## 3. 概念：顺序、拓扑序与两类解码

### 3.1 定义（拓扑序）

> **定义（拓扑序）**：`order` 是全部工序的一个排列。若对每张订单 `j` 的工艺路线
> `O_{j1} -> O_{j2} -> ... -> O_{jk}`，`order` 中 `O_{j i}` 总是出现在 `O_{j,i+1}` 之前，
> 则称 `order` 是一个**拓扑序**。

每条工艺路线是一条链（没有分叉），所以拓扑序的个数有一个闭式：

```text
拓扑序个数 = n! / Π_j (k_j!)        （多项式系数）
```

`2` 个订单、每个订单 `2` 道工序时：`4! / (2! * 2!) = 24 / 4 = 6`。也就是说，
`24` 个排列里有 `18` 个是非法顺序 —— 四分之三。

> **理论结论（为什么只能枚举拓扑序）**：解码时每道工序的开工下界是「它同订单前道工序的
> 完工时刻」。若顺序不是拓扑序，后道工序会被排到前道之前，工艺路线的先后约束就被绕过了。
> 这类排程**过不了独立验证器**（验证器会报 `precedence` 错误），而且它常常给出一个比真最优
> 更小的假值 —— 今天不求这个假值，只要记住它不能冒充最优。

### 3.2 附加式解码（append）

```text
按 order 依次放置每道工序：
    开工 = max(订单已完工时刻, 该机器已用到的最晚时刻)
    完工 = 开工 + 该工序在这台机器上的工时
    更新：订单已完工时刻 = 完工；机器已用到的最晚时刻 = 完工
```

机器只维护一个「末尾指针」，工序永远接在它后面。优点是逻辑极简、容易手推；
缺点是**看不见已经出现的空档**：某台机器在 `[0, 12)` 之间空着，附加式也不会把工序放进去。

### 3.3 插入式解码（insert / gap-filling）

```text
按 order 依次放置每道工序：
    开工 = 该机器上第一个 >= 订单已完工时刻 且能放下本工序工时的空档起点
    完工 = 开工 + 工时
    把 [开工, 完工) 记进该机器的占用区间列表
```

机器维护的是一张**占用区间表**，工序可以插进任何放得下的空隙。它生成的排程属于
**主动排程（active schedule）** 族 —— 通俗地说就是「没有任何一道工序能被合法地往左推」。

> **理论结论（主动排程族）**：`makespan` 目标下，主动排程族里一定含有一个最优排程。
> 因此**只枚举主动排程不会丢最优**。注意这条结论的适用条件：目标必须是**正则**目标
> （完工时间不减少的函数）；换成迟交类目标，最优解可能需要「故意空等」的非主动排程，
> 结论就不再成立 —— 插入式解码本身不保证最优，它只保证落在主动排程族里。

### 3.4 非延迟派工（dispatch）

前两条路线都要求外部先给一个 `order`。派工反过来：不要求外部顺序，让**状态**决定下一步。

```text
每一步：候选 = 每个订单工艺路线上的下一道待排工序
        对每个候选算出「它最早能开工/完工」（用当前机器空闲时刻与订单进度）
        按规则挑一个，放下它，更新状态
        重复直到全部工序排完
```

| 规则 | 排序键（越小越优先） | 直觉 |
|---|---|---|
| `ect` | 预计完工时刻 | 让机器尽快空出来 |
| `est` | 最早可开工时刻 | 先消化能立刻开工的工序 |
| `spt` | 在该机器上的工时 | 短工序先做 |
| `mwkr` | 剩余工作量（越大越优先） | 剩余活多的订单先推 |

派工产出的排程是**非延迟**的：机器只要有活就立刻开工，不允许空等。非延迟排程是主动排程
的一个子集，所以派工的表达能力**弱于**插入式解码 —— 代价换来的是「不需要外部顺序」
与「每一步都有明确依据」。平局一律按 `(job.id, operation.id)` 升序决胜，保证可复现。

## 4. 推导：空档是被什么逼出来的

今天的实验实例 `gap_2x2` 专门为「两种解码的差距」设计，工时如下：

| 工序 | 订单 | M0 | M1 | 工艺路线 |
|---|---|---|---|---|
| `O00` | `J0` | 2 | 4 | `J0`: `O00 -> O01` |
| `O01` | `J0` | 3 | 5 | |
| `O10` | `J1` | 9 | 8 | `J1`: `O10 -> O11` |
| `O11` | `J1` | 2 | 6 | |

待手算的指派与顺序：

```text
assignment = {O00: M1, O01: M0, O10: M1, O11: M0}
order      = (O00, O10, O11, O01)
```

这个顺序是拓扑序：`J0` 的 `O00` 排在 `O01` 前，`J1` 的 `O10` 排在 `O11` 前。

**关键结构**：`O11` 在 `M0` 上只要 `2` 分钟（比 `M1` 的 `6` 分钟快），但它是 `J1` 的第二道
工序，必须等 `O10` 做完。而 `O10` 被指派到了 `M1`、要 `8` 分钟，还得排在 `O00` 后面 ——
`M1` 上 `O00` 占 `[0, 4)`、`O10` 接着占 `[4, 12)`。于是：

```text
O10 在 M1 上 [4, 12)  ->  O11 最早只能在 t = 12 开工
O01 是 J0 的第二道工序，要等 O00 完工（t = 4）才允许进 M0
-> M0 在 [0, 4) 上没有一道合格的候选工序：这段时间只能空着，尽管它一开始就是空的
-> t = 4 之后 M0 才接得上活：插入式把 O01 放进 [4, 7)，附加式却一直等到 t = 12
```

这段空档不是机器的问题，是**工艺路线**逼出来的。附加式解码看不见它，插入式解码看得见。

## 5. 手算：17 与 14 两条时间线

### 5.1 附加式解码逐步推

```text
放置 O00（M1，4 分钟）：M1 末尾 = 0，J0 已完工 = 0
    → 开工 max(0, 0) = 0，完工 4          时间线：O00@M1[0,4)
    更新：M1 末尾 = 4，J0 已完工 = 4

放置 O10（M1，8 分钟）：M1 末尾 = 4，J1 已完工 = 0
    → 开工 max(4, 0) = 4，完工 12         时间线：O10@M1[4,12)
    更新：M1 末尾 = 12，J1 已完工 = 12

放置 O11（M0，2 分钟）：M0 末尾 = 0，J1 已完工 = 12
    → 开工 max(0, 12) = 12，完工 14       时间线：O11@M0[12,14)
    更新：M0 末尾 = 14，J1 已完工 = 14

放置 O01（M0，3 分钟）：M0 末尾 = 14，J0 已完工 = 4
    → 开工 max(14, 4) = 14，完工 17       时间线：O01@M0[14,17)
makespan = max(4, 12, 14, 17) = 17
```

### 5.2 插入式解码逐步推

```text
放置 O00（M1，4 分钟）：M1 占用表空，J0 已完工 = 0
    → 开工 0，完工 4                      O00@M1[0,4)      M1 占用表 = {[0,4)}
    J0 已完工 = 4

放置 O10（M1，8 分钟）：M1 占用表 {[0,4)}，J1 已完工 = 0
    → 候选起点 0 被 [0,4) 挡住，推到 4；4 之后无占用 → 开工 4，完工 12
                                          O10@M1[4,12)     M1 占用表 = {[0,4), [4,12)}
    J1 已完工 = 12

放置 O11（M0，2 分钟）：M0 占用表空，但 J1 已完工 = 12
    → 开工 max(12, 0) = 12，完工 14        O11@M0[12,14)    M0 占用表 = {[12,14)}
    J1 已完工 = 14

放置 O01（M0，3 分钟）：J0 已完工 = 4；M0 占用表 = {[12,14)}
    → 从 4 起找空隙：[12,14) 之前有 [4,12) 这段 8 分钟的空档，3 分钟放得下
    → 开工 4，完工 7                      O01@M0[4,7)
makespan = max(4, 12, 14, 7) = 14
```

两条时间线并排：

```text
附加式（17）：M1  O00[0,4) O10[4,12)
              M0  ............(空等 12 分钟)............ O11[12,14) O01[14,17)
插入式（14）：M1  O00[0,4) O10[4,12)
              M0  ....(空 4 分钟).... O01[4,7) ....(空).... O11[12,14)
```

省下 `17 - 14 = 3` 分钟，全部来自把 `O01` 塞进 `[4, 7)` 这段本会浪费掉的时间。
注意 `O01` 在 `order` 里是**最后**一个被放置的，插入式解码仍然把它放到了时间轴的前段 ——
「放置顺序」与「时间顺序」是两件事，这是插入式解码最容易让人迷惑的地方。

## 6. 实现：`decode` 与 `dispatch`

代码在 [fjsp.py](../../projects/03_industrial_fjsp/fjsp_shop/fjsp.py)。两个入口的签名：

```python
decode(instance, assignment, order, *, insert=True) -> Schedule
dispatch(instance, assignment, *, rule="ect") -> Schedule
```

`decode` 的骨架（去掉注释后的核心）：

```python
job_ready = {job.id: job.release_time for job in instance.jobs}
busy = {m.id: [] for m in instance.machines}       # 插入式：区间表
free_from = {m.id: 0 for m in instance.machines}   # 附加式：末尾指针
for operation_id in order:
    op = operations[operation_id]
    machine_id = assignment[operation_id]
    minutes = op.time_on(machine_id)               # 不合格机器返回 None
    earliest = job_ready[op.job_id]
    if insert:
        start = _earliest_fit(busy[machine_id], earliest, minutes)
        busy[machine_id].append((start, start + minutes))
        busy[machine_id].sort()
    else:
        start = max(earliest, free_from[machine_id])
    end = start + minutes
    free_from[machine_id] = max(free_from[machine_id], end)
    job_ready[op.job_id] = end
    placed.append(ScheduledOperation(op.id, machine_id, start, end))
schedule = Schedule(tuple(sorted(placed, key=_placement_key)))
validate_schedule(instance, schedule)              # 独立复核，不是自证
return schedule
```

三个细节值得单独指出：

| 细节 | 做法 | 理由 |
|---|---|---|
| 空档查找 | `_earliest_fit(intervals, earliest, minutes)` | 把「找空隙」抽成一个纯函数：输入是区间表、下界与工时，输出是一个开工时刻，单独就能手推 |
| 输出顺序 | 按 `(start_time, machine_id, operation_id)` 排序 | 让同一份排程永远打印成同一行，可复现比较的前提 |
| 释放时间 | `job_ready` 初值是 `release_time` 而不是 `0` | 释放时间是开工时刻的下界，模型与解码器都照做，不需要额外分支 |

`dispatch` 的骨架则是「候选集 + 键函数」的循环（第 3.4 节）。规则通过 `rule` 字符串选择，
落在 `DISPATCH_RULES = ("ect", "est", "spt", "mwkr")` 里；未知规则直接抛 `ValueError`，
而不是回落到默认规则 —— 静默回落会让一次实验的结论归因到错误的规则上。

**四道闸门**在解码前就把非法输入挡住（第 7 节会把报错原文打出来）：

```text
order 的元素集合 != 全部工序        -> ValueError: order must list every operation exactly once
order 违反工艺路线                  -> ValueError: order must respect the process route: ...
assignment 缺一道工序               -> ValueError: assignment is missing operation ...
工序被指到不合格的机器               -> ValueError: 'O00' cannot run on 'M9'
```

  每道工序各取最快机器的总工时 = 15，本指派的负载合计 = 17。

  解码器不判断好坏，只保证合法：指派是它的输入，不是它的输出。

### 7.1 怎么读这段输出

**第 2 节的两条时间线要对着第 5 节的手推逐行核。** 打印的排程按开工时刻排序，
所以插入式的第二行是 `O01@M0[4,7)` —— 它是 `order` 里最后一个被放置的工序，
却排在时间轴的第二位。

**第 3 节是今天最容易被误读的一段。** 它做的是「固定指派、只换顺序」：

```text
附加式：14 ~ 17（差 3）      插入式：14 ~ 15（差 1）
```

括号里的「最差/最好」不是质量的上下限，而是**同一个指派下顺序能造成的摆动幅度**。
插入式的摆动更小，因为它自动填了空隙，顺序的影响被削弱了。两个解码在本指派下的
最好值都是 `14`，**都拿不到 `10`** —— `10` 要靠换指派（Day 1 已经看到，`81` 个指派里
最好的那个给 `10`）。这句话是整个第 3 节的重点：顺序有分量，但不是万能药。

**第 4 节的四行要横着看。** 前三个规则（`ect` / `est` / `spt`）给出同一条时间线，
`mwkr` 给出另一条（`17`）。这不是巧合：`mwkr` 优先推「剩余工作量」大的订单，
一开始两个订单的剩余量相同，平局决胜按 `(job.id, operation.id)` 选了 `O00`；
一旦 `O00` 开工，`J1` 的剩余量就相对更大，第二步改推 `O10` —— 于是两条时间线岔开。
派工规则之间的差异要靠**实例结构**才显现，不是每条规则都必然给出不同结果。

**第 5 节的四条报错要当成产品来读。** 它们都指出「错在哪一道工序」或「错在哪个订单」，
而不是笼统地说「输入非法」。这是可运维性的要求：一条报错如果没有坐标，
读日志的人还得自己复现一遍。

**第 6 节的 `15` 与 `17` 是两个不同的量。** `15` 是「每道工序各取最快机器」的总工时，
`17` 是本指派的实际负载合计（`M0: 5 + M1: 12`）。差的 `2` 分钟来自 `O00`：
它被指派到了 `M1`（`4` 分钟）而不是更快的 `M0`（`2` 分钟）。解码器不评判这个选择 ——
它只保证排程合法。

## 10. 自测题

- Q1：`decode` 为什么要求 `order` 恰好包含每道工序一次？少一个或多一个分别会怎样？
- Q2：`4! / (2! * 2!) = 6` 里分母的两个 `2!` 分别对应什么？
- Q3：附加式解码能不能通过「换一个更好的顺序」达到与插入式完全相同的排程集合？为什么？
- Q4：`gap_2x2` 上插入式解码在本指派下的最差值是 `15`，附加式是 `17`。这个差说明了什么？
- Q5：`_earliest_fit` 要求传入的区间列表已排序吗？如果不排序，它会给出什么？
- Q6：`dispatch` 里的候选集合为什么是「每个订单的下一个待排工序」，而不是「全部未排工序」？
- Q7：`mwkr` 用自己的 `work_left[job]` 递减来估计剩余量，这个估计用的是 `min_time` 还是真实指派工时？会影响正确性吗？
- Q8：为什么 `decode` 在返回前调用 `validate_schedule`，而 `validate_schedule` 又必须不依赖 `decode`？
- Q9：如果一个实例某订单的释放时间是 `5`，插入式解码在 `t < 5` 时能不能把该订单的工序放进去？代码里是哪一行保证的？
- Q10：`dispatch` 的平局决胜为什么是 `(job.id, operation.id)` 而不是 `(operation.id, job.id)`？两者的差别在什么实例上会显现？

### 参考答案

- A1：因为 `order` 是「放置顺序」的完整描述：它决定了每道工序被放置的时刻。少一个会导致该工序永远不会被放置（排程缺工序，验证器会报错），所以在输入检查阶段就拒绝；多一个会导致同一道工序被放置两次（机器上出现重复占用）。`decode` 用 `set(order) != set(operations)` 一次拦住两种情况。
- A2：分母的两个 `2!` 分别对应两个订单内部工序的相对顺序。每个拓扑序在 `n!` 个排列里被重复计数 `Π_j k_j!` 次（把每个订单内部那 `k_j` 道工序任意重排，得到的排列在「订单间顺序」意义上与它等价，而它们都非法），所以 `n! / Π_j k_j!` 才是合法顺序数。
- A3：不能。附加式的可达排程集合是插入式的一个**真子集**：附加式只能生成「机器上后到者的开工不早于先到者的完工」这一类（没有插入），而插入式可以生成「后到者插进先到者之前的空档」。`gap_2x2` 第 3 节的数据就是证据：附加式最好 `14` 最差 `17`，插入式最好 `14` 最差 `15`，插入式的取值范围覆盖了附加式的一部分但把下界压得更低（对差顺序而言）。
- A4：说明**顺序的影响被空隙的自动填充削弱了**：插入式解码对顺序不那么敏感。实践含义是：用插入式解码时，优化顺序的收益空间比附加式小，收益更多在「选机」这一维。
- A5：要求已排序（按区间起点）。`decode` 每次插入新区间后都调用 `busy[machine_id].sort()` 维持这个不变量。若不排序，`_earliest_fit` 的「跳过整体在候选起点之前的区间」这一步会失效，可能返回一个与已有区间重叠的开工时刻，产物过不了验证器。
- A6：因为工艺路线是硬约束。如果允许挑「任意未排工序」，就会把某订单的第二道工序排到第一道之前（除非再加一层检查）。候选集定义在「每个订单的下一道」上，就把 precedence 自动保证了，不需要额外逻辑。
- A7：用的是 `min_time`（该工序在最快机器上的工时）。这是一个**乐观估计**，用于排序而不是用于正确性：即使估计不准，派工过程仍然只产出合法排程（合法性与排序键无关，只与「候选是订单下一道工序」有关），所以估计偏差只影响解的质量。
- A8：因为「自己构造、自己检查」不是独立证据：如果解码器把某条约束理解错了，它大概率会用同一种错法去检查自己。`validate_schedule` 从数据模型出发重新推导全部约束（机器不重叠、资格、工艺路线、释放时间），是被验证对象之外的第三方。这与测试里的「期望值不由被测函数生成」是同一条纪律。
- A9：不能。保证这一点的代码是 `earliest = job_ready[op.job_id]`，而 `job_ready` 的初值来自 `{job.id: job.release_time ...}`，所以第一道工序的最早开工就是释放时间；后续工序的 `job_ready` 只会被推向更大的值。插入式解码在找空隙时用这个 `earliest` 作为下界，不会把工序放到释放时间之前。
- A10：`(job.id, operation.id)` 先比订单再比工序，效果是「同一订单的工序自然连成一片」。改成 `(operation.id, job.id)` 在多数实例上给出相同结果，但在订单数超过 `9` 个、工序编号为 `J00_O0` 这类**字典序与实际顺序不一致**的命名上会不同：字符串比较 `J10` < `J2`，于是顺序会按字典序而不是编号错开。差异只在平局时显现，所以要看实例的编号方式。
