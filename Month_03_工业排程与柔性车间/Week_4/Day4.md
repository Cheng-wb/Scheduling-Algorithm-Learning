## 2. 为什么 Day 4 要谈紧急订单

前三天的约束有一个共同点：它们都在**砍可行域**。资质砍掉了不合格的机器组合，
人员容量砍掉了同时占用超限的排法，锁定把可行域收窄到一个点，换型在相邻两段之间插进间隔。
今天要处理的东西形状完全不同：

```text
「这张单子更急」不是一个「不允许这样排」的陈述，而是一个「这样排更糟」的陈述。
它不排除任何一张排程，它只是给不同的排程打不同的分。
```

把这句话写成模型语言：

```text
硬约束版    紧急订单必须最先上机        ->  砍掉可行域，可能砍掉全部最优解
软目标版    紧急订单的迟期在目标里权重更大  ->  可行域不变，最优解可能换一个
```

**为什么必须是软目标版。** 硬约束版有一个致命问题：它**过度承诺**。车间里可能同时有三张
「急单」，而机器只有一台。硬约束版这时直接报不可行 —— 但现实中你不会因为三张单子都急就不生产，
你会按「谁更急一点」排序。硬约束表达不了「更」，只能表达「是/否」，所以它在这种场景下
要么不可行，要么退化成「人为给急单排个序，然后全部钉死」—— 那就把决策权从求解器手里拿走了。

软目标版保留了「更」这个概念：权重是连续的，三张急单可以有不同的 `priority`，
求解器按性价比去排。这也是今天要用一个最小实例把它算清楚的原因 ——
权重的效果只有在「两个顺序原本同分」的临界点上才看得最清楚。

还有一个工程上的理由：优先级与 `due_date`、`weight` 一样，是**订单属性**，
不是工艺属性。把它建成硬约束意味着改优先级要动模型结构；建成权重只需要改一个数。
订单属性的变化频率远高于工艺属性（工艺改一次要重新认证，优先级天天在变），
所以它更应该落在「可以随时改」的那一层。

## 3. 概念：三个字段与一个开关

### 3.1 `weight` 与 `priority` 是两个字段

```python
@dataclass(frozen=True, slots=True)
class Job:
    ...
    weight: float      # 加权迟交里的 w_j，客户重要性 / 合同罚则
    priority: int      # 紧急程度，默认 0
```

两个字段都参与目标函数，但含义不同：

| 字段 | 量纲 | 典型来源 | 变化频率 |
|---|---|---|---|
| `weight` | 浮点，通常 `1.0` 上下 | 合同罚则、客户等级 | 合同变更时 |
| `priority` | 整数，默认 `0` | 车间的急单标记 | 可能每天变 |

把它们分成两个字段而不是「都乘进 `weight`」，有一个很实际的理由：
**`priority` 是整数**。整数意味着「急一点」「急很多」可以用 `1`、`5`、`10` 这种档位表达，
而且不会因为浮点乘法引入舍入。`weight` 保持浮点是为了容纳合同里的小数罚则。

### 3.2 有效权重

打开 `urgency` 之后，订单 `j` 在迟交项里的有效权重是：

```text
w_eff(j) = w_j · (1 + priority_j)
```

用 `(1 + p)` 而不是 `p` 或 `(1 + p / 10)`，理由有三条：

```text
一  priority = 0 时退化成 w_j         —— 「没标急单」不改变原有语义，向后兼容
二  p 是整数，w_eff 是 w_j 的整数倍    —— 权重之间是干净的比例关系，便于手算核对
三  乘法而不是加法                    —— 已经权重大（合同贵）的订单被标急之后仍然更大，
                                          两个维度不会互相淹没
```

第三条值得展开。如果写成 `w_eff = w + p`，那么一个 `w = 100` 的普通订单会淹没一个
`w = 1`、`p = 5` 的急单。乘法保序：`w` 的排序在放大之后仍然保留，
`priority` 只在**同一个 `w` 量级内部**起作用。这是把两个维度分开的常见做法。

### 3.3 一个开关

优先级不默认生效，要显式打开：

```python
spec = {"objective": "weighted_tardiness", "time_limit": 5.0, "seed": 0,
        "urgency": True}
```

为什么默认关闭？因为**打开它会改变已有实例的目标值语义**。
一批老实例的 `priority` 字段可能只是历史遗留的字段（比如用来排序报表），
如果默认生效，那么「同一份实例、同一份 `spec`、同一份代码」在不同版本之间会给出不同的目标值，
而调用方看不出为什么。默认关闭 + 显式打开，把这次语义变化变成一个**必须被写下来的决定**：

```text
写 urgency=True  的人在说：我知道这批实例的 priority 字段是有意义的，我要用它
不写的人          得到的是与上周完全一致的行为
```

打开之后，求解器会把这件事记进 `ShopResult.detail`：

```text
detail["urgency_applied"] = True
detail["urgent_jobs"]     = 有非零 priority 的订单 id 列表（已排序）
```

这不是装饰。目标值的算法里藏了一个开关，读报表的人有权知道这个数是在开关的哪一侧算出来的 ——
否则两份报告里的 `weighted_tardiness` 名字一样、数值不可比。

### 3.4 优先级与验证器的关系

验证器**故意不检查** `priority`。理由很直接：

```text
改一个订单的 priority，可行域一个点都没变 —— 同一张排程仍然合法。
所以没有任何「违反优先级」的排程可言，也就没有可报的诊断。
```

这一点在 `MODEL_COVERAGE` 那张表里被显式标出来：`priority` 那一行的「验证器」一栏写的是
「**故意不进**验证器：改了优先级，可行域不变」。把这句话写下来比留空更重要 ——
留空会被读成「漏了」，写清楚才是「刻意不查」。

## 4. 推导：为什么权重只改「值多少分」

### 4.1 从目标函数的形状看

把加权迟期写出来。设订单 `j` 的完工时刻是 `C_j`、交期是 `d_j`，则

```text
T_j = max(0, C_j - d_j)                        迟期
Σ w_eff(j) · T_j                               带优先级的加权迟期
w_eff(j) = w_j · (1 + priority_j)              打开 urgency 之后
```

这个式子里**没有出现任何约束**。它是纯粹的「给排程打分」。
所以从形式上看，`priority` 与 `due_date` 是同一种东西：它们都只出现在目标里。

```text
due_date 决定 T_j 从哪一刻开始为正     —— 影响「值是几」
weight   决定 T_j 前面乘多少           —— 影响「权是几」
priority 同样影响「权是几」             —— 只是换了输入字段
```

### 4.2 保证可行域不变的两条推理

```text
推理一   目标函数的系数变化不影响任何一条约束的形状
          -> 可行域 F 与是否打开 urgency 无关
推理二   验证器只查可行性不查最优性
          -> 同一张排程在两种设置下诊断完全相同
```

第 7 节的输出会给出推理二的实证：两次求解的可行性诊断都是「无（通过）」，
而且它们是**同一组工序、同一台机器**上的两份排程，只是一份按 `A→B`、一份按 `B→A`。
两行诊断都是空表，说明「谁先上机」这件事在验证器眼里完全平权 ——
优先级不是一条它能看见的规则。

### 4.3 同分翻转：权重的作用点

目标函数变化要在排程上产生效果，前提是**两个候选排程原本的分数不同**。
今天的实例刻意做成了「原本同分」的极端情形：

```text
一台机器、两道各 3 分钟的工序、两张单子的交期都是 2
-> 总完工时刻恒为 6，先做的那道迟 1 分钟、后做的那道迟 4 分钟
-> 裸权重下两种顺序都是 1 + 4 = 5：完全同分
```

同分意味着求解器**没有任何理由**偏好其中一个顺序 —— 它给出哪一个都对。
这时加入优先级，天平立刻倾斜：

```text
A 先：w_eff(J0)·1 + w_eff(J1)·4 = 1·1 + 6·4 = 25
B 先：w_eff(J1)·1 + w_eff(J0)·4 = 6·1 + 1·4 = 10
```

顺序翻转。这个例子的价值在于它把「权重的作用点」暴露得干干净净：
**它不改可行域，改的是同分点上的偏好。** 如果实例本身不同分，
权重就必须大到能跨过原本的差距才能翻转顺序 —— 那是另一个更复杂的计算，
今天的例子故意绕开了它。

## 5. 手算：`5` 与 `10` 的全部推导

实例（`examples/m3w4d4_urgency.py`）：

```text
订单 J0 = (A)，release = 0，due = 2，weight = 1.0，priority = 0
订单 J1 = (B)，release = 0，due = 2，weight = 1.0，priority = 5   <- 紧急订单
工序 A：{M0: 3}       工序 B：{M0: 3}      只有一台机器 M0
目标：weighted_tardiness
```

**第一步：可行排程只有两种。** 一台机器、两道工序，唯一的选择是谁先：

```text
顺序一  A[0,3) -> B[3,6)
顺序二  B[0,3) -> A[3,6)
```

两种的总完工时刻都是 `6`，与顺序无关。注意这里**没有换型矩阵**，
所以从前一道切到后一道不需要留间隔 —— 两道工序紧贴着排是合法的。

**第二步：算迟期。** 两张单子的交期都是 `2`：

```text
顺序一    C_J0 = 3 -> T_J0 = max(0, 3 - 2) = 1
          C_J1 = 6 -> T_J1 = max(0, 6 - 2) = 4
顺序二    C_J1 = 3 -> T_J1 = 1
          C_J0 = 6 -> T_J0 = 4
```

**第三步：裸权重（`urgency` 关闭）。** 两个权重都是 `1.0`：

```text
顺序一   1.0·1 + 1.0·4 = 5
顺序二   1.0·1 + 1.0·4 = 5        同分
```

所以 `urgency` 关闭时目标值**恒为 `5`**，与顺序无关。求解器给哪个顺序都是最优的，
它给 `A→B` 只是搜索顺序的产物，不代表任何偏好。

**第四步：打开 `urgency`。** 有效权重：

```text
w_eff(J0) = 1.0 · (1 + 0) = 1
w_eff(J1) = 1.0 · (1 + 5) = 6
```

再算两个顺序：

```text
顺序一   1·1 + 6·4 = 1 + 24 = 25
顺序二   6·1 + 1·4 = 6 +  4 = 10        <- 更小
```

**第五步：结论。** 打开 `urgency` 之后最优值是 `10`，最优顺序是**紧急订单先上机**
（`B` 先），与第 4.3 节的预测一致。而 `urgency` 关闭时的最优值是 `5`。

这里有一个必须写清楚的细节：`10` 与 `5` **不是同一个东西的两个读数**，
而是两个不同目标函数的最优值：

```text
urgency 关闭   min Σ w_j·T_j      最优是 5（两个顺序并列）
urgency 打开   min Σ w_j(1+p_j)·T_j  最优是 10（唯一顺序）
```

拿 `10 - 5 = 5` 去说「紧急订单让目标值增加了 5」是错的 —— 它们的分母（目标函数）不一样。
正确的读法是：`5` 与 `10` 是同一个排程在两种打分口径下的值，是两个世界的数，
**只能各自与自己那个世界的下界比**。

## 6. 实现：有效权重落在哪里

### 6.1 目标函数里的那一行

在 [constraints2.py](../../projects/03_industrial_fjsp/fjsp_shop/constraints2.py) 的 `_add_objective` 里，
有效权重就一行：

```python
effective = job.weight * (1.0 + job.priority if urgency else 1.0)
```

这一行的效果是：`urgency` 关闭时 `effective = job.weight`（完全等价于上周的行为）；
打开时 `effective = job.weight * (1 + job.priority)`。
`tardy[job.id] = (T_var, effective)` 之后，目标函数的构造对两种情形是同一段代码 ——
**开关只影响权重，不影响目标的形状**。这是「只改值多少分」这句话在代码里的样子。

同一段还做了两件记录工作：

```text
built.notes["urgency_applied"] = True      仅当开关打开
built.notes["urgent_jobs"] = 有非零 priority 的订单 id（排序后）
```

### 6.2 一个必须显式处理的差异

昨天之前，目标值的重算可以直接用 `fjsp_core.objective.evaluate`。今天不行了：

```text
Weights 是全局三个数（alpha / beta / gamma），装不下「逐订单优先级」这个维度。
所以在 urgency 打开时，evaluate 只能按裸 w_j 算 —— 它报的是模型**根本没有优化**的数。
实测：模型最优 10.0，evaluate 却报 5.0，差一倍。
```

这就是 `recompute_objective(...)` 存在的原因：它在 `urgency` 打开且目标名涉及迟交时，
自己按 `w_j · (1 + p_j)` 重算加权迟期；其余情形直接转给 `evaluate`。
**这不是重复实现，而是把一个「目标函数的口径差异」显式地放在一处。**

这件事的教训超出了今天的范围，值得单独记下来：

```text
「求解器的读数」与「独立重算的读数」必须能对上，对不上时首先要问
「它们算的是不是同一个目标函数」，而不是「谁算错了」。
```

本周的每个实验都会同时打印这两个数（`objective` 与 `objective_recomputed`），
就是为了让这类口径差异在实验阶段就暴露，而不是等报表发布之后才被发现。

## 7. 实验：`m3w4d4_urgency`

脚本：[m3w4d4_urgency.py](../../projects/03_industrial_fjsp/examples/m3w4d4_urgency.py)。

在项目目录 `projects/03_industrial_fjsp` 下运行：

```bash
python examples/m3w4d4_urgency.py
```

实际输出（原样粘贴）：

```text
=== 1. 手算：只有一台机器，两种顺序 ===
  A 先：[0,3) 与 [3,6) → T_A=1, T_B=4
  B 先：[0,3) 与 [3,6) → T_B=1, T_A=4
  不带优先级（w 都是 1）：两种顺序都是 1 + 4 = 5 —— 同分，选谁都一样。
  带优先级（J1 有效权重 1*(1+5)=6）：A 先 = 1*1 + 6*4 = 25；
                                    B 先 = 6*1 + 1*4 = 10 —— 最优顺序翻转为 B 先。

=== 2. 求解：plain vs urgency ===
  plain : status=OPTIMAL   objective=5  上机顺序 A -> B
           可行性诊断：无（通过）
  urgency: status=OPTIMAL   objective=10  上机顺序 B -> A
           可行性诊断：无（通过）
  urgency_applied = True

=== 3. 拆开看：目标值到底怎么算出来的 ===
  plain   完成时刻：A=3, B=6
           迟期项：A: max(0,3-2)；B: max(0,6-2)
           ΣT（不带权）=5   ΣwT（只认 Job.weight）=5
  urgency  完成时刻：B=3, A=6
           迟期项：B: max(0,3-2)；A: max(0,6-2)
           ΣT（不带权）=5   ΣwT（只认 Job.weight）=5
  两次求解的约束完全一样，只是**同一份排程值多少分**变了。

  注意最后那个 ΣwT：两次都读出 5。因为 `fjsp_core.objective.weighted_tardiness`
  的签名里没有 urgency —— 它只认 `Job.weight`，看不到 `priority`。
  有效权重 w_j*(1+priority_j) 是由求解器在**目标函数**里算的，
  它把这件事记在了 detail 里：
      plain   detail 关键项：urgency_applied=None
      urgency detail 关键项：urgency_applied=True
  所以「紧急订单」不是一条可行性规则，而是**读分方式**的开关：
  想让优先级起作用，必须在 spec 里显式打开 urgency。
```

### 7.1 怎么读这段输出

**第 2 节的两行是最直接的证据。** 四个读数摆在一起看：

| 设置 | 状态 | 目标值 | 上机顺序 | 可行性诊断 |
|---|---|---:|---|---|
| `plain` | `OPTIMAL` | 5 | `A -> B` | 无（通过） |
| `urgency` | `OPTIMAL` | 10 | `B -> A` | 无（通过） |

第三列与第四列是今天的结论：**目标是同一个、顺序换了**。
第五列是「可行域没动」的实证 —— 两行诊断都是空表。
如果 `urgency` 偷偷加了一条「急单优先」的约束，那么 `plain` 那一行（`A` 先上机）
在 `urgency` 那一侧就应该变成非法 —— 而它不会，因为 `B` 先上机的那份排程完全合法，
只是分数不同。

注意两行都是 `OPTIMAL`。这**不是**矛盾：两个 `OPTIMAL` 是关于两个不同目标函数的证明。
`5` 是 `min Σ w_j T_j` 的最优值，`10` 是 `min Σ w_j(1+p_j) T_j` 的最优值。
拿 `10 > 5` 去说「打开了 `urgency` 之后结果变差了」是读错了 —— 两个数没有共同的尺子。

**第 3 节是全节最容易被误读的地方，也是我特意留在输出里的。** 看这两行：

```text
plain     ΣT（不带权）=5   ΣwT（只认 Job.weight）=5
urgency   ΣT（不带权）=5   ΣwT（只认 Job.weight）=5
```

**四个读数全部是 `5`**，而第 2 节刚说 `urgency` 那一行的目标值是 `10`。
这不是矛盾，是口径不同：

```text
第 2 节的 10        求解器**为了让目标变小**而搜索出来的数（有效权重 6 参与）
第 3 节的 ΣwT = 5   `fjsp_core.objective.weighted_tardiness` 用裸权重 1 算出来的数
```

两个数都在描述同一份排程（`B[0,3)`、`A[3,6)`）：`6·1 + 1·4 = 10` 用的是有效权重，
`1·1 + 1·4 = 5` 用的是裸权重。**求解器报 `10` 是对的，核心库报 `5` 也是对的，
它们只是算的不是同一个式子。**

这一格的价值在于：它把「独立重算」这条纪律的边界指出来了。
前面三周我们一直强调「不要相信求解器的读数，要用 `evaluate` 重算」——
今天出现了一个反例：`evaluate` 在这里**重算不了**，因为它的签名里
根本没有 `priority` 这个维度（`Weights` 是全局三个数：`alpha` / `beta` / `gamma`）。
所以正确做法不是「放弃重算」，而是**在模型这一侧补一个能重算的函数**（第 6.2 节的
`recompute_objective`），并把它与 `evaluate` 的差异写进注释。

最后两行是开关的痕迹：

```text
plain   detail 关键项：urgency_applied=None
urgency detail 关键项：urgency_applied=True
```

`plain` 那一行是 `None` 而不是 `False` —— 这个区别有意义：`None` 表示
「这个字段在这个 `spec` 下根本没有被设置」，`False` 会表示「被显式关掉了」。
两者对读报表的人来说信息量不同，所以代码里用的是 `built.notes[...] = True`
只在打开时写入，而不是每次都写一个布尔值。

## 10. 自测题

- Q1：为什么紧急订单不做成硬约束（「急单必须最先上机」）？硬约束版在什么情形下直接不可行？
- Q2：有效权重为什么用 `w_j · (1 + p_j)` 而不是 `w_j + p_j`？请举一个参数例子说明差别。
- Q3：`urgency` 为什么默认关闭？默认打开会带来什么风险？
- Q4：打开 `urgency` 之后，验证器的诊断会不会变化？为什么这是「优先级不进可行域」的证据？
- Q5：本实例上 `urgency` 关闭时目标值恒为 `5`。这个「恒为」是怎么来的？
- Q6：`5` 与 `10` 能不能相减得到「紧急订单的代价是 5」？如果不能，该怎么表述？
- Q7：`fjsp_core.objective.weighted_tardiness` 在本实例上报 `5`，是 bug 吗？
- Q8：`detail["urgency_applied"]` 在 `plain` 那一行是 `None`。为什么不是 `False`？
- Q9：如果所有订单的 `priority` 都是 `0`、同时打开 `urgency`，结果会与关闭时一样吗？为什么？
- Q10：`priority` 会不会被验证器判为「未被使用的字段」而报错？为什么覆盖表要显式写它？

### 参考答案

- A1：因为车间里可能同时有多张急单，而机器只有一台。硬约束版这时直接不可行 ——
  但现实中你不会因为三张单子都急就不生产，你会按「谁更急一点」排序。
  硬约束只能表达「是/否」，表达不了「更」，所以它在多张急单的情形下必然失效。
- A2：两种形式的差是 `w(1+p) - (w+p) = p·(w-1)`。`w > 1` 时乘法更大、`w < 1` 时加法更大，
  所以它们对**同一对订单**可以给出相反的排序。举一个反例：
  `J_a` 取 `w = 0.5, p = 100`，`J_b` 取 `w = 40, p = 1`。乘法给 `50.5` 与 `80`（`J_b` 更重），
  加法给 `100.5` 与 `41`（`J_a` 更重）—— 排序反了。
  乘法把两个维度分开的理由是：`p` 只在同一个 `w` 量级内部起作用，
  「合同罚则差 100 倍」这件事不会被一个急单标记抹平；加法把它们混在一个数轴上，
  谁大取决于 `p` 的量级，而 `p` 是车间里天天在动的东西。
- A3：因为打开它会改变已有实例的目标值语义。老实例里的 `priority` 字段可能是历史遗留，
  默认生效会让「同一份实例、同一份 `spec`」在不同版本间给出不同的目标值，
  而调用方看不出原因。默认关闭把这次语义变化变成一次必须写下来的决定。
- A4：不会变。本实例两次求解的诊断都是「无（通过）」，而两次的上机顺序是不同的
  （`A -> B` 与 `B -> A`）。验证器对两个顺序都放行，说明「谁先上机」在它眼里完全平权 ——
  这就是「优先级不进可行域」在诊断层面的样子。
- A5：因为总完工时刻恒为 `6`（一台机器、两道各 3 分钟的工序，与顺序无关），
  于是两道工序必然一道迟 `1`、一道迟 `4`；两个权重都是 `1.0`，
  所以 `1 + 4 = 5` 与顺序无关。这也是「同分」的含义：求解器没有任何理由偏好任一个顺序。
- A6：不能。`5` 是 `min Σ w_j T_j` 的最优值，`10` 是 `min Σ w_j(1+p_j) T_j` 的最优值，
  两个式子不同，最优值不可相减。正确的表述是「在裸权重口径下最优值是 `5`；
  在带优先级的口径下最优值是 `10`，且最优顺序由 `A -> B` 翻转为 `B -> A`」——
  说的是同一个实例上两种目标函数各自的结论。
- A7：不是。它的签名里没有 `priority` 这个维度（`Weights` 是全局的三个数），
  所以它只能按裸 `w_j` 算 —— 它算得没错，只是算的不是模型优化的那个式子。
  修法不是改 `evaluate`（那会破坏它与 `fjsp_core` 其它部分的契约），
  而是在模型这一侧补一个 `recompute_objective` 并在注释里写明差异。
- A8：`None` 表示「这个字段在这个 `spec` 下没有被设置」，`False` 表示「被显式关掉了」。
  两者的信息量不同：看到 `None` 能推断调用方压根没用这个开关，
  看到 `False` 则说明调用方考虑过并选择了关闭。代码里只在打开时写入 `True`，
  就是为了保持这个区别。
- A9：结果完全一样（同一份排程、同一个目标值）。因为 `w_j · (1 + 0) = w_j`，
  有效权重退化成裸权重，目标函数的形状回到关闭时的样子。
  这也说明「打开开关」本身不引入任何偏差 —— 它只是让 `priority` 字段参与计算，
  而全是 `0` 时它参与等于不参与。
- A10：不会。验证器只查可行性，`priority` 不影响任何一条可行性检查，
  所以它既不报错也不被「使用」。但这不等于可以不管它：
  覆盖表要显式写出「**故意不进**验证器」，因为留空会被读成「漏了」，
  写清楚才能表明这是刻意的设计而不是疏忽。

## 11. 今日一句话总结

> **优先级的正确位置是目标函数而不是约束：`w_eff(j) = w_j · (1 + priority_j)` 只改「同一份排程值多少分」，一个可行点都不砍，所以两次求解的验证器诊断完全相同而上机顺序可以翻转 —— 第 7 节那个「一台机器、两道 3 分钟工序、交期都是 2」的最小实例把这件事压到了临界点上：裸权重下两种顺序同为 `5`，把急单标成 `priority = 5` 之后变成 `25` 与 `10`，最优顺序翻转为急单先上机；而 `fjsp_core.objective.weighted_tardiness` 报出的 `5` 提醒我们，独立重算的前提是它与模型算的是同一个式子。**
