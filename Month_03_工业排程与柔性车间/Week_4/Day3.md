## 2. 为什么 Day 3 要谈 WIP 与锁定工序

前三天的模型有一个共同的隐含假设：**整张排程可以推倒重排**。
求解器拿到实例，从零开始决定每道工序在哪台机器、什么时刻开工。现实里这个假设经常不成立：

```text
WIP（work in process）  车间里已经有一批半成品。它已经上了某台机器、已经开工了。
                        你的新排程不管怎么排，都不能让这台机器上的这批活「倒回去」
换型已开始              某台机器已经在为族 F1 做准备了，新排程必须把它当成既成事实
夹具/模具已装           某个夹具装在 M2 上，接下来的活只能围着它排
```

这类事实的共同形状是：**它是决策的残余，不是决策的对象**。它们不应该再被求解器选择一次。
这就带来一个建模上的要求：模型必须能表达「这道工序的机器与开工时刻我都已经知道了」，
而不是「这道工序可以选」。

一个容易犯的错是把锁定做成**软偏好**：给「不遵守锁定」加一个惩罚。理由听起来很合理 ——
「万一锁定导致不可行呢」。但这是把两类东西混在一起了：

```text
物理事实    已经上机的活不会因为新排程而回到待加工区
             -> 它必须是一条硬约束，不可行就是不可行，该报出来的是「这个实例无解」
管理偏好    某个订单优先
             -> 这才是软的东西（优先级属于管理偏好，不砍可行域）
```

把物理事实做成软约束的后果是：预算紧的时候求解器会拿它换目标值，
于是它输出一份「看起来目标更好」但车间根本执行不了的排程。
**排程的价值全部建立在它可执行之上**，所以锁定必须是硬的。

今天还要顺带回答一个数额上的问题：钉住一道工序要花多少钱？答案很直观 ——
它至少要让「不钉的收益」归零。但到底是多少，取决于那道工序在最优解里原本被放在哪里，
以及它的后继还有多少腾挪余地。第 5 节会算一个具体的数。

## 3. 概念：锁定的两个字段与三条边界

### 3.1 两个字段

```python
@dataclass(frozen=True, slots=True)
class Operation:
    ...
    locked_machine_id: str | None
    locked_start: int | None
```

两个字段都是可空的，含义是：

| 取值 | 含义 |
|---|---|
| 两个都是 `None` | 未锁定，求解器自由决定机器与时刻 |
| 两个都填了 | 完全锁定：机器必须是这一个，开工时刻必须是这一个 |
| 只填 `locked_machine_id` | 机器钉死，时刻仍可搜索（「这台活只能在 M3 上做，但什么时候做还看排程」） |
| 只填 `locked_start` | 时刻钉死，机器仍可搜索（「已经在做了，什么时候开始是既成事实，但换台机器复核一下」） |

**第三个与第四种组合是常见误用**。它们看起来有用，实际上各自都有问题：

```text
只钉机器    与资质、机器的专机属性是同一种约束，用资质或从 machine_times 里删掉更干净
只钉时刻    机器还没定却先定了时刻 —— 这不是「已上机」，而是「已排产」的另一种说法；
            更要紧的是：如果机器随后被选到另一台，这个时刻在那台机器上可能是不可行的
```

所以本模型对「已经上机」这件事只承认**两个一起给**这一种读法，
并且验证器对两个字段分别检查 —— 少填一个，检查就少一条，错误也就少被发现一次。

### 3.2 三条边界

锁定与其它约束的边界值得单独说清，因为它容易和三种东西混淆：

```text
与资质       资质限制「合格机器的集合」；锁定把这个集合进一步收窄到一个元素。
             两者的方向相同（都在砍），但可复核性不同：资质是实例属性，
             锁定是**这一份排程**的属性 —— 同一份实例可以有两份不同的锁定。
与释放时间   释放时间是下界（「不早于」），锁定是等式（「恰好是」）。
             一个 ≥，一个 ==，强度差一个数量级。
与优先级     锁定砍可行域；优先级不砍，它只改目标函数里的权重。
```

### 3.3 锁定为什么必须能挡住手写的排程

「锁定是硬约束」这句话在实现上要落成两个检查，缺一不可：

```text
检查一   这道工序被排到的机器 == locked_machine_id
检查二   这道工序的 start == locked_start
```

为什么两个都要有：如果只查机器，那么「锁在 M1 开工 20」的活可以被排到 `M1[16,22)`，
机器对了、时刻错了，而这份排程甚至可能更好看 —— 它是错的，只是错得不明显。
反过来只查时刻也有对称的问题。第 7 节的实验会分别制造这两类错误，
看诊断是不是恰好各报一条。

## 4. 推导：锁定在最优化里的位置

### 4.1 锁定是「收紧」还是「改变问题」

从最优化问题的角度看，锁定做的事是：

```text
原问题    min f(x)   s.t.  x ∈ F
加锁后    min f(x)   s.t.  x ∈ F ∩ {x | machine(o) = m*, start(o) = t*}
```

它只收紧了可行域，没有改变目标函数。由此立刻得到两条推论：

```text
推论一  加锁后的最优值 >= 加锁前的最优值（最小化问题，可行域变小，最优值不会变好）
推论二  若原最优解恰好满足锁定的取值，加锁后的最优值**不变**
```

**推论二是今天实验里必须如实报告的一句。** 一个问题是否值得单独写一节，
取决于锁定有没有真的挡路。如果某个实例的原最优解恰好落在锁定点上，
那么这一层的数字与上一层完全相同 —— 这时正确的写法是「没有改变」，
而不是去找一个「轻微影响」的说法。第 7 节用的实例是刻意构造的：
锁定值选在会挡路的位置上，所以能看到 `27 → 31` 这个真实差额。

### 4.2 锁定的代价从哪里来

把代价拆成三段，可以看清它是怎么来的：

```text
第一段   被锁的工序自己往后挪 —— 这一段的代价是 (t* - 原来的 start)
第二段   同一订单里它的后继被迫跟着往后推 —— 这一段的代价由路线长度决定
第三段   同机器上排在它后面的工序也可能被推 —— 但它被推多远取决于空档够不够用
```

三段里第三段最不确定：如果机器在被锁工序之后有一段长空档，
后面的工序可能原封不动地塞进去，代价就只有前两段。
所以**锁定的代价不是常数**，它与实例的空档结构有关。

### 4.3 一个反例：加锁也可能「不亏」

按推论一，加锁后最优值不会变好。但有一类情形特别值得记住：

```text
如果原最优解本来就把这道工序放在锁定点上，那么加锁的代价是 0。
于是这一层的读数与上一层的读数完全相同 —— 这时「锁定」这条约束
在这个实例上是**空转**的：它确实在模型里，也确实在验证器里，只是这个最优解不碰它。
```

判断一条约束是不是空转，不能看目标值，要看**能不能构造出一份违反它、其它方面都合法的排程**。
如果能构造出来（验证器也确实报错），那么约束是接上了的；目标值不变只说明这个实例没被它咬住。
Day 1 的资质筛选也适用同一把尺子：目标值没动，不等于约束没接上。

## 5. 手算：`+locked` 层的 `31`

今天用的实例来自 Week 4 实验驱动里的**分层实例构造函数**
（`fjsp_experiments/w4_industrial.py` 的 `ablation_instance`）。它按「约束一层层加上去」的顺序
生成同一个实例的不同版本；今天用到其中两层：

```text
+worker 层   订单 J0 = (A, B)、J1 = (C, D)；两台机器 M0、M1
             A：{M0: 5, M1: 4} F0      B：{M0: 6, M1: 5} F0
             C：{M0: 4, M1: 6} F1      D：{M0: 5, M1: 5} F1
             换型：F0->F1 = 3，F1->F0 = 4，同族 0
             日历：M0 = [0,10)，M1 = [0,10) 与 [16,40)
             资质：(M0,F0)、(M1,F0)、(M1,F1)  —— 注意**没有** (M0,F1)
             工人：W0 只会 M0、W1 只会 M1、W2 两台都会，容量都是 1
+locked 层   在 +worker 的基础上，C 被锁定到 M1、开工时刻 20
```

**先看 `+worker` 层（不加锁）的 `27` 是怎么来的。** 资质把 `F1` 的两道工序（`C`、`D`）
赶到 `M1` 上，`M1` 的可用窗只有 `[0,10)` 与 `[16,40)`：

```text
M1 必须先装下 A、B（同族 F0，紧贴不换型）：
  A(F0) [0,4) -> B(F0) [4,9)          9 分钟刚好落在第一个窗 [0,10) 里 ✓
C 是 F1，跟在 F0 后面要换型：最早 9 + 3 = 12，但第一个窗 10 就关了
  -> 只能进第二个窗，C(F1) [16,22)
D 是 F1，与 C 同族，紧贴：D(F1) [22,27)
Cmax = 27
```

**再看 `+locked` 层的 `31`。** `C` 被钉到 `M1` 的 `20` 开工：

```text
C(F1) 锁定在 [20,26)        工时 6，落在第二个窗 [16,40) 里 ✓
D 是 J1 的后继，C 结束 26 -> D 最早 26 开工，工时 5
D(F1) [26,31)               与 C 同族，紧贴不换型 ✓
Cmax = 31
```

**下界论证。** `D` 只能上 `M1`（它是 `F1`，而 `(M0, F1)` 没有资质），
且 `D` 必须晚于 `C`；`C` 被钉到 `20` 开工、占 6 分钟，所以：

```text
D 最早开工 20 + 6 = 26
D 占 5 分钟           -> D 最早完工 26 + 5 = 31
下界 LB >= 31
```

而上面的排程把 `A`、`B`、`C`、`D` 全部排下且收尾在 `31`，所以 `LB = 31` **可达**。
求解器报 `OPTIMAL 31`，与手算一致。差额：

```text
31 - 27 = 4 分钟
```

这个 `4` 不是「锁定的开销」这种抽象成本，它有具体的来源：`C` 从 `[16,22)` 被推到 `[20,26)`，
位移 `4` 分钟；而 `D` 紧跟在 `C` 后面，于是整条链一起后移 `4` 分钟。
**锁定的代价 = 被锁工序的位移，在这里恰好等于整条链的位移**，
因为 `M1` 在 `C` 之前没有可用的空档能让 `D` 提前塞进去（`16` 到 `20` 那 4 分钟不够 `D` 的 5 分钟工时）。

顺带一个自查点：这个实例上 `A`、`B` 为什么不能挪到 `M0` 上给 `M1` 腾地方？
`M0` 的窗只有 `[0,10)`，而 `A + B` 需要 `5 + 6 = 11` 分钟 —— 装不下。
所以两台同族工序只能挤在 `M1` 上，这也是 `C` 被逼到第二个窗的原因。

## 6. 实现：锁定在建模里的两处落地

### 6.1 建模：收窄候选集 + 钉住时刻

在 [constraints2.py](../../projects/03_industrial_fjsp/fjsp_shop/constraints2.py) 的 `build_model` 里，
锁定的建模是两行：

```text
机器    可选机器从 qualified_machine_ids(...) 的结果收窄为 [locked_machine_id]
        —— 与资质筛选走的是同一条路：少创建变量，而不是多一条禁止约束
时刻    locked_start 非空时，直接 model.Add(start[op] == locked_start)
```

注意第二行的写法：它是 `Add(... == ...)` 而不是「先建变量再约束到那个值」。
这样写的好处是预求解能立刻把 `start[op]` 固定成一个常量，缩减后续所有约束的规模。

### 6.2 验证：两条独立诊断

验证器那一侧是两条**分开**的检查，顺序也在代码里固定：

```text
locked: <op> start <实际> != <锁定值>
locked: <op> machine <实际> != <锁定机器>
```

两条分开写有实际价值：一次错误的锁定违反只报一条，能直接告诉人「是机器错了」还是「是时刻错了」。
把它们合成一条 `locked violated` 会丢掉这个信息，而这正是修复时要看的东西。

## 7. 实验：`m3w4d3_locked`

脚本：[m3w4d3_locked.py](../../projects/03_industrial_fjsp/examples/m3w4d3_locked.py)。

在项目目录 `projects/03_industrial_fjsp` 下运行：

```bash
python examples/m3w4d3_locked.py
```

实际输出（原样粘贴）：

```text
=== 1. 锁定的内容 ===
  工序 C：locked_machine_id=M1 locked_start=20
  C 的可选机器（工时表）：{'M0': 4, 'M1': 6}
  锁定的意思是：机器由 locked_machine_id 指定，开工时刻由 locked_start 指定，
  求解器没有自由裁量权 —— 这两条都要能挡住手写的排程。

=== 2. 两类改锁错误，看诊断 ===
  先用一个干净的小实例（只有锁定这一条约束），一条错误只对应一条诊断：
  诊断：无（通过）
      这是**遵守锁定**的排程，先自证一遍。
  把 X 挪到 M0（它锁在 M1，工时 4）：
  诊断：['locked: X machine M0 != M1']
  X 留在 M1，但开工时刻从 0 改成 3：
  诊断：['locked: X start 3 != 0']
  锁定是「机器 + 开工时刻」两个字段一起钉住，任缺其一都不算数。
  回到消融实例上再看一次（那里的 C 还带着日历与资质）：
      其余三行都合规，只把 C 的开工时刻从 20 改成 16：
          locked: C start 16 != 20
      一条违反就够把整条排程判掉 —— 验证器不给「差不多」留余地。

=== 3. 锁定本身的代价：同一天数据，加锁前后 ===
  +worker   status=OPTIMAL   Cmax=27
      A  M1  [0,4)  W1
      B  M1  [4,9)  W1
      C  M1  [16,22)  W1
      D  M1  [22,27)  W1
  +locked   status=OPTIMAL   Cmax=31
      A  M1  [0,4)  W1
      B  M1  [4,9)  W1
      C  M1  [20,26)  W1 <- 锁定
      D  M1  [26,31)  W1
  27 -> 31：把 C 钉在 [20,26) 上，C 之后的 D 与 J0 的收尾都被推后。
  这就是「已经做出的生产决策」的代价 —— WIP 锁定的现实含义。
```

### 7.1 怎么读这段输出

**第 2 节是我今天特意分两段做的。** 前半段用一个「只有锁定这一条约束」的小实例（`X` 锁在 `M1`、
开工 `0`；实例里没有日历、没有资质、没有工人），于是每次破坏只会触发一条诊断：

| 破坏 | 诊断 |
|---|---|
| 遵守锁定（`X@M1[0,3)`） | 无（通过） |
| `X` 挪到 `M1` 之外的 `M0[0,4)` | `locked: X machine M0 != M1` |
| `X` 留在 `M1` 但改成 `[3,6)` | `locked: X start 3 != 0` |

两条诊断分别对应第 3.3 节说的两个检查。**这是「一条违反一条诊断」的干净对照** ——
它证明验证器确实把机器与时刻分成两件事在查。

后半段换回消融那个实例（`C` 身上还挂着日历与资质），只把 `C` 的开工时刻从 `20` 改成 `16`，
其余三行都合规，诊断仍然只有一条：

```text
locked: C start 16 != 20
```

注意 `16` 这个值不是随便挑的：它是 `C` 在**不加锁**时的自然位置。
也就是说这一格制造的正是现实里最常见的错误 —— 「拿一份没考虑 WIP 的旧排程来用」。
验证器一句话就把它挡回去了。

**第 3 节是今天的核心对照，两行排程只差 `C` 与 `D` 的位置：**

| 层 | `C` | `D` | `Cmax` |
|---|---|---|---|
| `+worker` | `[16,22)` | `[22,27)` | 27 |
| `+locked` | `[20,26)` | `[26,31)` | 31 |

前两行 `A` 与 `B` 在两层里完全相同（`[0,4)` 与 `[4,9)`）—— 这符合第 4.2 节的拆解：
被锁的工序在 `M1` 的后半段，它前面的工序不受影响，被推的是它自己和它的后继。
如果锁定值选在 `A` 的位置上，受影响的行就会完全不同（`C`、`D` 可能反而可以提前）。
**所以 `27 → 31` 这 `4` 分钟的差额是「这个锁定值」的代价，不是「锁定」这项约束的代价。**
换个锁定值会得到另一个数。

**第 3 节两行的状态都是 `OPTIMAL`。** 所以：

```text
27 是「不加锁时的最优」      —— 关于那个模型的最优性证明
31 是「加锁后的最优」        —— 关于这个模型的最优性证明
两者不是同一个模型的两个解，而是两个模型各自的最优值。
```

把它们相减得到 `4`，得到的是**可行域收紧带来的最优值变化**，
不是「求解器变慢了」也不是「算法开销」。这个区分在报告里必须写清，
否则读表的人会以为锁定是一笔可以优化的运行成本。

## 10. 自测题

- Q1：为什么锁定的两个字段必须一起给？只给 `locked_machine_id` 有什么问题？
- Q2：锁定是硬约束还是软偏好？把物理事实做成软偏好会造成什么后果？
- Q3：把锁定实现成「从候选机器里删掉其它机器」与「加一条禁止约束」，两者在搜索上有什么区别？
- Q4：验证器为什么把机器与时刻拆成两条诊断，而不是合成一条？
- Q5：`+locked` 层的下界论证只用了 `C` 的锁定值与 `D` 的工时。为什么这个论证不需要考虑 `A`、`B`？
- Q6：`27` 与 `31` 都是 `OPTIMAL`。能说「求解器在加锁后变差了」吗？
- Q7：如果某个实例加锁前后的最优值完全相同，这一层还有没有信息量？该怎么报告？
- Q8：为什么说 `27 → 31` 这 `4` 分钟是「这个锁定值」的代价，而不是「锁定」的代价？
- Q9：现在把 `C` 锁到 `M1`、开工 `20`，但把 `D` 的 `machine_times` 加上 `M0`。
   `+locked` 层的最优值会变成多少？为什么？
- Q10：一份排程里有一道锁定工序的 `start` 比 `locked_start` **早**，验证器会报什么？
  它报的是「太早」还是「不等于」？

### 参考答案

- A1：因为「已经上机」这件事同时确定了机器与时刻，少一个就不是既成事实了。
  只给 `locked_machine_id` 的情况，本质是「这台活只能在这台机器上做」，
  用资质或直接改 `machine_times` 表达更干净，也不会让人误以为时刻也被钉住了。
- A2：硬约束。做成软偏好的后果是：预算紧时求解器会拿它换目标值，
  输出一份目标值更好但车间执行不了的排程 —— 而排程的全部价值建立在可执行之上。
- A3：删除候选机器会**少创建变量**，搜索空间从建模阶段就更小；
  加禁止约束是把变量建出来再把它压成 0（或禁止某个取值），预求解要多花力气去发现它恒为 0。
  两者可行域相同，代价不同 —— 这是本周反复出现的同一条工程判断。
- A4：为了保留「错在哪一维」这个信息。合成一条 `locked violated` 之后，
  修复排程的人看不出是机器选错了还是时刻填错了，而这两件事的修法完全不同。
- A5：因为下界只需要考虑「不可能更好的那一部分」。`C` 被钉在 `20` 且占 `6` 分钟，
  `D` 必须晚于 `C` 且只能上 `M1`，于是完工时刻不可能早于 `31`。
  `A`、`B` 怎么排都改变不了「`C` 结束于 26」这个事实，所以它们进不了这条论证。
  上界那一侧则必须给出 `A`、`B` 的完整排法 —— 下界只看瓶颈，上界要看全部。
- A6：不能。两个 `OPTIMAL` 是关于两个不同模型的证明，它们不可比。
  能说的是「可行域收紧使这个实例的最优值从 `27` 上升到 `31`」，
  这是关于**问题**的陈述，不是关于**算法**的陈述。
- A7：有。它说明这条约束在这个实例上**没有咬住最优解**（空转），
  进而说明「加锁不改变最优值」这种情形是真实存在的，报告里应该如实写「没有改变」。
  但「空转」的结论需要用另一条证据补上：构造一份违反锁定、其它都合规的排程，
  看验证器是否报错 —— 报错才说明约束确实接上了。
- A8：因为 `4` 这个数是「被锁工序的位移量」决定的。如果把它锁到另一个时刻，
  位移量就变了，代价也变了；如果锁到它在原最优解里的位置，代价就是 `0`。
  「锁定」这项约束本身没有固定价格，它只是把可行域收紧到某个点。
- A9：仍是 `31`（不会变好）。给 `D` 的 `machine_times` 加上 `M0` 貌似给了出路，
  但 `D` 是族 `F1`，而资质表里**没有** `(M0, F1)` —— 资质在机器那一侧又把它挡回去了。
  这道题考的是「权限是交集」：`machine_times` 是候选，资质是授权，二者取交。
- A10：报 `locked: <op> start <实际> != <锁定值>`。它报的是「不等于」，
  也就是**两种情况（太早、太晚）合在一条诊断里**。这与 Q4 的拆法不同：
  机器与时刻被拆成两条，而时刻的「太早」与「太晚」没有拆。
  判据是「修复动作是否相同」：早了晚了都要改成那一个值，所以不必拆。

## 11. 今日一句话总结

> **WIP 锁定的建模要求是「这道工序的机器与开工时刻我都不再选」—— 两个字段必须一起给、一起查，因为它描述的是既成事实而不是偏好；它只收紧可行域、不改变目标函数，所以加锁后的最优值只会不降，而当原最优解恰好落在锁定点上时最优值丝毫不变（这时该老实写「没有改变」）—— 第 7 节那个刻意挑选的锁定值把最优解从 `27` 推到 `31`，那 `4` 分钟是被锁工序的位移量付出的价钱，不是求解器的开销。**
