## 2. 为什么 Day 6 要做端到端与失败分析

前五天是一层一层往上加的：资质与人员（Day 1）、换型（Day 2）、锁定（Day 3）、
优先级（Day 4）、KPI 与存档（Day 5）。每一层都有各自的实验，但那些实验的实例是**分开构造**的：

```text
Day 1 的实例   只有资质与人员
Day 2 的实例   只有换型
Day 3 的实例   日历 + 资质 + 人员 + 锁定
```

分开构造的好处是干净，代价是**不知道它们能不能同时成立**。
一条约束单独加上去没问题，六条一起加上去可能出三类问题：

```text
建模冲突     两条约束的编码方式叠在一起切掉了合法解（Day 2 第 6 节那次 INFEASIBLE 就是这一类）
规模爆炸     变量与约束数量随约束条数增长，同样的预算能搜的空间变小
搜索退化     约束变多之后，求解器的分支策略可能踩进坏的路径，明明有解却找不到
```

这三类问题都只在**全约束**的实例上才暴露，所以今天的第一步是把六条约束累加到同一个实例上。

第二步是失败分析。前面五天的实验都比较顺：目标是 `OPTIMAL`，验证器通过，数字与手算一致。
但真实使用的报表里，**不是每个数字都那么干净**：

```text
有的格子是空的（没解出来）
有的格子有数字但没有证据（可行解）
有的格子有数字、看起来正常，但状态是 INVALID_SOLUTION（被验证器拒了）
```

这三种情况在报表里长得都很像 —— 都是一个格子。如果不能一眼认出它们，
就会把「没有证据的可行解」当成「最优值」引用。今天要练的正是这件事：
**看到一个数之前，先看它旁边的状态与下界。**

## 3. 概念：消融、单调性、三种失败模式

### 3.1 累加式消融

做法是不停地从零往上加：

```text
base            机器相关工时 + 柔性 + 释放/交期
+setup          sequence-dependent setup（工序族换型）
+calendar       机器日历（可用窗）
+qualification  机器资质（谁能做）
+worker         次生资源能力 + 容量
+locked         WIP / 锁定工序
```

**工序数据自始至终不变**，变的只是「哪些约束被打开」。这一点是消融能解释的前提 ——
如果每层换一套工序，那么目标值的变化就分不清是约束造成的还是数据造成的。

为什么用「累加」而不是「逐条删除」？因为删除式的起点是「全约束实例」，
而全约束实例的六条约束之间可能有交互（例如资质把某道工序赶到一台机器上，
而那台机器上又有一条锁定工序）。删掉一条之后，剩下的五条可能把可行域切出一个**新的形状**，
于是「删掉它之后变好了多少」这个数会受到其余五条的干扰。
累加式从裸露的基础实例出发，每一层只加一条，**上一层就是这一层的对照**，
因果链更短。

### 3.2 单调性

累加式消融自带一条正确性检查。今天加进去的六条约束全部是**限制性的**：

```text
日历      排除掉落在窗口外的排法
维护      排除掉与维护窗重叠的排法
资质      排除掉不合格的（工序，机器）组合
人员      排除掉不合格的（工序，工人）组合，并限制同时占用
锁定      把两道自由度收窄到一个点
换型      在相邻两段之间要求间隔
```

每一条都在**砍**，没有一条在放宽。所以：

```text
每加一层，可行域只会变小 -> 最小化问题的目标值只会变大或不变
```

这条性质的实际用处是当**报警器**：如果某一层的目标值比上一层**小了**，
那一定是某处建模写错了方向 —— 常见的是把不等式写反、
或者把「至少隔 `gap`」写成了「至多隔 `gap`」。
比逐个核对数字强的地方在于：它不依赖任何具体数值，只看序关系。

### 3.3 「没有改变」的两种原因

单调性说目标值不会变小，但它**不保证会变大**。某层加上去之后目标值一动不动，
有两种完全不同的原因：

```text
原因一  这个实例的最优解恰好落在缩小后的可行域里
        -> 约束确实生效了（能构造出违反它的排程），只是没咬住最优解
原因二  这个求解器的模型**本来就比实例更紧**
        -> 它不是「最优解恰好避开」，而是「它看不到那一片区域」
```

两种原因的判据完全不同：

```text
判原因一  构造一份违反这条约束、其它方面都合法的排程，看验证器报不报错
          —— 报错说明约束接上了；再看它有没有咬住最优解（比目标值）
判原因二  比较两个求解器在同一层的数字。数值不同，说明它们的模型不同
```

第 7 节会看到两种原因各占一半：`+setup` 与 `+calendar` 属于原因一，
而保守编码那一条链上的大部分层属于原因二。把两种原因混在一起，
就会得出「换型不影响排程」这种错误结论。

### 3.4 三种失败模式

`ShopResult.status` 的取值不只 `OPTIMAL` 与 `FEASIBLE` 两个。今天要认全三种「不好看」的状态：

| 状态 | 目标值 | `best_bound` | 含义 | 该看什么 |
|---|---|---|---|---|
| `UNKNOWN` | `None` | `None` | 预算内没找到任何可行解 | 建模型耗时、分支数、预求解设置 |
| `FEASIBLE` | 一个数 | 一个数（可能很差） | 有解，但没证明它最优 | `gap = (目标值 - 下界) / 目标值` |
| `INVALID_SOLUTION` | 一个数 | — | 求解器给了排程，**独立验证器拒绝了它** | 诊断列表；这时的目标值一律不可用 |

第三行是本周新引入的判据。前两周的 `ShopResult` 只记录求解器自己的说法；
从本月开始，报表生成器在写出任何一行之前都会跑一遍 `validate_result`，
不通过就把状态改写成 `INVALID_SOLUTION` 并把诊断写进 `failure_reason`。
**这一行的目标值不是「差一点」，而是「不可用」** —— 它描述的那份排程根本执行不了。

### 3.5 界与间隙

```text
best_bound   求解器已经证明的界（最小化问题里是下界）
gap          (目标值 - 下界) / 目标值        越小越好，0 表示证明了最优
```

读法上有两条纪律：

```text
纪律一  没有界就写空（None），不写 0
        —— 写 0 会让「没证明」看起来像「证明了 0」
纪律二  间隙要与状态一起报
        —— 「FEASIBLE 97，间隙 54%」与「OPTIMAL 97」是完全不同的两句话
```

第一条是 `fjsp_core.result` 从一开始就定下的约定；第二条是今天的重点。
一个 `FEASIBLE` 的目标值可以是任意好的数，**但它没有证据**，
而证据的有无恰恰是这个数能不能被写进报告的关键。

## 4. 推导：三个为什么

### 4.1 为什么预求解会把预算吃光

CP-SAT 在搜索之前做一次预求解（`cp_model_presolve`）：合并变量、收紧上下界、
检测恒真恒假的约束，目标是**换一个更小的模型**给搜索用。

```text
预求解的收益 = 搜索阶段省下的时间      预求解的成本 = 预求解本身花掉的时间
```

预算大时收益压倒成本，默认开启是对的；预算小时成本可能压倒收益，
极端情形是「预求解花掉了几乎全部预算，搜索阶段几乎没有开始」——
求解器既没有找到可行解、也没有推出下界，状态 `UNKNOWN`，两个值都是空的。

这个失败形态的特点是**它什么都没留下**：没有目标值、没有下界，
只有一个「求解耗时约等于预算」的读数。所以辨认它的方法不是看目标值，而是看：

```text
分支数（iterations）几乎为 0 / 为空     搜索根本没跑起来
求解耗时 ≈ 预算                        时间被别的东西占了
建模型耗时正常                          问题出在预求解，不是建模
```

本月的全约束求解器因此在**精确路径上默认关掉预求解**并降低线性化级别。
这不是「预求解不好」，而是「在 15 秒这个尺度上全约束模型的预求解成本太高」——
参数的默认值是有适用范围的。

### 4.2 为什么膨胀版会在同族之间多收钱

Day 2 已经推导过：膨胀版把每道工序的机器占用按 `max_outgoing_setup(自己的族)` 拉长。
今天把它落在**全约束实例**上：

```text
max_outgoing(F0) = max(setup(F0,F0), setup(F0,F1)) = max(0, 3) = 3
max_outgoing(F1) = max(setup(F1,F0), setup(F1,F1)) = max(4, 0) = 4
```

于是**两道同族工序之间也会被要求留出间隔**：`C(F1)` 与 `D(F1)` 相邻时真实换型是 `0`、
本可以紧贴，膨胀版却要求 `D` 在 `C` 结束后再等 `max_outgoing(F1) = 4` 分钟。
第 7 节的 `+locked` 层给出的实测正是这两行：

```text
fjsp_cpsat_full        C@M1[20,26)  D@M1[26,31)      紧贴，真实换型 0
fjsp_cpsat_qualified   C@M1[20,26)  D@M1[30,35)      中间空了 4 分钟
```

`35 - 31 = 4` 与 `max_outgoing(F1) = 4` 逐个对上。这就是「过紧」最干净的一个可指认实例：
**多收的 4 分钟落在两道同族的 `F1` 工序之间，而它们的真实换型是 `0`。**

### 4.3 为什么 `+calendar` 那一层的机制与 `+setup` 不同

两层在 `fjsp_cpsat_full` 上都是「没有改变」（`9 → 9`），但机制不一样：

```text
+setup      基础最优解的两台机器上都各自同族连排（A、B 是 F0；C、D 是 F1），
            同族对的换型是 0 —— 换型约束在这个解上**处处取等**，一个点都没砍掉
+calendar   基础最优解在 M1[0,9) 与 M0[0,9) 上收官，两台机器的第一个窗都是 [0,10)，
            9 < 10 —— 日历约束在这个解上**留了 1 分钟的余量**
```

一层是「约束在此处取等」，另一层是「约束在此处有余量」，两者对**敏感性**的预测不同：
取等的那一层只要换型矩阵变大一点（例如 `F0->F1` 从 `3` 变成 `5`）立刻会咬住；
有余量的那一层要最优值涨过 `10` 分钟才会咬住。
**「没有改变」不等于「这个实例对这条约束不敏感」。** 判断敏感性要看约束在最优解上
取不取等，而不是看目标值动没动。

## 5. 手算：三层「没有改变」的逐个解释与保守编码的代价

实例是同一份工序数据（Day 3 第 5 节用过它的两层）：

```text
订单 J0 = (A, B)，due = 14       订单 J1 = (C, D)，due = 12
A：{M0: 5, M1: 4} F0             B：{M0: 6, M1: 5} F0
C：{M0: 4, M1: 6} F1             D：{M0: 5, M1: 5} F1
换型：F0->F1 = 3，F1->F0 = 4，同族 0
日历：M0 = [0,10)          M1 = [0,10) 与 [16,40)
资质：(M0,F0)、(M1,F0)、(M1,F1)     —— 没有 (M0,F1)
人员：W0 只会 M0、W1 只会 M1、W2 两台都会，容量都是 1
```

**基础层 `9`。** 两台机器各自同族连排：

```text
M1：A(F0) [0,4) -> B(F0) [4,9)         同族，换型 0
M0：C(F1) [0,4) -> D(F1) [4,9)         同族，换型 0
Cmax = 9
```

三类下界（Day 2 第 5 节算过）都是 `9`，所以 `9` 是最优值。

**`+setup` 为什么仍是 `9`。** 上面那条排程的两处相邻对都是**同族**：
`setup(F0,F0) = 0`、`setup(F1,F1) = 0`。换型约束要求的是「间隔 ≥ 真实换型」，
而真实换型是 `0` —— 紧贴合法。约束在这一层上处处取等，一个点都没砍掉：

```text
下界 9（换型不改变下界：同族连排能做到 0 次换型）
上界 9（同一条排程仍然合法）
-> 最优值仍是 9，「没有改变」
```

**`+calendar` 为什么仍是 `9`。** 日历给的是可用窗：`M0 = [0,10)`、`M1 = [0,10) ∪ [16,40)`。
上面那条排程在两台机器上都落在 `[0,9)`，而第一个窗到 `10` 才关：

```text
9 < 10     留了 1 分钟余量
-> 同一条排程仍然合法，最优值仍是 9，「没有改变」
```

**`+qualification` 为什么跳到 `27`。** 资质表里**没有** `(M0, F1)`，所以 `C`、`D` 只能上 `M1`，
而 `C -> D` 还要按顺序做。这一对的最小占用（同族紧贴）是 `6 + 5 = 11` 分钟，
**比 `M1` 第一个窗的 `10` 分钟还长** —— 于是只有两种可能：

```text
情形 A   C、D 都落到第二个窗
         -> 收尾不早于 16 + 11 = 27（实测排程走的正是这一支）
情形 B   C 占住第一个窗 [0,6)
         -> 它后面任何工序跨族都要等 4 分钟（早已越过 10），第一个窗只剩这 6 分钟，
            A、B、D 全落到第二个窗：最少 29（A 上 M0、B 与 D 在 M1）
```

情形 A 的实测排程：`A@M1[0,4) B@M1[4,9)` 同族紧贴占满第一个窗的 `9` 分钟，
`C@M1[16,22) D@M1[22,27)` 在第二个窗里紧贴 —— 收尾 `27`。
**两个窗的边界（`10` 与 `16`）与同族紧贴这两件事合起来把 `27` 钉死了。**

**`+worker` 为什么又是 `27`。** 三个工人不会成为瓶颈：上面那份最优排程四道工序都在 `M1` 上，
`W1` 一个人按顺序看下来即可，`W0`、`W2` 全程空闲。手算核对：`W1` 的四段占用
`[0,4)`、`[4,9)`、`[16,22)`、`[22,27)` 互不重叠，容量 `1` 够用。这一层「没有改变」的原因是
**原因一**（最优解恰好不需要额外的人）。

**`+locked` 为什么是 `31`。** Day 3 第 5 节已经算过：`C` 被钉到 `M1` 开工 `20`，
它的后继 `D` 最早 `26` 开工、占 `5` 分钟 → `31`，且可达。

**保守编码在 `+locked` 层多收的 `4` 分钟落在哪。** 两个求解器同一层的实测排程：

```text
fjsp_cpsat_full        A@M1[0,4)  B@M1[4,9)   C@M1[20,26)  D@M1[26,31)   收尾 31
fjsp_cpsat_qualified   A@M1[0,4)  B@M0[4,10)  C@M1[20,26)  D@M1[30,35)   收尾 35
```

`C` 与 `D` 的位置是这一层的核心：两者都是 `F1`，**真实换型 `0`**，
所以精确版让它们紧贴（`D` 在 `26` 开工）；膨胀版要求 `D` 在 `C` 结束后等
`max_outgoing(F1) = 4` 分钟，于是 `D` 最早 `30` 开工、`35` 收官。

```text
35 - 31 = 4 = max_outgoing(F1) = setup(F1 -> F0)
```

**这 4 分钟就是「过紧」付出的钱，而且它落在两道同族工序之间** ——
膨胀版在两段本来免费的地方收了费。这一格是本日最值得记住的一个数。

## 6. 实现：实验驱动的三处约定

全约束实验的脚本是 [w4_industrial.py](../../projects/03_industrial_fjsp/fjsp_experiments/w4_industrial.py)，
它只做三件事：

```text
1. 用 ablation_instance(stage) 生成六层实例（同一份工序数据，约束逐层累加）
2. 每层分别跑两个求解器，把读数填进 rows
3. 落盘 results.csv / metadata.json / ablation.json / report.md
```

三处刻意的约定：

| 约定 | 做法 | 理由 |
|---|---|---|
| 版本状态先冻结 | `git rev-parse HEAD` 与 `git status --porcelain` 在**创建输出目录之前**执行 | 否则刚写进输出目录的 `config.json` 会让工作树恒为「脏」，这个标记就废了 |
| 目标值独立重算 | 每行都调 `evaluate(...)` 重算，并与求解器读数比对 | 不让「求解器自报的数」直接进报表 |
| 失败不中断 | 单次求解抛异常时把 `FAILED` 与 traceback 尾巴写进那一行，继续跑后面的 | 一轮实验跑几十分钟，不能因为一格失败就全部丢掉 |

第三条值得展开一点：`_row(...)` 在异常分支里把
`status` 写成 `FAILED`、`failure_reason` 写成 `类型名: 消息`，
并且**仍然填上 `wall_time`**。这样一份 CSV 里失败的行也是可分析的 ——
一个实例如果在 `0.02` 秒就 `FAILED`，那是建模问题；
如果跑到 `15.00` 秒才 `FAILED`，那是另一回事。

还有一处与本周前五天不同的地方：`_row` 会把 `result.detail` 里的三个键抄进 `rows`：

```text
cp_model_presolve   这一行跑的时候预求解是开是关
setup_encoding      这一行用的是哪种换型编码
model_variables     这一行的模型有多少个变量
```

**这三个键是「读数可复现」的另一半。** 只记目标值的话，
半年后看到两个不同的数，无法判断是求解器版本变了、参数变了、还是模型变了。

脚本：[m3w4d6_failures.py](../../projects/03_industrial_fjsp/examples/m3w4d6_failures.py)。

在项目目录 `projects/03_industrial_fjsp` 下运行：

实际输出（原样粘贴）：

```text
=== 1. 消融链里「没有改变」的层（预算 5 秒／次）===

  base        fjsp_cpsat_full        OPTIMAL        9     687     9
  base        fjsp_cpsat_qualified   OPTIMAL        9      31     9
  +setup      fjsp_cpsat_full        OPTIMAL        9     465     9

  要确认约束真的接上了，看的是验证器诊断与 MODEL_COVERAGE 表，不是这个数字。
  `fjsp_cpsat_qualified` 同两行是 13 与 28：它的**建模**比实例更紧，

=== 2. 预求解开关的代价（ind_qualified 配置，预算 5 秒）===
  presolve=True  status=UNKNOWN   obj=- 下界=- 分支=- 建模型=0.05s 求解=4.26s
      detail: cp_model_presolve=True linearization_level=1
  presolve=False status=FEASIBLE  obj=88 下界=34 分支=210085 建模型=0.04s 求解=5.01s
      detail: cp_model_presolve=False linearization_level=0
  预求解是「花预算换一个更小的模型」。预算大时划算，预算小时它可能把
  整个预算吃光，交回来的是一支根本没搜过的树 —— 看分支数就知道。

=== 3. 界与间隙：ind_worker 配置，预算 10 秒 ===
  status=FEASIBLE objective=108 best_bound=41 分支=120146
  相对间隙 = (108 - 41) / 108 = 62.04%
  FEASIBLE + 一个大间隙的意思是：这条排程**可行**（独立验证器判过），
  但没有任何证据说明它是同一模型下的最好解。要证据就得加预算。
  另做的一次更长运行（同实例、同 seed、单线程）：
      30 秒 -> FEASIBLE obj=97 下界=45（预算用尽，未证完）
      60 秒 -> OPTIMAL  obj=97 求解耗时 30.78 秒

=== 4. 结论 ===
  * 目标值不动 != 约束没生效；目标值变差 != 建模错了（可能是编码更保守）。
  * 报一个数字时必须同时报它的状态与下界，否则无法判断可信度。
  * 单次运行的 `iterations` 比 wall time 更能说明求解器到底做了什么。
```

### 7.1 怎么读这段输出

**第 1 节六行要竖着读（同一层比两个求解器），也要横着读（同一个求解器跨层）。**

竖着读：

| 层 | `fjsp_cpsat_full` | `fjsp_cpsat_qualified` | 差值 |
|---|---:|---:|---:|
| `base` | 9 | 9 | 0 |
| `+setup` | 9 | 13 | 4 |
| `+calendar` | 9 | 28 | 19 |

`base` 那一行差值是 `0`，因为**没有换型矩阵时膨胀量恒为 0**，
两条编码退化成同一个模型 —— 这是一格刻意留下的对照，它证明两者的差别确实只来自换型编码。
`+setup` 的差值 `4` 与第 5 节手算一致（`A`、`B` 之间多收 `3`，`C`、`D` 之间多收 `4`，
结果由 `max(12, 13)` 决定）。`+calendar` 的差值扩大到 `19`：可用窗被切成两段之后，
膨胀造成的「一段装不下就得整体推到下一个窗」的代价被放大。

横着读：

```text
fjsp_cpsat_full       9 -> 9 -> 9        三行不动
fjsp_cpsat_qualified  9 -> 13 -> 28      每层都动
```

同一个实例上，一个编码三行不动、另一个编码两行都动。**这不是矛盾，是两种原因的对照**
（第 3.3 节）：`full` 属于「最优解恰好避开」（原因一），
`qualified` 属于「它的模型本来就比实例更紧」（原因二）。
只跑一个求解器就无法区分两者 —— 会得出「换型与日历对这个实例毫无影响」这种错误结论。

**第 2 节是第一个失败案例，它的形态最容易被忽略。** 两行唯一的差别是 `presolve`：

```text
presolve=True   status=UNKNOWN   目标值空、下界空、分支空       求解 4.26s
presolve=False  status=FEASIBLE  目标值 88、下界 34、分支 210085  求解 5.01s
```

第一行的三个「空」是同一个事实的三种写法：**搜索没有产出任何东西**。
它跑掉了 `4.26` 秒（预算 `5` 秒），却连一个可行解都没有 —— 按第 4.1 节的判据，
这正是「预求解吃掉了预算」的痕迹。要记住的不是「预求解不好」，而是**判据的形状**：

```text
看到目标值为空时，先看分支数。
分支数也为空 -> 搜索没跑起来     -> 怀疑预求解与建模参数
分支数很大   -> 跑了但没找到解   -> 怀疑可行域太紧或约束冲突
```

**第 3 节是第二种失败案例：有解，但没有证据。**

```text
FEASIBLE  objective=108  best_bound=41  分支=120146     相对间隙 = (108 - 41) / 108 = 62.04%
```

`108` 是可信的（独立验证器判过它是合法排程），但它**不是最优值**：
间隙 `62%` 意味着下界只到 `41`，这条模型下可能存在好得多的排程，只是这次没找到也没排除。
下面两行是**另一次更长的运行**（同实例、同 seed、单线程，不是本脚本跑出来的）：

```text
30 秒 -> FEASIBLE obj=97 下界=45（预算用尽，未证完）
60 秒 -> OPTIMAL  obj=97 求解耗时 30.78 秒

10 秒   可行解 108，下界 41，间隙 62%       —— 只有「有一个解」这一条信息
30 秒   可行解  97，下界 45，间隙 54%       —— 解更好了，但仍没有证据
60 秒   最优值  97，下界 97，间隙  0%       —— 有证据了
```

`60` 秒那次在 `30.78` 秒就证完了，而 `30` 秒那次跑到预算用尽（`30.00` 秒）还没证完。
两次是**独立的运行**，墙钟会有抖动，正确的读法是「证明大约需要三十出头秒」，
而不是「`30.78` 比 `30.00` 大所以矛盾」。这也提醒一件事：
**状态是这一次运行的属性，不是这个方法的天性。**

**第 2、3 节的读数都是「观测值」，不是「规格值」。** 重跑一次，
`presolve=False` 那一行可能给出别的可行解（实测另一次是 `obj=84`、分支 `218630`），
第 3 节那一行也可能给出 `101` 而不是 `108`。原因是**预算被用尽时，
搜索停在哪个分支由墙钟决定**：单线程 + 固定种子保证「走过的那条路径」是确定的，
但走到哪里停不是。所以：

```text
证明完成的运行（OPTIMAL）           最优值、分支数都可跨次复现
预算用尽的运行（FEASIBLE / UNKNOWN） 可行解、下界、分支数都只是这一次的观测值
```

这是「状态是这一次运行的属性」的另一面：**连证据等级都会随预算变。**
本节要记住的是判据的形状（三个字段一起看），而不是某一次的具体数字。

**第 4 节三条结论逐条对应上面三节：**

```text
目标值不动 != 约束没生效        <- 第 1 节，两种原因要分开
目标值变差 != 建模错了          <- 第 1 节的 delta 列，可能是编码更保守
报数字必须带状态与下界          <- 第 2、3 节，否则无法判断可信度
```

第三条还有一句补充：**分支数比 wall time 更能说明求解器做了什么**。
wall time 是预算与机器负载的函数，分支数是搜索实际展开的节点数 ——
第 2 节两行的 wall time 都在 `5` 秒附近（被预算截断），
但分支数是「空」与 `210085`。

### 7.2 另一次运行：完整消融链（`15` 秒预算）

第 7.1 节只跑了三层。完整的六层由实验驱动产出，命令是：


它落盘在 `artifacts/month3_w4/`（`results.csv` / `metadata.json` / `ablation.json` / `report.md`）。
实测的完整链条（`makespan`、seed `0`、`15` 秒／次、单线程）：

| 阶段 | 新增约束 | `fjsp_cpsat_full` | 变化 | `fjsp_cpsat_qualified` | 变化 |
|---|---|---:|---|---:|---|
| `base` | 机器相关工时 + 柔性 + 释放/交期 | 9 | — | 9 | — |
| `+setup` | 工序族换型 | 9 | 没有改变 | 13 | **变了** |
| `+calendar` | 机器日历 | 9 | 没有改变 | 28 | **变了** |
| `+qualification` | 机器资质 | 27 | **变了** | 29 | **变了** |

单调性核对（目标值随约束增加不下降）：两条链都**通过**。

`qualified` 那条链上的「变了」则混杂了原因二 —— `+setup` 与 `+calendar` 那两行的变化

## 10. 自测题

- Q1：消融为什么要「累加」而不是「逐条删除」？
- Q2：单调性说目标值不会变小。它为什么能当正确性检查用？
- Q3：`+setup` 在 `full` 上「没有改变」。这能不能说明换型约束没接上？
- Q4：同一层上两个求解器的数字不同。差值应该算给谁？
- Q5：预求解在短预算下可能让状态变成 `UNKNOWN`。它的痕迹是什么？
- Q6：`FEASIBLE 108` 与 `OPTIMAL 97` 哪个更可信？为什么不能只看数字大小？
- Q7：`best_bound` 为空时为什么不写 `0`？
- Q8：`+calendar` 与 `+setup` 在 `full` 上都是「没有改变」，但敏感性不同。请说明。
- Q9：第 6 节说版本状态必须在创建输出目录之前冻结。不这样做会怎样？
- Q10：第 7.2 节的表里两条链都在 `+qualification` 与 `+locked` 处「变了」。
    这两次变化的原因相同吗？请分别说明。

### 参考答案

- A1：因为删除式的起点是全约束实例，六条约束之间有交互：删掉一条之后剩下的五条会把
  可行域切出一个新形状，于是「删掉它之后变好多少」这个数会被其余五条干扰。
  累加式从裸露的基础实例出发，每一层只加一条、上一层就是这一层的对照，因果链更短。
- A2：因为今天加进去的六条约束全部是限制性的（日历、维护、资质、人员、锁定、换型都在砍）。
  如果某一层的目标值**变小**了，那一定有一处建模写反了方向（例如把「至少隔 `gap`」
  写成「至多隔 `gap`」）。这条检查不依赖任何具体数值，只看序关系，所以比逐格核对数字更硬。
- A3：不能。它的机制是「基础最优解处处同族连排，换型约束在那里取等，一个点都没砍掉」
  （原因一）。要确认约束接上了，得构造一份违反它的排程 —— Day 2 第 7 节第 3 个实验
  就是这么做的（把 `D` 提前到 `9`，验证器报 `overlap: M1/D`）。
- A4：差值应该算给**建模**，不是算给实例。两个求解器只差换型编码一处，
  所以同层之差可以干净地归因到编码上；至于这份差值是「保守编码多收的钱」
  还是「精确编码少收的钱」，答案是前者 —— 精确编码与手算的真实换型逐个对上。
- A5：痕迹有三个：分支数几乎为 `0`（或为空）、求解耗时约等于预算、建模型耗时正常。
  三者合起来指向「预求解吃掉了预算，搜索没有跑起来」。
- A6：都可信，但可信的内容不同：`108` 可信的是「它是一条合法排程的目标值」，
  `97` 可信的是「它是这个模型的最优值」。不能只看数字大小，是因为
  `FEASIBLE 108` 的 `108` 是「这一次搜索里最好的解」，没有证据说它离最优有多远；
  而 `OPTIMAL 97` 的 `97` 带着一条证明。比较两个数之前要先比较它们的**证据等级**。
- A7：因为写 `0` 会把「没有证明」显示成「证明了一个 `0` 的界」——
  对最小化问题来说，下界 `0` 是一个极弱但**真实**的陈述，读者会以为求解器证明了它。
  空值表示「没有这个信息」，`0` 表示「有这个信息，值是 0」，两者必须区分。
- A8：`+setup` 是在最优解上**取等**（同族对换型 `0`，紧贴合法），
  所以换型矩阵只要变大一点就会立刻咬住；`+calendar` 是在最优解上**留了余量**
  （收尾 `9`，窗到 `10` 才关），需要最优值涨过 `10` 才会咬住。
  「没有改变」不代表「不敏感」，敏感性要看约束在最优解上取不取等。
- A9：不这样做的话，刚写进输出目录的 `config.json`（或 `results.csv`）会被 git 当成未跟踪文件，
  于是 `working_tree_dirty` 恒为 `True`。这个标记的用途是「登记这次运行对应的源码状态」，
  恒为真的是它等于废掉 —— 半年后无法判断当时的树是干净的还是脏的。
- A10：不同。`+qualification` 那一次变化是**实例的约束**造成的：资质表里没有 `(M0, F1)`，
  `C`、`D` 被赶到 `M1` 上，可行域真的变小了（Day 5 第 5 节手算过下界从 `9` 涨到 `27`）。
  `+locked` 那一次也是实例约束造成的：`C` 的机器与开工时刻被钉死，`D` 只能跟着后移。
  两次都属于「原因一」的机制（可行域被真实地砍小了），
  与保守编码那种「模型比实例更紧」的变化（原因二）必须分开记 ——
  后者的数值即使在同一个实例上换一个求解器就会消失。

## 11. 今日一句话总结

> **把六条约束累加到同一份工序数据上之后，读出来的是一张「有变化」与「没变化」混在一起的表 —— 而「没变化」有四行属于「最优解恰好避开」、有若干变化属于「保守编码的模型比实例更紧」，两种原因必须分开报，判据分别是「能不能构造出违反它的排程」与「换一个求解器数字会不会跟着变」；同时三种失败形态各有各的痕迹：`UNKNOWN` 要看分支数（预求解可能把 `5` 秒预算吃光，交回一支没搜过的树），`FEASIBLE` 要配着 `gap` 读（同一实例 `10s → 108/间隙 62%`、`30s → 97/间隙 54%`、`60s → OPTIMAL 97`），而 `INVALID_SOLUTION` 那一格的目标值一律不可用。**
