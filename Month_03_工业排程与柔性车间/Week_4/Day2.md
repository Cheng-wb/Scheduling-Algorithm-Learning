## 2. 为什么 Day 2 要谈批处理

前三周的工序是**一件一件**做的：一道工序占一段机器时间，做完下一道。真实车间里有一大类活
不是这样干的：

```text
热处理   一炉里同时放若干件，炉时相同 —— 放 1 件和放 8 件都是 4 小时
表面处理 同一槽液可以连续过若干件，换槽液（换液、调温、试片）才是贵的
印刷/涂装 同一个颜色连续印，换色要清洗墨路
```

这些活的共同结构是：**把「准备」这件事摊销到一批活上**。批越大，摊销到每件的准备时间越少。
这就是 `batching` 的动机，也是它为什么值得单独一天。

现在的模型里**没有**批对象，也没有「一炉几件」这个决策。本周对它的编码是：

```text
同族的工序连续加工    ->  不付换型时间
不同族的工序相邻加工  ->  付一次换型时间
```

也就是说，`batching` 被编码成**序列相关的准备时间**（sequence-dependent setup）。
这个选择不是偷懒，它有一个明确的理由：在给定「一批里放哪些件」之后，
唯一影响排程的就是「哪些工序连续、连续的两段之间要不要换型」。序列相关的准备时间
恰好就是这件事的精确表达。至于「一批放几件」这个决策，本周的模型不表达它 —— 见第 4.3 节。

这一层约束还有一个身份上的特点，与 Day 1 的三条不同：

```text
Day 1 的资质与人员  ->  只砍可行域，不进目标函数
Day 2 的换型        ->  既砍可行域（相邻两段之间要留出间隔），又进目标函数（换型总时间）
```

「既砍又进」意味着它有两套可观测的痕迹：验证器上的 `overlap` 与 `setup undefined` 标签，
以及 `ShopResult.breakdown["setup"]` 里的换型总量。两套痕迹都要核 —— 只看目标值会漏掉
「换型被正确计算但没有被正确约束」这种错法。

## 3. 概念：族、换型矩阵、以及「一批」到底被编码成了什么

### 3.1 族是相似性的载体

```python
@dataclass(frozen=True, slots=True)
class Operation:
    ...
    family: str | None
```

`family` 是一个字符串标签。它对模型只意味着一件事：**两道工序的族相同或不同**。
同一族的两道工序在设备看来是同一类活，切换它们不需要准备；不同族之间需要准备。

注意族不携带任何数量信息：`F0` 与 `F1` 的地位完全对称，没有大小、没有顺序、
没有「族 A 比族 B 难做」这种含义。所有数量信息都在**换型矩阵**里，而不是在族的命名里。

### 3.2 换型矩阵为什么不对称

```python
@dataclass(frozen=True, slots=True)
class Setup:
    from_family: str
    to_family: str
    minutes: int
```

三个字段读作「从 `from_family` 切到 `to_family` 需要多少分钟」。它**不是**一个对称关系：

```text
清洗是单向的       从浅色切到深色只需冲一遍（3 分钟）
                   从深色切回浅色要彻底清洗（4 分钟）—— 更贵
```

脚本里的矩阵就用了这个例子：

```text
F0 -> F0 : 0 分钟        F0 -> F1 : 3 分钟
F1 -> F0 : 4 分钟        F1 -> F1 : 0 分钟
```

同族到同族的 `0` 是必须显式写出来的一行，不是默认值：矩阵是完备的，
验证器在缺一行时报 `setup undefined`，而不是「当作 0」——**这一点很关键**：
**「没定义」与「定义为 0」在数据上必须是两件事**，否则模型会悄悄放过一个未定义的切换。

### 3.3 模型里的「批」长什么样

把第 2 节的编码写具体。设某台机器上的加工序列是：

```text
A(F0) -> B(F0) -> C(F1) -> D(F1)
```

这个序列在模型里的换型成本是：

```text
setup(F0, F0) + setup(F0, F1) + setup(F1, F1) = 0 + 3 + 0 = 3
```

读法：`A` 与 `B` 是**同一批**（同族连续），它们之间不付准备；`B` 与 `C` 是**换批**，
付一次 3 分钟；`C` 与 `D` 又是同一批，不付。所以「一批」在模型里就是
**同族工序在机器序列上的一段极大连续子串**。批的边界不在数据里，而是在排程里 ——
它是求解器决定的，不是输入的一部分。

这就是本模型对 `batching` 的全部表达。用四句话概括它能与不能：

| 能表达 | 不能表达 |
|---|---|
| 同族连续加工不付准备时间 | 一批的**容量上限**（一批最多几件） |
| 异族相邻付一次换型，且方向可以不对称 | 一批必须**整体开始、整体结束**（一批内部不许插进别族的活） |
| 一段连续同族工序只付一次换型 | 一批的**共同工时**（3 件同炉与 1 件同炉耗时相同） |
| 换型成本进入目标函数与 `breakdown` | 批规模对换型时间的影响（换型时间只与族对有关） |

第三行那一条最要紧，也最容易误解：真实的批处理之所以有吸引力，主要收益是
「凑批之后**单件的加工时间**下降」；本模型只表达了「凑批之后**准备时间**下降」。
所以本模型的结论只能说「同族连排省换型」，不能说「凑批省工时」。
这两句话听起来接近，在数值上可以差很远。

## 4. 推导：两条编码，两种代价

### 4.1 「按相邻对计费」为什么不重不漏

先说一个容易担心的点：真实车间里「一批只付一次换型」，而模型是按**相邻对**逐个计费的。
这两者会不会对不上？

设机器序列是 `… X(f) Y(f) Z(g) …`，`X` 与 `Y` 同族。按相邻对计费：

```text
setup(f, f) + setup(f, g) = 0 + setup(f, g)
```

按批计费：`X` 与 `Y` 是同一批，批内不计；批间一次 `setup(f, g)`。两者相同。
反过来，序列是 `… X(f) Y(g) …`：按相邻对是 `setup(f, g)`，按批是一次换批
（若 `X` 与 `Y` 各自成批），也是 `setup(f, g)`。也相同。

**结论：在「同族连续 = 同一批」这个定义下，按相邻对计费与按批计费是同一件事。**
这不是巧合：相邻对里同族的那些项恰好是 `0`，把 0 加进去不改变总数。
反过来说，如果矩阵里的同族项不是 `0`，这个等价关系立刻破裂 ——
所以「同族项必须是 0」这条约定其实是 `batching` 语义的一部分，不是可选的填法。

### 4.2 两种编码：精确槽位链与区间膨胀

要在 CP-SAT 里表达「相邻两段之间至少隔 `setup(前一族, 后一族)`」，至少有两种做法。

```text
做法一（区间膨胀）  让每道工序的机器占用变长一点：把 [start, end) 膨胀成
                    [start, end + max_outgoing_setup(自己的族))
                    然后用一条 AddNoOverlap 覆盖全部膨胀后的区间
做法二（槽位链）    在每台机器上给「实际在场的工序」排一条槽位链：
                    第 p 个槽位用 AddElement 指向「这一槽是哪道工序」，
                    相邻槽位之间用 AddAllowedAssignments 查表得到该对的换型常量
```

做法一的好处是模型小、约束少（一台机器一条 `AddNoOverlap`）；代价是**它过紧了**：

```text
膨胀量取的是「自己族的最大出向换型」，而不是「下一道工序真正的那个换型」。
于是同族的下一道工序也被要求空出 max_outgoing —— 而真值只需要 0。
```

本案里 `max_outgoing(F0) = max(0, 3) = 3`、`max_outgoing(F1) = max(4, 0) = 4`。
一个 F0 的工序后面跟一个 F0 的工序，本来可以紧贴着做，膨胀版却要求空出 3 分钟。
**同族连排这件 batching 的核心收益，被膨胀版整片切掉了。**

做法二是精确的：槽位链的相邻槽之间查的是「这两道工序的族对」的真实换型时间，
同族对查到 0，于是紧贴合法。代价是模型变量与约束都多了一大截（槽位变量、元素约束、表约束），
在固定预算下搜索推进得更慢。

于是有了今天最有意思的一个现象：**可行域更大的那个，在固定预算下不一定给出更好的解。**
第 7 节会实测到这一点。

### 4.3 一条被切掉的可行域意味着什么

膨胀版切掉的不是「一些无关紧要的排程」，而是**整个 batching 收益**：

```text
真实模型     A(F0) [0,4) 与 B(F0) [4,9) 紧贴，换型 0 分钟     -> J0 在 9 分钟做完
膨胀模型     A(F0) 的区间膨胀到 [0,7)，B 最早 7 开工          -> J0 至少 12 分钟
```

本周的两个注册名字就是这两条编码：

| 名字 | 换型编码 | 模型规模 | 可行域 |
|---|---|---|---|
| `fjsp_cpsat_qualified` | 区间膨胀 | 小 | 更小（过紧） |
| `fjsp_cpsat_full` | 精确槽位链 | 大 | 正确（不过紧） |

它们**只差这一处**。所以两者在同一实例上的目标值之差，可以干净地归因到换型编码上 ——
这是一个刻意保留的对照，后面的实验都建立在它上面。

## 5. 手算：下界 `9` 与保守编码的 `13`

脚本用的实例（`examples/m3w4d2_batching.py`）：

```text
订单 J0 = (A, B)，due = 20        订单 J1 = (C, D)，due = 20
A：{M0: 5, M1: 4}，F0             B：{M0: 6, M1: 5}，F0
C：{M0: 4, M1: 6}，F1             D：{M0: 5, M1: 5}，F1
换型：F0->F0 = 0，F0->F1 = 3，F1->F0 = 4，F1->F1 = 0
无日历、无资质、无工人 —— 今天只看换型这一层
```

**下界。** 三类取最大：

```text
订单链下界    J0：A 最快 4（M1）+ B 最快 5（M1）= 9
              J1：C 最快 4（M0）+ D 最快 5（M0 或 M1）= 9                     -> 9
机器负载下界  总工时（取各工序最快机器）= 4 + 5 + 4 + 5 = 18，两台机器
              ceil(18 / 2) = 9                                                -> 9
换型下界      同族连排可以做到 0 次换型（每个订单的两道工序同族）              -> 0
下界 LB = max(9, 9, 0) = 9
```

**上界。** 把同族的两道工序排在同一台机器上紧贴着做：

```text
M1：A(F0) [0,4) -> B(F0) [4,9)      换型 setup(F0,F0) = 0，紧贴合法
M0：C(F1) [0,4) -> D(F1) [4,9)      换型 setup(F1,F1) = 0，紧贴合法
Cmax = 9
```

逐条核对：工艺路线 `A` 结束 4 ≤ `B` 开始 4、`C` 结束 4 ≤ `D` 开始 4；
两台机器各自不重叠；换型总量 `0 + 0 = 0`。
**`LB = 9` 且上界 `9`，所以 `9` 是最优值。** 求解器在同一实例上给 `OPTIMAL 9`，
两条独立路径一致。

**保守编码为什么会给 `13`。** 把膨胀量算出来：

```text
max_outgoing(F0) = max(setup(F0,F0), setup(F0,F1)) = max(0, 3) = 3
max_outgoing(F1) = max(setup(F1,F0), setup(F1,F1)) = max(4, 0) = 4
```

于是每段占用被拉长：

```text
A [0,4) 膨胀 -> [0,7)      M1 上的下一段最早 7 开工
C [0,4) 膨胀 -> [0,8)      M0 上的下一段最早 8 开工
```

两条机器分别被推到：

```text
M1：A[0,4) -> B 最早 7，B 占 5 分钟 -> B[7,12)        这台机器的收尾 = 12
M0：C[0,4) -> D 最早 8，D 占 5 分钟 -> D[8,13)        这台机器的收尾 = 13
Cmax = max(12, 13) = 13
```

实测的排程正是这两行（第 7 节输出里的 `B M1 [7,12)` 与 `D M0 [8,13)`），
所以 `13` 不是「保守编码没搜到好解」，而是**它的模型里 `9` 根本不可行**：
同族连排要求的紧贴被膨胀量挡住了。这 4 分钟的差就是 batching 收益在膨胀版里的损失。

注意 `13 = max(12, 13)` 这个结构也说明另一件事：膨胀造成的损失**不是均匀分摊**的，
它取决于哪个族的最大出向换型更大（`F1` 的 4 比 `F0` 的 3 大，所以 `M0` 那一侧更紧）。

## 6. 实现：两处关键代码

一切都在 [constraints2.py](../../projects/03_industrial_fjsp/fjsp_shop/constraints2.py)。

**第一处是精确路径的槽位链**（`_add_machine_sequences`）：

```text
每台机器 m：
  在场[o][m]      bool：工序 o 是否排在这台机器上（由机器指派推出）
  槽位[p][m]      第 p 个槽位放哪道工序（AddElement 指向候选集合）
  链的相邻槽之间   AddAllowedAssignments((槽位[p], 槽位[p+1], gap), 允许表)
                  允许表里的每一行 = (前工序, 后工序, setup(前族, 后族))
  Σ_p (槽位[p] == o) == 在场[o][m]        每道在场工序恰好占一个槽位
  槽位链保持工艺顺序：start[槽位[p+1]] >= end[槽位[p]] + gap
```

允许表是按实例现算的（`setup_lookup()`）：把每一对（前工序，后工序）的换型时间查出来，
同族对查到的就是 `0`。**这就是精确性的来源**：约束里出现的是「这一对工序的真实换型」，
而不是「自己族的最坏换型」。

**第二处是保守路径的膨胀**（`_add_machine_no_overlap`，参数 `inflate_setup=True`）：

```text
对每台机器：AddNoOverlap({ [start[o], end[o] + inflate(o)) | o 排在这台机器上 })
其中 inflate(o) = max_outgoing_setup(o.family)     没有换型矩阵时为 0
```

顺便记一笔第一次写这段时踩的坑，它值得留下：

```text
第一版把「膨胀版」当成一条**冗余的冗余约束**加在槽位链之外 —— 理由是「多一条不会错」。
这个理由是错的：槽位链蕴含的只是「不重叠 + 相邻留够换型」，
而膨胀版另外要求「任何相邻两段之间至少隔 max_outgoing」。
两者叠加之后，同族紧贴被禁掉了 —— 于是精确路径报出 INFEASIBLE，
而手工核过的一个合法排程明明存在（独立验证器对它零诊断）。
所以精确路径**必须**用 inflate_setup=False 跳过膨胀版，两者是二选一，不是叠加。
```

这个坑的教训与数值无关：**「多加一条约束不会更差」只在约束是重言式时才成立**。
判断一条约束是不是重言式，要拿它的**语义**去对，不能拿「它看起来更严」当理由。

## 7. 实验：`m3w4d2_batching`

脚本：[m3w4d2_batching.py](../../projects/03_industrial_fjsp/examples/m3w4d2_batching.py)。

在项目目录 `projects/03_industrial_fjsp` 下运行：

```bash
python examples/m3w4d2_batching.py
```

实际输出（原样粘贴）：

```text
=== 1. 换型矩阵（不对称）===
  F0 -> F0 : 0 分钟
  F0 -> F1 : 3 分钟
  F1 -> F0 : 4 分钟
  F1 -> F1 : 0 分钟

=== 2. 同族连排：A(F0) 与 B(F0) 紧贴，不需要换型 ===
  诊断：无（通过）
  Cmax=9  换型总量=0

=== 3. 异族相邻：B(F0) 后面接 D(F1)，必须空出 setup(F0->F1)=3 ===
  诊断：无（通过）
  换型总量=3（一次 F0->F1）
  把 D 提前到 9（不空换型）：['overlap: M1/D']

=== 4. 精确编码 vs 保守编码：保守编码切掉了多少 ===
  fjsp_cpsat_full        精确（槽位链 + 查表）                 status=OPTIMAL   Cmax=9 换型=0
  fjsp_cpsat_qualified   保守（区间膨胀 AddNoOverlap）        status=OPTIMAL   Cmax=13 换型=0
  保守编码为什么更差：它把每道工序的机器占用按 max_outgoing_setup 膨胀，
  A(F0) 的区间变成 [0, 7)，于是同族的 B 再也贴不上 [4,9) —— 同族连排被切掉了。
```

### 7.1 怎么读这段输出

**第 2 节的一行 `Cmax=9 换型总量=0` 是 batching 收益的最干净的表达。**
两个订单各自的两道工序同族，各自在一台机器上连排，换型总量是 `0`，
`Cmax` 正好等于第 5 节算出来的下界 `9`。这一格同时说明「下界可达」与「同族连排是免费的」。

**第 3 节做了一个对照：把 D 提前到 9。** 这时 `B` 刚在 `9` 结束、`D` 是异族，
中间必须空出 `setup(F0, F1) = 3`，所以 `D` 最早只能 12 开工。输出给的诊断是：

```text
overlap: M1/D
```

注意标签是 `overlap` 而不是 `setup`。这是验证器的一个设计选择：换型间隔不足
在几何上就是「与外推的边界撞了」，所以它复用同一条标签 `overlap: <机器>/<工序>`。
读诊断时要意识到这一点 —— 看到 `overlap` 时，可能撞的是另一个工序的实体区间，
也可能撞的是「上一段结束 + 换型」这条看不见的边界。两种情况的修法都是往后挪。

**第 4 节是全天的核心。** 两个求解器、同一个实例、同一份预算：

| 求解器 | 换型编码 | 状态 | `Cmax` | `breakdown["setup"]` |
|---|---|---|---:|---:|
| `fjsp_cpsat_full` | 精确槽位链 | `OPTIMAL` | 9 | 0 |
| `fjsp_cpsat_qualified` | 区间膨胀 | `OPTIMAL` | 13 | 0 |

两行都是 `OPTIMAL`，所以 `13` **不是**「保守编码没搜好」，而是「在它的模型里 `9` 不可行」。
两者的可行域是真包含关系：精确版的可行域严格更大。

还有一格值得盯住：**两行的 `breakdown["setup"]` 都是 `0`。**
保守编码的那条排程（`A[0,4)`、`B[7,12)`、`C[0,4)`、`D[8,13)`）里，
`M1` 上 `A` 与 `B` 之间空了 3 分钟、`M0` 上 `C` 与 `D` 之间空了 4 分钟，
看上去像付了换型 —— 但 `breakdown["setup"]` 是 `0`。原因是
`total_setup_time` 按**相邻对的族**查表求和，而同族对查到的是 `0`。
那两段空隙是膨胀版**多要求**的，不是真实换型。

这一格是今天最容易读错的地方，值得单独记下来：

```text
排程上的「空隙」不等于「换型时间」。
换型时间是按相邻对的族查表得到的**代价**；空隙是约束允许的**空闲**。
两者只有在约束恰好取等时才对得上。
```

所以核换型要核 `breakdown["setup"]`，核约束是否被遵守要核验证器的诊断，
核「这个排程好不好」才看目标值。三个数各管一件事，缺一个都可能读错。

## 10. 自测题

- Q1：模型里为什么没有 `Batch` 这个对象？不建它，`batching` 的哪一部分就表达不了了？
- Q2：同族连排不付换型，这是「约束」还是「目标函数的性质」？两者能分开吗？
- Q3：换型矩阵里 `F0 -> F0 = 0` 这一行能不能省掉？省掉会怎样？
- Q4：`_add_machine_sequences` 里的允许表是「按工序对」还是「按族对」建的？为什么要这样建？
- Q5：膨胀量取 `max_outgoing_setup` 是一个**上界**还是**下界**？由此判断膨胀版是过松还是过紧。
- Q6：精确编码的可行域更大，为什么在固定预算下可能给出更差的目标值？
- Q7：第 7 节第 4 节里两行都是 `OPTIMAL`，能不能说「两个求解器一样好」？
- Q8：一个排程里某台机器上有 4 分钟空隙，`breakdown["setup"]` 却可能为 `0`。请解释。
- Q9：如果实例给了工序族但**没有给换型矩阵**，验证器会不会报一堆 `setup undefined`？
- Q10：把本节的编码用在「一炉最多放 3 件」的实例上，模型会给出什么？这个答案能用吗？

### 参考答案

- A1：因为「一批」的边界在排程里而不在输入里：给定「一批放哪些件」之后，
  唯一影响排程的就是相邻两段之间要不要准备。建 `Batch` 对象需要先决定批的划分，
  那是另一个决策层，本周的模型不表达它。不能表达的部分是**批的容量上限**与
  **批的共同工时**（同炉共时），见 3.3 节那张表。
- A2：两个身份都有。作为约束：相邻两段之间要留出 `setup(前族, 后族)` 的间隔（验证器与槽位链管）。
  作为目标：换型总量进入 `breakdown["setup"]`，并且在 `weighted_sum` 一类的目标里会进目标函数。
  两者能分开：可以建一个「留间隔但不计成本」的模型，也可以建一个「计成本但不留间隔」的模型，
  本节的两个求解器都属于前者（都留间隔），差别只在间隔取真值还是取最大值。
- A3：不能省。矩阵必须完备，缺一行时验证器报 `setup undefined` 而不是「当作 0」。
  这个设计是为了让「没定义」与「定义为 0」在数据上可区分 —— 否则一个未定义的切换会被
  静默当成免费，模型会在此基础上给出一个偏乐观的排程。
- A4：按**工序对**建表，表里的值按**族对**查出来。槽位链的相邻槽是两个具体的工序，
  表约束需要枚举「前槽放哪道工序、后槽放哪道工序」，所以表的行是按工序对列的；
  但同一（前族，后族）的所有工序对填的是同一个值 —— 把族对查表的结果摊平到工序对上。
- A5：它是该族**所有出向换型**的最大值，所以是真实换型时间的一个上界。
  约束用的是上界，所以它比真实要求更严 —— 膨胀版是**过紧**的，它的可行域是真子集。
- A6：因为预算固定时，搜到多好的解取决于搜索推进的速度，而不只是可行域的大小。
  模型更大（槽位变量、元素约束、表约束都要预求解）意味着同样的墙钟时间里
  分支少得多，可能停在离最优更远的可行解上。可行域大是「最终能到多远」，
  预算是「这段时间能走多远」，两者是不同的问题。
- A7：不能。两行的 `OPTIMAL` 都是**关于各自模型**的证明：精确版证明了它模型的最优是 `9`，
  保守版证明了它模型的最优是 `13`。它们不是同一个模型，所以两个 `OPTIMAL` 不可比。
  可比的是「模型」与「实例」的关系：精确版的模型与实例一致，保守版比实例更紧。
- A8：因为 `total_setup_time` 按相邻对的**族**查表求和，同族对查到 `0`，加进去不改变总数。
  那 4 分钟空隙是膨胀版额外要求的（`max_outgoing` 而不是真实换型），不是换型代价。
  核对换型要看 `breakdown["setup"]`；核对该留的间隔要看验证器的 `overlap` 诊断。
- A9：不会。验证器只在 `instance.setups` 非空时才检查换型（`check_setup` 那一个开关）。
  这是刻意的宽容：只给工序族而不给矩阵，往往是把族用于资质或分组，
  这时不该逼出一堆「换型未定义」。反过来说，**只要给了矩阵，就必须给全**。
- A10：模型会把它当成普通的同族连排 —— 因为它根本不知道「一炉最多 3 件」这件事，
  它会排出 5 件同族的工序连续加工并宣称省了准备时间。这个答案**不能用**：
  它违反了一条模型没有表达的约束。这正是 3.3 节「不能表达」那一列的现实后果，
  也是使用本模型时必须自己核对的事。

## 11. 今日一句话总结

> **本模型不建「批」对象，而是把 `batching` 编码成序列相关的换型：同族工序连续加工免费、异族相邻付一次换型（方向可以不对称），于是「一批」就是机器序列上一段同族的极大连续子串 —— 这个编码精确表达了「凑批省准备时间」，却完全表达不了「凑批省加工时间」与「一批的容量上限」；而在 CP-SAT 里它有两条路：精确槽位链（查真实换型，可行域正确）与区间膨胀（按各族最大出向换型拉长占用，过紧），本案实测 `9` 与 `13`，差的那 4 分钟正是同族连排被膨胀量切掉的部分。**
