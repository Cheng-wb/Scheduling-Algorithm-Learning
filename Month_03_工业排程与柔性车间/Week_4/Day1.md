## 2. 为什么 Day 1 要先做「谁能做」与「谁在场」

前三周的模型里，资源只有一种：机器。只要工序的 `machine_times` 里写了这台机器，
这台机器就能做这道工序，做完就完事。真实车间不是这样运作的：

```text
资质：某台机器只被认证过加工某几个工序族 —— 没认证的活放上去就是不合格品
人员：机器不会自己开。要有持证的操作工在场，而且一个人同一时刻只能看一台机器
```

这两件事在任何一本车间排程的教材里都是「资源约束」的标准成员，而它们有一个共同的形状：

```text
它们都在回答「可不可行」，不在回答「好不好」。
它们的作用是**砍掉整片可行域**，而不是给目标函数加减分。
```

这一点决定了今天的建模方式。如果资质只是一句「最好别这么排」的软提示，
那求解器在预算紧的时候就会拿它换目标值 —— 而车间里没有「稍微不合格」这回事。
所以资质必须是**变量层面的删除**：不合格的（工序，机器）组合根本不该生成决策变量。

次生资源（工人）比资质多一层麻烦：它把「一道工序占什么」从一元变成二元。

```text
Day 1 之前：工序 o 占一台机器 m，在 [start, end) 上
Day 1 之后：工序 o 占一台机器 m 与一个人 w，在 [start, end) 上；w 有自己的能力集合与容量
```

多出来的这一维不是装饰。加了工人之后，两台机器可以同时开工却因为只有一个人而必须排队 ——
这种冲突**机器不重叠**这条约束完全看不见。今天要练的就是把这类冲突显式地建出来，
并且让独立验证器能够单独判它。

顺带说明今天的产出为什么叫 `fjsp_cpsat_qualified` 而不是别的名字：本月批次会按名字调它，
一个没注册的名字在批次记录里就是一行 `FAILED`。所以「能跑」不够，**必须出现在
`fjsp_shop.registry.available()` 里**。

## 3. 概念：三种资源属性，三组诊断

### 3.1 资质是「（机器，族）」对

`Qualification` 只有两个字段：

```python
@dataclass(frozen=True, slots=True)
class Qualification:
    machine_id: str
    family: str
```

一行 `Qualification("M0", "F0")` 的意思是「`M0` 有权加工族 `F0` 的工序」。
它读起来像是在给机器发证书，但**判定发生在工序那一侧**：一道工序 `o` 合格可用的机器是

```text
{ q.machine_id | q.family == o.family }
```

也就是说，资质把「族」当作授权的最小单位。这样做的理由是车间里的实际做法：
认证（首件检验、工艺验证）是按**工艺族**批量发放的，不是逐道工序发的。
同一族的工序在设备看来是同一类活，换的只是参数。

这个设计有三个直接后果：

| 情形 | 后果 |
|---|---|
| 工序的 `family` 是 `None` | 不发任何资质也**不**限它（`family is None` 时资质不参与判定） |
| 实例里一条资质都没有 | 资质不参与判定，退化成纯 FJSP |
| 工序的族没有任何资质 | 合格机器集合为空 —— 这是个不可行实例，建模阶段就会暴露 |

### 3.2 能力：这个人能不能开这台机器

`Worker.machine_ids` 是一张机器清单。一个人只被培训过开 `M0`，那他去开 `M1` 就是违规操作，
与「他忙不忙」无关 —— 验证器给这类错误发的标签是：

```text
worker: W0 cannot operate M1
```

注意它与资质是**两个方向**的判定：资质限制「机器能不能做这道工序」，
能力限制「人能不能开这台机器」。两者都不看时间，只看配对。

### 3.3 容量：这个人同时能看几台机器

`Worker.capacity` 是整数。容量为 `1` 时，同一个人负责的两段占用不能重叠：

```text
占用的口径是半开区间 [start, end)
end == next start  ->  合法（紧贴）
end >  next start  ->  违规
```

为什么是半开区间？因为 `end` 这个时刻工序已经做完、人可以走了。若用闭区间，
`[0,5)` 与 `[5,9)` 会被判成重叠 —— 那样连「一道接一道连着干」都不允许，明显过严。
验证器给的标签是：

```text
worker: W1 double-booked
```

容量大于 `1` 时不允许的是「同时占用数超过容量」，标签是：

```text
worker: W1 peak 3 > capacity 2
```

也就是说容量 `1` 的 `double-booked` 是 `peak > capacity` 的一个特例。两条标签分开写，
是因为它们指向的返工动作不同：前者是「同一时刻排了两次活」，后者是「同时开的机器太多」。

### 3.4 三种属性归到一张表

| 属性 | 模型字段 | 验证器标签 | 建模上的作用 |
|---|---|---|---|
| 资质 | `Qualification`（机器 + 族） | `qualification: <op> on <machine>` | 删除不合格的（工序，机器）变量 |
| 能力 | `Worker.machine_ids` | `worker: <w> cannot operate <m>` | 把不合格的（工序，工人）变量压成 0 |
| 容量 | `Worker.capacity` | `worker: <w> double-booked` / `peak n > capacity c` | `AddCumulative` 的资源约束 |

## 4. 推导：为什么「每道工序都要有 worker_id」不是多余的

### 4.1 两种可选的做法

给排程加人员有三种做法，它们的强度依次上升：

```text
做法 A  求解时给每道工序配人，但排程里不记 —— 人员冲突只在求解器内部成立
做法 B  排程里记 worker_id，可选（可以是 None）—— 由调用方决定要不要用
做法 C  排程里记 worker_id，且必须是某个已知工人 —— 漏指派本身就是错误
```

做法 A 是最差的：它把一条硬约束藏进了求解器的内部状态。任何人拿到这份排程去复核，
都只能看到机器维，看不到人。一旦有人换个求解器重新排一次，人员冲突就复活了。
排程的**可复核性**要求约束必须落在数据上，不能落在过程的记忆里。

做法 B 也不够：`worker_id = None` 与 `worker_id = "W0"` 在机器维上完全一样，
但一个是「没人管」，一个是「张三在看」。如果没有一道检查要求它非空，
那么「求解器忘了配人」和「这道工序本来就不需要人」在数据里长得一模一样。

所以本周采用做法 C：`ScheduledOperation.worker_id` 在**有工人资源的实例里必须落在已注册的工人集合内**。
验证器给未知工人的标签是：

```text
worker: unknown 'W9'
```

### 4.2 为什么求解器必须「强制占用」而不是「可选占用」

`Worker` 是一个**次生**资源：它不改变工序的加工时间，只决定工序能不能开工。
这类资源共享一个陷阱：

```text
如果把「用不用人」做成可选，求解器的最优策略永远是「不用人」——
因为不用人就没有人员冲突，可行域更大，目标值只会更好。
于是整条人员约束在最优解上自动失效，等于白建。
```

避免它的办法不是加惩罚项（惩罚项也是可以不被选择的），而是**取消选择权**：
容量约束作用在「所有工序的可选工人区间」上，而每道工序**恰好**要选一个工人。
一旦「必须选」，人力就成了瓶颈的真实来源。

### 4.3 三条约束的写法

```text
资质    qualified = { m | (m, op.family) 在资质表里 }      若 op.family 非空
        不在 qualified 里的机器，这道工序的 x[op][m] 变量**根本不创建**
        （不是创建后压成 0 —— 少一个变量就少一片搜索空间）

能力    w[op][worker] 只有当 worker 能操作这台候选机器时才存在
        对每道工序：Σ_m Σ_w x[op][m] · w[op][worker] == 1   （恰好一个工人）

容量    对每个工人资源 r：
        AddCumulative({ 该工人可选的所有区间 }, 需求 = 1, 容量 = r.capacity)
```

第一条的关键是「根本不创建」。这不只是写法上的讲究：变量少了，预求解与搜索都轻，
在预算固定的批次里这是实打实的差别。这一点本月后面还会再遇到一次。

## 5. 手算：`m3w4d1` 实例的下界与最优值

脚本用的实例（`examples/m3w4d1_qualified.py`）：

```text
订单 J0 = (A, B)，due = 8          订单 J1 = (C)，due = 4
A：machine_times = {M0: 5, M1: 6}，family = F0
B：machine_times = {M1: 4}，       family = F1
C：machine_times = {M1: 3}，       family = F1
资质：(M0, F0)、(M1, F1)            工人：W0 只会 M0；W1 只会 M1；W2 两台都会（容量都是 1）
```

先按资质筛一遍合格机器：

```text
A 是 F0 -> 只有 M0 有 (M0, F0) 资质 -> A 只能上 M0，工时 5
B 是 F1 -> 只有 M1 有 (M1, F1) 资质 -> B 只能上 M1，工时 4
C 是 F1 -> 只有 M1 有 (M1, F1) 资质 -> C 只能上 M1，工时 3
```

注意 `A` 的 `machine_times` 里**写了** `M1`（6 分钟）。资质的作用正是把这条看起来可行的路砍掉 ——
这类实例是刻意构造的：如果 `A` 的工时表里根本没有 `M1`，那么「把 A 放到 M1」违反的是
`illegal assignment`，而不是资质，实验就测不到想测的东西。

现在算下界。三类下界取最大：

```text
订单链下界        J0：A(5, 在 M0) + B(4, 在 M1) = 9      J1：C(3) = 3        -> 9
机器负载下界      M0：5 分钟      M1：4 + 3 = 7 分钟      max = 7            -> 7
                    （单机不并行，所以机器负载本身就是下界）
人员下界          W1 一个人要看着 M1 上的 B 与 C：4 + 3 = 7                  -> 7
下界 LB = max(9, 7, 7) = 9
```

上界：把 A 排在 `M0[0,5)`，C 排在 `M1[0,3)`，B 排在 `M1[5,9)`（B 是 J0 的第二道工序，
必须等 A 做完，所以最早 5 开工）：

```text
A  M0  [0, 5)   W0
C  M1  [0, 3)   W1
B  M1  [5, 9)   W1
Cmax = max(5, 3, 9) = 9
```

逐条核对：

```text
资质      A 在 M0（F0，合格）；B、C 在 M1（F1，合格）
能力      W0 只开 M0；W1 只开 M1
容量      W1 的两段是 [0,3) 与 [5,9)：不重叠（连紧贴都不是，中间空了 2 分钟）
工艺路线  A 结束 5 <= B 开始 5；J1 只有一道工序
机器不重叠 M1 上 [0,3) 与 [5,9) 不重叠；M0 上只有一段
```

**LB = 9 且上界 = 9，所以 9 是最优值。** 这条推理是今天唯一一个「不需要相信求解器」的结论，
也是后面读第 7 节输出时的尺子：求解器报 `OPTIMAL 9` 时，我们可以说它算对了；
如果它报 `OPTIMAL 10`，我们就知道它的模型比实例更紧或者更松。

## 6. 实现：三条约束落在哪里

三个方法都在 [constraints2.py](../../projects/03_industrial_fjsp/fjsp_shop/constraints2.py)，
与本周其余求解器共用同一条建模路径：

```text
build_model(instance, spec, *, exact_setup)   建变量与约束；_Built 里挂着全部决策变量
  ├─ qualified_machine_ids(instance, op)      资质筛选：返回合格机器 id 列表
  ├─ _prepare_choices(...)                    逐工序生成 (机器, 时长) 决策变量
  ├─ _add_workers(built)                      能力过滤 + 恰好一个工人 + AddCumulative
  └─ _add_objective(built, spec)              目标函数（今天用 makespan）
solve_with(instance, spec, method, *, exact_setup)   跑求解器、组装 ShopResult
```

资质那一行是本文件里最省代码、最省搜索空间的一处：

```python
def qualified_machine_ids(instance, op):
    """工序 ``op`` 的合格机器 id；实例里没有资质表时返回它的全部候选机器。"""
    if not instance.qualifications:
        return [machine_id for machine_id, _ in op.machine_times]
    if op.family is None:
        return [machine_id for machine_id, _ in op.machine_times]
    allowed = {q.machine_id for q in instance.qualifications if q.family == op.family}
    return [machine_id for machine_id, _ in op.machine_times if machine_id in allowed]
```

三个分支对应第 3.1 节那张表：没有资质表就全放行；工序没有族就不参与判定；
否则取交集。返回的列表直接决定 `_prepare_choices` 里生成几个变量 ——
**不合格的机器不会留下任何决策变量**。

工人那一段的核心是三句话：

```text
w[op][worker] 只在该工人能操作这台机器时创建
每道工序：Σ(机器) Σ(工人) x[op][m] · w[op][worker] == 1     恰好一个人
每个工人：AddCumulative(该工人的全部可选区间, 需求 = 1, 容量 = worker.capacity)
```

第三条用的是 CP-SAT 的累积约束而不是 `AddNoOverlap`：容量为 `1` 时两者等价，
但 `AddCumulative` 能直接表达容量 `>1` 的情形，不需要为容量写两条分支。

另外，`solve_with` 在组装 `ShopResult` 时会把每个工人区间上的 `worker_id` 原样写进
`ScheduledOperation`，所以第 4.1 节的「做法 C」在数据上是成立的：
返回的排程本身就带着人员指派，不需要回头去问求解器。

## 7. 实验：`m3w4d1_qualified`

脚本：[m3w4d1_qualified.py](../../projects/03_industrial_fjsp/examples/m3w4d1_qualified.py)。

在项目目录 `projects/03_industrial_fjsp` 下运行：

```bash
python examples/m3w4d1_qualified.py
```

实际输出（原样粘贴）：

```text
=== 1. 手算排程先自证清白 ===
  A@M0[0,5) W0 / C@M1[0,3) W1 / B@M1[5,9) W1
      诊断：无（通过）

=== 2. 三次故意破坏，看诊断是不是那一条 ===
  把 A 放到 M1（A 是 F0，资质只发了 (M0,F0)）
      诊断：qualification: A on M1
  让 W0 去开 M1（W0 的 machine_ids 只有 M0）
      诊断：worker: W0 cannot operate M1
      诊断：worker: W0 double-booked
  W1 容量 1，两段占用重叠
      诊断：precedence: A -> B
      诊断：overlap: M1/C
      诊断：worker: W1 double-booked
  同一工人两段占用**紧贴**（半开区间 [start,end)，相接不算冲突）
      诊断：无（通过）

=== 3. fjsp_cpsat_qualified 自己解一遍 ===
  status=OPTIMAL objective=9.0
  独立验证器诊断：无（通过）
  排程（按开工时刻排序）：
      A  M0  [0,5)  资源=W0
      C  M1  [0,3)  资源=W1
      B  M1  [5,9)  资源=W1
  每道工序都被指派了资源：True
  实际用到的资源：['W0', 'W1']
```

### 7.1 怎么读这段输出

**第 1 节是「先自证再求解」。** 手算排程先过一遍验证器，是为了把「验证器认可什么」
与「求解器给什么」这两件事分开。如果跳过这一步，第 3 节求解成功时我们无法判断
是「求解器对」还是「验证器松」——两条独立的判据必须分别确认。

**第 2 节四次破坏里有三次触发了不止一条诊断，这是正常的。** 逐条看：

| 破坏 | 触发的诊断 | 为什么会连带 |
|---|---|---|
| A 放到 M1 | `qualification: A on M1` | 只有这一条：A 在 M1 上不与其他工序抢机器 |
| W0 去开 M1 | `worker: W0 cannot operate M1`、`worker: W0 double-booked` | W0 同时被指派到 M0 的 A 与 M1 的 C，于是既越权又重叠 |
| W1 两段重叠 | `precedence: A -> B`、`overlap: M1/C`、`worker: W1 double-booked` | 把 C 塞到 `[2,5)` 之后 B 被推到 `[0,4)`，A 还没做完；同时 C 与 B 在 M1 上撞了，W1 也撞了 |

「一次错误决定触发多条诊断」不是验证器啰嗦，而是**它按维度独立检查**的必然结果。
验证器不做「找根因」这件事：它只报告每一维上观察到的事实。找根因是人的工作，
所以诊断列表要完整而不是第一条就停 —— 停下来的验证器会让人以为只有一个问题。

**最后一次破坏是全节最要紧的一格**：同一工人 `W2` 的两段占用是 `[0,5)` 与 `[5,8)`，
`end == next start`，验证器的结论是「无（通过）」。这一格锁定了半开区间的语义。
把它换成闭区间，这一格就会报 `double-booked`，而现实里「一道接一道连着干」是合法且常见的，
所以半开区间是唯一站得住的口径。

**第 3 节的 `OPTIMAL 9` 与第 5 节的手算下界一致**，这是今天唯一一处「两条独立路径互证」：
手算给出 `LB = 9` 与一个 `9` 的可行排程，求解器给出 `OPTIMAL 9`。
注意 `OPTIMAL` 只说明求解器**证明了自己那个模型**的最优值；它的模型比实例更紧还是更松，
仍要靠独立验证器的那一行「无（通过）」来兜底。两句话合起来才是完整结论。

**最后两行是数据层面的确认。** `每道工序都被指派了资源：True` 对应第 4.1 节的
「做法 C」；`实际用到的资源：['W0', 'W1']` 说明求解器挑了 `W0` 与 `W1`，
把「多面手」`W2` 留着没用 —— 容量富余的工人自然不会被浪费，这不是巧合，
而是「恰好一个工人」这个等式在起作用：不指派是不允许的，指派到必要的那一个即可。

## 10. 自测题

- Q1：为什么资质用「（机器，工序族）」对表示，而不是给每台机器一张「可做工序清单」？
- Q2：实例里一条资质都没有时，资质这条约束会怎样？
- Q3：一道工序的 `family` 是 `None`，它受不受资质限制？为什么这样设计？
- Q4：为什么不合格的（工序，机器）组合是「不创建变量」而不是「创建后压成 0」？
- Q5：工人容量为 `1` 时，`AddNoOverlap` 与 `AddCumulative` 的区别在哪？为什么本周选了后者？
- Q6：如果求解时允许「不用工人」，最优解会发生什么？这条约束为什么不能靠惩罚项实现？
- Q7：`worker: W1 double-booked` 与 `worker: W1 peak 3 > capacity 2` 有什么关系？
- Q8：手算的 `LB = 9` 只用了订单链、机器负载、人员三类下界。还能想到第四类下界吗？
- Q9：第 7 节最后一行显示求解器没有用到 `W2`。这是不是因为求解器「倾向少用人」？
- Q10：如果批次记录里 `fjsp_cpsat_qualified` 这一行是 `FAILED`，最可能的原因是什么？

### 参考答案

- A1：因为认证是按工艺族批量发放的。同一族的工序在设备看来是同一类活，换的只是参数；
  按工序逐条发证既不符合车间做法，也会让模型数据量随工序数线性膨胀。
  用族表示之后，「这台机器能不能做这道工序」退化成一次集合查表。
- A2：资质不参与判定，实例退化成纯 FJSP（加上人员与其余已给的约束）。
  这是刻意的宽容：没有资质数据不等于「什么都不许做」，而等于「没有发过证、不限制」。
  判据是 `not instance.qualifications` 这一个分支。
- A3：不受。`family is None` 时不发资质也不限它。设计理由是没有族的工序根本没有授权单位，
  硬要限制就得发明一个默认族，那会把「没填」悄悄变成「填了一个特殊的族」——
  数据里的空值必须保持为空值。
- A4：因为变量数就是搜索空间。压成 0 的变量仍然存在于模型中（预求解要花力气去发现它恒为 0），
  而不创建的变量从一开始就不在空间里。在固定预算的批次里，这个差别直接体现为搜索进度的差别。
- A5：容量为 `1` 时两者在可行域上等价；区别在表达与扩展：`AddCumulative` 用「需求 1、容量 c」
  统一表达任意容量，不需要为容量 `>1` 另写一条分支。本周选了后者是为了容量 `>1` 时不用改代码。
- A6：最优解会退化成「一道工序都不用工人」，人员约束在最优解上自动失效。
  这条约束不能靠惩罚项，是因为惩罚项也是可以被选择放弃的：只要「不用人」代价有限，
  预算紧的时候求解器就可能在它上面妥协。让每道工序**恰好**选一个工人，就没有这个选项。
- A7：`double-booked` 是 `peak > capacity` 在容量为 `1` 时的特例。两条标签分开写是为了可操作性：
  前者指向「同一时刻排了两次活」，后者指向「同时开的机器太多」。
- A8：可以再加一类：**释放时间下界** —— 所有工序的最早开工时刻中的最大值加它的时长。
  本实例所有工序的 `release_time` 都是 `0`，所以这一类下界是 `max(5, 4, 3) = 5`，被 `9` 盖住了，
  没有出现在 max 里。写下来是为了记住：下界是「取最大」，多算几类只会更紧或不变，不会更松。
- A9：不是。求解器没有偏好，它只是不需要第三个人：`W0` 与 `W1` 已经能覆盖 `M0` 与 `M1` 上的全部工作，
  用 `W2` 不会让任何目标值变好。`W2` 的价值在别处 —— 当 `W1` 成为瓶颈时它可以分担，
  但本实例的 `W1` 只用了 7 分钟，远没到瓶颈。
- A10：最常见的原因是**注册没有发生**：模块导入成功但 `@register` 装饰器那一行没执行到
  （例如被异常跳过、或文件名不在 `load_week_modules` 的清单里）。批次只认注册表里的名字，
  所以核对的正确姿势是问一遍 `describe_missing(["fjsp_cpsat_qualified"])`，而不是「能 import 就算数」。

## 11. 今日一句话总结

> **资质、人员能力、人员容量这三条约束都不改变目标函数，它们只砍可行域 —— 所以它们必须落在数据上、由独立验证器单独判；资质用「（机器，族）」对把不合格的机器从变量层面删掉，人员用「恰好一个工人 + 累积容量」把「谁在场」变成真实的瓶颈，而半开区间 `[start, end)` 让「一道接一道连着干」这种现实做法成为合法解。**
