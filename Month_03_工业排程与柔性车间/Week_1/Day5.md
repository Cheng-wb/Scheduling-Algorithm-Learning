## 2. 为什么第 5 天要做「对拍」

到第 4 天为止，四个方法都已经跑起来了。现在有两个必须回答的问题：

1. **它们给的数对不对？** Day 2 与 Day 4 的复核都是「同一份排程、换一条路径再算一遍」：`makespan` 重算、关键路径重算。这能抓住「算错」的错误，但**抓不住一类更隐蔽的错误**：如果「什么叫做一份更好的排程」这件事在实现里被理解错了，两条路径会一起错，而且互相印证得很一致。
2. **它们之间差多少？** 说「NEH 比瓶颈机对 Johnson 好」需要参照物。一个**已知最优值**的实例才是硬参照。

对拍（cross-validation）解决的正是第一件事：让两个**实现路径完全不相干**的程序去解同一个实例。今天的枚举器就是这样一份实现：

```text
枚举器：机器顺序 -> 图上最长路径（不认识 CP-SAT，也不调用 fjsp_shop 的求解代码）
CP-SAT：区间变量 + NoOverlap + 先后链（不认识枚举器，也不知道最长路径这回事）
```

两者在 `tiny3x3` 上给出同一个 7，意义和「同一个库换个参数又得到 7」完全不同：**它们的错误模式不重叠。** 一个算法写错了图上的最长路径计算，不会让 CP-SAT 也错；CP-SAT 的模型写漏了一类约束，也不会让枚举器跟着漏。

第二个问题由同一份枚举器回答：在**能枚举完的**小实例上，枚举值是真正的最优值，于是启发式的差距可以被量出来。

## 3. 对拍的方法论：什么才算「独立的第二种实现」

不是所有「再算一遍」都算独立。判据是**错误模式是否重叠**：

| 做法 | 独立性 | 能抓住什么 |
|---|---|---|
| 同一个函数跑两遍 | 无 | 只能抓住不确定性 |
| 换一个目标值函数重算 | 弱 | 目标函数实现错误 |
| 用一个库的两种配置 | 弱 | 配置相关的问题 |
| **换一套完全不同的算法**（枚举器 vs CP-SAT） | 强 | 算法实现错误、模型漏约束、对问题结构理解错误 |

今天走的是最后一档。代价很明确：**枚举器只能是阶乘级的**，因此只在小实例上可用。这不是缺陷，而是对拍的本质 —— 强独立性的检验天然只能在小规模上做，大实例上只能靠「同一份排程换路径复核」。

**对拍之外还要有一个真的参照**。枚举器给的是**真最优值**（在小实例上），所以它同时充当「参照物」：

```text
小实例（能枚举）  枚举最优 = 真最优  -> 用来判「谁最好」以及「差多少」
大实例（不能枚举）CP-SAT 的 OPTIMAL 解 = 参照（它自带最优性证明）
```

第二种参照必须**带状态**：拿一份 `FEASIBLE` 的解当参照算「与最优差」，等于把「还不知道」当成「已知」。今天的表里 CP-SAT 那一行的状态全部是 `OPTIMAL`，所以那四列才可以这么算。

## 4. 自建枚举器：机器顺序 → 最长路径

**核心等价关系**（Day 3 建立的）：一份排程可以只用一个「每台机器上的工序顺序」来描述；给定顺序之后，**最早的**（左移的）可行开工时刻是唯一确定的，而它的 `makespan` 就等于析取图上源点到汇点的最长路径长度。

于是「求最优 `makespan`」在小实例上可以这样暴力做：

```text
对每台机器 m：列出在 m 上加工的工序集合，取它们的所有排列
对每台机器的排列做全组合（笛卡尔积）
  对每个组合：
      建图（订单弧 + 该组合决定的机器弧）
      若有环 -> 这个组合不可行，跳过
      否则算最长路径
取「无环组合」里最长路径最小的那个 = 枚举最优值
```

**为什么有环就跳过**：机器弧与路线弧互相矛盾（例如 `A` 必须在 `B` 前、`B` 也必须在 `A` 前），这种组合不对应任何真实排程，必须剔除。

**规模有多大**：组合数 = 各机器工序数的阶乘之积。今天四个小实例：

```text
tiny2x2    2! x 2!     = 4
tiny4x2    4! x 4!     = 576
tiny3x3    3!^3        = 216
3x3 flow   3!^3        = 216
```

`tiny2x2` 只有 4 种组合，而 `tiny4x2` 已经是 576 种；机器数与工序数各加一点，数字就会爆炸（10 道工序的机器上是 `10! = 3628800`）。所以脚本里有**空间护栏**：组合数超过 `ENUMERATION_LIMIT = 200000` 直接拒绝枚举并报出组合数，而不是卡死。这是本仓库处理「规模不合适的方法」的一贯做法：**明确拒绝，而不是给一个跑不完的任务。**

**枚举器为什么必须自己写一份最长路径**：如果用 Day 3 的 `graph.py` 来算最长路径，两份实现就共享了同一段代码 —— 那段代码一错，两边一起错，对拍立刻失去意义。所以脚本里的 `longest_path_of_orders` 是独立写的：它做拓扑排序、在 DAG 上递推距离，完全不 import `fjsp_shop`。这与 M2 的做法一致：**对拍的价值来自不共享代码。**

**枚举器只支持「一工序一机器」**：如果每道工序有多台合格机器，「每台机器上的工序集合」本身就成了决策的一部分，枚举空间要乘上「指派」的组合数。`enumerate_optimum` 遇到多合格机器的实例会抛 `ValueError`，而不是给出一个只枚举了顺序、漏了指派的「最优值」。

**规模感**（各机器工序数越接近，组合数越大）：

```text
2 台机器、每台 2 道      2! x 2!        = 4
2 台机器、每台 4 道      4! x 4!        = 576
3 台机器、每台 3 道      3!^3           = 216
4 台机器、每台 4 道      4!^4           = 331776      <- 已超过今天的 200000 护栏
5 台机器、每台 5 道      5!^5           = 24 883 200 000（约 2.5 x 10^10）
```

第 4 行就是护栏在那个位置的原因：`4!^4 = 331776 > 200000`，脚本会**拒绝**而不是开始跑。拒绝时它返回组合数与上限，让人一眼看出「离可枚举还差多少」。

## 5. 小实例上的一致性

**先把最小的那台手算一遍**。`tests/data/tiny2x2.jsp` 是两个订单的 flow shop：

```text
J0：M0(3) -> M1(2)
J1：M0(4) -> M1(6)
```

两台机器各 2 道工序，组合数 = `2! x 2! = 4`。逐个算最长路径（用「机器就绪时刻与订单前一道完工时刻取大」这条 Day 1 的递推式）：

```text
组合 (M0 顺序, M1 顺序)      时间线                                      Cmax
(J0,J1) / (J0,J1)     J0_O0[0,3) J1_O0[3,7) J0_O1[3,5) J1_O1[7,13)        13
(J0,J1) / (J1,J0)     J0_O0[0,3) J1_O0[3,7) J1_O1[7,13) J0_O1[13,15)       15
(J1,J0) / (J0,J1)     J1_O0[0,4) J0_O0[4,7) J0_O1[7,9) J1_O1[9,15)         15
(J1,J0) / (J1,J0)     J1_O0[0,4) J0_O0[4,7) J1_O1[4,10) J0_O1[10,12)       12
```

最小的是 12，出现在 `M0` 与 `M1` 上都是 `J1 -> J0` 的那个组合上。用 Johnson 规则验证：`J1` 的 `p1 = 4 < p2 = 6` 归入集合 A，`J0` 的 `p1 = 3 >= p2 = 2` 归入集合 B，顺序 = A 后接 B（B 按 `p2` 降序）= `J1, J0` —— 与枚举器找到的最优组合一致。

**注意这个手算过程里没有「机器弧与路线弧冲突」的情形**（4 种组合全部无环），这正是 flow shop 的特征，下面 `tiny3x3` 会形成对照。

脚本第 1 节的实测结果（`tiny3x3` 部分）：

```text
tiny3x3.jsp（3 订单 x 3 机器 job shop）
  机器顺序组合数 = 216，其中无环（可行）的组合 = 64
  枚举最优值 = 7
    最优组合里 M0：J0_O0 -> J2_O1 -> J1_O2
    最优组合里 M1：J1_O0 -> J0_O1 -> J2_O2
    最优组合里 M2：J2_O0 -> J1_O1 -> J0_O2
```

三件事值得逐条看：

1. **216 种组合里只有 64 种无环**（约 29.6%）。也就是说，随机取一个「机器顺序组合」，七成以上是**自相矛盾**的、根本排不出来的。这解释了为什么「随便找个顺序」不是办法，也解释了为什么 JSP 难。
2. **最优值 7**，与 Day 4 的 CP-SAT（`OPTIMAL`，7）一致，也与 Day 3 手算的 `HAND_MADE`（`makespan = 7`）一致。**三条互不相干的路径**给出同一个数。
3. **枚举器给出的最优机器顺序，与 Day 3 手算排程的三台机器顺序逐字相同** —— 说明手算那天不是「碰巧凑出 7」，而是真的取到了最优。

同一个小结（第 2 节汇总表）：

```text
实例        组合数   无环组合数   枚举最优
tiny2x2.jsp       4            4        12
tiny4x2.jsp     576          576        12
tiny3x3.jsp     216           64         7
3x3 flow        216          216        10
```

两组对照很重要：

```text
tiny2x2     flow_johnson = 12.0   枚举最优 = 12
tiny4x2     flow_johnson = 12.0   flow_neh = 12.0   枚举最优 = 12
3x3 flow    组合数 = 216，无环 = 216，枚举最优 = 10
            flow_johnson（瓶颈机对）= 11.0，flow_neh = 10.0
```

**读懂「无环组合数」这一列的差别**：两个 flow shop 实例上 `组合数 = 无环组合数`（4/4、576/576、216/216），一个都不浪费 —— 因为所有订单走同一条机器序列，任意排列都不会让机器弧与路线弧冲突。而 `tiny3x3` 是 216 里只有 64 无环。**这一列本身就是「flow shop 与 job shop 难度差在哪」的定量体现。**

**关于 `tiny2x2` 与 `tiny4x2` 的严谨说法**：这两台上 Johnson 都是精确算法（`F2||Cmax` 有最优性定理），枚举得到同一个 12，属于**验算定理**（确认实现与定理一致），而不是「枚举发现了新结论」。真正有信息量的是 `tiny3x3` 与 3×3 flow：那里没有定理，枚举才是唯一的最优性来源。

**3×3 flow 上的那个 1**：`flow_johnson`（瓶颈机对）= 11、`flow_neh` = 10、枚举最优 = 10。这是今天最有价值的一行 —— 它证明**瓶颈机对 Johnson 在 3 台机器上不是最优**（差 1），同时说明 NEH 在这台实例上恰好取到了最优。注意最后半句只对**这一台实例**成立：NEH 是启发式，没有最优性保证。

## 6. 差异定位：四个实例 × 八个方法

脚本第 3 节把 `configs/month3.json` 里 Week 1 关注的四个实例跑了一遍，参照列用 `jsp_cpsat`（`OPTIMAL`）。实测结果见第 7 节的完整表格，这里先把读法立起来：

**四列的含义**：

```text
状态      OPTIMAL / FEASIBLE / FAILED —— 前两个带排程，FAILED 表示方法拒绝了这个实例
目标值    排程的 makespan（由 evaluate 独立重算得到）
界        best_bound —— 只有能证明下界的方法才填；启发式一律是 "-"
与最优差  目标值 - 参照值；参照是 CP-SAT 的 OPTIMAL 解
```

**四条读表纪律**：

1. **`FAILED` 不等于「更差」。** `jsp_6x4` 与 `jsp_8x5` 上两个 flow 方法都是 `FAILED` —— 它们的入口检查发现「订单路线互不相同」，于是拒绝。这是**不适用**，不是「算出来一个很大的数」。若把 `FAILED` 当成 `+∞` 去参与排序，会得到「flow 方法在所有 job shop 上垫底」这种无聊结论。
2. **「与最优差」列里每个数都只在它自己那一行成立。** 4 个实例 × 8 个方法 = 32 行，每行对应 4 个参照中的一个（每实例一行 `OPTIMAL` 的 `jsp_cpsat`），其余行都是相对各自实例的参照算出来的。
3. **`界` 列的 `-` 不是缺数据，是纪律。** 启发式没有下界可报，宁可留空。只有 `jsp_cpsat` 那一列有数字，且它只在自己最小化的目标上才有意义。
4. **同一个方法在不同实例上的名次会变。** 例如 `jsp_priority/mwr` 在 `jsp_8x5` 上只差 2，在 `flow_8x4` 上差 36。

**三个观察**（都只针对这四个实例，不能当定律）：

```text
观察 1  NEH 在两个 flow shop 实例上都是启发式里最好的：flow_5x3 差 1，flow_8x4 差 1
观察 2  优先级规则里没有一条四个实例通吃：flow shop 上 spt 最好，job shop 上 mwr 最好，
        而 lpt 在每个实例上都落在偏差的那一档（flow_5x3 与 jsp_6x4 上最差，
        flow_8x4 与 jsp_8x5 上仅次于最差）
观察 3  CP-SAT 在这四个实例上都给出 OPTIMAL，界与目标值相等
```

**观察 1 顺带回答了一个 Day 2 留下的疑问**。Day 2 第 4 节算过 `flow_5x3` 的初等下界是 62，而两个启发式给出 78 与 70，当时只能说「差 16，分不清是结果不够好还是下界太松」。今天有了参照：最优值是 **69**。

```text
flow_5x3   下界 62   最优 69   NEH 70   Johnson 78
flow_8x4   下界 109  最优 126  NEH 127  Johnson 151
```

所以答案是**两件事同时成立**：下界确实松（62 不可达，最优是 69，差 7），启发式也确实不够好（NEH 与最优差 1）。这正是第 3 节说的「参照物必须带最优性证明」的用处 —— 没有 `OPTIMAL` 这个状态，那 7 与那 1 都只是猜测。

**观察 2 的处理方式**：脚本把「哪条规则最好」写成了一句带实例名的观察，然后**明确说不据此调参**。理由是：在这四个实例上挑一条规则、再把它当作「默认规则」，等于在测试集上做选择 —— 换一批实例，名次可能就翻过来（`spt` 在 flow shop 上领先、在 job shop 上却输给 `mwr`，已经是一个警告）。Week 1 的四个优先级规则并列保留，谁都不设为默认。

## 10. 自测题

- Q1：为什么枚举器必须自己写一份最长路径，而不能调用 `graph.py`？
- Q2：「机器顺序组合」里有环意味着什么？为什么必须跳过？
- Q3：`tiny4x2` 的组合数是 576，是怎么算出来的？
- Q4：为什么 `tiny3x3` 的 216 种组合里只有 64 种可行，而 flow shop 实例是 100% 可行？
- Q5：枚举最优值 7 与 CP-SAT 的 7 相同，能说明什么？不能说明什么？
- Q6：拿 `jsp_cpsat` 的结果当参照，为什么要先确认它的状态是 `OPTIMAL`？
- Q7：`flow_johnson` 在 `jsp_6x4` 上是 `FAILED`，在差异表里它该排在 `jsp_priority` 之前还是之后？
- Q8：为什么说「NEH 在 3×3 flow 上达到最优」这句话不能推广？
- Q9：`flow_5x3` 的下界是 62、最优是 69，这两个数一起说明了什么？
- Q10：如果以后有人在 `jsp_6x4` 上把某条规则调得更好，为什么不该直接把它设为默认规则？

### 参考答案

- A1：因为对拍的价值来自**不共享代码**。若枚举器调用 `graph.py` 算最长路径，两者共享同一段实现，那段代码一错两边一起错，对拍就退化成「同一份代码跑两遍」。所以脚本里的 `longest_path_of_orders` 是独立实现的拓扑排序加距离递推，且不 import `fjsp_shop` 的任何求解代码。
- A2：意味着机器弧与订单路线弧互相矛盾（例如两条工序互相要求对方先做），这样的组合不对应任何真实排程。如果不跳过，最长路径算法会在环上无法收敛，或者算出一个没有意义的数。
- A3：两台机器各 4 道工序，排列数分别是 `4! = 24` 与 `4! = 24`，组合数 = `24 x 24 = 576`。两台机器的组合互相独立，所以相乘。
- A4：`tiny3x3` 上每个订单的路线不同，机器弧与路线弧容易互相矛盾，216 种组合里只有 64 种自洽（约 29.6%）。flow shop 上所有订单走同一条机器序列，无论怎么排机器顺序都不会让机器弧与路线弧冲突，所以每一种组合都可行。
- A5：能说明**在两套错误模式不重叠的实现上，这台实例的最优值都是 7** —— 这比单个实现自己报 7 可信得多。不能说明的是：两台实现在别的问题上一定对（例如大实例上无法用枚举器复核）。
- A6：因为参照必须是**已知最优值**。若参照本身只是 `FEASIBLE`，「与最优差」这一列实际算的是「与某个可行解的差」，会把「我还不知道最优在哪」写成「我只差这么点」。今天表里四行 `jsp_cpsat` 全是 `OPTIMAL`，所以那列才可以这么算。
- A7：不能排 —— `FAILED` 表示没有给出排程，它既不是「很大」也不是「很小」。正确做法是把它标成「不适用」并排除在排序之外；若强行参与排序（例如当成无穷大），得到的「flow 方法在 job shop 上垫底」是自造结论。
- A8：因为 NEH 是启发式，没有最优性保证。它在 3×3 flow 这台实例上恰好取到了枚举最优 10，只能说明这台实例上它没出错；换一台实例可能就不是最优的。
- A9：说明两件事同时成立：**(1) 下界 62 太松**（真实最优是 69，差 7，所谓「下界是门槛而不是承诺」）；**(2) 启发式确实不够好**（NEH 70 距离最优 69 还差 1，Johnson 78 差 9）。只看 62 与 70 的差是分不清这两件事的，必须有最优值当参照。
- A10：因为那是在这四个实例上做的选择，换一批实例名次可能翻过来 —— 本仓库四个实例上 `spt` 与 `mwr` 的分工已经说明了这一点（flow shop 上 `spt` 领先，job shop 上 `mwr` 领先）。把「在已知实例上挑出来的最好规则」当默认规则，就是把测试集当训练集用。正确做法是保留全部规则并列报告，并在结论里写明实例名。
