## 3. 标准格式：三行话讲完的格式

**定义**：本仓库实现的经典 JSP 文本格式只有三条规则（[standard.py](../../projects/03_industrial_fjsp/fjsp_io/standard.py)）：

```text
第一行      订单数 机器数
之后每行    2 x 机器数 个整数，成对出现 —— 机器号 加工时间
            机器号 0 基（0 表示第一台机器）
            成对出现的顺序 = 该订单的工艺路线
```

`tests/data/tiny3x3.jsp` 就是这种格式：

```text
3 3
0 2 1 3 2 1
1 2 2 2 0 2
2 3 0 1 1 2
```

逐行读出来：

```text
第 0 行：M0 上 2 个时间单位 -> M1 上 3 个 -> M2 上 1 个
第 1 行：M1 上 2 个 -> M2 上 2 个 -> M0 上 2 个
第 2 行：M2 上 3 个 -> M0 上 1 个 -> M1 上 2 个
```

**这个格式没有的东西**（重要，因为它们决定了后面的分析能做到哪一步）：

| 缺失的信息 | 解析器填的默认值 | 影响 |
|---|---|---|
| 释放时间 | `Job.release_time = 0` | 这份实例里所有订单零时刻都可开工 |
| 交期 | `Job.due_date = None` | 拖期类目标在这类实例上恒为 0（没有交期的订单不参与） |
| 权重 / 优先级 | `weight = 1.0`、`priority = 0` | 订单之间没有轻重之分 |
| 多合格机器 | 每道工序**恰好一台** | 实例必然是经典 JSP，不含柔性 |
| 加工时间的机器依赖性 | 只有一项 `machine_times` | 工时与「哪台机器」无关 |

**所以「读进来一个标准格式文件」得到的是一类很窄的实例**：经典 JSP、零释放时间、无交期。这句话必须写在实验记录里，否则读者会以为「算法能解基准文件」等于「算法能解真实车间」。

**证据来源必须说清楚**（本仓库的纪律）：解析器是用 `tests/data/` 下**手写的**几个同格式小文件（`tiny2x2.jsp`、`tiny3x3.jsp`、`tiny4x2.jsp`）验证的。**OR-Library 原始的 FT / LA / ABZ 文件不在本仓库，也没有下载它们。** 因此「格式解析正确」这句话在本仓库成立的范围是「与手写样例一致的写法」；真实基准文件里常见的额外花样（行首注释、行尾空白、多余空格）本模块不保证支持 —— 遇到不认识的内容会抛 `StandardFormatError`，而不是猜一个解释。

**写回（round-trip）**：`format_standard_jsp` 把实例写回同样的格式。它有一个明确的前提检查：机器 id 必须恰好是 `M0 … M{n-1}` 且顺序一致。原因是这个格式**用整数位置表示机器**（写出去的是 `0 1 2` 这样的机器号），如果机器 id 与位置不是一一对应，写出去再读回来就会**静默地换了一台机器** —— 这种「看似成功的往返」比直接报错危险得多，所以宁可拒绝。

**机器号越界与非法工时会当场报错**：机器号必须在 `0 .. m-1` 内，工时必须是正数。这两条是格式层面的硬约束，不是「宽松解析」能补救的。

## 4. 甘特行：六个字段的展示模型

**定义**：甘特行是把一份排程摊平成「一行一道工序」的表格，六列固定：

```text
machine_id | job_id | operation_id | start_time | end_time | duration
```

排序键固定为 `(machine_id, start_time, operation_id)`。第三项是**必要的**：同一台机器上两道工序不可能同时开工，但为了让「同样的数据永远得到同样的行序」（确定性），仍然把 `operation_id` 作为末位键写进排序 —— 这样任何一份排程的 CSV 都是逐字节可复现的。

**为什么它是展示模型，而不是领域模型**：领域里的排程是 `Schedule`（工序 → 机器 + 起止时刻），它只记**必要**的信息；甘特行里多出来的

```text
job_id      可以由 operation_id 反推（工序号的前缀就是订单号）
duration    可以由 end_time - start_time 反推（也等于工时表里那一项）
```

两个字段都是**冗余**的。保留它们的理由是「看表的人不该被迫做格式推算」，而不是「排程需要它们」。把展示模型与领域模型分开，好处很直接：

1. 换展示（改列、改排序、加颜色）不碰调度逻辑；
2. 换调度算法（换 `Schedule` 的来源）不碰展示逻辑；
3. 校验时有一个明确的对应关系 —— 展示层任何一列都能从 `Schedule` 与实例反推出来，因此**展示层的错误总能被抓出来**。

**ASCII 甘特**：脚本还会画一张字符版甘特图，数字表示订单下标，`.` 表示空闲：

```text
  M0 |00.2.11|
  M1 |1100022|
  M2 |222110.|
```

读法：一格一个时间单位，横向就是时间轴。三行各有各的故事，**空隙的原因并不相同**：

```text
M0 |00.2.11|   第 2 格空：等 J2_O1（它的前道 J2_O0 要到 3 才完工）
               第 4 格空：等 J1_O2（它的前道 J1_O1 要到 5 才完工）     <- 两处都是「等前道」
M1 |1100022|   没有空隙：从 0 到 7 一路不停                            <- 瓶颈机器
M2 |222110.|   第 6 格空：M2 的活已经干完了（J0_O2 在 6 完工），
               而 makespan 是 7 —— 这一格是「早收工」，不是「等前道」
```

最后一行那种空隙最容易被误读成「这台机器在等活」—— 其实它只是**没有更多活要干**。区分「等前道」与「早收工」的办法是看空隙的位置：如果空隙之后还有工序，那是等前道；如果空隙在最后一格（或所有工序之后），那是早收工。字符版的作用就是**在没有图形界面的地方也能一眼看出空隙在哪**。

## 5. 瓶颈：机器负载汇总

**定义**：对每台机器统计五个量（`machine_load_summary`）：

```text
operation_count 该机器上的工序数（自检用：各机器工序数之和 = 总工序数）
busy_time       该机器上所有工序的工时之和
span            从该机器最早开工时刻到最后完工时刻的跨度
idle_in_span    跨度内空闲 = span - busy_time
utilization     busy_time / span（跨度为零时按 1 计）
load_share      busy_time / 所有机器的 busy_time 之和
sequence        该机器上工序的加工顺序（按开工时刻）
```

多出来的两个量都不是装饰：`operation_count` 用来做「量」的自检，`sequence` 用来做「序」的自检（它与 Day 3 图上的机器定向必须是同一个顺序）。

**瓶颈机器 = `busy_time` 最大的那台**。汇总按 `busy_time` 降序、`machine_id` 升序输出，所以第一行就是瓶颈。

**理论结论（下界）**：瓶颈机器的 `busy_time` 是 `makespan` 的下界。

理由与 Day 2 手算 `flow_5x3` 时用的完全一样：同一台机器上的工序两两不重叠，所以该机器的完工时刻不小于它自己的总负载；而 `makespan` 是所有机器里最晚的完工时刻，因此不小于任何一台机器的负载。

**本实例上的观察**：`tiny3x3` 上瓶颈机器是 `M1`，`busy_time = 7`，而 `makespan = 7` —— **两者相等**。这表示 `M1` 从 0 到 7 一路不停、没有任何空闲（`idle_in_span = 0`，`utilization = 1.000`）。当瓶颈机器的忙时等于 `makespan` 时，「缩短 `makespan`」这件事在物理上就等价于「让这台机器少干点活或者干得快点」。

**但要小心三个容易说错的点**：

1. **瓶颈机器的忙时不等于 `makespan` 是常态**，不是异常。`tiny3x3` 上另外两台机器（`M2` 忙时 6、`M0` 忙时 5）都小于 `makespan`，各有空闲。
2. **忙时最大 ≠ 一定在关键路径上**。`busy_time` 是「负载」，关键路径是「依赖链」；一台忙时很大的机器可能因为整体排序得当而不出现在任何最长路径上。今天用 `utilization` 与 `idle_in_span` 两个量辅助判断，真正的「谁在压着 `makespan`」要看 Day 3 的关键路径。
3. **`load_share` 之和恒为 1**，`busy_time` 之和恒等于「所有工序工时之和」（本实例 18）。后一条是很好的自检：如果总忙时对不上，说明有的工序漏排或多排了。

## 6. 落盘：为什么要有一个驱动

今天的第 4 节要**写文件**，而这带来两个必须处理的问题：

```text
1. 示例脚本的规矩是「只打印、不写盘」—— 写盘会污染别人的工作区
2. 写盘的结果要能被复盘：这份 CSV 是哪个版本的代码、在哪个提交上、用什么预算跑出来的
```

于是有了 [week1_gantt.py](../../projects/03_industrial_fjsp/fjsp_experiments/week1_gantt.py)（实验驱动），它做三件事：

```text
1. 先在内存里捕获「版本状态」：git 提交号、工作区是否 dirty、源码的 sha256、跑的时间与 Python 版本
2. 再创建输出目录 artifacts/month3_w1/（目录非空则拒绝，保留上一次实验）
3. 写三个文件：metadata.json（版本状态 + 实例清单）、gantt_<名字>.csv（每个实例一份）、
   summary.json（每个实例上各方法的状态 / 目标值 / 界 / 瓶颈机器）
```

**为什么版本状态要在建目录之前捕获**：如果先建目录、再采集版本状态，那么「目录已经存在」这件事本身就会溜进采集结果（至少 `working_tree_dirty` 会变 —— 新建的未跟踪目录会让工作区变成 dirty）。顺序反了，元数据就记录了「我自己造成的脏」。**顺序本身就是正确性的一部分。**

**为什么目录非空就拒绝**：实验结果的价值来自「这一次的输入与这一次的输出对应」。如果允许覆盖，第二次实验会静静抹掉第一次的 CSV，而 `metadata.json` 里的时间戳还留在新的那份 —— 事后无法分辨哪份结果对应哪次运行。拒绝覆盖把这个问题变成了一个显式的动作：「要重跑，先自己清空目录」。

**示例脚本怎么写盘**：脚本本身不调用写盘函数，而是 `import` 驱动里的 `run()` 并自己捕获「目录非空」的异常。这样示例脚本仍然是「跑一次、打印一次」的形状，落盘的规矩集中在驱动里，一处修改、处处生效。

**每个实例只写一份甘特 CSV**：驱动跑一个实例时会跑多个方法（本实例上是 2 到 4 个），但**只把其中一个方法的排程写成 `gantt_<实例>.csv`** —— 选择的是 `jsp_cpsat` 的那一份（它保证同实例可比、且是 `OPTIMAL`）。理由很实际：如果每个方法都写一份，文件名就要带上方法名，读者还得自己决定看哪一份；而甘特图的用途是「看这份排程长什么样」，用最好（且被证明最优）的那一份最合适。**每个方法的完整数字（状态、目标值、界、瓶颈机）仍然全部记在 `summary.json` 里**，一个都没丢 —— 只是 CSV 只画一份。

**一张汇总表里同时有「有排程」与「没排程」两类行时怎么写**：`summary.json` 的每一行都带 `validation` 字段（`ok` 或 `no schedule`）。没有排程的行只写状态、目标值 `null`、界 `null` 与 `failure_reason`，不写 `breakdown`、不写 `machine_loads`、也不写甘特行 —— **宁可少写字段，也不给不存在的排程编造字段**。

## 7. 实验：`m3w1d6_gantt_bottleneck.py`

脚本链接：[m3w1d6_gantt_bottleneck.py](../../projects/03_industrial_fjsp/examples/m3w1d6_gantt_bottleneck.py)。

在项目目录下运行（若 `artifacts/month3_w1/` 非空，先把它清空，好让第 4 节走「首次落盘」的路径）：

```bash
cd projects/03_industrial_fjsp

```

第 1 节（读文件与往返写回）的实际输出：

```text
========================================================================
第 1 节：读标准格式文件
========================================================================
来源文件 = tiny3x3.jsp，格式 = or-library-jsp，机器号 0 基 = True
```

写回的内容与文件原文**逐字相同** —— 这是往返一致的最强形式：不只是「值相等」，而是「字节相等」。注意 `meta` 里的三项：`format = or-library-jsp`、`source = tiny3x3.jsp`（记录来源文件名，便于回溯到磁盘证据）、`machine_id_base = 0`。

第 2 节（甘特行）：

```text
========================================================================
第 2 节：甘特行 —— 六个字段
========================================================================
字段顺序 = ('machine_id', 'job_id', 'operation_id', 'start_time', 'end_time', 'duration')
行数 = 9，排序键 = (machine_id, start_time, operation_id) 且已排序 = True

machine_id | job_id | operation_id | start | end | duration
        M0 |     J0 |     J0_O0 |     0 |   2 |        2
        M0 |     J2 |     J2_O1 |     3 |   4 |        1
        M0 |     J1 |     J1_O2 |     5 |   7 |        2
        M1 |     J1 |     J1_O0 |     0 |   2 |        2
        M1 |     J0 |     J0_O1 |     2 |   5 |        3
        M1 |     J2 |     J2_O2 |     5 |   7 |        2
        M2 |     J2 |     J2_O0 |     0 |   3 |        3
        M2 |     J1 |     J1_O1 |     3 |   5 |        2
        M2 |     J0 |     J0_O2 |     5 |   6 |        1

从甘特行独立复核：最大完工时刻 = 7，makespan() = 7

ASCII 甘特（数字是订单在 jobs 里的下标，点表示空闲）：
  时间轴：1 格 = 1 个时间单位，总长 7，共 7 格
    M0 |00.2.11|
    M1 |1100022|
    M2 |222110.|
  图例：0=J0  1=J1  2=J2
```

**这里有两条独立的复核**：

1. **行数 = 9 = 工序数**，且按 `(machine_id, start_time, operation_id)` 已排序（脚本真的比较了一次排序前后是否相等）。
2. **从甘特行独立重算 `makespan`**：取所有 `end_time` 的最大值 = 7，与 `makespan(instance, schedule)` = 7 一致。这一条抓的是「展示层丢字段」或「区间算错」类的错误。

三台机器的顺序（`M0：J0_O0 -> J2_O1 -> J1_O2` 等）与 Day 3 手算排程、Day 4 求解器解出来的顺序**完全一致**：同一个最优解在三条路径上都出现了。

第 3 节（瓶颈）：

```text
========================================================================
第 3 节：机器负载与瓶颈
========================================================================
machine_id | 工序数 | 忙时 | 跨度 | 跨度内空闲 | 利用率 | 负载占比
        M1 |      3 |    7 |    7 |          0 |  1.000 |    0.389
        M2 |      3 |    6 |    6 |          0 |  0.857 |    0.333
        M0 |      3 |    5 |    7 |          2 |  0.714 |    0.278

总忙时 = 18（= 所有工序工时之和），负载占比之和 = 1.000
瓶颈机器 = M1（忙时 7，利用率 1.000）
机器上的顺序：J1_O0 -> J0_O1 -> J2_O2
瓶颈机器的忙时 7 与 makespan 7 的关系：相等（本实例瓶颈机器一路不停）
```

**逐项核对**（都能手算）：

```text
M0 负载 = J0_O0(2) + J2_O1(1) + J1_O2(2) = 5      跨度 [0,7) -> 空闲 2
M1 负载 = J1_O0(2) + J0_O1(3) + J2_O2(2) = 7      跨度 [0,7) -> 空闲 0
M2 负载 = J2_O0(3) + J1_O1(2) + J0_O2(1) = 6      跨度 [0,6) -> 空闲 0
总忙时 = 5 + 7 + 6 = 18 = 9 道工序的工时之和（2+3+1 + 2+2+2 + 3+1+2 = 18）
负载占比 = 5/18 = 0.278、7/18 = 0.389、6/18 = 0.333，和为 1.000
```

`M1` 的 `busy_time = 7 = makespan`，所以它没有任何空闲：`idle_in_span = 0`、`utilization = 1.000`。`M0` 的跨度也是 7，但空闲 2（`utilization = 0.714`）—— **两台的跨度相同，忙时不同**，这正说明「看跨度看不出瓶颈，要看忙时」。而 `M2` 的跨度只有 6：它在 6 之后就完工了，晚收工的是 `M0` 与 `M1`。

两个分支读回的结果完全一致 —— 这本身就是一条核对：**「这次新写的 CSV」与「上一次留下的 CSV」内容相同**，说明驱动是确定性的（同一实例、同一方法、同一参数下重跑产出同样的文件）。反过来说，如果两次读回不一致，那说明要么实例参数变了，要么方法里有不确定的东西，两种都值得停下来查。

**每个实例登记的方法清单不同**：两个 flow shop 实例登记了四个方法（`flow_johnson`、`flow_neh`、`jsp_priority`、`jsp_cpsat`）；两个 job shop 实例只登记了 `jsp_priority` 与 `jsp_cpsat` —— 因为两个 flow 方法在它们上是 `FAILED`，没有排程可画甘特（Day 5 的差异表里能看到那些 `FAILED` 行）。

两个观察：

1. **瓶颈机器随实例而变**：flow shop 上都是 `M1`（`flow_5x3` 的 `M1` 负载 62、`flow_8x4` 的 `M1` 负载 109，正是 Day 2 手算的那两个下界），而 `jsp_6x4` 是 `M3`、`jsp_8x5` 是 `M4`。**瓶颈不是固定的某一台机器**，所以 `detail` 与 `summary.json` 里必须把它是哪一台记下来。
2. **`flow_5x3` 上四个方法的瓶颈机都是 `M1`，但 `makespan` 各不相同**（69 / 70 / 78 / 78）。这再次印证第 5 节的说法：瓶颈机器的**忙时**是下界，四种排程都让 `M1` 的忙时停在 62，`makespan` 却不同 —— 因为决定 `makespan` 的不只是负载，还有依赖链上的等待。**忙碌的机器不一定是压着 `makespan` 的那台。**

读回验证的两条：**行数 15 = `flow_5x3` 的工序数（5 订单 × 3 道）**，**表头与 `GANTT_FIELDS` 六列完全一致**。最后一行是 `M2` 上的 `J003_O2`（`67 -> 69`），而 `flow_5x3` 上 `jsp_cpsat` 的目标值正是 69（`summary.json` 里的那一行）—— CSV 的最后一行结束于 69，与目标值对得上，这是「落盘内容与内存结果一致」的又一条独立核对。

`metadata.json` 里记录了什么（这是复盘时唯一能回答「这份结果是哪来的」的东西）：

```text

git_commit           代码版本
working_tree_dirty   工作区是否干净（本次为 True —— 实验过程里还有未提交的改动）

time_limit_seconds   求解预算

```

**`working_tree_dirty = True` 这件事要如实写下来**：本次实验是在工作区有未提交改动时跑的，所以「这份 CSV 对应哪个代码版本」只能靠 `source_sha256`，不能只靠 `git_commit`。这正是驱动要同时记两个字段的原因。

## 10. 自测题

- Q1：标准格式的头行写的是什么？为什么必须写两个数？
- Q2：这个格式里「机器号 0 基」意味着什么？如果把它当成 1 基会出什么错？
- Q3：把一个实例读进来后，`Job.due_date` 是什么？这会让哪些目标函数变成退化情形？
- Q4：为什么 `format_standard_jsp` 要求机器 id 恰好是 `M0 … M{n-1}`？
- Q5：甘特行里哪两个字段是冗余的？保留它们的理由是什么？
- Q6：甘特行的排序键为什么要把 `operation_id` 放在末位？
- Q7：怎么从 `machine_load_summary` 里判断瓶颈机器？它的忙时与 `makespan` 是什么关系？
- Q8：`M0` 与 `M1` 的跨度都是 7，为什么只把 `M1` 叫瓶颈？
- Q9：`flow_5x3` 上三个方法的瓶颈机都是 `M1`，为什么它们的 `makespan` 不同？
- Q10：为什么实验驱动要在创建输出目录**之前**采集版本状态？

### 参考答案

- A1：头行是「订单数 机器数」。两个数都必须写：解析器要用订单数校验后面有几行工序数据（多一行少一行都报错，而不是猜），用机器数校验每行有多少个整数（`2 x 机器数`）。
- A2：意味着 `0` 表示第一台机器，合法范围是 `0 .. m-1`。若把它当 1 基来解析，机器号 `0` 会被判成越界（或首台机器 `M1` 永远用不到），最后得到一份「机器错位」的实例 —— 而且它看起来仍然合法，属于最难发现的一类错误。
- A3：`due_date = None`（格式里没有交期字段）。这会让所有以拖期为基础的目标函数退化：按定义「没有交期的订单不参与」，于是 `total_tardiness` 恒为 0、`max_lateness` 无从计算。所以在这类实例上比较拖期类目标是没有意义的。
- A4：因为这个格式**用整数位置表示机器**（写出的是 `0 1 2` 这样的号）。只有 id 与位置一一对应，写出去再读回来才是同一台机器；否则往返会静默换机器，而调用方看到的却是「成功」。
- A5：`job_id`（可由 `operation_id` 的前缀反推）与 `duration`（可由 `end_time - start_time` 反推，也等于工时表里那一项）。保留是为了让看表的人不必自己做推算 —— 这是展示层的职责，不是领域模型的需要。
- A6：为了保证**确定性**。同一台机器上两道工序不可能同时开工，所以单看 `(machine_id, start_time)` 已经能定序；但把 `operation_id` 写进排序键之后，即便将来出现「同一时刻」的数据（例如某种退化解），行序也仍然是唯一确定的，CSV 才能逐字节复现、才能拿两次实验的文件直接做 diff。
- A7：瓶颈 = `busy_time` 最大的那台（汇总按忙时降序输出，第一行就是它）。它的 `busy_time` 是 `makespan` 的**下界**：同一台机器上的工序两两不重叠，所以它自己的完工时刻就不小于它的总负载，而 `makespan` 又不小于任何一台机器的完工时刻。本实例上 7 = 7，两者相等。
- A8：因为「跨度」只是这台机器从最早开工到最后完工的区间长度，里面可以有空闲。`M1` 的 `idle_in_span = 0`（`busy_time = 7 = span`，`utilization = 1.000`），说明它从 0 到 7 一路不停；`M0` 的跨度同为 7，但 `busy_time` 只有 5、空闲 2。**瓶颈看的是忙时，不是跨度。**
- A9：因为瓶颈机器的忙时只是 `makespan` 的下界，不等于 `makespan`。三种排程都让 `M1` 忙到 62，但订单之间的等待不同：等待由依赖链（订单的先后关系）决定，而依赖链的长度决定了 `makespan`。本实例上 `jsp_cpsat` 的 69 是最优的，说明它把等待压到了最小。
- A10：因为创建目录这个动作会**改变**要采集的状态 —— 新建的未跟踪目录会让 `git status` 变成 dirty，于是 `working_tree_dirty` 会记录成「我自己造成的脏」。先采集、后创建，元数据记录的才是「跑之前代码仓库的真实状态」。

## 11. 今日一句话总结

今天这条链条是「把结果交出去」：

```text
读标准格式（外部输入）-> 求解（前三天的成果）-> 甘特行（给人看）
                                           -> 机器负载汇总（定位瓶颈）
                                           -> 落盘 + 版本状态（可复盘）
```

> **瓶颈不是「最忙的那台机器」这么简单的一句话：它的忙时是 `makespan` 的下界，而 `makespan` 还要看依赖链 —— 两个量都算出来，才知道该动哪里。**
