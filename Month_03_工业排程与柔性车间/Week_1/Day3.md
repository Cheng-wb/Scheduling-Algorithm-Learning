## 2. 为什么第 3 天要做「图」

Day 1 与 Day 2 处理的是 Flow Shop：所有订单走同一条机器序列，所以「机器上的顺序」可以用一个全局排列表示。到了 Job Shop，各订单路线不同，**每台机器上的顺序都不一样**，「一个排列」这种表示失效了。

析取图正是为这件事发明的（Roy 与 Sussmann 1964）：

1. **它把「约束」与「决策」画在同一张图上**：路线弧是给定的约束，机器弧是排程做出的决策（每对工序之间选一个方向）。
2. **它把 `makespan` 变成一个图论量**：最短完工时间 = 最长路径长度（有向无环图上）。于是「改进排程」等价于「改变某些弧的方向让最长路径变短」。
3. **它给出「谁是瓶颈」的精确含义**：关键路径上的工序没有松弛，改动它们才能缩短 `makespan`；关键块是「连续抢同一台机器的一段」，局部搜索就是在这上面做文章。
4. **它提供一条独立的复核路径**：无论一份排程是怎么来的（手排、规则、求解器），都可以用图来复核「它到底可不可行、`makespan` 到底是多少」，这条路径与被复核的实现完全无关。

一句话：**从今天起，「这个排程好不好」不再靠感觉，而是靠一张可以逐条弧核对的有向图。**

## 3. 析取图的定义

**定义**：给定实例（`FJSPInstance`）与一份排程（`Schedule`，即「每道工序在哪台机器上、什么时候开工」），析取图 `D = (V, A)` 的构造如下：

| 节点 | 含义 |
|---|---|
| 每道工序一个节点 | 用 `operation_id` 命名 |
| 源点 `__source__` | 虚拟起点，代表「所有订单都还没开始」 |
| 汇点 `__sink__` | 虚拟终点，代表「所有工序都已完成」 |

| 弧类 | 从哪里到哪里 | 权重 | 含义 |
|---|---|---|---|
| 源弧 | 源点 → 每个订单的第一道工序 | 该订单的 `release_time` | 订单最早可开工时刻 |
| 路线弧（conjunctive / job） | 同订单的第 `k` 道 → 第 `k+1` 道 | 前者的加工时长 | 工艺顺序，硬约束 |
| 机器弧（disjunctive / machine） | 同机器上相邻两道工序 | 前者的加工时长 | 由排程决定的先后关系 |
| 汇弧 | 每道工序 → 汇点 | 该工序的加工时长 | 让「路径终点」统一为汇点 |

三个必须说清楚的点：

1. **权重只记「节点自己的时长」**。等待时间不写在权重里 —— 等待是「路径上绕了远路」的结果，不是某条弧的属性。
2. **机器弧的方向来自排程**：把每台机器上的工序按开工时刻排序，相邻两道之间连一条弧，方向是从先开工的指向后开工的。这一排序步骤就是「析取弧定向」。
3. **源弧的权重是释放时间**。所以 `longest_path` 的长度可以写成「首道工序所在订单的释放时间 + 沿途所有工序的时长」，本仓库的 `path_length` 就是按这个式子**独立重算**的，与图上的最长路径互为交叉验证。

**定义（左移排程 / left-shifted schedule）**：一份排程是左移的，当且仅当每道工序的开工时刻都等于它在图上的最早可开工时刻（`earliest_starts`，即从源点到该节点的最长路径长度）。直观说法：**没有任何工序可以往前挪而不违反任何约束。**

**图上三类信息的规模**（对 `n` 道工序、`m` 个订单、`k` 台机器）：

```text
节点 = n 个真实工序 + 虚拟源点 + 虚拟汇点
弧数 = m 条源弧 + (n - m) 条路线弧 + (n - k) 条机器弧 + n 条汇弧
     = m + (n - m) + (n - k) + n = 3n - k
本实例：n = 9、m = 3、k = 3  ->  3 x 9 - 3 = 24，与脚本数出来的 24 条一致。
（前提：每台机器上至少有一道工序，否则 (n - k) 要按「实际用到的机器台数」算。）
```

**实现要点（读代码时注意这三件事）**：

1. **`Arc` 是带 `kind` 的**（`source` / `job` / `machine` / `sink`）。分析函数靠这个字段区分「这是硬约束还是排程决策」；`critical_path` 的逐条弧验证也用它回答「`J2_O0 -> J1_O1` 到底是路线弧还是机器弧」。
2. **`nodes` 只装真实工序**。虚拟点不作为独立对象存在，它们只在弧的端点上出现 —— 所以 `len(graph.nodes) = 9` 而拓扑序长度是 11。写分析代码时不要用 `nodes` 的长度当「节点总数」。
3. **同一对工序之间可能有两条弧**（既是同订单的相邻工序，又恰好是同机器的相邻工序）。本仓库不在建图时去重：两条弧的信息不同（一条来自路线，一条来自排程），全部保留，`arc_between` 返回先遇到的那条，逐条弧验证时要意识到这一点。

## 4. 定理：最长路径 = makespan（以及它的前提）

**理论结论**：若排程是左移的，则 `makespan` 等于析取图中从源点到汇点的最长路径长度。

**证明思路**：记 `ES(v)` 为图上源点到 `v` 的最长路径长度。

```text
(1) ES(v) + duration(v) <= Cmax        （对任意工序 v 成立：ES 是下界，实际完工不会早于它）
(2) 设 u 是最后完工的那道工序，则 Cmax = start(u) + duration(u)
    由左移性 start(u) = ES(u)，所以 Cmax = ES(u) + duration(u) <= 最长路径长度
(3) 反方向：最长路径上每道工序的完工时刻逐个不小于「路径长度累加」，所以
    最长路径长度 <= Cmax
两条不等式合起来得到等号。
```

**关键在 (2)**：如果没有左移性，`start(u) > ES(u)`，等号就不成立。Day 3 的实验（第 7 节）会构造一个反例：把一道工序人为推迟 3 个时间单位，`makespan` 变成 9，而最长路径长度仍然是 7。

**三条推论**（第 6、7 节的实现与实验都会用到）：

```text
推论 1（下界）：对任意排程，makespan >= 最长路径长度。因为 (3) 那一步不依赖左移性，
        它只用到「路径上每道工序都得按顺序做完」。
推论 2（上界）：对左移排程，最长路径长度 <= makespan，这条才依赖左移。
推论 3（不变性）：左移不增加 makespan。左移后的排程仍然是左移排程（幂等），
        且每道工序的新开工时刻 = 原地的最早可行时刻 <= 原开工时刻。
```

推论 1 是「图上的长度」能当排程质量标尺的原因：无论求解器给了什么解，图上算出来的长度都不会超过真实 `makespan`，所以它永远是一个合法的检验量。推论 3 则是「先左移再分析」这个动作安全的原因。

**这条前提在工程上意味着什么**：

1. 拿到一份排程**必须先归一化再分析**。本仓库的做法是：分析之前先调用 `left_shift_schedule` 做左移，并把「这份排程是不是左移的」（`is_left_shifted`）与有没有松弛工序（`slack`）一并记下来。左移可能破坏实例上某些非工艺性的约束（例如某道工序的开工时刻被别人指定过），遇到这类实例时左移会被跳过并记录原因，此时分析函数会拒绝工作而不是给出一个错的长度。
2. 分析函数不能「悄悄算一个数」。本仓库的 `check_critical_path` 在没有左移性时**抛出 `ValueError`**，并在消息里列出被推迟的工序，而不是返回一个看似合理的长度。
3. 松弛是可以量化的：`slack = {工序 : start_time > ES(工序)}`。本仓库的 `GraphAnalysis.slack` 就是为了让「这份排程不满足前提」这件事可见。

## 5. 手算：把一份排程画成图

实例用 `tests/data/tiny3x3.jsp`（仓库里手写的小文件，格式是「第一行订单数与机器数，随后每订单一行的『机器号 工时』对」；今天只用到「每道工序固定在一台机器上」这一点）：

```text
3 3
0 2 1 3 2 1      J0：M0(2) -> M1(3) -> M2(1)
1 2 2 2 0 2      J1：M1(2) -> M2(2) -> M0(2)
2 3 0 1 1 2      J2：M2(3) -> M0(1) -> M1(2)
```

手算出的最优排程（`makespan = 7`，恰好等于最大机器负载）：

```text
M0：J0_O0[0,2)   J2_O1[3,4)   J1_O2[5,7)
M1：J1_O0[0,2)   J0_O1[2,5)   J2_O2[5,7)
M2：J2_O0[0,3)   J1_O1[3,5)   J0_O2[5,6)
```

**第一步：节点与弧数**。9 道工序 + 源点 + 汇点 = 11 个节点。

```text
源弧   3 条（三个订单的第一道工序：J0_O0、J1_O0、J2_O0）
路线弧 6 条（每个订单 3 道工序 -> 2 条弧，共 6 条）
机器弧 6 条（每台机器 3 道工序 -> 2 条弧，共 6 条）
汇弧   9 条（每道工序都连到汇点）
合计   24 条
```

**第二步：机器定向**。这就是「析取弧选了哪个方向」：

```text
M0：J0_O0 -> J2_O1 -> J1_O2        （开工时刻 0 < 3 < 5）
M1：J1_O0 -> J0_O1 -> J2_O2        （0 < 2 < 5）
M2：J2_O0 -> J1_O1 -> J0_O2        （0 < 3 < 5）
```

**第三步：手算最长路径**。候选路径要一条条比，只列两条最长的：

```text
路径 A：J2_O0 -> J1_O1 -> J1_O2
        J2_O0 在 M2 [0,3)，J1_O1 是 M2 上的下一道 [3,5)，J1_O2 是 J1 的下一道 [5,7)
        长度 = J2_O0 的 3 + J1_O1 的 2 + J1_O2 的 2 = 7
路径 B：J1_O0 -> J0_O1 -> J2_O2
        长度 = 2 + 3 + 2 = 7        （也是 7，本例有两条并行的最长路径）
路径 C：J0_O0 -> J0_O1 -> J0_O2
        长度 = 2 + 3 + 1 = 6        （被路径 A/B 压住，不是关键路径）
```

`makespan = 7`，最长路径长度也是 7，等式成立。

**一个容易看漏的点**：路径 A 里的 `J2_O0 -> J1_O1` 是**机器弧**（同在 `M2`），而 `J1_O1 -> J1_O2` 是**路线弧**（同属 `J1`）。关键路径通常由两类弧交替拼成，这也解释了为什么「只盯着一台机器优化」往往收效有限：路径会从这台机器跳到另一台。

## 6. 关键块：把关键路径切成机器上的连续段

**定义（关键块 / critical block）**：关键路径上的一段**极大**连续工序，满足「同属一台机器，且在该机器的工序顺序里位置相邻」。

以前面的关键路径 `J2_O0 -> J1_O1 -> J1_O2` 为例：

```text
J2_O0 在 M2 的序号 0，J1_O1 在 M2 的序号 1  -> 相邻，可以进同一块
J1_O2 在 M0 的序号 2                        -> 换机器了，只能另起一块
关键块 = [ (J2_O0, J1_O1), (J1_O2) ]        对应机器 M2、M0
```

**判定时不要偷懒**：仅仅「两台工序在同一台机器上」不够，还必须在该机器的顺序里**紧挨着**（序号差 1）。若中间隔着一道非关键工序，那这两段之间不存在机器弧，它们不是同一个块。本仓库 `critical_blocks` 用的就是「工序在机器顺序里的下标是否连续」这条判据。

**块内性质**：在左移排程上，同一个关键块内的相邻工序必须**首尾相接**（前一道的完工时刻 = 后一道的开工时刻），因为弧存在就意味着没有等待。这条性质是很好的自检：块内出现空隙，说明上游工序被推迟过（即排程不是左移的），或者建图时机器顺序取错了。

**为什么块是有意义的单位**：局部搜索的经典做法（Nowicki 与 Smutnicki 1996）是**只在关键块上做交换**：把块首与块尾的工序互换位置，其余不动。理由很直接 —— 只有关键路径上的操作才有机会缩短 `makespan`，而块首/块尾的交换最有可能打断当前的最长路径。今天只把「哪些工序构成块」算清楚，不在这里实现任何交换动作。

**切块算法**（沿关键路径扫一遍，每台机器记一个「该机器上的工序顺序表」）：

```text
输入：关键路径 path = [v1, v2, ..., vp]
      pos[m][工序] = 该工序在其机器 m 的顺序里的下标

blocks = []，current = [v1]
for k in 2..p:
    记 a = path[k-1]，b = path[k]
    if 机器(a) == 机器(b) 且 pos[机器(a)][b] == pos[机器(a)][a] + 1:
        current.append(b)          # 与上一道同机器且紧挨着 -> 延长当前块
    else:
        blocks.append(current)     # 换机器或中间夹了别的工序 -> 收块
        current = [b]
blocks.append(current)
```

**复杂度与坑**：整个切块是 `O(p)` 的（`p` 是关键路径长度），前提是事先算好每台机器上的工序下标表。两个常见错误：

1. **只看「同机器」不看「相邻」**。若把中间隔着非关键工序的两段拼成一个块，块内会出现空隙（前一道的完工时刻 ≠ 后一道的开工时刻），交换邻域就会去交换两道根本不相邻的工序，产生非法排程。
2. **顺序表取自「开工时刻排序」而不是排程本身**。开工时刻可能相同（两道工序同时开工是不可能的 —— 同机器不允许重叠），但如果读取的是「我随手排的顺序」而非「按开工时刻排的顺序」，方向就会错。本仓库在建图时就把顺序固定下来，`sequence_on(machine_id)` 返回的就是这个顺序，切块时直接查它，不重新排序。

**本实例上的一个观察**：`mwr` 与 `spt` 两条优先级规则在这个 3×3 实例上都给出 `Cmax = 7`，关键块也都是 `[['J2_O0', 'J1_O1'], ['J1_O2']]`，与手算排程一致。这说明**同一个最优值可能对应不同的排程，但它们的关键路径结构可以完全相同**。

## 7. 实验：`m3w1d3_disjunctive_graph.py`

脚本链接：[m3w1d3_disjunctive_graph.py](../../projects/03_industrial_fjsp/examples/m3w1d3_disjunctive_graph.py)。

在项目目录下运行：

```bash
cd projects/03_industrial_fjsp
python examples/m3w1d3_disjunctive_graph.py
```

第 1 节（建图）的实际输出：

```text
实例：tiny3x3.jsp，3 订单 x 3 机器，9 道工序
手算排程的 makespan = 7

========================================================================
第 1 节：建图 —— 节点与四类弧
========================================================================
工序节点数 = 9（虚拟源点与汇点不放进 nodes，只在弧的端点上出现），弧数 = 24
  source   弧   3 条
  job      弧   6 条
  machine  弧   6 条
  sink     弧   9 条

每台机器上的定向（这就是「析取弧选择了哪个方向」）：
  M0：J0_O0 -> J2_O1 -> J1_O2
  M1：J1_O0 -> J0_O1 -> J2_O2
  M2：J2_O0 -> J1_O1 -> J0_O2

源点出发的弧（权重 = 订单释放时间）：
  __source__ -> J0_O0  权重 0
  __source__ -> J1_O0  权重 0
  __source__ -> J2_O0  权重 0

拓扑序长度 = 11（= 工序节点 9 + 源点 + 汇点），含环 = False
```

四类弧的条数（3/6/6/9）与第 5 节手算完全一致。`nodes` 里只有 9 个真实工序节点，**虚拟源点与汇点不作为节点对象存在**，只在弧的端点上出现；所以拓扑序是 11 项（9 + 源点 + 汇点）。拓扑序长度 = 11 恰好排完了所有真实工序，说明图上没有环，最长路径存在。

**怎么读这一节的输出**：先看「工序节点数 = 9」与「弧数 = 24」，与第 5 节手算对得上；再看四类弧的分布，「源弧 3 条」正好是订单数（每个订单一条源弧），「汇弧 9 条」正好是工序数（每道工序一条汇弧）—— 这两条是最容易一眼看出建图漏项的检查。最后看每台机器的定向字符串，与手算的 `M0：J0_O0 -> J2_O1 -> J1_O2` 逐字比对；不一致就说明「按开工时刻定序」这一步有问题，本节后面的所有结论都不用看了。

第 2 节（关键路径）：

```text
关键路径（3 道工序）：
   J2_O0  M2 [0,3)
  -> J1_O1  M2 [3,5)
  -> J1_O2  M0 [5,7)

路径长度（独立重算：首道工序所在订单的释放时间 + 沿途工时）= 7
makespan = 7
两者相等：True

逐条弧验证（关键路径上每对相邻工序之间必须真的有弧）：
  J2_O0 -> J1_O1  弧类型 = machine
  J1_O1 -> J1_O2  弧类型 = job

analyze：path_length = 7，graph_length = 7，makespan = 7
check_critical_path 返回 = 7
```

「逐条弧验证」这一步是**独立于最长路径算法的**：它不问「哪条路径最长」，只问「我给出的这条路径是否真的由弧连成」。两种检查都通过，才能相信路径是对的。

第 3 节（关键块）：

```text
  机器 M2：['J2_O0', 'J1_O1']
        从 0 到 5，共 2 道工序，块内无空隙 = True
  机器 M0：['J1_O2']
        从 5 到 7，共 1 道工序，块内无空隙 = True

块拼起来 = ['J2_O0', 'J1_O1', 'J1_O2']
与关键路径完全相同：True
```

第 4 节（定理前提被破坏）—— 把 `M2` 上的末道工序 `J0_O2` 从 `[5,6)` 人工推迟到 `[8,9)`：

```text
J0_O2 从 [5,6) 推迟到 [8,9)
推迟后排程仍然可行：validate_schedule 未报错
推迟后 makespan = 9
推迟后路径长度 = 7
松弛工序（开工晚于最早可开工时刻的工序）= ['J0_O2']
是否左移排程 = False
路径长度 == makespan = False
check_critical_path 拒绝：排程不是左移的，最长路径定理不适用；以下工序被人为推迟：['J0_O2']
```

**这一段是今天最重要的证据**：同一份排程，推迟一道工序之后 `makespan` 从 7 变成 9，而最长路径长度仍然是 7。等式失效了，但**没有任何函数偷偷给出错的数** —— `analyze` 把松弛工序列了出来，`check_critical_path` 直接报错并指出是谁破坏了前提。

第 5 节（左移归一化把前提补回来）：

```text
左移后 makespan = 7（不高于推迟后的 9）
左移后是否左移排程 = True，松弛 = []
左移后路径长度 = 7，重新等于 makespan = True

左移前后的时间线对比：
  J0_O0  (0, 2) -> (0, 2)
  J0_O1  (2, 5) -> (2, 5)
  J0_O2  (8, 9) -> (5, 6)   <- 被前移
  ...
```

只有被推迟的那道工序被前移，其余 8 道工序原地不动，`makespan` 从 9 降回 7。这顺带说明一件事：**左移只会让 `makespan` 不变或变小，绝不会变大**（因为它是把每道工序挪到「当前排程下的最早可行时刻」）。所以「先左移再分析」这个动作不会破坏解的质量。

最后与优先级派工的对照：

```text
  mwr  Cmax =   7.0  关键路径长度 = 7  关键块 = [['J2_O0', 'J1_O1'], ['J1_O2']]
  spt  Cmax =   7.0  关键路径长度 = 7  关键块 = [['J2_O0', 'J1_O1'], ['J1_O2']]
```

脚本最后的当日结论：

```text
1. 析取图 = 路线弧（硬约束）+ 机器弧（由排程定向）+ 源弧/汇弧（权重=工时/释放时间）。
2. 左移排程上，最长路径长度恰好等于 makespan —— 一切基于关键路径的判断都以它为前提。
3. 关键块 = 关键路径上同机器且相邻的极大段；块内相邻工序必须首尾相接。
4. 非左移排程上等式失效，必须先归一化再谈关键路径 —— 检查函数会明确报错而不是硬算。
```

## 10. 自测题

- Q1：析取图的权重为什么不包含等待时间？
- Q2：源弧的权重是什么？如果某个订单的 `release_time = 3`，图上会多出什么？
- Q3：`topological_order()` 返回 `None` 意味着什么？此时 `longest_path()` 应该怎么做？
- Q4：「最长路径长度 = `makespan`」在什么前提下成立？给出一个前提被破坏的具体例子。
- Q5：怎么判断一份排程是不是左移的？
- Q6：关键块的两个判定条件是什么？少了任何一个会怎样？
- Q7：为什么说「只优化瓶颈机器」往往收效有限？
- Q8：为什么分析一份排程之前要先把它左移归一化？什么情况下不允许左移？
- Q9：本实例的关键路径不止一条（长度都是 7），这对「改进排程」意味着什么？
- Q10：`analyze` 返回的 `graph_length` 与 `path_length` 有什么区别？两个都要看吗？

### 参考答案

- A1：因为等待不是某条弧的属性，而是「路径绕远」的结果。若把等待写进权重，同一份排程在不同机器顺序下权重会变，图就不再只由「哪些工序相邻」决定，最长路径也会与「开工时刻」纠缠在一起。
- A2：源弧的权重是订单的释放时间（`Job.release_time`）。若释放时间是 3，则该订单第一道工序的最早开工时刻是 3，它的 `earliest_starts` 会相应增大，最长路径若经过该订单也会变长。
- A3：意味着图上有环，即机器顺序与工艺路线互相矛盾，这份「排程」根本不可行。`longest_path()` 应当抛 `ValueError`（本仓库就是这样做的），而不是在环上无限推进。
- A4：前提是排程左移。反例：3×3 实例上把 `J0_O2` 从 `[5,6)` 推迟到 `[8,9)`，`makespan` 变成 9 而最长路径长度仍是 7。
- A5：对每道工序比较「实际开工时刻」与「图上最早可开工时刻」（`earliest_starts`），全部相等才是左移的；不相等的工序就是松弛工序。
- A6：两个条件：同机器，且在该机器的工序顺序里位置相邻。少了「同机器」会跨机器成块（那条路径中间必然没有弧，块内会断裂）；少了「相邻」会把中间隔着非关键工序的两段拼在一起（它们之间没有机器弧，块内出现空隙）。
- A7：因为关键路径通常由机器弧与路线弧交替拼成，会从一台机器跳到另一台。只改一台机器上的顺序，路径可能立刻绕到别的机器上，`makespan` 不变。
- A8：因为最长路径定理依赖左移性，而一份刚拿到手的排程不保证左移（它只保证满足自己那一套约束，可能被人为推迟过）。当左移会破坏该实例上别的约束时（例如某道工序的开工时刻是被指定过的），就不允许左移 —— 前移会让那份排程不再满足它原本要满足的条件。
- A9：意味着有多条互不相同的路径都在决定 `makespan`，只打断其中一条不会让 `makespan` 下降；改进需要同时影响所有并行的关键路径。
- A10：`path_length` 是「沿某一条具体路径（`path`）重算的长度」，`graph_length` 是「图上最长路径的长度」。正常情况下两者相等；不等说明 `path` 不是最长的那条，或者左移性被破坏（本仓库在后者上会抛错）。

作为对 A10 的补充：本仓库的 `analyze` 把两个量都返回，是因为它们回答不同的问题。`graph_length` 回答「这份排程的 `makespan` 至少是多少（图上算出来的）」，`path_length` 回答「我手上这条路径有多长」。前者是不依赖具体路径的图论量，后者是对某条路径的复核。两个都看，才能发现「路径取错了」与「排程不左移」这两类不同的问题。

## 11. 今日一句话总结

今天走完的链条是：

```text
排程（每道工序在哪台机器、什么时候开工）
   -> 析取图（路线弧是给定的，机器弧是排程决定的）
   -> 拓扑排序（有环 = 排程不可行）
   -> 最长路径 = makespan（前提：左移）
   -> 关键路径上同机器且相邻的极大段 = 关键块
   -> 关键块是「交换两道工序」这类改进方法的单位
```

每一步都有对应的实现函数，也都有一条独立的复核方式：建图靠「四类弧条数与手算一致」核对，最长路径靠「沿路径重算长度」核对，关键路径靠「逐条弧验证」核对，左移性靠「松弛集合为空」核对。

> **关键路径说的是「谁在决定 `makespan`」，关键块说的是「从哪里动手能改变它」—— 但这两句话都只在左移排程上成立，所以分析之前先归一化。**
