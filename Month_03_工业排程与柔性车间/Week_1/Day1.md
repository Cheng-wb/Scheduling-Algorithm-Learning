## 2. 为什么第 1 天要先做「构造规则」

M1 与 M2 打下的地基是：**可信输入 → 排程 → 目标值 → 可核对的数字**。M3 要在这条流水线上真正做车间调度，而车间调度的第一课不是求解器，是**问题结构**：

1. **Flow Shop 是最容易被手算验证的多机问题。** 每个订单走同一条机器序列，非决策的部分全部固定，剩下的只有「顺序」这一件事。手算可以逐格填表，代码写错了立刻能看出来。
2. **规则是任何方法的最低基线。** 以后无论用什么方法解更复杂的车间问题，都要和「Flow Shop baseline」比。基线不可信，比较就全部无效。
3. **Johnson 规则是「精确算法」与「启发式」的分界线。** 两台机器有最优性定理，三台机器就是 NP-hard（Garey、Johnson 与 Sethi 1976 年证明）。这条界线要在第一天就说清楚，否则极易出现「NEH 最优」这种错话。
4. **NEH 的插入过程可以完全摊开。** 每一步插在哪里、当时的 `makespan` 是多少，都能打印出来逐行核对 —— 这是建立「代码可信」最省力的方式。

一句话：**先把结构最简单、但结论最容易说错的那一课做扎实。**

今天产出的两个东西本身就是可复用的资产：**手写解码器**（不含任何启发式规则，只按给定顺序算时间线）与**手算时间线**。它们的作用是给「注册方法」提供一份不依赖被测代码的对照物：手写解码器用来核对方法返回的排程，手算时间线用来核对解码器本身。

## 3. 三种车间：先分清「约束」与「决策」

调度问题的差别，本质是「哪一部分已经给定、哪一部分要你决定」。

| 问题 | 记号 | 每道工序的机器 | 机器上的顺序 | 订单的路线 |
|---|---|---|---|---|
| 单机 | `1 \|\| Cmax` | 唯一 | 决策 | 每订单一道工序 |
| Flow Shop | `Fm \| prmu \| Cmax` | 给定，所有订单相同 | 决策 | 给定，全部相同 |
| Job Shop | `Jm \|\| Cmax` | 给定，各订单不同 | 决策 | 给定，各不相同 |
| Flexible Job Shop | `FJm \|\| Cmax` | **决策**（多台合格机器） | 决策 | 给定 |

换成 M3 领域模型的语言（[models.py](../../projects/03_industrial_fjsp/fjsp_core/models.py)）：

1. `Operation.machine_times` 里**只有一个** `(machine_id, minutes)`，说明这道工序的机器是给定的；这是 Flow Shop 与 Job Shop。
2. 同一个元组里有**多个** `(machine_id, minutes)`，说明机器要选：这就是 Flexible。`eligible_machine_ids` 是「允许范围」（约束），结果里的 `ScheduledOperation.machine_id` 才是「实际选择」（决策）。
3. `prmu` 的含义是：**所有订单在每台机器上的相对顺序相同**。它把「每台机器一个排列」压缩成「一个全局排列」，所以 `Fm | prmu | Cmax` 的解可以只用一个订单序列表示。

**定义**：本仓库的 Flow Shop 实例 = 每个订单的工序数相同、每道工序恰好一台合格机器、且所有订单的机器序列完全一致、且序列里没有重复机器。

最后两条检查不是形式主义：

1. **「所有订单序列一致」**：代码要从第一个订单的工序里归纳出「机器序列」（本仓库 `flow_shop_route` 的做法），若某个订单的序列不同，归纳出来的 `route[k]` 映射到别的订单上就是错的机器 —— 那已经是 Job Shop，必须拒绝。
2. **「序列里没有重复机器」**：如果某个订单的路线是 `M0 -> M1 -> M0`，那么「第 k 道工序在第 k 台机器上」这句话失效，`route[index]` 的写法会把它当成两台不同的机器。这种实例在真实车间里很常见（去毛刺后回炉），但它不属于经典 Flow Shop，必须在入口处报错而不是算出一个看着合理的数。
3. 同理，**「每道工序恰好一台合格机器」**：多台合格机器意味着机器选择是决策的一部分（Flexible），这与 `prmu` 假设叠加后不再有「一个全局排列」这种简洁表示。

## 4. Johnson 规则：`F2 || Cmax` 的精确算法

设每个订单在两台机器上的工时为 `p1(j)` 与 `p2(j)`。

**理论结论（Johnson 1954）**：把订单分成两个集合

```text
集合 A = { j : p1(j) <  p2(j) }     按 p1 升序排在前面
集合 B = { j : p1(j) >= p2(j) }     按 p2 降序排在后面
最优排列 = A 的顺序 + B 的顺序
```

它有两种等价的写法，今天两种都会用到：

| 写法 | 做法 | 何时好用 |
|---|---|---|
| 集合写法 | 先分 A/B，再各自排序，最后拼接 | 写成代码最短，一行一个排序键 |
| 两端构造法 | 每次取全表最小工时：属于 M0 就接到头部，否则接到尾部 | 手算方便，一眼能看出「谁先谁后」 |

两端构造法的直觉：全表最小工时是 `p1(j)` 时，`j` 在第一台机器上几乎不占时间，放最前面最不伤人；全表最小工时是 `p2(j)` 时，`j` 在第二台机器上几乎不占时间，放最后面最不挡路。把这两个「无害的订单」不断剥离，剩下的问题规模变小。

**最优性的直观（交换论证）**：只看相邻的两个订单 `a`、`b`，把前面积压的时间记为 `t`，则「`a` 在前」与「`b` 在前」两种排法的差只取决于一个比较：

```text
a 排在 b 前面  不差于  b 排在 a 前面    当且仅当
min( p1(a), p2(b) )  <=  min( p1(b), p2(a) )
```

这条判据可以完全手算。拿第 5 节的 4×2 实例的相邻对来核对 Johnson 排出来的顺序 `J2 -> J0 -> J3 -> J1`：

```text
(J2, J0)：min(p1(J2), p2(J0)) = min(1, 3) = 1
          min(p1(J0), p2(J2)) = min(2, 5) = 2       1 <= 2  -> J2 在前，符合
(J0, J3)：min(2, 2) = 2    vs   min(3, 3) = 3        2 <= 3  -> J0 在前，符合
(J3, J1)：min(3, 1) = 1    vs   min(4, 2) = 2        1 <= 2  -> J3 在前，符合
```

三对全部满足，说明这个排列没有可改进的相邻交换 —— 这正是 Johnson 定理的证明思路：**只要所有相邻对都满足上述不等式，整个排列就是最优的**（因为任何改进都可以分解成一系列相邻交换，而每次相邻交换都不会变好）。注意这条判据对**任意两台机器**都成立，但它只覆盖 `m = 2` 的情形；`m >= 3` 时无法把问题分解成相邻对的比较。

**平局与等号的处理**（本仓库的约定，代码与手算一致）：

1. 平局按 `job.id` 升序决胜，结果与输入顺序、运行次数都无关。
2. `p1(j) == p2(j)` 归入集合 B（判据用 `>=`，不是 `>`），让「长尾」集中在机器后段。

**适用条件**：2 台机器、所有释放时间为 0、无交货期与权重、只最小化 `makespan`、加工时间与顺序无关。任何一条不满足，「最优」就不再成立。

## 5. 手算：一个 4 订单 × 2 机器实例

四个订单的工时如下（这份「4×2 手算实例」今天会反复用到）：

```text
订单    p1(M0)   p2(M1)   总工时
J0        2        3        5
J1        4        1        5
J2        1        5        6
J3        3        2        5
```

**第一步：分派**。

```text
J0: 2 < 3   -> A        J1: 4 >= 1  -> B
J2: 1 < 5   -> A        J3: 3 >= 2  -> B
```

**第二步：组内排序**。

```text
A = [J2(1), J0(2)]         按 p1 升序：J2 在前
B = [J3(2), J1(1)]         按 p2 降序：J3 在前，J1 在后
排列 = J2 -> J0 -> J3 -> J1
```

**第三步：用两端构造法复核**。每一步取「剩余订单里 `min(p1, p2)` 最小、平局取订单号小」的那个：

```text
剩余 {J0(2,3), J1(4,1), J2(1,5), J3(3,2)}
  候选最小 = J1 的 1（p2）  -> p1 >= p2，接到尾部：  [J1]
  候选最小 = J2 的 1（p1）  -> p1 <  p2，接到头部：  [J2, J1]
  剩余 {J0, J3}，J0 的 2 < J3 的 2？两者 min 都是 2，取订单号小的 J0
  J0(2,3)：p1 < p2 -> 接到头部： [J2, J0, J1]... 等等，J1 已在尾部
  实际上：头部 = [J2, J0]，尾部 = [J1]，再处理 J3
  J3(3,2)：p1 >= p2 -> 接到尾部：尾部 = [J3, J1]
结果 = [J2, J0] + [J3, J1] = J2 -> J0 -> J3 -> J1
```

两种写法给出同一个排列 `J2 -> J0 -> J3 -> J1`。**注意**：两端构造法里「接到尾部」是把订单插到尾部序列的**最前面**（相当于从后往前填），这一点写代码时最容易写错；`m3w1d1_flowshop_rules.py` 里用 `back.insert(0, job_id)` 实现，并把两种写法的结果打印出来对照。

**第四步：解码**。按排列依次投放，`M0` 上一台接一台不停；`M1` 上的开工时刻取「同订单在 `M0` 的完工」与「`M1` 上一道完工」的较大者。

```text
订单    M0 区间     M1 区间     M1 开工的由来
J2      [0,  1)     [1,  6)     max(J2 在 M0 完工 1, M1 空闲 0) = 1
J0      [1,  3)     [6,  9)     max(3, J2 在 M1 完工 6) = 6      <- 等 M1
J3      [3,  6)     [9,  11)    max(6, 9) = 9
J1      [6, 10)     [11, 12)    max(10, 11) = 11
```

`makespan = max(M0 完工 10, M1 完工 12) = 12`。

**解码的两条递推式**（把它写成公式，代码才不容易写错）。设排列为 `π(1), …, π(n)`，`p(j, k)` 是订单 `j` 在第 `k` 台机器上的工时：

```text
开工时刻  S(π(i), 0) = C(π(i-1), 0)                        （M0 上 = 上一订单在 M0 的完工）
          S(π(i), k) = max( C(π(i), k-1), C(π(i-1), k) )   （k >= 1：自己上一道 vs 机器上一道）
完工时刻  C(π(i), k) = S(π(i), k) + p(π(i), k)
makespan  Cmax = C(π(n), m-1)
```

`π(0)` 视为空，`C(π(0), k) = 0`。

递推式成立的关键是 `prmu`：**每台机器上的投放顺序都是同一个排列**，所以「机器 `k` 上的上一道工序」就是 `π(i-1)`，不需要额外记每台机器各自的顺序。若换成 `Fm || Cmax`（不同机器顺序不同），这两条式子立刻不够用 —— 因为那时「上一道工序是谁」取决于每台机器各自的顺序，不再由一个全局排列决定；这类问题的表示方式超出了今天的范围。

由第一条式子还能得到一个白送的性质：`M0` 从 0 开始一路不停，所以 `C(π(n), 0)` 就等于 `M0` 上全部工时之和 —— 本实例是 `1+2+3+4 = 10`。**手算时先算这个量**，它能立刻否掉算错的解码结果。

**不要只看最后一个数**。这张表还能读出两件事：(1) `M0` 从 0 到 10 一路不停，`M1` 从 1 到 12 一路不停 —— 两台机器都没有空闲，但 `M1` 上有等待；(2) `J0` 在 `M1` 上等了 3 个时间单位（`M0` 完工 3，`M1` 开工 6），这段等待是「上游是瓶颈」的典型形状。**等待发生在哪台机器上、由谁造成，是判断瓶颈的直接线索**，今天先记住这个形状。

## 6. NEH：≥3 台机器时改用什么

**理论结论**：`Fm | prmu | Cmax` 在 `m >= 3` 时是 NP-hard（Garey、Johnson、Sethi，1976）。所以「一般 m 台机器的 Flow Shop 有快速精确算法」这句话是错的。

工程上的标准做法是 **NEH**（Nawaz、Enscore、Ham，1983）：

```text
1. 算每个订单的总工时 T(j) = Σ_k p(j, k)
2. 按 T(j) 降序排序（平局按 job.id 升序）
3. 按这个顺序逐个取出订单，插入到当前部分排列的每个可能位置，
   算出每个位置的 makespan，取最小的那个位置
4. 平局时取**最靠前**的位置（确定性决胜）
```

插入位置有 `len(partial) + 1` 个，每个位置都要完整解码一次，所以单步代价是 `O(n^2 m)`；总代价 `O(n^3 m)` 量级，对几十个订单的实例完全够用。

**为什么是「总工时降序」**：总工时大的订单对 `makespan` 的影响最大，先安排它、让后面的订单去适应它，比反过来更划算。这是一条启发式直觉，不是定理 —— 第 8 节的练习 4 会让你构造一个反例（按总工时排序后不插入的排列不是最优）。

**三个最常见的实现错误**：

| 症状 | 根因 | 后果 |
|---|---|---|
| 排列与手算不同但 `makespan` 相同 | 平局取了最后一个最优位置（写成 `<=`） | 实验不可复现，同一输入两次运行可能给出不同排程 |
| 第 2 步的候选值是 `[10, 9]` 这种顺序 | 插入位置从后往前枚举 | 平局决胜随之反转，同上 |
| 插入后 `makespan` 比部分解码的结果小 | 每次都从头解码，但把「机器就绪」重置了 | 得到一个违反机器约束的排程，`validate_schedule` 会拒绝 |

第三条正好说明为什么要有**独立验证器**：解码函数自己算出来的 `makespan` 是不可信的，必须换一条路径（`makespan(instance, schedule)` + 逐机器查重叠）复核。

**手算 3 订单 × 3 机器的 NEH**（Day 1 的第二个实例）：

```text
订单    M0   M1   M2   总工时
J0       3    2    2      7
J1       2    1    3      6
J2       1    3    1      5
```

插入顺序 = `J0(7) -> J1(6) -> J2(5)`：

```text
第 1 步：插 J0        部分排列 [J0]，候选位置只有 0，makespan = 7
第 2 步：插 J1，两个候选位置
  [J1, J0]：J1 M0[0,2) M1[2,3) M2[3,6)；J0 M0[2,5) M1[5,7) M2[7,9)    -> 9
  [J0, J1]：J0 M0[0,3) M1[3,5) M2[5,7)；J1 M0[3,5) M1[5,6) M2[7,10)   -> 10
  取最小 -> [J1, J0]，makespan = 9
第 3 步：插 J2，三个候选位置
  [J2, J1, J0]：J2 M0[0,1) M1[1,4) M2[4,5)；J1 M0[1,3) M1[4,5) M2[5,8)；J0 -> 10   <- 选它
  [J1, J2, J0]：J1 M0[0,2) M1[2,3) M2[3,6)；J2 M0[2,3) M1[3,6) M2[6,7)；J0 -> 10
  [J1, J0, J2]：J1 M0[0,2) M1[2,3) M2[3,6)；J0 M0[2,5) M1[5,7) M2[7,9)；J2 -> 11
```

三个候选值是 `[10, 10, 11]`：前两个并列最小，**平局取最靠前的**，得到 `[J2, J1, J0]`，`makespan = 10`。

**同一实例上把 Johnson 硬套到两台机器会怎样**：`Fm` 里没有「指定哪两台」的说法，所以只能自己挑一对。若挑 `(M0, M1)`，Johnson 给出 `J2 -> J0 -> J1`，放回 3 台机器解码得 11；若挑 `(M0, M2)`，Johnson 给出 `J1 -> J0 -> J2`，解码也是 11。两者都不如 NEH 的 10。

**这里的措辞必须精确**：

1. 「NEH 给出 10」是**实验观察**，只对这一个实例成立。
2. 「Johnson 给出 11」也是实验观察，且它是**装饰性退化**：把一个只在两台机器上成立的定理搬到三台机器上，结果没有任何最优性保证。
3. 正确做法是**把退化情形写进结果里**：本仓库的 `flow_johnson` 在三台机器以上会返回 `status="FEASIBLE"`、`detail["applicability"]="johnson_on_bottleneck_pair"`、`detail["applies_directly"]=False`，并把选中的机对写进 `detail["bottleneck_pair"]`。绝不会返回 `OPTIMAL`。
4. 「NEH 是最优的」这句话本身是错的。`flow_neh` 永远返回 `FEASIBLE`，永远不报下界。

**关于瓶颈机对的一个细节**：本仓库选「路线里负载最大的两台机器，按路线位置排序」（负载平局时取路线靠前的），而不是随便挑。这是工程上常见的 `Fm` 化简手法，但**它仍然是启发式**：把机器的负载当作重要性代理，与「这两台机器上的最优性」之间没有任何定理。

```text
J0           1        3         6         9
J3           3        6         9        11
J1           6       10        11        12
makespan = 12
```

这一段验证了三件事：手算的两个排列一致、手写解码的 `makespan` 是 12、以及下面的注册方法给出同一个答案。

```text
再用注册方法跑同一个实例，看是否给出同一个答案：
  flow_johnson 状态 = OPTIMAL，目标值 = 12.0
  排列 = ['J2', 'J0', 'J3', 'J1']，是否精确适用 = True
  模块给出的 makespan = 12（手写解码 = 12）
  flow_neh     状态 = FEASIBLE，目标值 = 12.0，排列 = ['J2', 'J1', 'J0', 'J3']
```

注意 `flow_neh` 在这台机器数为 2 的实例上**也恰好给出 12**，但排列与 Johnson 不同（`[J2, J1, J0, J3]`）。两个不同的排列可以同为最优，这不是矛盾。

```text
NEH 的插入过程（总工时降序，逐个插到最靠前的并列最优位置）：
  第 1 步：插入 J0（总工时 7）
          候选位置与对应 makespan：[(0, 7)]
          选中位置 0，当前排列 ['J0']，makespan = 7
  第 2 步：插入 J1（总工时 6）
          候选位置与对应 makespan：[(0, 9), (1, 10)]
          选中位置 0，当前排列 ['J1', 'J0']，makespan = 9
  第 3 步：插入 J2（总工时 5）
          候选位置与对应 makespan：[(0, 10), (1, 10), (2, 11)]
          选中位置 0，当前排列 ['J2', 'J1', 'J0']，makespan = 10
```

第三步的三个候选 `[(0, 10), (1, 10), (2, 11)]` 是今天最重要的证据：它把「平局取最靠前」这条决胜规则摆在了明面上。若实现里写成 `<=`（后来的并列最优覆盖前面的），结果会变成 `[J1, J2, J0]` —— `makespan` 一样是 10，但排列不同，实验就不确定了。

```text
把 Johnson 硬套到 (M0, M2) 这两台机器上会得到什么：
  (M0, M2) 上的 Johnson 排列 = ['J1', 'J0', 'J2']，放回 3 台机器解码 = 11
  与 NEH 的 10 相比：更差

注册方法复核：
  flow_neh     状态 = FEASIBLE，目标值 = 10.0，排列 = ['J2', 'J1', 'J0']
  flow_johnson 状态 = FEASIBLE，目标值 = 11.0，适用性 = johnson_on_bottleneck_pair
  flow_johnson 自报的下界 = None（启发式必须为 None）
```

脚本最后打印的甘特行与结论：

```text
NEH 排程的甘特行（前 4 条，字段固定为六列）：
  machine_id=M0 | job_id=J2 | operation_id=J2_O0 | start_time=0 | end_time=1 | duration=1
  machine_id=M0 | job_id=J1 | operation_id=J1_O0 | start_time=1 | end_time=3 | duration=2
  machine_id=M0 | job_id=J0 | operation_id=J0_O0 | start_time=3 | end_time=6 | duration=3
  machine_id=M1 | job_id=J2 | operation_id=J2_O1 | start_time=1 | end_time=4 | duration=3

========================================================================
当日结论
========================================================================
1. Johnson 规则只对 F2||Cmax 精确；>=3 台机器的 flow shop 是 NP-hard，
   只能给启发式，不能声称最优。
2. NEH 是启发式：插入顺序按总工时降序，位置取第一个达到最小 makespan 的点。
3. 同样两台机器时，手写解码与注册方法的 makespan 必须一致 —— 这是对拍基线。
4. 本实例观察：NEH 10.0 vs 瓶颈对 Johnson 11.0。
```

**今天的三条实验观察**（都只对今天这两个实例成立）：

1. 4×2 实例上 Johnson 的 12 与 NEH 的 12 相同 —— 两台机器上 `12` 是定理保证的最优值，NEH 恰好也取到了它。
2. 3×3 实例上 NEH（10）优于瓶颈机对 Johnson（11）。
3. 单机退化情形下两个方法都应给出「所有工序工时之和」，可作为实现的边界检查（今天没有跑，可以先想清楚为什么它一定是这个值）。

**关于「手写实现」与「注册方法」的关系**：Day 1 的脚本里手写了一份 Johnson 与 NEH，目的不是重复造轮子，而是建立**对拍基线**。手写版把每一步都打印出来供人眼核对；注册版是给整月批次调用的实现。两者的 `makespan` 在 4×2 实例上都是 12、在 3×3 实例上都是 11/10 —— 只有当两套独立实现给出同一个数，才敢说实现可信。

**三个常见的读法错误**（今天最容易踩的三个）：

```text
1. 把 Johnson 当成「多台机器也精确」   —— 只有两台机器时它才是定理；
   m >= 3 时今天的脚本用「瓶颈机对上的 Johnson」，那是启发式，
   状态必须报 FEASIBLE。
2. 把 NEH 记成「按总工时降序排一下」    —— 排序只是准备步骤，
   真正的构造是「逐个取出、插到第一个使 makespan 最小的位置」。
   少了插入这一步，得到的只是一个普通排列。
3. 把 makespan 记成「最后一台机器一直忙到那一刻」 —— 它是所有机器上
   最大的完工时刻，机器可以中途空闲。今天 3×3 实例的 NEH 排程
   makespan = 10，但三台机器的忙时都只有 6：M2 从时刻 4 才开始忙
   （`[4,5) [5,8) [8,10)`），M1 在 5 到 6 之间空了一段
   （`[1,4) [4,5) [6,8)`）。
```

## 10. 自测题

- Q1：`Fm | prmu | Cmax` 里 `prmu` 表示什么？去掉它会变成什么记号？
- Q2：Johnson 规则的两个集合 A、B 的分界判据是 `p1 < p2` 还是 `p1 <= p2`？本仓库选了哪个？
- Q3：4×2 实例里 `M1` 从什么时刻开始忙？为什么不是 0？
- Q4：`M0` 与 `M1` 在最优排程里都没有空闲，是否说明这个排程一定是「无空闲即最优」？
- Q5：为什么 ≥3 台机器时 Johnson 规则不能直接用？给出理论理由与工程替代方案。
- Q6：NEH 的插入顺序依据是什么？平局如何处理？
- Q7：3×3 实例上 NEH 与瓶颈机对 Johnson 的目标值分别是多少？这两个数能推广到别的实例吗？
- Q8：`flow_johnson` 在 3×3 实例上返回什么 `status`？它在 `detail` 里必须写清哪三个字段？
- Q9：为什么启发式的 `best_bound` 必须是 `None`？如果填上目标值会怎样？
- Q10：单机实例上两个 flow 方法的 `makespan` 应当等于什么？为什么这个性质可以当边界检查？

### 参考答案

- A1：`prmu` 表示「排列假设」：所有订单在每台机器上的相对顺序相同。去掉它得到 `Fm || Cmax`（允许不同机器上顺序不同，一般解空间更大、难度更高）。
- A2：本仓库用 `p1 < p2` 进 A、`p1 >= p2` 进 B（即 `p1 == p2` 归入 B）。理由是让等号情形与 B 的单调性一致，长尾集中在后段；两个写法只要用同一个约定就不会分叉。
- A3：`M1` 从 1 开始忙。第一道工序 `J2_O1` 要等 `J2` 在 `M0` 上完工（时刻 1），`M1` 在这之前即使空闲也无活可干。
- A4：不能。本实例的 `M0`、`M1` 都不空闲，但在别的实例上「无空闲」的排程可能仍然不是最优 —— 无空闲只是「非延迟」的性质，与最优性无关。
- A5：理论理由：`Fm | prmu | Cmax` 在 `m >= 3` 时是 NP-hard（Garey、Johnson、Sethi 1976）。工程替代方案：NEH 插入启发式，或把 Johnson 退化到「负载最大的两台机器」上并在结果里标明这不再是精确方法。
- A6：插入顺序按订单总工时降序（平局按 `job.id` 升序）；位置取使当前部分排列 `makespan` 最小的那个，平局取最靠前的位置。
- A7：NEH = 10，瓶颈机对 Johnson = 11。不能推广：这是两个实例上的一次观察，换实例可能反过来。
- A8：返回 `FEASIBLE`。`detail` 里必须写清 `applicability`（此处是 `johnson_on_bottleneck_pair`）、`applies_directly=False` 与 `bottleneck_pair`。
- A9：因为启发式没有任何最优性证明，`best_bound` 是「可证明的下界」这一栏。填上目标值等于宣称「我证明了这就是下界」，是假陈述；M2 的 `ShopResult.__post_init__` 还会拒绝 `best_bound > objective` 这种自相矛盾的组合。
- A10：应当等于所有工序的工时之和（此时 `makespan` 与顺序无关）。可以用它做边界检查：实现里若把「机器就绪」与「订单就绪」取错，单机情形会立刻暴露。
