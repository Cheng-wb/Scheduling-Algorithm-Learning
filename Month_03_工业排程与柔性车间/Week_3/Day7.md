## 2. 这一周做了什么

一周前，模型只会排「谁先谁后、在哪台机器」。这一周把四种真实约束加了进来：

```text
Day 1  释放时间与交期      目标函数里多了 ΣT，工序多了最早开工时刻
Day 2  加权迟交与多目标    α·Cmax + β·ΣT + γ·setup，权重就是交换率
Day 3  归一化与敏感性      分母决定交换率；同一个 β 换个口径就换个排程
Day 4  sequence-dependent setup  换型是相邻对之间的间隔，用紧前弧编码
Day 5  机器日历与计划维护  可用区段 = 日历扣掉维护，再判「放得下」
Day 6  模型对照            边界、规模与时间、质量、不可行定位
```

四条约束面各自带来一个新东西：

```text
释放时间/交期/权重   订单的时间属性，不新增硬约束，只改目标和起点
setup               相邻关系上的时间间隔，需要新的编码（紧前弧）
日历/维护            机器自己的时间表，需要新的几何（可用区段）
多目标              一个标量目标，需要新的口径（归一化）
```

**这四条合起来才是「能执行」的排程**：一条不在交期内、不付换型、跨过停机段的顺序，
在模型里可能最优，在车间里无法执行。

## 3. 定义：能力表、结论与留白

**定义（能力表）**：一份「约束 → 支持它的模型 → 违反时的验证器标签」的对照。
它回答的是「这个模型收得下什么、收不下什么」。

**定义（被证明的结论）**：能指到某一天某个脚本的某一行输出的陈述。
说不出来源的陈述只能算「印象」。

**定义（留白）**：明确知道「没做」的事。留白不是遗漏——它指明了下一步。

三者的关系：

```text
能力表  说清模型现在能做什么
结论    说清做完之后被证明了什么（每条必须有可复现的数）
留白    说清还没做什么（每条必须指出该改哪里）
```

一份只有结论没有留白的总结，读者无法判断可信度；一份只有留白没有结论的总结，
读者得不到任何可用的东西。

## 4. 汇总：三个模型怎么拼成一条流水线

这一周的三个模型不是三选一，而是**各管一个约束面**：

```text
fjsp_cpsat_setup      换型（紧前弧，blocker 日历编码）
fjsp_cpsat_calendar   日历与维护（split 日历编码）
fjsp_cpsat_multiobj   α·Cmax + β·ΣT + γ·setup（加权和 + 归一化）
```

其中 `fjsp_cpsat_setup` 与 `fjsp_cpsat_calendar` 是**同一个模型**的两种日历编码：

```text
split    每个 (工序, 机器, 可用窗) 一个布尔变量 + AddExactlyOne
blocker  起点域 Domain.FromIntervals([[lo, hi - duration]]) + 停机区间塞进 AddNoOverlap
```

它们共用同一份几何（Day 5 第 4.1 节），所以**必然同解**；
规模可以差三成（Day 5 的 `11/20` 与 `7/12`；Day 6 的 `348/411` 与 `298/292`），
耗时甚至可能大的更快（`0.19` 秒对 `0.33` 秒）。
**换模型和换编码不是一回事**：换模型会改变可行集，换编码不会。

### 4.1 权重敏感性表怎么读

表有三块列：

```text
分量列      Cmax / ΣT / setup            —— 由 objective_breakdown 从排程反算
两种加权和   原始加权和 / 归一化加权和     —— 前者是报告值，后者是模型最小化的对象
状态列      模型状态（求解器原话）        —— 归一化口径下报告状态会被降级（Day 3）
```

三种口径的分母：

```text
none      (1, 1, 1)          不归一化
trivial   (50, 115, 32)      平凡上界，不求解就能算
ideal     (9, 2, 1)          三个单目标最优值，必须先解三个模型
```

**关键**：口径决定的是**交换率**。归一化后「1 单位 `ΣT`」值「`d_cmax / d_ΣT` 单位 `Cmax`」：

```text
none      1 / 1       = 1
trivial   50 / 115    = 0.4348
ideal     9 / 2       = 4.5
```

于是同一个 `β = 0.25` 在 `none` 口径下还没到翻转点（选 `S1`），
在 `ideal` 口径下已经翻过去了（选 `S2`）。**两组分母在说两件不同的事**，
没有哪一组是「客观正确」的。

### 4.2 八条结论各自的证据

| 结论 | 证据 |
|---|---|
| 换型是顺序相关的相邻间隔，不是工序的固有属性 | Day 4：相邻对 `3` vs 任意前后对 `6` |
| 单机上 `Cmax = Σp + Σsetup`，两目标必然同向 | Day 4：`6 + 3 = 9 = Cmax` |
| 日历要先扣维护再判「放得下」 | Day 5：`Y` 要 6 分钟，`[0, 5)` 被筛掉 |
| 两条日历编码可行集相同、规模不同 | Day 5：`11/20` vs `7/12`，同解 |
| 归一化口径决定 `β*`（交换率） | 本节：`1.0000` / `2.3000` / `0.2222` |
| 单目标最优解可能被多目标解**支配** | Day 6：`(63, 67, 3)` vs `(63, 55, 3)` |
| 目标值相等时排程不唯一 | Day 6：`setup` 都是 `2`，`Cmax` `14` vs `19` |
| `ideal` 口径在 `min setup = 0` 时不可用 | 驱动 `report.md`：唯一分母为 0 的边界 |

每一行的数字都能在本周的脚本里重现，没有一个是估的。

### 4.3 五条留白

```text
1. 换型矩阵只测了 2x2；真实车间的族数决定矩阵是几十乘几十，需要按实例生成。
2. 权重只扫了 6 组、实例只有 2 个；口径的影响还需要更多实例才敢下一般性结论。
3. 归一化只实现了一种线性口径（各自除以一个常数）；非线性口径没实现也没测。
4. `total_tardiness` 是不带订单权重的；`Job.weight` 目前只进 `weighted_tardiness`。
5. 驱动在 `plant_batch` 上的 `ideal` 口径整列跳过，只证明了「跳过是对的」，没给替代方案。
```

每一条都指出了下一步该改哪个函数、哪张表：第 1 条改实例生成器，
第 2 条改实验规模，第 3 条改 `Normalization`，第 4 条改目标表达式，
第 5 条改驱动对理想点的处理。**把留白写清楚，比含糊地宣布「模型已完整」有用。**

## 5. 手算：把表里的几行重算一遍

### 5.1 原始加权和

取 `none` 口径的 `balanced`（`α = β = γ = 1`，排程 `(9, 9, 2)`）：

```text
1 × 9 + 1 × 9 + 1 × 2 = 20.00        <- 与表里的 20.00 一致
```

取 `none` 口径的 `tardiness_light`（`α = 1, β = 0.25, γ = 0`，排程仍是 `(9, 9, 2)`）：

```text
1 × 9 + 0.25 × 9 + 0 × 2 = 9 + 2.25 = 11.25     <- 与表里的 11.25 一致
```

取 `none` 口径的 `tardiness_heavy`（`α = 1, β = 4, γ = 0`，排程换成 `(16, 2, 9)`）：

```text
1 × 16 + 4 × 2 + 0 × 9 = 16 + 8 = 24.00         <- 与表里的 24.00 一致
```

### 5.2 归一化加权和

同一行在三种口径下会得到三个不同的归一化值，分母各不相同：

```text
cmax_only (9, 9, 2):
  none     9/1   + 0×9/1   + 0×2/1   = 9.0000     <- 表里 9.0000
  trivial  9/50  + 0×9/115 + 0×2/32  = 0.1800     <- 表里 0.1800
  ideal    9/9   + 0×9/2   + 0×2/1   = 1.0000     <- 表里 1.0000

tardiness_light (none/trivial 下是 (9, 9, 2)，ideal 下是 (16, 2, 9)):
  trivial  9/50 + 0.25×9/115 + 0 = 0.18 + 0.019565 = 0.1996    <- 表里 0.1996
  ideal    16/9 + 0.25×2/2   + 0 = 1.7778 + 0.25   = 2.0278    <- 表里 2.0278

balanced (none/trivial 下是 (9, 9, 2)，ideal 下是 (13, 9, 1)):
  trivial  9/50 + 9/115 + 2/32 = 0.18 + 0.078261 + 0.0625 = 0.3208   <- 表里 0.3208
  ideal    13/9 + 9/2   + 1/1  = 1.4444 + 4.5 + 1        = 6.9444   <- 表里 6.9444
```

**七个数逐位对上。** 这一步值得单独做，因为脚本只校验了**原始**加权和
（打印的「最大偏差 = 0.0e+00」是这一项的）；归一化那一列没有自动校验，
它靠的就是这种手算。

### 5.3 翻转点

`cmax_only` 与 `tardiness_heavy` 两条排程的差额是 `ΔCmax = +7`、`ΔΣT = -7`（大小相等），
令加权和相等：

```text
none      β* = d_ΣT / d_cmax = 1 / 1     = 1.0000
trivial   β* = 115 / 50                  = 2.3000
ideal     β* = 2 / 9                     = 0.2222
```

与表里第 7 节第四块的三行逐位一致。

```text
  把这些留白写清楚，比含糊地宣布「模型已完整」有用：
  上面每一条都指出了下一步该改哪个函数、哪张表。
```

### 7.1 这张输出里值得逐行看的五处

**第一处：能力表的「验证器标签」列。** 每一行约束都对应一个**独立的**检查：
`release`、`overlap`（换型间隔不够时）、`calendar` / `maintenance`。
标签的意义在于：排程被否掉时，你立刻知道是哪一类约束被违反，
也就知道该改模型还是改实例。

**第二处：`min Cmax = 9.0`、`min ΣT = 2.0`、`min setup = 1.0` 三个值。**
它们既是 `ideal` 口径的分母，也是**下界的参考**：
任何排程的 `Cmax` 不可能低于 9，任何排程的 `ΣT` 不可能低于 2。
表里后面 `tardiness_only` 那一行的 `ΣT = 2` 正好贴着下界。

**第三处：`none` 口径下「原始加权和」与「归一化加权和」两列完全相同。**
因为三个分母都是 1。这是自检位：不相等说明分母被动过。

**第四处：`trivial` 口径下所有归一化值都 `< 1`，`ideal` 口径下都 `>= 1`。**
前者是上界分母（分量除以它不超过 1），后者是下界分母（不小于 1）。
两句话都能从定义直接推出来，输出与定义一致。

**第五处：`ideal` 口径的 `balanced` 那一行换了排程。**
`none` 与 `trivial` 都选 `(9, 9, 2)`，`ideal` 换成 `(13, 9, 1)`：
多花 4 分钟 `Cmax`（值 `4/9 = 0.4444`）换回 1 分钟 `setup`（值 `1/1 = 1.0000`），
在 `ideal` 口径下划算。**这不是求解器不稳定，是两组分母在说两件事。**

### 7.2 本日实验的四条结论

1. **能力表把「模型能做什么」变成一张可查的表**：四条约束面、
   对应的模型与验证器标签，一行一条。
2. **18 行的表逐行可核**：原始加权和的最大偏差是 `0.0e+00`；
   归一化那一列也在第 5.2 节被手算逐位对上。
3. **口径决定交换率**：`β* = 1.0000 / 2.3000 / 0.2222`，
   同一个 `β = 0.25` 在 `none` 下选 `S1`、在 `ideal` 下选 `S2`。
4. **结论必须挂证据、留白必须指方向**：八条结论各有出处，五条留白各指一个函数或一张表。

## 10. 自测题

- Q1：这一周加进来的四条约束面各是什么？哪一条不新增硬约束？
- Q2：`ideal` 口径的 `(9, 2, 1)` 是从哪来的？为什么必须先解三个模型？
- Q3：`trivial` 口径的 `(50, 115, 32)` 里，哪个数是「完全串行」的完工时间？
- Q4：为什么 `none` 口径下「原始加权和」与「归一化加权和」两列相同？
- Q5：同一个 `β = 0.25` 在两种口径下选出不同排程。哪一个是错的？
- Q6：`min setup = 0` 时 `ideal` 口径为什么不可用？驱动的处理是什么？
- Q7：`fjsp_cpsat_setup` 与 `fjsp_cpsat_calendar` 的两个 `Cmax` 必须相等吗？为什么？
- Q8：八条结论里哪一条是**反直觉**的？它的证据是什么？
- Q9：五条留白里哪一条是「方法本身的边界」，哪一条只是「投入不够」？
- Q10：如果要给这份总结再加一条结论，你会先补哪个实验？

### 参考答案

- A1：释放时间与交期（Day 1）、加权多目标（Day 2～3）、`sequence-dependent setup`（Day 4）、
  日历与维护（Day 5）。第一条（订单的时间属性）不新增硬约束——
  它只改目标函数和起点域，不改变「谁先谁后」的可行集。
- A2：它们是实例 `T` 上三个单目标模型的最优值：`min Cmax = 9`、`min ΣT = 2`、
  `min setup = 1`，而且每个都必须是 `OPTIMAL` 才敢用。
  必须先解三个模型是因为「理想点」的定义就是各分量的最优值。
- A3：`50`。它等于「释放时间最大值 + 各工序最长工时的总和 + 换型上限 + 1」，
  也就是「完全串行加工」的完工时间上界。
- A4：因为 `none` 的三个分母都是 `1`，除以 1 不改变数值。
  这也可以当自检位：不相等说明分母被动了手脚。
- A5：都不是错的。两种口径隐含两种交换率（`1` 与 `4.5`），
  不同的定价自然可能选出不同的排程。要说谁「对」，
  先得回答业务问题：1 分钟迟交值多少分钟完工时间。
- A6：因为理想点归一化要求分母是正数，而 `min setup = 0` 让分母为 0。
  驱动没有用别的数顶替，而是把那一整列标成 `SKIPPED`。
  这是方法的固有边界，不是可以靠加时间预算修好的问题。
- A7：必须相等。它们共用同一份几何（可用区段 → `fitting_windows` → `starting_domain`），
  可行集相同，所以最优值必须相同。Day 5 的 `11/20` 与 `7/12`、
  Day 6 的 `348/411` 与 `298/292` 都是同解不同规模。
- A8：「单目标最优解可能被多目标解支配」最反直觉——
  直觉上「最优」应当不劣于任何解，但 `min Cmax` 的 `(63, 67, 3)`
  被等权模型的 `(63, 55, 3)` 支配（`ΣT` 少 12 分钟）。
  原因是 `Cmax` 最小的排程有多条，模型没有义务在并列解里挑最好的。
- A9：「`ideal` 口径在 `min setup = 0` 时不可用」是方法本身的边界（除以 0 无定义）；
  「权重只扫了 6 组、实例只有 2 个」只是投入不够，加大实验规模就能改进。
  两者要分开说，因为一个要换方法、另一个只要加时间。
- A10：优先补「理想点归一化里分母为 0 的替代方案」——
  它已经有真实的失败场景（`plant_batch` 的 `setup` 分量），
  而且可以用现成的实例验证：把 `d_setup` 换成另一个正数分母（例如 1），
  看排程会不会变、以及变的方向是否符合「换了一组定价」的解释。
