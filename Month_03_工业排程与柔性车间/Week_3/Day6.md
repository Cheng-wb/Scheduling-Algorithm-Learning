## 2. 为什么要把模型放到同一个实例上比

前面五天，每个模型只解决一个问题：Day 1 加释放时间与交期，Day 2 加加权多目标，

```text
边界    哪些模型根本不认识这个实例？它怎么告诉你？

质量    同一个目标值，返回的排程是不是一样好？
```

再加一件事：**不可行的时候，谁告诉你为什么**。

## 3. 定义：边界、可诊断的失败、规模、支配、退化

**定义（模型边界）**：一个方法**声明**支持哪些约束。超出边界的实例应当被拒绝，
而不是被「尽力处理」。

**定义（可诊断的失败）**：失败时给出的信息足以让调用方决定下一步做什么。
`ValueError: ... unsupported constraints: calendars, maintenances, setups`
是可诊断的——它点名了不认识的约束。

**定义（模型规模）**：`detail["model_size"]` 里的变量数与约束数。
它们是模型的**描述**，不是它的难度。

**定义（支配）**：若排程 `S'` 在三个分量上都不劣于 `S` 且至少一个严格更好，
称 `S'` 支配 `S`，`S` 是被支配的。

**定义（目标退化）**：目标函数在**所有**可行解上取值相同（或取值与决策无关）时，
称目标退化。此时求解器仍会返回一个 `OPTIMAL`，但「最优」这个词对排程没有约束力。

**定义（两类 `INFEASIBLE`）**：

```text
建模期判死    开始搜索之前，几何上就没有合法时间线可建
              detail["failure_reason"] 有具体内容
搜索期证明   模型建起来了，但约束之间没有共同可行解
              detail["failure_reason"] 为空
```

## 4. 推导：三条必须分开定位的机制

### 4.1 为什么拒收比静默放行诚实

假设一个模型不认识换型，却「尽力」给一条排程：它会输出一条不付换型时间的顺序。
这条排程在它自己的模型里最优，在**真实车间**里却是错的——机器需要额外的换型时间，
而这条排程里没有。后果分两级：

```text
拒收      benchmark 记一条 FAILED（没做成），调用方换模型
静默放行   benchmark 记一条 INVALID_SOLUTION（求解器给了不合法解）——比 FAILED 更严重
```

**理论结论 1**：「求解器给出了一个不合法解」比「求解器没做出来」更坏，
因为它把建模缺口伪装成了结果。所以边界必须在**算之前**声明，
理由按实例里实际出现的约束逐条列出（没出现的约束不进消息）。

### 4.2 规模不是耗时的代理

规模大意味着搜索树更大，但 CP-SAT 的耗时还取决于传播强度、
分支决策、约束之间的耦合程度。`G201` 上两条编码给出同一个可行集：

```text
编码       变量    约束    Cmax     求解耗时
blocker   298    292     63      0.33 s
split     348    411     63      0.19 s
```

**理论结论 2**：`split` 的模型大三成，却解得快。
这不是「越大越快」的规律——它只说明**规模描述不足以预测耗时**。
`split` 每个候选窗一个布尔变量，窗越多变量越多；
`blocker` 用起点域加停机区间，变量数不随窗数增长。
两者描述的是同一个可行集（Day 5 第 4.1 节），所以 `Cmax` 必须相等。

### 4.3 单目标最优解可能被支配

设 `S*` 是 `min Cmax` 的一个最优解，`S'` 是加权和解。若

```text
Cmax(S') = Cmax(S*)      两个解在 Cmax 上并列最优
ΣT(S') < ΣT(S*)          但 S' 的迟交更少
setup(S') = setup(S*)    setup 也一样
```

那么 `S'` 支配 `S*`。这不矛盾：

```text
Cmax 最小的排程**有多条**（Day 2 第 4.3 节、Day 4 第 5.1 节都见过并列）
min Cmax 的模型只被要求把 Cmax 压到最小值
它没有义务在并列解里挑 ΣT 最小的那一条
```

**理论结论 3（目标没写的量，模型不会替你优化）**：单目标模型的返回值
只对它自己那一项负责。想拿到等权意义下最好的排程，就把三个分量写进同一个目标；
只跑单目标，就要接受并列解里可能挑到差的那一条。

### 4.4 目标退化

`D6` 的两个换型方向都是 2 分钟。于是无论 `A` 在前还是 `B` 在前，`M0` 上的换型都是 2：

```text
顺序 A -> B：Setup(F0, F1) = 2
顺序 B -> A：Setup(F1, F0) = 2
```

**理论结论 4**：目标退化的实例上，`min setup` 对顺序没有任何偏好，
所有顺序的目标值都是 2。此时 `OPTIMAL` 只说明「找到了一条满足目标的排程」，
不说明任何关于顺序的信息。两条目标值相同、质量不同的排程会同时是「最优解」。

### 4.5 两类不可行的分界

```text
几何上无解：某道工序在所有机器上都没有装得下它的窗
          -> 建模期判死，failure_reason = "operation Z fits in no allowed window"
约束冲突  ：单独看都放得下，合起来没有共同可行解
          -> 搜索期证明，failure_reason 为空
```

**理论结论 5**：两类要修的地方不同——前者放宽日历或换机器（改**实例**），
后者加窗、提前释放时间或加机器（改**约束**）。
把两者混成一句「无解」，就丢掉了「该改哪里」这个决策信息。

## 5. 手算：`D6` 的下界与两条排程

### 5.1 `D6` 的 `min Cmax = 13`

```text
工序    机器    工时    族    交期
A      M0     4     F0     8
B      M0     3     F1     6
C      M1     5     F0    20
M0 可用区段 ((0, 6), (10, 30))      <- 日历 ((0, 7), (10, 30)) 被维护窗 (6, 10) 削过
换型：F0 <-> F1 各 2 分钟
```

`M0` 上的工作量：`A` 4 分钟 + `B` 3 分钟 + 一次换型 2 分钟 = 9 分钟。
第一段可用区段只有 6 分钟，装不下 9 分钟，所以**至少有一道工序要放进第二段**：

```text
下界：Cmax >= 10 + min(4, 3) = 13        （放 B 进第二段，只需 3 分钟）
方案：A[0, 4) 换型2 B[10, 13)，C[0, 5) 在 M1     -> Cmax = 13
```

下界与方案相等，所以 `13` 是最优值。求解器报的也是 `13`，
`breakdown = {'cmax': 13.0, 'total_tardiness': 7.0, 'setup': 2.0}`。

注意 `ΣT = 7`：`B` 在 13 点完工、交期 6，迟交 7 分钟。**`min Cmax` 的模型
并不介意这 7 分钟**——这正是 4.3 节那条结论的最小例子。

### 5.2 退化目标下的两条排程

目标换成 `total_setup_time`（两个方向都是 2，目标退化）：

```text
blocker  B[0, 3)  C[0, 5)  A[10, 14)     Cmax 14   ΣT 6    setup 2
split    C[0, 5)  B[10, 13)  A[15, 19)   Cmax 19   ΣT 18   setup 2
```

逐项手算第一条：

```text
M0 的顺序是 B 然后 A：B 是 F1、A 是 F0 -> 换型 2 分钟
B[0, 3) 落在第一段 (0, 6) 里，A[10, 14) 落在第二段 (10, 30) 里，都合法
Cmax  = max(14, 5) = 14
ΣT    = (14-8)^+ + (3-6)^+ + (5-20)^+ = 6 + 0 + 0 = 6
setup = 2
```

第二条：

```text
M0 的顺序是 B 然后 A，但两道都挤进第二段：B[10, 13)、A[15, 19)
中间那 2 分钟换型正好垫在 [13, 15)
Cmax  = max(19, 5) = 19
ΣT    = (19-8)^+ + (13-6)^+ + (5-20)^+ = 11 + 7 + 0 = 18
setup = 2
```

两条的 `setup` 都是 2（目标值相同），但 `ΣT` 差了 12 分钟、`Cmax` 差了 5 分钟。
**目标值相等时排程不唯一**，谁被返回由搜索路径决定。

## 6. 实现：边界怎么声明、`detail` 里有什么

**边界的声明**在 [fjsp.py](../../projects/03_industrial_fjsp/fjsp_shop/fjsp.py) 的
`require_plain_fjsp`：

```python
reasons: list[str] = []
if instance.calendars:
    reasons.append("calendars")
if instance.maintenances:
    reasons.append("maintenances")
if instance.setups:
    reasons.append("setups")
...
if reasons:
    raise ValueError(
        "plain FJSP only (release times are supported); unsupported constraints: "
        + ", ".join(reasons)
    )
```

两条纪律：

1. **按实例里实际出现的约束逐条列出**。消息只点名真实存在的约束，
   所以调用方能一次看懂「换个什么模型就够」。
2. **在算之前拒绝**。解码器一旦丢掉换型或日历，产出的排程一定过不了独立验证器；
   与其让 benchmark 记一条 `INVALID_SOLUTION`（求解器给出了不合法解），
   不如在这里带原因拒绝。

**`detail` 里与本日相关的四个字段**：

```text
model_size         {"variables": …, "constraints": …}，规模描述
calendar_mode      本次用的日历编码（"split" / "blocker"）
failure_reason     建模期判死的具体原因；搜索期不可行时为空
model_status       求解器的原话；报告状态被降级时（Day 3）它与 status 不同
```

`model_size` 是**描述**不是**预测**：它解释「模型长什么样」，
不解释「要解多久」。把它当成耗时的代理，就会在 Day 6 第二件事上得出错误结论。

### 7.1 这张输出里值得逐行看的六处

**第一处：三条拒收消息一字不差。** 三个上一代模型给的是**同一条**消息，
因为它来自同一个检查函数 `require_plain_fjsp`，按实例里实际出现的约束逐条列出。
消息里点名了 `calendars, maintenances, setups`——调用方据此知道
「换成 `fjsp_cpsat_setup` 或 `fjsp_cpsat_calendar` 就够」。

**第二处：规模与耗时的两行。** `298/292` 对 `348/411`，耗时 `0.33` 对 `0.19`。
模型大的一方反而快：这与「规模越大越慢」的直觉相反，所以脚本把结论限定成
「本次实例的实测，不是普遍规律」。（求解耗时列是墙钟时间，同一台机器上重跑
会在几分之一秒的范围内浮动；**变量数与约束数是确定性的，不会浮动**。）

**第三处：等权加和的排序。** `121 < 128 < 133 < 242`——
等权模型比三个单目标模型**都**好。这不是巧合：等权模型最小化的是那一列本身，
另外三行最小化的是别的函数。把三个分量按同一种权重加起来再排序，
等权模型必然排在前面。

**第四处：`(63, 67, 3)` 与 `(63, 55, 3)`。** 两行的 `Cmax` 与 `setup` 完全相同，
`ΣT` 差 12 分钟。这不是求解器出错，而是**并列解**的必然结果：
`Cmax = 63` 的最优排程有多条，`min Cmax` 的模型没有义务在它们之间挑。
一行数据就说明了「目标没写的量，模型不会替你优化」。

**第五处：`D6` 两行的 `目标值` 都是 `2`。** 换型矩阵两个方向都是 2 分钟，
目标退化了，所以顺序对目标值没有影响。两行都是 `OPTIMAL`——
但 `ΣT` 差了 12 分钟。**`OPTIMAL` 这个词只对目标函数负责**，
不对排程质量负责。

**第六处：四种不可行情形的两行分类。** 只有第一条有具体原因
（`operation Z fits in no allowed window`），另两条的原因是空的。
空不等于「不知道为什么」——它表示这次失败**不是建模期判死的**，
而是搜索期证明的。脚本还把它们的**具体机制**写在了下面：
释放时间那条是 `release = 10` 与窗 `(0, 5)` 交集为空；
窗总长那条是两道工序争同一段窗。最后一条是边界对照：
释放时间 `12` 落在第二个窗里，题目**可行**。

### 7.2 本日实验的四条结论

1. **模型边界是可诊断的**：三个上一代模型拒收同一个实例，
   拒收消息点名 `calendars, maintenances, setups`，调用方据此换模型。
2. **规模不是耗时的预测**：`split` 大三成、`0.19` 秒；`blocker` 小三成、`0.33` 秒。
   两条编码的 `Cmax` 都是 `63`（同一个可行集，见 Day 5 第 4.1 节）。
3. **单目标最优解可能被支配**：`min Cmax` 给出 `(63, 67, 3)`，
   等权模型给出 `(63, 55, 3)`——同样的 `Cmax` 与 `setup`，少 12 分钟迟交。
4. **不可行要分两类**：建模期判死（有 `failure_reason`）与搜索期证明（空）。
   前者改实例，后者改约束。

## 10. 自测题

- Q1：为什么 `fjsp_cpsat` 会拒收带日历的实例？它拒收时给出的是什么？
- Q2：拒收消息里为什么只列实例里**实际出现**的约束？
- Q3：`split` 的模型更大却更快。能不能得出「模型越大越快」的结论？
- Q4：`min Cmax` 给出 `(63, 67, 3)`，等权模型给出 `(63, 55, 3)`。后者支配前者吗？
- Q5：为什么 `min Cmax` 的模型不顺手把 `ΣT` 也压小？
- Q6：`D6` 上 `min setup` 的目标值两条都是 2。这说明两条排程一样好吗？
- Q7：`min setup` 的两条排程都是 `OPTIMAL`，能不能说「求解器认为它们一样好」？
- Q8：`release = 10` 与窗 `(0, 5)` 为什么判 `INFEASIBLE`？是建模期还是搜索期？
- Q9：同样报 `INFEASIBLE`，为什么有的有 `failure_reason`、有的是空的？
- Q10：`model_size` 里的变量数能用来预测耗时吗？如果要用它做什么，该怎么用？

### 参考答案

- A1：因为它的解码器不认识日历，会输出一条跨过停机段的排程，
  而那条排程过不了独立验证器。拒收时抛 `ValueError`，
  消息里列举它不支持的约束（`calendars, maintenances, setups`），
  调用方据此换模型。
- A2：因为「不支持哪些约束」是一句话，而「这个实例里有哪些约束是我不支持的」
  才是调用方能行动的信息。列全固定清单会让消息变长且与当前实例无关。
- A3：不能。这只是本次实例上的一次实测：模型大小描述的是**结构**，
  耗时还取决于传播强度、分支决策与约束耦合。脚本自己把结论限定为
  「本次实例的实测，不是普遍规律」。
- A4：是。两者 `Cmax` 相同、`setup` 相同，而 `ΣT` 少 12 分钟，
  满足「都不劣且至少一个严格更好」。
- A5：因为模型只被要求最小化 `Cmax`。`Cmax = 63` 的最优排程有多条，
  模型对它们一视同仁；挑哪一条由搜索路径决定。
  **要让 `ΣT` 变小，就得把 `ΣT` 写进目标。**
- A6：不说明。目标退化（两个方向的换型都是 2 分钟）意味着所有顺序的目标值都是 2，
  目标函数对顺序没有偏好。两条的 `Cmax`（14 与 19）与 `ΣT`（6 与 18）完全不同。
- A7：不能。`OPTIMAL` 只说明「在目标函数这个口径下已证明最优」，
  不说明两条排程在别的口径下也一样好。质量差异要靠 `breakdown` 的三个分量来看。
- A8：因为工序虽然在窗里放得下，但释放时间 10 晚于窗的末端 5，
  两者的交集为空，没有任何合法的开工时刻。这是**搜索期**证明的
  （模型能建起来，是约束之间没有公共解），所以 `failure_reason` 是空的。
- A9：因为 `failure_reason` 只记录**建模期**判死的原因（几何上就没有合法时间线）。
  搜索期证明的不可行没有这样的几何原因，硬填一个就会把两类混淆。
- A10：不能直接用来预测耗时。它可以用来做**同口径的相对比较**：
  同一个实例上两种编码的规模差异（例如 `348` 对 `298`）说明
  「哪条编码的窗变量在涨」，但耗时仍要实测。

## 11. 今日一句话总结

> **把模型放到同一个实例上比，才能分出边界、规模与质量三件事**：
> 三个上一代模型拒收 `D6` 并点名 `calendars, maintenances, setups`（可诊断的失败）；
> `G201` 上 `blocker` 的 `298/292` 比 `split` 的 `348/411` 小而慢（`0.33` 对 `0.19` 秒）、
> 两者 `Cmax` 都是 `63`——**规模是描述，不是耗时的预测**；
> 最扎眼的是 `min Cmax` 返回的 `(63, 67, 3)` 被等权模型的 `(63, 55, 3)` 支配
> （`Cmax` 与 `setup` 相同、`ΣT` 少 12 分钟），因为**目标没写的量，模型不会替你优化**；
> 而 `INFEASIBLE` 必须分成建模期判死（有 `failure_reason`）与搜索期证明（为空）两类，
> 它们的修法完全不同。
