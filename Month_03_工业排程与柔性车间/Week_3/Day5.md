## 2. 为什么机器会「不在」

Day 1 到 Day 4 的模型里，机器一旦存在就永远可用：`A[0, 100)` 就是把机器占满 100 分钟，
没人会问「这 100 分钟里机器是不是该休息」。真实车间不是这样：

```text
班次          早班 8:00-12:00、午休、晚班 13:00-17:00     —— 每天都在重复
检修          周六 9:00-11:00 换刀具、校精度              —— 计划好的、必须发生
```

两类事有共同点：**机器在这段时间里物理上不可用**，而且**不可用区间与别的工序无关**。
这和 Day 4 的换型不同——换型是相邻两道工序之间的事，而日历与维护
只由车间自己的时间表决定。

把它们建成一个约束，就是「工序区间必须整体落在某一个可用区段内」：

```text
允许：X[0, 4)   落在 [0, 5) 里
不允许：X[3, 7)  跨过 5 点，机器在 5 点到 10 点之间不在
```

## 3. 定义：日历窗、维护窗、可用区段

**定义（`calendar` 日历窗）**：机器可用的时间区间集合，例如 `((0, 5), (10, 20))`。
空集合表示「无约束」（不排班次的机器）。

**定义（`maintenance` 维护窗）**：机器不可用的时间区间集合，
由检修计划给出，例如 `((5, 10),)`。

**定义（可用区段）**：`allowed_windows(instance, machine_id, horizon)` 把两者合成一份：

```text
基准 = 日历窗，若为空则取 ((0, horizon))
可用区段 = 基准 逐段扣掉维护窗
```

**定义（装得下 / 起点域）**：

```text
fitting_windows(可用区段, duration)   = 长度 >= duration 的区段
starting_domain(可用区段, duration)   = {(lo, hi - duration)}，即「[s, s+duration) 落在某段里」的 s 区间并
```

**理论结论 1（先扣维护，再判放得下）**：判定顺序不能反。
先判「`[0, 5)` 装得下 6 分钟的工序」得到「否」，再去看维护——这没错；
但先判「工序能在 0 点开工」，再去看维护——就会得出「0 到 6 点可用」，
而机器在 5 点已经停机了。**维护窗必须先参与几何计算，然后才轮到长度判断**。

**理论结论 2（维护窗可能被日历窗蕴含）**：如果某段维护窗完全落在日历的缝隙里，
它就被日历约束蕴含了——加上它不会改变可行集，也不会改变最优值。
这类「加了约束但什么都没变」的情形必须明确说出来，否则读者会把功劳记到它头上。

**理论结论 3（半开区间语义）**：所有区间都是 `[start, end)`。
于是 `end = 10` 与维护窗 `(5, 10)` 没有公共点，**贴边不算重叠**。
这条规则与工序之间的不重叠用的是同一套语义，没有例外。

## 4. 推导：两条编码为什么必然同解

### 4.1 两份几何

`industrial.py` 里两条日历编码的区别只在**表达方式**：

```text
split    每个 (工序, 机器, 可用窗) 一个布尔变量，配 AddExactlyOne；
         区间端点由窗的字面量约束：start >= lo、end <= hi
blocker  起点域限制：Domain.FromIntervals([[lo, hi - duration]])；
         把不可用区间做成 NewFixedSizeIntervalVar 塞进同一个 AddNoOverlap
```

两条编码**共用**同一份几何：`allowed_windows` → `fitting_windows` → `starting_domain`，
以及 `_forbidden_windows`（`[0, horizon]` 内不在任何可用窗里的部分）。
所以：

**理论结论 4（同解不是巧合）**：「`[s, s+duration)` 落在某个可用段内」
这件事只有一种几何表达，两条编码只是把同一个集合写成两种 CP-SAT 变量形式。
**几何算错了两条会一起错，算对了必然同解。**
规模可以不同：`split` 每个候选窗一个变量，窗越多变量越多；
`blocker` 只用起点域加停机区间，变量数**不随窗数增长**。
`tests/test_week3.py::test_calendar_encodings_agree` 断言的就是「同解」这件事。

### 4.2 「停机间隔」与「等待间隔」不是一回事

两者的时间线看着都像空白，语义完全不同：

```text
等待    machine 可用但没活干     —— 排得再紧一点就能消掉
停机    machine 不可用           —— 与排程无关，消不掉，只能绕开
```

这在目标函数上表现为：等待不进任何分量，停机则会把 `Cmax` 顶高。
`C1b` 里 `Y` 从 10 点开工、`Cmax = 16`，其中 5 到 10 那 5 分钟不是它「等」来的，
是机器不在。

### 4.3 手算判据：什么时候必须跨段

一道 `duration` 的工序在某个可用段 `(lo, hi)` 里放得下，当且仅当 `hi - lo >= duration`。
于是「这道工序会不会被推到第二段」有一个立刻可算的判据：

```text
存在装得下的段  <=>  该工序的 starting_domain 非空
```

`C1a` 里两段是 `(0, 5)` 与 `(10, 20)`，`X` 要 4 分钟、`Y` 要 3 分钟，
两段都装得下两者；`C1b` 里 `Y` 要 6 分钟，`(0, 5)` 长度只有 5，**第一段被筛掉**。

## 5. 手算：三个实例

### 5.1 `C1a`：两段日历 + 维护

```text
日历窗 ((0, 5), (10, 20))   维护 ((5, 10),)
可用区段 = (0, 5), (10, 20)          （维护窗正好落在两段之间，见 5.4）
X 要 4 分钟：装得下的段 = (0, 5), (10, 20)
Y 要 3 分钟：装得下的段 = (0, 5), (10, 20)
```

两道工序都要占机器，而 `(0, 5)` 只有 5 分钟，装不下 `4 + 3 = 7` 分钟。
所以**至少有一道必须放进第二段**，即它的完工时刻 `>= 10 + min(4, 3) = 13`：

```text
下界：Cmax >= 13
方案：X[0, 4)，Y[10, 13)        -> Cmax = 13
```

下界与方案相等，所以 `13` 是最优值。求解器报的 `objective=13`、
`breakdown={'cmax': 13.0, 'total_tardiness': 0.0, 'setup': 0.0}` 与手算一致。

### 5.2 `C1b`：整段日历 + 同一份维护

```text
日历窗 ((0, 20),)           维护 ((5, 10),)
可用区段 = (0, 5), (10, 20)          （这次维护是真的在削日历）
X 要 4 分钟：装得下的段 = (0, 5), (10, 20)
Y 要 6 分钟：装得下的段 = (10, 20)    <- (0, 5) 只有 5 分钟，被筛掉
```

`Y` 的起点域变成 `(10, 14)`（`10` 到 `20 - 6`），所以

```text
下界：Cmax >= 10 + 6 = 16
方案：X[0, 4)，Y[10, 16)        -> Cmax = 16
```

求解器报 `objective=16`，与手算一致。

### 5.3 `C1c`：11 分钟的工序

```text
日历窗 ((0, 5), (10, 20))   维护 ()
可用区段 = (0, 5), (10, 20)
Z 要 11 分钟：装得下的段 = ()         <- 5 < 11 且 10 < 11
起点域 = ()
```

起点域是空的，模型里没有一条合法的时间线可建，所以判 `INFEASIBLE`，
`detail["failure_reason"]` 是 `operation Z fits in no allowed window`。
**这不是「搜索没找到」，是「问题本身没有可行解」**——两者在验收表上必须能分开，
因为补救措施完全不同（前者加时间预算，后者加窗或换机器）。

### 5.4 `C1a` 里的维护窗是冗余的

把 `C1a` 的可用区段和日历窗并排看：

```text
日历窗     ((0, 5), (10, 20))
可用区段   ((0, 5), (10, 20))     <- 与日历窗逐段相同
```

维护窗 `(5, 10)` 正好落在两段日历之间的缝隙里，所以它**被日历约束蕴含**了：
任何满足日历的排程都不可能碰到它。结论要如实说：

```text
C1a 上「加维护」没有改变可行集，也没有改变最优值 Cmax = 13。
```

它仍然会在验证器上独立报警（第 7 节的 `[6, 9)` 同时踩两条），
但那是「两条约束都被违反」，不是「两条约束各自起了作用」。
真正让维护参与几何计算的是 `C1b`：日历改成整段 `(0, 20)` 之后，
维护窗把 `(0, 20)` 削成了 `(0, 5)` 与 `(10, 20)`，`Y` 的第一段就是这样被筛掉的。
**一个被蕴含的约束不会让模型变难，也不该被当成证据。**

## 6. 实现：扣减、筛选、两条编码

`allowed_windows` 的扣减是逐段裁剪：

```python
calendar = instance.calendar_window(machine_id)
base: tuple[tuple[int, int], ...] = calendar if calendar else ((0, horizon),)
blocked = instance.maintenance_windows(machine_id)
segments: list[tuple[int, int]] = []
for lo, hi in base:
    pieces = [(max(lo, 0), min(hi, horizon))]
    for blocked_lo, blocked_hi in blocked:
        kept: list[tuple[int, int]] = []
        for piece_lo, piece_hi in pieces:
            if blocked_hi <= piece_lo or piece_hi <= blocked_lo:
                kept.append((piece_lo, piece_hi))  # 不相交，原样保留
                continue
            if piece_lo < blocked_lo:
                kept.append((piece_lo, blocked_lo))
            if blocked_hi < piece_hi:
                kept.append((blocked_hi, piece_hi))
        pieces = kept
    segments.extend(pieces)
return tuple(sorted(item for item in segments if item[0] < item[1]))
```

四个细节：

1. **不相交时原样保留**（`blocked_hi <= piece_lo or piece_hi <= blocked_lo`）。
   用的是 `<=` 而不是 `<`，与半开区间语义一致：`end = 10` 与 `(5, 10)` 不算相交。
2. **相交时最多切成两片**。左片 `(piece_lo, blocked_lo)` 与右片 `(blocked_hi, piece_hi)`
   各自只在非空时才加入，所以「维护窗盖住整段」自然退化成空。
3. **最后清掉空段并排序**。空段（`lo >= hi`）留着会让 `starting_domain`
   算出 `lo > hi` 的区间，那类区间在 `Domain.FromIntervals` 里是另一个含义。
4. **为什么不让维护窗直接当「不可用区间」塞进 `AddNoOverlap`？**
   因为两条编码都需要同一份区段表；把它抽成唯一的一份几何计算，
   「模型里允许的」与「验证器接受的」就由同一段代码保证一致——
   不一致时验证器会立刻报 `calendar` / `maintenance`，而不是静默地放过。

`split` 侧用的是窗字面量（`start >= lo`、`end <= hi`），
`blocker` 侧用的是起点域加 `_forbidden_windows` 造出的 `NewFixedSizeIntervalVar`。
两边的**输入**都是同一个 `starting_domain` / `allowed_windows`。

### 7.1 这张输出里值得逐行看的五处

**第一处：`C1a` 的 `扣掉维护后的可用区段 = ((0, 5), (10, 20))` 与日历窗逐段相同。**
维护窗 `(5, 10)` 正好落在两段日历之间的缝隙里，**它是冗余的**（第 5.4 节）。
输出没有隐藏这一点：把两行并排看就能发现。凡是「加了约束但没改变任何东西」的地方
都要这样明说，而不是让读者以为维护在那里起了作用。

**第二处：`C1b` 里 `Y` 的 `装得下的窗 = ((10, 20),)`——第一段被筛掉了。**
`Y` 要 6 分钟，`(0, 5)` 只有 5 分钟。这一步筛选发生在**建模期**，
不是搜索期：`Y` 的起点域里根本没有 `(0, 1)` 这一段。
也正因为如此，`Y` 一旦被排到 `[10, 16)`，`Cmax` 的下界就是 16。

**第三处：四条手工排出的违规时间线，验证器给出的标签组合。**
`[4, 7)` 与 `[6, 9)` 报两条（既不在日历窗里、又和维护窗相交），
`C1b` 的 `[4, 10)` 只报 `maintenance`，而贴边开工的 `[10, 13)` 一条都不报。
**四条里有三条是「构造出来的错」，一条是「边界对照」**：
`end = 10` 与 `(5, 10)` 没有公共点，所以「贴着维护窗结束开工」是合法的。
如果验证器在这里报了错，说明它把半开区间当成了闭区间。

**第四处：两条编码的规模表。**

```text
实例    编码          变量    约束  Cmax
C1a   split         11    20     13
C1a   blocker        7    12     13
C1b   split         10    17     16
C1b   blocker        7    12     16
```

两行两两相等的是 `Cmax`，不是规模。`split` 的变量数随窗数变化
（`C1a` 有三段可用窗信息、`C1b` 有两段，所以 11 与 10 不同），
`blocker` 两次都是 7/12。**规模差是编码的差，不是可行集的差**——
这是第 4.1 节那条理论结论的实测。

**第五处：`C1c` 的 `起点域 = ()`。**
空起点域是 **建模期** 判死不可行的依据，所以 `failure_reason` 有具体内容
（`operation Z fits in no allowed window`），而不是一句「INFEASIBLE」。
与搜索期证明的 `INFEASIBLE` 对比：后者没有这条原因，
两者的补救措施也不同。

### 7.2 本日实验的三条结论

1. **日历要先把维护扣掉，再判「放得下」**：`C1b` 里 `Y` 要 6 分钟、
   `[0, 5)` 只有 5 分钟，所以它被筛掉；`C1a` 里 `Y` 只要 3 分钟，两段都留着。
2. **两条编码可行集相同、规模不同**：`11/20` 与 `7/12`（`C1a`）、`10/17` 与 `7/12`（`C1b`），
   四个 `Cmax` 两两相等。
3. **一个被蕴含的约束不会改变结果**：`C1a` 的维护窗落在日历缝隙里，
   加不加它都是 `Cmax = 13`——这是本日的空结果，如实报出。

## 10. 自测题

- Q1：`calendar` 为空集合时代表什么？为什么不是「机器不可用」？
- Q2：可用区段是怎么算出来的？能不能先把维护窗做成不可用区间、再让工序去避让？
- Q3：`C1a` 里 `Y` 从 4 点开工（`[4, 7)`）不行。它是被哪条约束拦住的？
- Q4：`C1b` 里 `Y` 要 6 分钟，为什么不能放 `(0, 5)`？是长度不够还是别的？
- Q5：`C1c` 的 `INFEASIBLE` 是建模期还是搜索期判定的？依据是什么？
- Q6：两条编码的变量数差了三成，为什么还能保证同解？
- Q7：`[10, 13)` 紧贴着维护窗 `(5, 10)` 开工，验证器为什么不报错？
- Q8：`C1a` 的维护窗是冗余的。那是不是说明「这个实例里维护不起作用」？
- Q9：报错标签是 `calendar` 还是 `maintenance`，对生产上的处理有什么不同？
- Q10：如果某台机器的日历窗都不够长，装不下某道工序，模型能做什么？

### 参考答案

- A1：代表**没有日历约束**，机器在整个 `[0, horizon]` 内都可用。
  如果它代表不可用，那任何一道工序都排不进去，模型只能报 `INFEASIBLE`——
  这与「没排班次的小车间」这种真实情形不符。
- A2：基准取日历窗（空则取 `((0, horizon))`），再逐段扣掉维护窗。
  「做成不可用区间让工序避让」是 `blocker` 编码的**手段**，但它用的区间表
  （`_forbidden_windows`）仍然是从同一份可用区段算出来的——
  几何只有一份，两条编码只是把它写成两种变量形式。
- A3：两条都拦：`[4, 7)` 不在任何一个日历窗里（`calendar: Y on M0`），
  又与维护窗 `(5, 10)` 相交（`maintenance: Y on M0`）。
  在这个实例上日历约束单独就能拦住它，维护只是「也报了」。
- A4：长度不够。`(0, 5)` 只有 5 分钟，`Y` 要 6 分钟，
  所以它落在 `fitting_windows` 的筛除条件 `hi - lo >= duration` 之外——
  这与维护无关，纯是几何。
- A5：建模期。依据是 `starting_domain` 算出来是空的（`起点域 = ()`），
  模型里没有一条合法的时间线可建，所以 `detail["failure_reason"]` 有具体内容。
- A6：因为两条编码的**输入**都是同一个 `starting_domain` / `allowed_windows`，
  它们只是把同一个集合写成两种 CP-SAT 形式。
  几何算错了两条会一起错（并被独立验证器抓到），算对了必然同解。
- A7：因为区间是半开的：`[start, end)` 中 `end = 10`，
  与 `(5, 10)` 的公共部分是空集。若验证器按闭区间比较，
  它会把「贴边」误判成重叠，从而否掉一条合法排程。
- A8：不是。它说明「在这份日历下，这条维护约束是多余的」，
  但维护窗本身仍然被验证器独立检查（`[6, 9)` 那条同时报了 `maintenance`）。
  正确的说法是：**它被日历蕴含了**——想知道维护真正起作用是什么样，
  看 `C1b`（日历整段 `(0, 20)`，维护把它削成两段）。
- A9：`calendar` 要去调班次或加班窗（车间的工作时间安排），
  `maintenance` 要去调检修计划（什么时候停下来修）。
  两件事的责任人通常都不是同一个人，所以标签必须分开。
- A10：模型只能报 `INFEASIBLE`。日历的硬度是**实例给的**，
  求解器不能自己决定加班或者改检修计划。
  生产上的两条出路是：加一次加班窗，或者把这单分到别的机器
  （后者要改工序的候选机器集合，属于建模层面的改动）。

## 11. 今日一句话总结

> **机器不是永远在**：`calendar` 划出机器可用的时段，`maintenance` 从中挖掉检修段，
> 两条合起来算成一份**可用区段**，然后才轮到「这道工序放不放得下」；
> `C1b` 里 `Y` 要 6 分钟、第一段只有 5 分钟，所以它的 `fitting_windows` 只剩 `(10, 20)`，
> 最优 `Cmax` 从 `C1a` 的 `13` 变成 `16`；`split` 与 `blocker` 两条编码共用这一份几何，
> 于是 `11/20` 与 `7/12` 两种规模给出同样的四个 `Cmax`；
> 而 `C1a` 的维护窗恰好落在日历缝隙里、**被日历蕴含**——加不加它都是 `13`，
> 这个空结果如实报出，比把它说成「维护起了作用」有用得多。
