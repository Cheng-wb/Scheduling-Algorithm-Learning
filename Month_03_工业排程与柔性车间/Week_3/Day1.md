## 2. 为什么今天要看订单的时间属性

Week 2 把 FJSP 的两维决策（选机、排序）写进了同一个 CP-SAT 模型，但那个模型里所有订单的
地位是**对称**的：谁都能在第 0 分钟开工，谁做完都算完事。真实车间不是这样。

```text
订单 J0：料 8 点才到         -> release_time = 8
订单 J1：答应客户 3 点前交货  -> due_date = 3
订单 J2：客户催得紧，罚款高   -> weight = 3.0
```

前两个属性只在**两个不同的地方**起作用，这一点必须先分清，否则很容易写错模型：

```text
release_time  ->  进约束：start >= r_j
due_date      ->  进目标：把 max(0, C_j - d_j) 加进目标函数
```

一个把可行集剪小，另一个只改变「哪条可行解更好」。今天要做的就是分别弄清这两件事的后果。

## 3. 定义：释放时间、交期、迟交

**定义（`release time`）**：订单 `j` 的释放时间 `r_j` 是它的**第一道工序最早可以开工**的时刻。
所有 `j` 的工序都满足 `start >= r_j`，这是一条硬约束，任何合法排程都不能违反。

**定义（`due date`）**：订单 `j` 的交期 `d_j` 是承诺给客户的完工时刻。它**不约束**任何变量。

**定义（迟交 `tardiness`）**：订单 `j` 的迟交量 `T_j = max(0, C_j - d_j)`，其中 `C_j` 是订单
最后一道工序的完工时刻。总迟交 `ΣT = Σ_j T_j`。

**定义（`weight`）**：订单 `j` 的权重 `w_j`。带权迟交 `Σ_j w_j · T_j` 与不带权的 `ΣT`
是两个不同的量：前者把「哪个订单迟到」也当成信息，后者只数迟到多少分钟。

**理论结论 1（不对称）**：`release time` 与 `due date` 在模型里的地位**不对称**：
前者是硬约束，后者是目标里的一个分量。这不是实现偷懒，而是业务语义的忠实翻译。

**理论结论 2（迟交不可单靠约束表达）**：如果强行要求 `C_j <= d_j`（把交期做成硬约束），
可行集可能直接变成空集——而现实中客户不会因为你排不出来就取消订单，他会收违约金。
把交期写成硬约束，等于宣称「迟交不可接受」，这是一句比现实更强的话。

**实验观察 1**：在 `D1` 上求解器给出的最优排程里，机器上出现了一段 `[5, 8)` 的空转。
下一节证明这段空转是**被迫**的，不是求解器不小心。

## 4. 推导：为什么 `release` 是硬的、`due date` 是软的

### 4.1 释放时间把机器顶空

单机、四道工序，工时各不相同。先看不含释放时间时的直觉：单机上「越早开工越不亏」，
因为机器只要空着就是纯损失。有了释放时间，这个直觉就不再成立。

**理论结论 3（被迫空转）**：若某道工序的释放时间晚于「其余工序工时之和」，
则机器在它开工前**必然**出现空转。论证只用两条事实：

```text
事实 1：A 的释放时间 r_A = 8，所以 A 只能在 [8, ...) 里开工
事实 2：其余三道工序 B、C、E 的总工时 = 2 + 2 + 1 = 5

在 [0, 8) 这段时间里，机器能加工的只有 B、C、E
可加工的工时上限 = 5 分钟
所以 [0, 8) 里至少有 8 - 5 = 3 分钟是空的
```

这不是「求解器没排满」，而是**任何**合法排程都躲不掉的结论：宁可让机器空着，
也不能让 `A` 提前开工——前者损失产能，后者违反承诺的到料时间，是硬约束。

### 4.2 交期为什么只能进目标

把交期写进约束会改变问题的**性质**：从「挑一条最好的排程」变成「先问有没有排程」。
而 `ΣT` 作为目标分量有一个非常好用的性质：

**理论结论 4（分段线性）**：`max(0, C_j - d_j)` 是 `C_j` 的凸函数，可以用一个额外的整型变量
`T_j` 加一条 `T_j >= C_j - d_j`、`T_j >= 0`（等价地：`T_j = max(C_j - d_j, 0)`）表达，
不需要任何 `if`。凸性让「提前完工」有收益上限：`C_j <= d_j` 之后再怎么提前，
`T_j` 都是 0。

**理论结论 5（`makespan` 对交期无感）**：若存在两条排程 `S1`、`S2` 满足
`Cmax(S1) = Cmax(S2)` 而 `ΣT(S1) != ΣT(S2)`，那么「最小化 `Cmax`」这个目标在
`S1` 与 `S2` 之间**没有任何偏好**。于是：

- 只优化 `Cmax` 的模型，返回 `S1` 还是 `S2` 不由目标决定，而由搜索路径决定；
- 「求解器证明了 `Cmax` 最优」这句话，对 `ΣT` 一个字都没有说。

这条结论在本日的实验里有一个可以亲眼看见的例证：求解器返回的那条 `Cmax = 12` 的排程，
`ΣT = 5`；而手写的另一条排程同样 `Cmax = 12`，`ΣT = 0`。**两条都是 `Cmax` 最优解**。

## 5. 手算：`D1` 实例的下界、空转与 `ΣT`

实例 `D1`：单机 `M0`，四道工序各属一个订单。

```text
工序   订单    工时 p   释放 r   交期 d
A      J0        4        8       14
B      J1        2        0        3
C      J2        2        0       20
E      J3        1        0        1
```

### 5.1 下界：为什么最优值不可能小于 12

```text
下界 1（工作总量）：Cmax >= Σp = 4 + 2 + 2 + 1 = 9
下界 2（A 的释放时间）：Cmax >= r_A + p_A = 8 + 4 = 12
取其大者：Cmax >= 12
```

下界 2 的论证只有一句话：`A` 不允许在 8 之前开工，而它自己就要占 4 分钟，
所以整张排程不可能在 12 之前结束。求解器给出的最优值正好是 `12`，
**下界碰上界**——这就是本例最优性的独立证据，不依赖求解器自己的 `OPTIMAL` 标签。

（注意下界 1 在这里被下界 2 完全盖住了：单机问题里「机器空转」可以让工作总量那条下界失效，
所以真正起作用的是与释放时间有关的那条。）

### 5.2 空转：`[5, 8)` 这 3 分钟是算出来的

由第 4.1 节的论证，`[0, 8)` 里最多只能加工 `B`、`C`、`E` 的 5 分钟，
所以至少有 3 分钟空转。实验里求解器给出的排程是：

```text
M0  CCBBE...AAAA   (0 -> 12)

C[0, 2)  B[2, 4)  E[4, 5)  空 [5, 8)  A[8, 12)
```

空转段是 `[5, 8)`，长度 3，与手算的下限**恰好相等**——说明这段空转已经短到不能再短。
求解器没有「浪费产能」，它是在释放时间这条硬约束下，把 `B`、`C`、`E` 尽量往前塞的结果。

### 5.3 `ΣT` 的手算

先算求解器给的这条最优排程（`Cmax` 最小意义下最优）：

```text
订单    工序   C_j    d_j    T_j = max(0, C_j - d_j)
J0      A      12     14     0
J1      B       4      3     1        <- 迟到 1 分钟
J2      C       2     20     0
J3      E       5      1     4        <- 迟到 4 分钟
ΣT = 0 + 1 + 0 + 4 = 5
```

`E` 是这一串里最急的订单（`d = 1`），却被排在 4 分钟之后开工——因为 `Cmax` 的目标
根本不知道有交期这回事。手写第二条排程就能看出来：

```text
手写排程二：E[0,1)  B[1,3)  C[3,5)  A[8,12)
手算 ΣT = (1-1)^+ + (3-3)^+ + (5-20)^+ + (12-14)^+ = 0 + 0 + 0 + 0 = 0
Cmax   = 12

手写排程三：C[0,2)  B[2,4)  A[8,12)  E[12,13)
手算 ΣT = (2-20)^+ + (4-3)^+ + (12-14)^+ + (13-1)^+ = 0 + 1 + 0 + 12 = 13
Cmax   = 13
```

三条排程摆在一起，故事就完整了：

```text
排程                     Cmax    ΣT
求解器返回的最优解          12     5
手写排程二                  12     0     <- 同样 Cmax 最优，ΣT 却最小
手写排程三                  13    13
```

排程二与求解器返回的那条 `Cmax` 相同，`ΣT` 却从 5 降到 0。**只优化 `Cmax` 时，
这两条在目标函数眼里完全等价**，谁被返回都不算错。这句话是今天最重要的一句。

## 6. 实现：这两条约束在模型里的位置

模型在 [industrial.py](../../projects/03_industrial_fjsp/fjsp_shop/industrial.py)。
释放时间是一行硬约束，交期是一组带 `AddMaxEquality` 的辅助变量：

```python
# 释放时间：不早于所属订单的释放时刻（验证器的第 4 项）
model.Add(start[op.id] >= instance.job(op.job_id).release_time)
```

```python
tardiness: dict[str, Any] = {}
for job in instance.jobs:
    if job.due_date is None or job.id not in job_end:
        continue
    var = model.NewIntVar(0, horizon, f"T[{job.id}]")
    model.AddMaxEquality(var, [job_end[job.id] - job.due_date, 0])
    tardiness[job.id] = var
```

四处值得注意的细节：

1. **释放时间挂在订单上、写进每道工序的 `start`**。同一订单的每道工序都要加这条约束，
   而不是只加在首道工序——虽然首道工序的约束加上 precedence 之后能传递下去，
   但逐道工序写更直白，也让「模型里的约束」与「验证器的检查」一一对应。
2. **没有交期的订单不建 `T` 变量**，于是它对 `ΣT` 的贡献是 0。这比建一个恒为 0 的变量干净。
3. **`AddMaxEquality(var, [C_j - d_j, 0])` 就是在表达 `max`**，不需要引入布尔变量做分支。
   `max` 是凸运算，CP-SAT 有原生传播器，写出来比「先猜一个界再验证」紧得多。
4. **`C_j` 取的是订单最后一道工序的 `end`**（`job_end[job.id]`），不是订单里所有工序的完工
   最大值——对一条工艺路线来说这两者相等（后面的工序不会早于前面的结束），但用最后一道工序
   更贴合「`C_j` 的定义」。

### 6.1 为什么本例能报 `best_bound`

`best_bound` 不是所有情形都能报的。模型内部把目标系数乘了一个常数再取整，
目的是把归一化之后的**小数权重**变成整数系数：

```text
mode = "none"  ->  系数 = 权重 × OBJ_SCALE        （权重都是整数倍时无舍入）
mode = "trivial" / "ideal"  ->  系数 = 权重 × OBJ_SCALE / 分母  （一般要舍入）
```

只有在**没有舍入**的时候，模型目标与报告目标之间才有确定的换算关系，
求解器给的界才能换算回原始单位。本例用的是 `mode = "none"` 且权重是
`(α, β, γ) = (1, 0, 0)`，所以 `best_bound = 12.0` 是一个能直接读的数；
一旦开了归一化，同一个字段只能是 `None`——**不是求解器没算，
而是算出来的界和你要报的那个量之间没有确定的换算关系**。

### 7.1 这张输出里值得逐行看的四处

**第一处：`release: A` 只有一条诊断。** 反例一把 `A` 提前到 0 点，验证器报的标签是
`release`（格式是 `release: <工序>`），而不是 `precedence` 或 `overlap`——
排程在机器互斥与工艺顺序上都没问题，唯一的错误是「开工早于到料」。
这种「只错一条」的反例，是验证器能被信任的关键：标签指到哪，就知道该改哪。

**第二处：`手算 ΣT` 与 `求解器复算 ΣT` 逐行相等。** 手算那行是脚本里写死的算式，
复算那行是 `fjsp_core.objective` 从排程反算出来的。两条独立的算法给出同一个数，
才能排除「目标函数算错了但没人发现」。

**第三处：手写排程二 `ΣT = 0` 而求解器返回的那条 `ΣT = 5`。** 这两条的 `Cmax` 都是 12，
所以它们都是 `Cmax` 最优解。求解器返回哪一条，不由 `α = 1, β = 0` 的目标决定。

**第四处：`best_bound=12.0` 与手算下界相同。** 求解器说「我把界推到 12」，
手上算的下界也是 12，`objective` 也是 12：三个数从三个方向指向同一个结论。

### 7.2 本日实验的三条结论

1. **释放时间是硬约束**：违反它会被独立验证器当场拒绝，诊断标签 `release: A`。
2. **被迫空转是可以算出来的**：`[0, 8)` 里可加工的工时上限是 5 分钟，
   所以至少空 3 分钟；求解器给出的排程正好空 3 分钟。
3. **交期不进模型就等于不存在**：`Cmax` 最小的排程里 `ΣT` 可以是 5，也可以是 0，
   只优化 `Cmax` 的模型无法区分。要让交期起作用，必须把 `ΣT` 写进目标。

## 10. 自测题

- Q1：`release time` 是订单级属性，为什么它的约束要写在**每道工序**的 `start` 上？
- Q2：如果某个订单没有交期（`due_date is None`），它对 `ΣT` 的贡献是多少？模型里会不会为它建变量？
- Q3：`Cmax` 最小化与 `ΣT` 最小化，谁的目标函数更「挑剔」？用 `D1` 的三条排程回答。
- Q4：`[5, 8)` 这段空转能不能靠「把 `E` 拆成两段」消掉？为什么不能？（提示：工序不可中断。）
- Q5：手写排程二的 `ΣT = 0`。是否说明「交期在这个实例上不起作用」？
- Q6：`ΣT = 5` 与 `ΣT = 0` 的两条排程都是 `Cmax` 最优解。求解器返回了 `ΣT = 5` 的那条，
  能不能说「求解器不稳定」？
- Q7：带权迟交 `Σ_j w_j T_j` 与 `ΣT` 在 `D1` 上会选出不同的排程吗？（`w = (1, 3, 1, 1)`）
- Q8：验证器为什么不检查「机器空转太多」这类问题？
- Q9：`best_bound = 12.0` 与「手算下界 = 12」是同一条证据吗？
- Q10：如果给 `D1` 加上归一化 `mode = "ideal"`，`best_bound` 会变成什么？为什么？

### 参考答案

- A1：因为释放时间约束的是**加工行为**，而加工行为发生在工序上。只写在首道工序上也不算错
  （precedence 会把下界传下去），但那样一来「模型里的约束条数」和「验证器检查的项数」就不对应了，
  排查问题时容易漏。逐道工序写，是让模型与验证器一一对应。
- A2：贡献是 0。模型里**不会**为它建 `T` 变量：循环里有一句 `if job.due_date is None: continue`。
  没有变量的好处是求解器连「这个量恒为 0」都不需要推理。
- A3：`ΣT` 更挑剔。`D1` 上 `Cmax` 最优解有多条（实验里的求解器解与手写排程二），
  它们在 `Cmax` 上并列，在 `ΣT` 上差 5 分钟。只写一个分量的目标函数，
  能在候选解之间做出的区分比多分量目标少——它只对「自己那个分量」的差异有反应。
- A4：不能。工序是不可中断的（non-preemptive），`E` 一旦开工就必须连续做完 1 分钟，
  不能拆成两半塞进 `[4, 5)` 与别的空隙；而 `[0, 8)` 的空余时间就算拆出来也装不下 `A`
  （`A` 的释放时间是 8）。拆分工序会得到另一个问题，不是本实例的一条排程。
- A5：不能这么读。`ΣT = 0` 只说明**存在**一条 `ΣT = 0` 的排程，而求解器返回的那条 `ΣT = 5`。
  交期在这条排程上确实「没被照顾到」，而照顾它需要把它写进目标。交期在**目标**里起作用，
  在**约束**里从来不起作用。
- A6：不能。`α = 1, β = 0` 的目标函数在这两条排程上取值相同，返回哪条都满足最优性。
  要拿到 `ΣT` 更小的那条，就得把 `β` 提到正数——这是**改目标**，不是修 bug。
- A7：会。`ΣT` 的算法里每条订单的迟交等权，而带权迟交里 `J1` 的权重是 3：
  求解器返回的那条排程 `J1` 迟到 1 分钟（计 3）、`J3` 迟到 4 分钟（计 4），合计 7；
  手写排程二两条都不迟，带权也是 0。权重改变了「哪条排程更好」的排序，
  但如果目标里根本不写迟交，权重也一样不起作用。
- A8：因为空转不违反任何约束。机器可以在任意时刻空着，验证器只检查
  「有没有违规」，不检查「效率高不高」。效率是目标函数的职责——
  也正因为如此，一个「合法但很差」的排程在验证器眼里是完全合格的。
- A9：不是同一条。`best_bound = 12.0` 来自求解器在**它自己的模型**上的搜索；
  手算下界 12 来自 `Cmax >= r_A + p_A` 这一句推理，与求解器无关。
  两条证据指向同一个数，结论才站得住——其中任何一条单独拿出来都只能算「一个数的来源」。
- A10：会变成 `None`。`ideal` 口径下模型目标系数要除以分母再取整，一般会有舍入，
  模型目标与报告目标之间就没有确定的换算关系了。求解器仍然会给出界，
  但它对应的是「除过分母、乘过 `OBJ_SCALE` 的整数目标」，换算不回来。

## 11. 今日一句话总结

> **`release time` 是硬约束、`due date` 只在目标里：`D1` 上 `A` 的释放时间 8 与其余工序的
> 5 分钟工时把机器顶出了 3 分钟空转（`[5, 8)`），这个数可以纯手算，求解器给出的排程正好空 3 分钟；
> 而交期的作用要弱得多——`Cmax = 12` 的最优排程至少有一条 `ΣT = 5`、一条 `ΣT = 0`，
> 只写 `makespan` 的目标函数在两者之间没有任何偏好，所以「求解器证明了最优」
> 这句话对迟交一个字都没有说。**
