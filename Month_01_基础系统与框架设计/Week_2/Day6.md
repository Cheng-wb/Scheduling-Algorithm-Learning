# Day 6：五个极小实例的独立枚举对拍

> 目标：用可承受规模的完整枚举校验解码与搜索目标。建议 3 小时。

## 1. 穷举范围

[oracle.py](../../../projects/01_scheduling_core/scheduling_core/oracle.py) 只支持每作业一道工序。对 n 个任务、每个有 m 台资格，遍历 n! 个排列与全部指派。n=4、m=2 时为 `24×16=384` 个组合。

Oracle 自己维护机器可用时刻，不调用 decoder。测试另用 Candidate+decode 遍历同样的决策空间，比较最小目标。共享领域模型与目标公式，因此目标公式还需要 Week 1 手算提供另一层证据。

## 2. 为什么能称 optimum

固定每台机器上的任务顺序后，按释放时间尽早启动不会使 Cmax、ΣT 或 ΣwC 变差；这些目标随完成时间增大不会下降。遍历全部机器指派与每台机器的顺序便覆盖最优解所需决策。全局排列会重复覆盖某些并行顺序，但不会漏掉。

该说明不适用于任意新目标，例如提前惩罚可能需要有意延后。Oracle 拒绝多工序输入，并在组合数量超过 100000 时拒绝运行，不能拿受限枚举结果冒充整个问题的 optimum。

## 3. 运行与结果含义

仓库根目录：

```powershell
python projects/01_scheduling_core/examples/m1w2d6_verification.py
```

或项目目录 `python -m pytest tests/test_month1.py -k enumeration -v`。固定实例种子 0…4，共五个四任务两机实例；每例验证枚举最小值一致、oracle 排程可行，以及所有搜索算法返回值不低于 optimum。

## 4. 练习

把 jobs 改为 5：每例组合数变成 `120×32=3840`。改为 8：`40320×256=10321920`，超过默认限额。阶乘增长解释了为何穷举适合对拍却不适合大规模求解。

验收：能够区分“一个启发式追平了枚举最优值”和“启发式本身具有全局最优保证”；前者只是一例上的事实。
