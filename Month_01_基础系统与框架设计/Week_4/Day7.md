# Day 7：月度报告与交付验收

> 目标：形成别人能够重跑、核查和理解的 Scheduling Core & Search Lab。建议 2 小时复盘＋2 小时统计。

## 1. 报告结构

完整报告：[MONTH1_REPORT.md](../MONTH1_REPORT.md)。按问题与范围→模型→方法→正确性证据→运行设置→结果→局限→复现组织，避免只是按日期重复开发流水账。

任何“最好”都应说明在什么实例、什么目标、什么预算下。任何“最优”都应说明证据来自公式、界，还是完整枚举。只在算法集合内排名第一不等于数学最优。

## 2. 月末验收对应

| 月计划要求 | 交付 |
|---|---|
| ≥10 个手算规则与指标案例 | Week 1 Day 6 与 HAND_CASES |
| 独立拒绝五类违规 | schedule_validation.py 与九类破坏测试 |
| 统一五种搜索比较 | search.py、SearchConfig、完整评价预算 |
| ≥5 个小实例枚举 | oracle.py 与五种子对拍 |
| 一条命令生成表和图 | benchmark CLI 与 month1.json |
| 参数、状态、失败与 gap 留痕 | results.csv、metadata、runs、failures |
| 每周七天记录与周报 | 28 篇 Day 笔记＋week1…week4 |

## 3. 完成不等于掌握

代码、材料和实验记录已完成；个人掌握程度建议用闭卷方式自测：重写两任务交换证明、手推一条 decoder 轨迹、解释一个验证器错误、从 trace 解释一次 SA 接受、复现一条结果。

如果某题答不出，回到对应日笔记补练，而不必重新搭整个工程。周报中的“待学习练习”不假装已经由你完成。

## 4. 接入下个月

M2 的 MILP/CP-SAT 应复用 Instance、Schedule、验证器和 Objective。在同一输入上比较精确方法与本月基线，扩展 status、bound 和真实求解 gap；不能把本月 best-known gap 直接当作求解器证明的 gap。

统计补充：三种子均值差只作探索；更正式结论需要更多实例、独立测试集、配对分析和不确定性估计。项目最终的价值是把这些步骤变成可重复的过程。
