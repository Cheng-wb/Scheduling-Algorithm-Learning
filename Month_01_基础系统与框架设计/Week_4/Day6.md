## 2. 为什么第 6 天要做敏感性，而不是「调参」

昨天把 162 行压成了统计表，今天要回答一个必然会遇到的问题：**SA 的那两个参数（`temperature`、`cooling`）到底重不重要？**

这个问题的危险在于，它可以被两种偷懒的方式「回答」：

- 只用公式回答：「温度低就更少接受坏解，所以低温更好。」——接受公式只约束**接受与否**，不约束**最终解的质量**。
- 只用一批数据回答：「我试了四组，第三组均值最小，所以第三组最好。」——这已经把结论建立在看过答案的基础上了。

今天要做的是把这两件事分开：

```text
理论预期：从 exp(-Δ/T) 能推出的方向        → 机制层面，可靠，但不含质量结论
实验观察：summary.csv 里每实例每组的均值    → 质量层面，必须读数据，且带样本量限制
```

两者的关系是：**理论预期负责解释「为什么会出现差异」，实验观察负责回答「差异是多少」**。任何一句把方向直接读成质量的话都是过度陈述。

本日不重新跑基准、不新增参数组合，只对 Day 1 已经落盘的四组做只读复盘。

## 3. 已执行的设置：四组、54 次运行

### 3.1 四组参数与组名

`configs/month1.json` 的主实验 SA 使用 `T0 = 10.0`、`cooling = 0.98`；`sensitivity` 数组额外声明三组设置。加上主实验，一共四组：

| 组名 | `temperature` | `cooling` | 运行次数 | 与主配置只差 |
|---|---|---|---|---|
| `main` | 10.0 | 0.98 | 18 | 基准 |
| `sa_t0.1_c0.98` | 0.1 | 0.98 | 18 | 初温（更低） |
| `sa_t100.0_c0.98` | 100.0 | 0.98 | 18 | 初温（更高） |
| `sa_t10.0_c0.9` | 10.0 | 0.9 | 18 | 冷却率（更快） |

每组的 18 次 = 六个实例 × 三个 `seed`；敏感性部分共 54 次，加上主实验的 18 次 SA，`results.csv` 里共有 72 行 SA 记录。

**组名与参数的对应不是靠命名猜的**：`results.csv` 有 `temperature` 与 `cooling` 两列，第 7 节的脚本会先按组名分组、取出这两列的唯一值，再与 `configs/month1.json` 的声明对拍（`sa_t{temperature}_c{cooling} == group`），最后才允许使用这个映射。

### 3.2 哪些被固定、哪些被改变

```text
固定：instances（六个，同一批输入文件）、seeds（0/1/2）、
      budget（150 次评价）、restart_interval（40）、算法（sa）
改变：temperature ∈ {0.1, 10, 100}，cooling ∈ {0.9, 0.98}
```

两两对照可以看出因子被分开了：

- 初温的影响：`main` 与 `sa_t0.1_c0.98`、`sa_t100.0_c0.98` 三组 `cooling` 同为 0.98，只差 `T0`。
- 冷却率的影响：`main` 与 `sa_t10.0_c0.9` 两组 `T0` 同为 10.0，只差 `cooling`。

**结论**：这是一个 3×2 设计里的四个点，不是「四边形上的四点比较」；任何结论都必须说明它来自哪一组对照。

### 3.3 同 `seed` 只是配对起点

同一个 `seed` 意味着两次运行从同一个随机状态出发，**不**意味着每一步的随机动作都相同。原因是 SA 的接受分支会消耗随机数：

```python
accepted = delta <= 0 or rng.random() < exp(-delta / max(temperature, 1e-12))
```

`delta <= 0` 时短路，不消耗 `rng`；`delta > 0` 时才抽一个随机数比较。两条轨迹只要有一次 `delta` 的符号不同，后续消耗的随机数个数就不同，`rng` 状态分叉，之后提出的候选也完全不同。

所以「同 `seed` 换参数」是**配对起点**，不是受控实验。第 7 节的实测会给出分叉位置：`routes_12`、`seed = 0` 上，高温组在第 8 次提议之后就走出了主配置的轨道，另外两组在第 14 次之后。

## 4. 理论预期与实际结果必须分开

### 4.1 从接受公式能推出的三条方向性结论

```text
规则：delta <= 0 必接受；delta > 0 时以概率 exp(-delta / T) 接受。
推论 1：T 越小，exp(-delta/T) 越接近 0，越少接受坏解（趋近贪心下降）。
推论 2：T 越大，exp(-delta/T) 越接近 1，越常接受坏解（更像随机游走）。
推论 3：cooling 越小，T 衰减越快，越早进入「几乎只接受改善」的阶段。
```

这三条是**理论结论**，可以用数字感受（Δ = 5 时）：

```text
T = 0.1    exp(-5/0.1)   = exp(-50)  ≈ 1.92875e-22   （等于不接受）
T = 10.0   exp(-5/10)    = exp(-0.5) ≈ 0.606531
T = 100.0  exp(-5/100)   = exp(-0.05) ≈ 0.951229     （几乎总接受）
```

温度沿评价次数衰减（`T_k = T0 · cooling^k`，预算 150 次评价，k 从 1 到 149）：

```text
主配置 10/0.98     k=1 → 9.8000；k=20 → 6.6761；k=50 → 3.6417；k=149 → 0.4928
低温 0.1/0.98     k=1 → 0.0980；k=20 → 0.0668；k=50 → 0.0364；k=149 → 0.0049
高温 100/0.98     k=1 → 98.0000；k=20 → 66.7608；k=50 → 36.4170；k=149 → 4.9282
快冷却 10/0.9      k=1 → 9.0000；k=20 → 1.2158；k=50 → 0.0515；k=149 → 0.0000
```

`10/0.9` 在 k = 20 时温度已经降到 1.22，而 `10/0.98` 还停在 6.68——快冷却确实更早变贪心。注意 `max(temperature, 1e-12)` 这个下界：快冷却后期 T 会下溢到极小值，没有下界会让 `exp(-delta/T)` 出现除零或溢出。

### 4.2 公式推不出来的部分

上面三条只说「接受坏解的概率」，**没有说最终解更好还是更差**：

- 接受更多坏解可以跳出局部最优，也可能把已经找到的好解丢掉。
- 接受更少坏解可以更彻底地下降，也可能很早就卡在一个普通局部最优。
- 150 次评价里前 20 次温度还很高，后期才变贪心；低温组从第 1 次提议起就几乎只接受改善，探索时间窗完全不同。

**结论**：参数好坏必须读 `summary.csv` 的逐实例均值；公式只用来解释「为什么会观察到这种差异」。

### 4.3 温度是「相对量」

`exp(-Δ/T)` 里 Δ 与 T 是同量纲的比值。本批实例的 `objective` 尺度差别很大：`parallel_12` 的 Cmax 在 43 上下，`single_12` 的 ΣT 在 250 上下。同样是「改善 5」，在两个实例里对应的接受概率完全不同。

**结论**：**一组固定参数不可能对所有实例尺度都合适**；这也解释了第 5 节会看到「没有任何一组在六个实例上都最好」。要在不同实例间复用参数，得先做尺度归一化（例如按初始解的目标值缩放）。

## 5. 示例：`routes_12` 上的四组真实对照

在 `routes_12`（Cmax，参考 `best-known = 40`）上，从 `results.csv` 取出 SA 组的三个 `seed` 值：

| 组 | seed 0 | seed 1 | seed 2 | `mean` | `median` | `best` |
|---|---|---|---|---|---|---|
| `main`（10/0.98） | 42 | 42 | 42 | 42.0 | 42 | 42 |
| `sa_t0.1_c0.98`（低温） | 40 | 41 | 44 | 41.67 | 41 | 40 |
| `sa_t100.0_c0.98`（高温） | 49 | 42 | 48 | 46.33 | 48 | 42 |
| `sa_t10.0_c0.9`（快冷却） | 41 | 42 | 45 | 42.67 | 42 | 41 |

四个均值的手算（用精确分数）：

```text
主配置 10/0.98 : (42 + 42 + 42) / 3 = 126 / 3 = 42.0
低温   0.1/0.98: (40 + 41 + 44) / 3 = 125 / 3 = 41.666666666666664   极差 4
高温 100.0/0.98: (49 + 42 + 48) / 3 = 139 / 3 = 46.333333333333336   极差 7
快冷却  10.0/0.9: (41 + 42 + 45) / 3 = 128 / 3 = 42.666666666666664   极差 4
```

理论方向与实测结论并排：

| 层面 | 说法 | `routes_12` 上的实测 |
|---|---|---|
| 理论（机制） | 低温更少接受坏解 | 接受 79/149 次，其中接受坏解 0 次 |
| 理论（机制） | 高温更常接受坏解 | 接受 137/149 次，其中接受坏解 21 次 |
| 理论（机制） | 快冷却更早变贪心 | 接受 78/149 次，其中接受坏解 1 次 |
| 实验（质量） | 公式推不出谁更好 | 均值最好的是低温（41.67），最差的是高温（46.33） |

**实验观察**：

1. 主配置三个 `seed` 全部落在 42，是四组里唯一零极差的一组；这既可能是它稳定，也可能只是三个 `seed` 恰好都没跳出同一个局部最优——三个样本分不出这两种解释。
2. 低温组均值最小，但它的 `best = 40` 恰好等于本实例的 `best-known = 40`；换句话说，**参考值本身有一部分来自这一组的运气**，再拿这个参考去评价同一组，就等于自己给自己打分。
3. 高温组的 `mean = 46.33` 却 `median = 48`：均值被 `seed = 1` 那次侥幸的 42 拉低了。**只报均值会让人以为高温「平均来说还不错」**，中位数才说明它的典型表现是 48。这正是 Day 5 第 4.1 节强调「三个统计量要一起给」在真实数据上的体现。
4. 极差对比：高温 7、低温 4、快冷却 4、主配置 0。**结论**：高温不仅均值差，波动也最大，两个维度指向同一个方向，这个结论比单看均值更稳。

## 6. 实现：`search.py` 的退火循环与三处必要修复

### 6.1 SA 分支：接受规则与降温

对应文件 [search.py](../../projects/01_scheduling_core/scheduling_algorithms/search.py)：

```python
temperature = config.temperature
trace = [TracePoint(1, value, value, value, True, None)]

elif config.algorithm in ("random", "sa"):
    while len(trace) < config.budget:
        candidate = random_candidate() if algorithm == "random" else random_move()
        schedule, score = evaluate(candidate)
        delta = score - value
        accepted = (
            score < value
            if config.algorithm == "random"
            else delta <= 0 or rng.random() < exp(-delta / max(temperature, 1e-12))
        )
        if accepted:
            current, value = candidate, score
        record(candidate, schedule, score, accepted,
               temperature if config.algorithm == "sa" else None)
        temperature *= config.cooling
```

五个必须记住的设计选择：

1. **初始解与 `seed` 无关**：`current = initial_candidate(instance)`（LPT 优先级 + 最早完工指派，确定性）。所以四组设置的第一行完全相同，轨迹差异只可能来自搜索过程。
2. **`delta <= 0` 时短路，不消耗 `rng`**：这是第 3.3 节讲的随机流分叉来源，也是最容易被忽视的一行。
3. **`record` 更新 `best` 用严格小于**：`if score < best_value`，所以 `best` 序列单调不增（Day 5 第 7 节审计过）。
4. **`random_move` 允许 no-op**：`swap(i, i)`、`insert(i, i)`、`reassign` 抽到当前机器都算一次评价。这避免了单元素或单资格时死循环，但**接受率因此不等于有效探索率**——一部分「接受」的目标值根本没变。
5. **`SearchConfig` 在进入循环前就校验参数**：`temperature` 必须有限且为正，`cooling` 必须落在 (0, 1]。四组设置都满足，所以不存在「参数非法导致运行失败」的干扰项。

### 6.2 `benchmark.run` 怎么构造敏感性组

[benchmark.py](../../projects/01_scheduling_core/scheduling_experiments/benchmark.py) 里，每个实例都会构造两组变体：

```python
variants = [("main", algorithm, {}) for algorithm in config.get("algorithms", ALGORITHMS)]
variants += [
    (f"sa_t{item['temperature']}_c{item['cooling']}", "sa", item)
    for item in config.get("sensitivity", [])
]
...
settings = SearchConfig(algorithm=algorithm, objective=spec["objective"], seed=seed,
                        **(config["search"] | parameters))
```

`config["search"] | parameters` 是字典合并：敏感性项只覆盖 `temperature` / `cooling`，其余字段（`budget`、`restart_interval`）沿用主实验。**这意味着敏感性组与主实验共用同一个评价预算**，所以两组数字可以直接在同一实例内比较。

### 6.3 三处必要修复：改变的是合法性条件

本月在跑正式批次之前修了三处工程问题，它们都属于「什么输入算合法、什么结果算可行」这一类：

| 修复 | 位置 | 修复后的行为 |
|---|---|---|
| 单机规则的机器资格检查 | `scheduling_algorithms/rules.py` | 派发前逐个工序检查 `machine.id in operation.eligible_machine_ids`，不满足直接抛 `illegal assignment: {op.id} -> {machine.id}` |
| JSON 工时不再被静默截断 | `scheduling_io/parser.py` | 解析时原样传 `item["processing_time"]`（此前是 `int(...)`），由输入校验报 `processing_time must be an integer` |
| 非有限权重与非整数时刻 | `scheduling_core/validation.py` | `weight` 必须是有限数（`weight must be finite numeric`），`release_time` / `due_date` 必须是整数 |

为什么必须把这三条单独说出来：**它们改变的是合法性条件，不是解的质量。**

- 修复前，一个工时 3.7 的工序会被静默当成 3 参与计算；修复后同样的输入直接报错。前后两次「运行成功」说的不是同一道题。
- 修复前，一台没资格的机器可能被静默排上工序；修复后同一份结果会被独立验证器判为 `illegal assignment`。
- 所以**修复前跑出来的数字与修复后跑出来的数字不能直接比较**，否则会把工程修复读成「算法变好了」或「算法变差了」。

本月的正式批次（`artifacts/month1_refactored/`）全部在修复后运行；`verification.json` 记录了「重构前的结果行除计时外全部相等」的逐行核对，用来证明这些修复没有改变合法输入上的结果，而不是用来证明算法变好。

== 3. 理论预期：公式直接读出的方向（理论结论，不是实测） ==
  SA 接受规则：Δ <= 0 时必接受；Δ > 0 时以概率 exp(-Δ / T) 接受。
  由此可以推出三条方向性结论：
    1. T 越小，exp(-Δ/T) 越接近 0，越少接受坏解（趋近贪心下降）。
    2. T 越大，exp(-Δ/T) 越接近 1，越常接受坏解（更像随机游走）。
    3. cooling 越小，T 衰减越快，越早进入「几乎只接受改善」的阶段。

  用具体数字感受（exp(-Δ/T)）：
    Δ=5.0，T=0.1    接受概率 = 1.92875e-22
    Δ=5.0，T=10.0   接受概率 = 0.606531
    Δ=5.0，T=100.0  接受概率 = 0.951229

  T 随评价次数衰减（T_k = T0 * cooling^k，预算 150 次评价，k 从 1 到 149）：
    主配置 10/0.98     k=1 → 9.8000；k=20 → 6.6761；k=50 → 3.6417；k=149 → 0.4928
    低温 0.1/0.98     k=1 → 0.0980；k=20 → 0.0668；k=50 → 0.0364；k=149 → 0.0049
    高温 100/0.98     k=1 → 98.0000；k=20 → 66.7608；k=50 → 36.4170；k=149 → 4.9282
    快冷却 10/0.9      k=1 → 9.0000；k=20 → 1.2158；k=50 → 0.0515；k=149 → 0.0000
  10/0.9 在 k=20 时 T 已经降到 1.22，10/0.98 还停在 6.68：快冷却确实更早变贪心。
  注意这三条只说「接受坏解的概率」，没说「最终解更好还是更差」——
  接受更多坏解可以跳出局部最优，也可能把好解丢掉，方向不确定。

  parallel_12   均值区间 [44.33, 44.67]，极差 0.33，均值最小：高温 100/0.98 / 快冷却 10/0.9
  parallel_24   均值区间 [91.67, 94.33]，极差 2.67，均值最小：低温 0.1/0.98

  两个 tiny 实例上四组完全相同（都追平各自 optimum），说明这两个实例已经饱和，
  测不出参数差异——「同分」是实例太小的结果，不是「温度永远不重要」的证据。

== 5. 同 seed 的轨迹对照（routes_12、seed=0，配对起点 ≠ 同随机流） ==
  设置                接受/提议         接受坏解        首个最好      末个最好

  与主配置的 proposed 序列首次出现差异的位置：快冷却 10/0.9 → 第 14 次提议之后

  同一个 seed 只是「相同的起始随机状态」，从第一次接受/拒绝判断不同开始，

  轨迹能说明机制：高温接受了最多的坏解，低温几乎不接受坏解（符合第 3 节方向），

== 6. 并列：三个 seed 上的同分说明不了什么 ==
  parallel_12   均值 44.33 并列：高温 100/0.98 / 快冷却 10/0.9
  parallel_12   均值 44.67 并列：主配置 10/0.98 / 低温 0.1/0.98
  tiny_parallel 均值 38 并列：主配置 10/0.98 / 低温 0.1/0.98 / 高温 100/0.98 / 快冷却 10/0.9

  同分不能证明「温度不重要」：它只说明在这三个 seed、这批小实例上分辨不出来。
  小预算也可能是原因之一——低温的收益常在后期才体现，150 次评价可能还没走到那一步。

== 7. 如果把这四组里最好的一组当成新默认值 ==
  那就是在这批数据上调参（tuning on the batch）：选中的设置见过这批实例的分数。
  之后再用同一批数据报告「参数 B 比参数 A 好」，这批数据就已经不是未见数据。
  正确做法是另留独立测试集（同分布、不参与选择），在它上面报告结果；
  或者做配对比较并给出不确定性，而不是直接比较四个均值。
  本项目保留原教学默认值 10/0.98：它是教学设置，不是调优结果，
  报告里也不声称已完成参数优化。

== 8. 本月必要修复：不能让「修复前后」混成算法优劣 ==
  1. 单机规则的机器资格检查：现在 machine 不在 eligible_machine_ids 里会直接
     抛 illegal assignment，而不是静默排到一台没有资格的机器上。
  2. JSON 工时不再被静默截断：解析阶段原样保留，由输入校验要求整数，
     非整数的 processing_time 会被拒绝，而不是被 int() 悄悄改小。
  3. 非有限权重与非整数时刻被拒绝：weight 必须是有限数，
     release_time / due_date 必须是整数，nan / inf 一律报错。

  这三条改变的是「什么输入算合法」和「什么结果算可行」。
  修复前跑出来的数字与修复后跑出来的数字，合法性条件不同，
  直接比较它们会把工程修复读成算法变好/变差。本月的正式批次全部在修复后运行。

  最终质量如何必须读 summary.csv 的每实例均值，而且要考虑 seed 数与并列。
  全部断言通过。

**实验观察**：

1. 第 1 段先把组名→参数的映射从数据列验证出来（断言 `sa_t{temperature}_c{cooling} == group`），再与 `configs/month1.json` 的声明对拍。**结论**：后面所有「低温组」「高温组」的说法都有数据支撑，不是从组名读出来的。
2. 第 4 段的均值极差按实例给出：`single_12` 27.33、`routes_12` 4.67、`parallel_24` 2.67、`parallel_12` 0.33、两个 tiny 0。**实验观察**：差异只在较大实例上出现，且没有任何一组在六个实例上都最好。`parallel_12` 的 0.33 小于一个加工时间单位，不值得解读。

5. 第 6 段清点出 4 组并列。**实验观察**：三个 `seed` 下差 1 个单位就能翻转排名，所以本节的排序只能当探索性描述；正式结论需要更多实例、独立测试集与配对分析（这是 Day 7 的统计补充要交代的内容）。

### 参考答案

- A1：`main` = (10.0, 0.98)、`sa_t0.1_c0.98` = (0.1, 0.98)、`sa_t100.0_c0.98` = (100.0, 0.98)、`sa_t10.0_c0.9` = (10.0, 0.9)；`t` 对应 `temperature` 列，`c` 对应 `cooling` 列。
- A2：敏感性 54 次（6 实例 × 3 设置 × 3 `seed`）；加上主实验的 18 次，`results.csv` 里共 72 行 SA 记录。
- A3：前三组的 `cooling` 同为 0.98、只差 `T0`；`main` 与 `sa_t10.0_c0.9` 的 `T0` 同为 10.0、只差 `cooling`。因子被分开，两两对照才可解释。
- A4：Python 的 `or` 在 `delta <= 0` 为真时短路，不执行右边的 `rng.random()`，因此不消耗随机数；两条轨迹只要有一次 `delta` 符号不同，消耗的随机数个数就不同，`rng` 状态分叉，之后提出的候选也不同。
- A5：主配置 54.0 → 42.0；高温组 54.0 → 49.0；四组首个 `best` 都是 54.0，因为初始解由 `initial_candidate` 确定生成，与 `seed` 和参数无关。
- A6：主配置 42.0、低温 41.67、高温 46.33、快冷却 42.67；最好与最差相差 139/3 − 125/3 = 14/3 ≈ 4.67。
- A7：因为 `exp(-Δ/T)` 里 Δ 与 T 是同量纲比值，而各实例的 `objective` 尺度差别很大（Cmax 约 43，ΣT 约 250），同一组参数在不同尺度上的相对温度完全不同。
- A8：接受坏解少只是「更接近贪心下降」，它可能更彻底地下降，也可能更早卡在普通局部最优；最终质量只能读数据（`single_12` 上最好的是快冷却组，不是低温组）。
- A9：这批数据已经参与了选择，不再算未见数据，再用于报告会高估改进；正确做法是另留独立测试集（同分布、不参与选择）并在其上报告，或做配对比较并给出不确定性。
- A10：单机规则的机器资格检查（把静默指派改成报错）、JSON 工时不再被静默截断（改由输入校验拒绝非整数）、非有限权重与非整数时刻被拒绝。它们改变的是合法性条件，修复前后的「成功运行」不是同一道题，直接比较会把工程修复读成算法优劣。
