## 2. 为什么 Day 5 要换一个 formulation

Day 3 的结论是：sequence 模型的 LP relaxation 在 `ΣTj` 上的界是 0，而 **`M` 的紧度不是原因** —— 即使把 `M` 换成可证明的最小可行值、再补上 `x_jk + x_kj = 1` 的等式，界仍然是 0。既然如此，出路只能在别处：

```text
sequence 模型的病根：
  机器互斥是靠「二元变量 × Big-M」表达的
  → LP 放松二元变量时，两条约束可以同时被放松一半
  → 机器容量在松弛里消失，所有工序都能重叠

换一种「变量定义」：
  不要问「谁先谁后」，直接问「在哪个时刻开工」
  → 互斥变成「每台机器每个时刻的占用数 <= 1」
  → 这是一条**容量约束**，不是一条析取约束，不需要 Big-M
```

这个替代模型叫 time-indexed 模型。它的代价很明显：变量数与时间界 `H` 成正比（`H` 一大就爆炸）；但它的收获也很明确 —— **松弛强度换了一个数量级**（Day 6 会量到：同一个实例上 sequence 模型的界是 `0`，time-indexed 是 `83.9347`，而真最优是 `85`）。

今天的目标不是「宣布它更好」，而是先把两件事做实：

1. **它是对的**：在可以穷举的实例上给出与独立枚举相同的最优值；
2. **它有多大**：把规模代价摆上台面，为 Day 6 的总账做准备。

## 3. 定义：time-indexed formulation

### 3.1 变量与约束

**定义（time-indexed MILP）**：把时间离散成整数格点 `t = 0, 1, ..., H`，对每道工序 `o`、每台可选机器 `m`、每个可行时刻 `t` 定义一个二元变量：

```text
y[o][m][t] = 1  ⟺  工序 o 在机器 m 的 t 时刻开工
```

约束有四组：

```text
① 每道工序恰好开工一次：   Σ_{m, t} y[o][m][t] = 1
② 机器容量：              对每台机器 m、每个时刻 τ：
                           Σ_{o 可达 m} Σ_{t' ∈ [τ - p_o + 1, τ]} y[o][m][t'] <= 1
③ precedence（同 job）：   相邻工序 before → after：
                           Σ_t t·y[after][m][t] >= Σ_t (t + p_before)·y[before][m][t]
④ 完成时间：               C_o = Σ_{m, t} (t + p_o)·y[o][m][t]
```

四组约束里只有第 ② 组需要多看一眼：它说的是「**在时刻 `τ` 正在加工的工序数不超过 1**」，其中「正在加工」包含了恰在 `τ` 开工的那些（区间 `[τ - p_o + 1, τ]` 覆盖了所有「在 `τ` 结束时仍在进行」的开工时刻）。**这一条把所有两两互斥一次性表达了**，所以既不需要 Big-M，也不需要 `x_jk`。

### 3.2 与 sequence 模型的逐项对照

| 维度 | sequence（disjunctive） | time-indexed |
|---|---|---|
| 二元变量 | `x_jk`：一对 job 一个（`C(n,2)` 个） | `y[o][m][t]`：一道工序 × 时间窗长度（`Σ_o 窗口长度` 个） |
| 互斥表达 | 每对两条 Big-M 不等式 | 每台机器每个时刻一条容量约束 |
| 需要 Big-M | 需要 | 不需要 |
| 多机选机 | 不支持（超出定义范围） | 天然支持（`m` 就是第二个下标） |
| 多工序 job | 不支持 | 支持（第 ③ 组 precedence 约束） |
| 规模随什么增长 | `O(n²)`（job 数的平方） | `O(n · H)`（与时间界成正比） |
| LP 松弛 | 机器容量在松弛里消失 | 容量约束仍然有效 |

规模那一行是核心：**两个 formulation 的变量数是两个不同的函数**，一个随时间界的增长而线性膨胀，一个随 job 数的平方增长。Day 7 会把这两条曲线画出来（实测 8 → 40 个 job 时，`alt/seq` 的变量数之比从 `10.8` 涨到 `17.1`）。

### 3.4 容量约束为什么在松弛后仍然有效

用 `hand3`（`A: r=0, p=3`；`B: r=0, p=2`；`C: r=5, p=4`）在机器 `M0` 的 `τ = 4` 时刻上算一遍，覆盖集合是哪些变量：

```text
A 的 p = 3：开工 t ∈ {2, 3, 4} 时 [t, t+3) 覆盖 4   → y_A2, y_A3, y_A4
B 的 p = 2：开工 t ∈ {3, 4}   时 [t, t+2) 覆盖 4   → y_B3, y_B4
C 的最早开工是 5，覆盖不到 τ = 4                    → 不出现
于是容量约束是：  y_A2 + y_A3 + y_A4 + y_B3 + y_B4 <= 1
```

这条约束是**对二元变量之和**的直接限制，放松成 `[0, 1]` 之后依然成立：LP 不能把 `y_A2` 与 `y_B3` 同时取到 1（那会让和等于 2），想把两道工序都排在 `0` 附近也做不到。对比同一个实例上 sequence 模型的两条 disjunctive 约束（`M_AB = M_BA = H - 0 = 14`）：`x = 1/2` 时它们变成 `s_B >= s_A - 4` 与 `s_A >= s_B - 5`，**两条在 `s_A = s_B = 0` 时都被满足**，于是 `A` 与 `B` 可以都在 `0` 时刻开工、完全重叠。

**同一个物理事实（机器一次只能加工一道工序），两种写法在松弛后的命运完全不同**：

```text
sequence 模型：互斥 = 两条「择一成立」的约束
              → 分数解让两条同时放松 → 松弛里互斥消失
time-indexed：互斥 = 「每个时刻占用数 <= 1」的容量约束
              → 分数解仍然受这条和的限制 → 松弛里互斥仍在
```

这就是 Day 3 那句「真正改变松弛强度的是变量定义」的具体机制，也是今天最值得带走的推导。

### 3.3 有效时间界在 time-indexed 模型里的第二次利用

`H` 在 time-indexed 模型里出现在变量下标的范围上：`t ∈ [最早开工, H - p_o]`。本仓库的实现把下界进一步收紧：

```text
最早开工(o) = r_job + (同 job 内 o 之前所有工序的加工时间之和)
```

理由是同 job 的工序必须按顺序加工，所以第 `k` 道工序不可能早于 `r_job` 加上前 `k-1` 道工序的总加工时间。这道收窄直接减少二元变量的个数 —— **同 job 的后道工序会少掉一整段不可能的时间格点**。这是 `earliest_start_bounds` 的职责，也是 Day 1 那条「有效时间界」的第三次出场。

没有这道收窄，窗口是 `[r_job, H - p_o]`；有它之后窗口变成 `[r_job + 前置总加工, H - p_o]`。窗口长度从 `H - p_o - r_job + 1` 缩短为 `H - p_o - r_job - 前置总加工 + 1`，**每道非首道工序少掉的格点数恰好等于它前面所有工序的加工时间之和**。一个 job 的工序越多，这道收窄省下的变量越多 —— 它也是规模闸门 `MAX_TIME_INDEXED_VARS = 400_000` 能在更大的实例上仍然留有余地的原因之一。

## 4. 规模：等价是要付账的

同一个 3 job 实例（`hand3`）上，两个 formulation 的规模：

| 实例 | 方法 | 变量 | 二元 | 约束 | 非零元 |
|---|---|---|---|---|---|
| hand3 | milp_tight | 7 | 3 | 9 | 25 |
| hand3 | milp_loose | 7 | 3 | 9 | 25 |
| hand3 | milp_alt | 32 | 31 | 20 | 152 |
| hand3_parallel | milp_alt | 55 | 54 | 30 | 324 |

三件事值得注意：

1. `alt` 的变量数是 sequence 模型的 4.6 倍（`32 / 7`），二元变量几乎占满全部变量（`31 / 32`，唯一的连续变量是目标里的完成时间表达）；
2. sequence 模型的「变量 7 = 3 个二元 + 3 个开工时间 + ... 」看起来更省，但它省下的代价在后面要用搜索成本付（Day 6）；
3. **`hand3_parallel` 只有 `milp_alt` 一行**：并行机实例对 sequence 模型来说超出定义范围，它返回 `FAILED`（第 7 节第 4 段会出现这个状态）。

`alt` 的变量数不是「多了一点」，而是随 `H` 线性增长的量级差异。换一个更大的实例看同一个比值：8 job 单机实例（`H = 71`）上，`sequence` 是 `44` 个变量，`alt` 是 `475` 个，比值 `10.8` —— **3 个 job 时是 4.6 倍，8 个 job 时是 10.8 倍**，这个比值会随实例规模继续变大（Day 7 实测到 40 个 job 时是 `17.1` 倍）。

本仓库因此设了一道闸门：

```python
if var_estimate > MAX_TIME_INDEXED_VARS:      # 400_000
    raise ValueError(f"time-indexed 变量数估算 {var_estimate} 超过上限 "
                     f"{MAX_TIME_INDEXED_VARS}（H={horizon}），请缩小子实例")
```

**超过闸门时如实拒绝建模，而不是让整批实验卡在一个巨型模型上。** 这是接口纪律：一个「可能跑一小时也可能跑不动」的方法，比一个「明确拒绝」的方法更难用。

## 5. 等价性：操作定义与三类证据

### 5.1 定义

**定义（等价性，本日的操作口径）**：设 `z_seq`、`z_alt` 分别是两个模型在同一个实例、同一个目标上的最优值，若 `z_seq = z_alt`（在容差内），称两者在**该实例、该目标**上等价。

这个定义比「两个模型表达同一个可行域」弱，但它是可以被实验检验的，而且足以支撑后面的比较：Day 6 比较的就是最优值与界。需要强调的是：**等价是最优值相等，不是最优排程相同**（第 7.3 节会给出实测例子）。

### 5.2 三类证据，强度从高到低

| 证据 | 做法 | 强度 | 本日结果 |
|---|---|---|---|
| 独立穷举对拍 | 与 M1 的 `exhaustive_optimum` 比（枚举另一条计算路径） | 最强 | 6 行全部一致 |
| 跨 formulation 一致 | 三个模型互相比较（`tight` / `loose` / `alt`） | 辅助 | 3 个目标全部一致 |
| 排程过验证器 | 返回的排程过 `schedule_errors`（独立于模型） | 必要条件 | 0 条报错 |

**为什么「三个模型互相一致」只算辅助证据**：三个模型可能一起错 —— 例如三处都用了同一个错误的时间界，就会一致地给出偏大的目标值。**「一致」不能代替「对拍」**，这一点在自测题里会专门考。

反过来，「过验证器」是必要条件但不能证明最优性：它只能说明交出的排程是可行的，不能说明它是最优的。三类证据合起来才构成完整的正确性论证：

```text
穷举对拍   → 最优值对（主证据）
跨模型一致 → 没有互相矛盾（辅证据）
过验证器   → 交出去的排程可行（必要条件）
```

## 6. 实现：time-indexed 模型的三处关键

脚本 [m2w2d5_alt_formulation_equivalence.py](../../projects/02_optimization_models/examples/m2w2d5_alt_formulation_equivalence.py)，模型实现在 [milp_scheduling.py](../../projects/02_optimization_models/opt_models/milp_scheduling.py) 的 `build_time_indexed_model`。

**第一处：变量窗口由 `earliest_start_bounds` 决定。**

```python
for t in range(earliest[op.id], latest - op.processing_time + 1):
    var = _binary(solver, f"y_{op.id}_{machine_id}_{t}", relax)
```

窗口为空（`latest - p < earliest`）时抛 `InfeasibleModelError`，在 `_run` 里被映射成 `INFEASIBLE` 而不是 `FAILED` —— 这与 Day 1 的 `deadline` 机制是同一个出口：**建模阶段就能证明的不可能性，不该和建模错误混在一起**。

**第二处：容量约束的覆盖区间。**

```python
covering = [
    var
    for op in instance.operations
    if machine_id in op.eligible_machine_ids
    for t in range(max(earliest[op.id], tau - op.processing_time + 1), tau + 1)
    if (var := y.get((op.id, machine_id, t))) is not None
]
if covering:
    solver.Add(solver.Sum(covering) <= 1)
```

`covering` 的构造有两个细节：起点取 `max(最早开工, τ - p + 1)`（不早于时间窗），终点取 `τ`（开工时刻不晚于 `τ` 才能覆盖时刻 `τ`）；若某台机器在 `τ` 时刻没有任何可能的工序，则不加约束（`if covering`），避免往模型里塞空约束。

**第三处：完成时间的表达与选机指示量。**

```python
start_expr[op.id] = solver.Sum([t * y[key] for key in window])
built.end_expr[op.id] = start_expr[op.id] + op.processing_time
built.selectors[op.id] = [(m, solver.Sum(per_machine[m])) for m in op.eligible_machine_ids]
```

`Σ t·y` 里每个 `t` 是常数，所以整条表达式对变量是线性的（**没有乘积项**，Day 2 第 4.2 节留的伏笔在这里收口）。`selectors` 是「选机指示量」：`per_machine[m]` 的和为 1 的那个 `m` 就是被选中的机器，解码时取「取值最大」的那个 —— 这一套 `selectors` / `end_expr` 抽象让 `_decode` 对两个 formulation 通用：**解码器只认「结束时间表达式 + 选机指示量」，不关心模型长什么样**。

两个 formulation 各自往这两个槽里填什么，对照如下：

```text
                  end_expr                          selectors
sequence         s_j + p_j                         [(唯一机器, 常量 1.0)]
time-indexed     Σ_{m,t} (t + p_o)·y[o][m][t]      [(m, Σ_t y[o][m][t]) 对每个可达 m]
```

`sequence` 的选机指示量是常量 `1.0`（因为单机实例里每道工序只有一台可选机器），`time-indexed` 的是一个变量之和。解码时用「取值最大」而不是「等于 1」来挑机器，正是为了让这两种形状走同一条代码路径。**这也是 Day 5 能用一个 `milp_alt` 同时覆盖单机与并行机的原因**：模型规模与机器数无关地写在同一个循环里，解码器也不需要为并行机写分支。

### 7.1 第 2 段：与独立穷举对拍

这一段的读法与《Day 1 第 7.2 节》的三条数字链完全一致，只是把「手算」换成了「穷举」：

```text
3 job 实例：穷举 3! = 6 个加工顺序 → 三个目标的最优值 9.0 / 1.0 / 16.0
2 机 3 job 实例：穷举 6 种顺序 × 选机 = 48 种组合 → 7.0 / 0.0 / 15.0
```

**六个格子里的每一个都同时满足两件事**：三个 formulation 互相一致，且等于穷举值。注意 `hand3_parallel` 那三行的 `tight` 与 `loose` 列是 `—`：并行机实例上那两个方法返回 `FAILED`（各自的用例在 `tests/test_milp_scheduling.py` 里单独覆盖），所以对拍只能拿 `alt` 一个列去比 —— 这也是 `alt` 的适用范围更广的直接证据。

### 7.2 第 4 段：sequence 模型做不到的事

实例是 2 个 job、每个 2 道工序、全部在 `M0` 上，工序链为 `A1(2) → A2(3)` 与 `B1(4) → B2(1)`，目标是 `ΣCj`：

```text
独立枚举（满足 precedence 的加工顺序共 6 个）：ΣCj 最优 = 15
milp_alt：status=OPTIMAL  ΣCj=15  best_bound=15  nodes=0  solve_time=0.013s
sequence 模型：milp_tight=FAILED  milp_loose=FAILED
alt 给出的排程：A1[0,2) A2[2,5) B1[5,9) B2[9,10)   （独立验证器报错 0 条）
```

三件事：

1. **`alt` 一次就解对了**（`best_bound = objective = 15`，`nodes = 0`），因为它把 precedence 写成了第 ③ 组约束；
2. **sequence 模型如实拒绝**（`FAILED`），而不是硬套一个不正的模型 —— 它的变量定义是「同一台机器上谁先谁后」，多工序超出定义范围；
3. **precedence 由独立验证器检查**，不是模型自己说了算。`schedule_errors` 会检查「同 job 的后道工序不早于前道完工」，这一条与模型无关。

第 2、3 点合起来说明了一件事：**适用范围也是模型的一部分**。一个只能做单机单工序的模型，即使写得再漂亮，也不能回答「多工序 + 选机」的问题；反之一个能做多工序的模型，在单机单工序上也不会因此变差。Day 6 的比较必须在这种「适用范围有差别」的前提下进行 —— 比较的口径只能是「都能做的那些实例」。

### 7.3 第 5 段：等价的边界

```text
milp_tight  ΣTj=1  排程 OB(0-2) OA(2-5) OC(5-9)
milp_loose  ΣTj=1  排程 OB(0-2) OA(2-5) OC(6-10)
milp_alt    ΣTj=1  排程 OB(0-2) OA(2-5) OC(5-9)
```

三行都给出 `ΣTj = 1`，但 `loose` 给出的排程**与另外两个不同**：`C` 从 `5` 推到 `6`，完工从 `9` 变成 `10`，仍然不迟交（`d_C = 10`）。

**三行都满足 `C_C = 9` 或 `10` 时 `T_C = 0`**，所以目标值相同 —— 这就是「等价」与「同一个排程」的差别：

> 等价性说的是**最优值**相同。最优解可能有多个（本实例至少两个），不同的 formulation 在不同的最优解上停住是完全正常的。**把「排程不同」当成「模型不等价」是这类对拍里最常见的误判。**

要检验「排程是否真的等价」需要额外工作（例如比较目标值集合、或在目标里加一条极小的扰动打破平局），本日不做。要注意的是，`milp_loose` 报出的目标值仍然经过了 `_finish` 的重算与 `schedule_errors` 的复核，所以它的 `ΣTj = 1` 是可信的。

### 7.4 本日证据的边界

今天验证了等价性，但验证的范围必须写清，否则很容易被读成「已经证明两个模型在所有实例上等价」：

| 已覆盖的 | 未覆盖的 |
|---|---|
| 3 job 单机：3 个目标（`makespan`、`ΣTj`、`ΣwjCj`） | 更大的实例（穷举只能到 3–4 个 job） |
| 2 机 3 job：3 个目标（48 种组合） | `oracle` 不支持的其余 3 个目标（只做了跨模型一致，未与穷举对拍） |
| 2 job × 2 工序带 precedence：1 个目标（6 个合法顺序） | 更长的工序链、更复杂的机器资格约束 |
| 与独立穷举的最优值对拍 | 「可行域完全相同」这种更强的等价（本日只验证了最优值） |

三层证据叠起来给出的是**归纳性的可信度**：模型在小实例上与一条独立计算路径完全吻合，在大实例上互相不矛盾、返回的排程都过验证器。这正是工程上「可以被接受的正确性」的标准形状 —— **它不是数学证明，但它的每一条都能被复现、被质疑、被推翻**。Day 6 的比较建立在这个基础上。

## 10. 自测题

- Q1：`y[o][m][t]` 同时编码了哪两个决策？为什么一个变量就能编码两个？
- Q2：time-indexed 模型的容量约束覆盖的开工时刻区间是什么？为什么不是 `[τ, τ + p - 1]`？
- Q3：为什么 time-indexed 模型不需要 Big-M？这与它的松弛强度有什么关系？
- Q4：`earliest_start_bounds` 为什么要加上「同 job 前置工序的总加工时间」？
- Q5：本日 `hand3` 上 `alt` 用了 32 个变量、`sequence` 用了 7 个，多出来的变量买到了什么？
- Q6：「三个 formulation 一致」为什么只是辅助证据？
- Q7：「排程过验证器」能证明最优性吗？它证明了什么？
- Q8：为什么 sequence 模型在 2 job × 2 工序实例上返回 `FAILED`，而不是给一个近似答案？
- Q9：等价性是否要求最优排程相同？请用本日的输出举例说明。
- Q10：如果一个实例的时间界 `H` 很大（例如 5000），time-indexed 模型会发生什么？本仓库怎么处理？

### 参考答案

- A1：编码了「选哪台机器」与「什么时候开工」两个决策。因为机器集合与时间格点的笛卡尔积被直接当作变量下标，一个 `= 1` 的变量就唯一确定了机器与时刻。
- A2：覆盖 `[τ - p_o + 1, τ]`。因为「在时刻 `τ` 正在加工」等价于「开工时刻 `t` 满足 `t <= τ <= t + p_o - 1`」，把不等式整理即得 `τ - p_o + 1 <= t <= τ`。
- A3：机器互斥被写成「每台机器每个时刻的占用数 `<= 1`」这条容量约束，它不含析取逻辑、不需要二元变量之间的「谁先谁后」；LP 放松后容量约束**仍然在起作用**（不会像 Big-M 那样被两边同时放松），这正是界从 `0` 抬到最优值附近的机制。
- A4：因为同 job 的工序必须按顺序加工，第 `k` 道工序不可能早于 `r_job` 加上前 `k-1` 道工序的总加工时间；把这段不可能的时间格点剪掉可以直接减少二元变量个数。
- A5：买到了「不需要 Big-M 的互斥表达」与「容量约束在 LP 放松后仍有效」，也就是更强的松弛；代价是变量数随时间界线性增长，以及更大的模型与建模时间。
- A6：因为三个模型可能共享同一个错误（例如都用了同一个错误的界或解码），从而一致地给出错误答案；只有与**另一条独立计算路径**（穷举）比较才能排除这一类共同错误。
- A7：不能证明最优性。它只证明了「交出去的排程是可行的」—— 可行性与最优性是两件事。
- A8：因为「一个 job 多道工序」超出它的变量定义范围（它的 `x_jk` 只描述「同一台机器上两道工序的先后」）；如实拒绝比硬套一个不正的模型更可信。
- A9：不要求。本日输出里 `milp_loose` 给出 `OC(6-10)` 而 `milp_tight` / `milp_alt` 给出 `OC(5-9)`，三者 `ΣTj` 都是 `1`，因为 `C_C = 9` 与 `10` 都不超过 `d_C = 10`。
- A10：变量数估算会超过规模闸门 `MAX_TIME_INDEXED_VARS = 400_000`，模型在建模阶段就抛 `ValueError`、由 `_run` 记成 `FAILED`；本仓库选择如实拒绝，而不是让整批实验卡在一个巨型模型上。

## 11. 今日一句话总结

> **time-indexed 模型把「谁先谁后」换成「在哪个时刻开工」，用机器容量约束替代 Big-M，从而在 LP 放松后仍然保住机器互斥；它的正确性由与独立穷举的对拍保证（3 job 与 2 机 3 job 的 6 个目标全部一致），代价是变量数随时间界线性增长 —— 等价说的是最优值，不是最优排程。**
