## 1. 今日学习目标

完成今天的学习后，你应该能够：

1. 用 `indicator logic` 的记号写出「`x = 1` 时某条线性不等式成立」这类条件约束，并说清它为什么不是线性约束。

## 2. 为什么 Day 2 要专门做线性化

Day 1 把析取写成了：

```text
s_k >= s_j + p_j - M_jk·(1 - x_jk)
```

这条式子本身没有任何新鲜内容：**它只是把「要么……要么……」用一个足够大的数抹掉了一侧**。真正需要论证的只有一件事：

> 这个 `M` 到底多大才算够？拿什么保证它不会把真正的可行解也一起抹掉？

这个问题的答案有两种给法，一种很常见、另一种很可靠：

```text
常见给法（不可证明）：M = 10^6，因为「反正足够大」
  问题：当 Σp 超过 10^6 时它就不再足够大，而模型不会报错。
可靠给法（可证明）：M 由有效时间界 H 推出，上界有明确的式子
  好处：换任何实例都能重算，且能逐对验算
```

今天要把第二种给法做到底，并且**故意做一次错的**，把两种失败模式的形状看清楚。后面所有关于松弛强度的讨论都建立在一个前提上：模型是精确的、`M` 是合法的。前提不牢，后面的比较没有意义。

## 3. 概念与推导：从指示逻辑到 Big-M

### 3.1 定义（indicator logic）

**定义（指示约束）**：设 `x ∈ {0, 1}`，`a` 为系数向量，`b` 为常数，称下面两条为一对指示约束：

```text
x = 1  ⇒  a'z <= b          （x 取 1 时这条不等式必须成立）
x = 0  ⇒  a'z <= b'         （x 取 0 时另一条成立）
```

「`⇒`」不是线性约束：它描述的是一组**条件**成立的集合，两个条件分支的并集一般是非凸的（Day 1 第 2 节）。把 `⇒` 变成线性的标准手法是引入一个足够大的常数：

```text
x = 1  ⇒  a'z <= b      ⟺      a'z <= b + M·(1 - x)
```

右侧在 `x = 1` 时退化为 `a'z <= b`，在 `x = 0` 时变成 `a'z <= b + M`。**代价是这条不等式在 `x = 0` 时不再有约束力，而这也是它的目的**：它在 `x = 0` 时必须不起作用。

### 3.2 推导：M 的充分条件是「被放松那一侧的最大松弛量」

把上面那条不等式写成调度里的形式，取 `a'z` 为「某一对 job 的先后关系」：

```text
x_jk = 1  ⇒  s_k >= s_j + p_j
```

对照 Day 1 的实现，我们把它写成 `s_k >= s_j + p_j - M_jk·(1 - x_jk)`。要让这条不等式在任何可行排程上都成立，只需：

```text
M_jk >= max { s_j + p_j - s_k  :  可行排程里 k 排在 j 之后 }
```

注意这个最大值是**在真实可行域上取的**，而不是在所有排程上取 —— 定义域越清楚，能给出的 `M` 越小。原则上可以「穷举全部排程」算出每一对的最小可行 `M`（在 8 job 实例上实测，逐对最小可行 `M ∈ [61, 66]`），但穷举本身是指数级的，只能做实验校准，不能成为通用算法。

通用做法是**放缩**：

```text
s_j + p_j - s_k  <=  H - r_k            （用 C_j <= H 与 s_k >= r_k）
```

于是得到一个与实例数据直接相关的合法 `M`：

```text
M_jk = H - r_k
```

这个式子里有一处容易记错：**`r_k` 是「后者」的释放时间**（`k` 是排在后面的那个），因为被放松的是「`k` 先于 `j`」那一侧的约束，而那一侧越靠后、能暴露的差距越大。释放时间越大，界越小 —— 这正是「逐对比全局常数紧」的唯一来源。

### 3.3 推导：本仓库用的两种 M

| 名称 | 取值 | 合法性论证 |
|---|---|---|
| tight | `M_jk = H - r_k`（逐对、两方向各一个） | 由第 3.2 节的不等式直接得到 |
| loose | `M = n · H`（全局一个常数） | `n·H >= H >= H - r_k`，即它是 tight 的上界 |

`loose` 的意义不在于「它好用」，而在于**它是一个可证明的松**：任何实例上都能算出 `n·H` 并写出上面的两行不等式。这与 `M = 10^6` 有本质区别 —— 后者的「合法」依赖于「问题规模不会超过 10^6」这个**没有写进任何地方的假设**。

### 3.4 逻辑方向核对表

`M` 的系数写反（该乘 `x` 的写成 `1 - x`）是这类模型最常见的错误，而且它往往不会报错，只会给出奇怪的排程。用一张表核对：

| 要表达的逻辑 | 线性写法 | `x = 1` 时 | `x = 0` 时 |
|---|---|---|---|
| `x = 1 ⇒ s_k >= C_j` | `s_k >= s_j + p_j - M_jk(1 - x)` | 生效：`s_k >= C_j` | 放松：`s_k >= C_j - M_jk` |
| `x = 0 ⇒ s_j >= C_k` | `s_j >= s_k + p_k - M_kj·x` | 放松：`s_j >= C_k - M_kj` | 生效：`s_j >= C_k` |

**核对口诀**：「生效的一侧不要带 `M` 项，放松的一侧要带足 `M` 项」。`M` 项与「生效方向」必须互补 —— `x = 1` 生效的式子乘 `(1 - x)`，`x = 0` 生效的式子乘 `x`。

## 4. 乘积线性化：什么时候真的需要它

### 4.1 定义（二元 × 连续的乘积线性化）

**定义（McCormick 线性化）**：设 `x ∈ {0, 1}`、`y ∈ [L, U]`（有限），要表达乘积 `z = x·y`，可用下面四条线性不等式（令 `L`、`U` 为 `y` 的界）：

```text
z <= U·x
z >= L·x
z <= y - L·(1 - x)
z >= y - U·(1 - x)
```

验证只需看两个端点：`x = 1` 时中间两条给出 `z <= y` 与 `z >= y`，即 `z = y`；`x = 0` 时前两条给出 `z <= 0` 与 `z >= 0`，即 `z = 0`。**它的形状与 Big-M 完全一样**：也是用界把「不该起作用的一侧」撑开，区别只是撑开的量级由 `y` 的界决定，而不是由约束右边的常数决定。

### 4.2 本模型为什么不需要乘积线性化

回到 Day 1 的两条 disjunctive 约束：

```text
s_k >= s_j + p_j - M_jk·(1 - x_jk)
```

右边的 `M_jk` 是一个**常数**（`H - r_k`），乘上 `(1 - x_jk)` 得到的仍是一个关于二元变量的一次表达式 —— 整条约束对变量是线性的。这里没有 `二元 × 连续` 的乘积。

真正会产生乘积的写法是让界本身变成决策：例如

```text
s_k >= s_j + p_j - (H - s_j)·(1 - x_jk)          ← 界里含变量 s_j
```

这时 `s_j·x_jk` 才是乘积，才需要上第 4.1 节的四条不等式。**「M 必须是常数」不是风格偏好，而是线性性的前提**。凡是看到「用变量当界」的写法，都要立刻警觉这里藏着乘积项。

在调度模型里，乘积还有一处常见来源：把「机器 m 是否被选中」与「开工时间」相乘（例如 `s_j = Σ_m y_jm · s_jm` 这种写法）。本仓库的 time-indexed 模型采用「二元变量自带时间下标」的写法绕开了它：`y[o][m][t] = 1` 本身就编码了选机与时刻，开工时间写成加权和 `Σ t·y`，是二元变量的线性组合（每个 `t` 是常数），仍然没有乘积。

## 5. 手算：逐对验证 M 从不切掉可行解

验证的实例是 4 个 job 的单机实例（本仓库 `four_jobs`）：

| job | `r_j` | `p_j` | `d_j` | `H - p_j` |
|---|---|---|---|---|
| J0 | 0 | 3 | 6 | 16 |
| J1 | 2 | 4 | 9 | 15 |
| J2 | 5 | 2 | 20 | 17 |
| J3 | 1 | 5 | 12 | 14 |

`H = max r + Σ p = 5 + (3+4+2+5) = 19`。逐对 `tight` 的取值为 `{19 - r_k}`，也就是 `{14, 17, 18, 19}` —— 四个 job 的释放时间分别是 `0/2/5/1`，所以四个 `M` 值互不相同。`loose = 4 × 19 = 76`，是 tight 最大值的 4.00 倍。

**「合法」的操作定义**：枚举全部 `4! = 24` 个加工顺序，对每个顺序、每一对「先加工的 `a` 与后加工的 `b`」，算出约束 `s_a >= s_b + p_b - M_ba·x` 在「这一侧被放松」时需要多大（即 `C_b - s_a`），取所有顺序上的最大值，就得到该方向所需的最小 `M`。只要所用的 `M` 不小于这个数，就没有任何可行排程会被切掉。

手算表（完整的 144 次检验见第 7 节的运行输出，这里列前几行）：

```text
job 对（后-先）   排程中需要的最大 M   tight 给的 M   合法
J1-J0                    16                19         是
J3-J0                    16                19         是
J0-J1                    14                17         是
J0-J2                    14                14         是
J0-J3                    14                18         是
J1-J2                    14                14         是
```

最紧的一对是 `J1-J0`：需要 16，而 `tight` 给了 `19`，仍有余量 3。这条余量不是浪费：`16` 是在**这 24 个排程上**取到的最大值，而 `M_jk = H - r_k = 19` 是在**所有可行排程**上给出的上界 —— 前者是「实验测到的下确界」，后者是「证明出来的上界」，两者不相等是正常的，而且方向必须正确（上界 ≥ 下确界）。

这个 16 可以手推，过程值得走一遍。要最大化「`J1` 在后、`J0` 在前」时的 `C_J1 - s_J0`：让 `J0` 尽量早、让 `J1` 尽量晚。`J0` 的 `r = 0`，可以直接从 0 开工；`J1` 想晚，就得让中间两道工序把它推后：

```text
顺序 J0 → J2 → J3 → J1：
  J0: start = max(0, 0)   = 0   end = 3
  J2: start = max(3, 5)   = 5   end = 7      ← 空转 [3, 5) 等 J2 释放
  J3: start = max(7, 1)   = 7   end = 12
  J1: start = max(12, 2)  = 12  end = 16
于是 C_J1 - s_J0 = 16 - 0 = 16，正是这一对需要的最大 M。
```

所以 `M_{J1,J0} = 19` 与「实测需要的 16」之间那 3 个单位的余量，来源是放缩 `s_j + p_j - s_k <= H - r_k` 里丢掉的细节：`H` 是「所有工序」的加工时间之和，而这个排程里 `J0` 只占 3 个时间单位。**余量就是这样来的：放缩换来了通用性，代价是系数偏大。**

## 6. 实现：两种 M 在代码里怎么来

[milp_scheduling.py](../../projects/02_optimization_models/opt_models/milp_scheduling.py) 里，`M` 的两种取法各自是一个纯函数，不含任何求解逻辑：

```python
def pair_big_m(instance, horizon):
    release = {job.id: job.release_time for job in instance.jobs}
    return {
        (a.id, b.id): horizon - release[b.id]
        for a in instance.jobs
        for b in instance.jobs
        if a.id != b.id
    }

def loose_big_m(instance, horizon):
    return len(instance.jobs) * horizon
```

`pair_big_m` 返回的是**有序对**的字典：键 `(a, b)` 对应的值是 `M_ab`，即「在约束 `s_b >= s_a + p_a - M_ab·(...)` 里用的界」。因为两方向的 `r` 不同，`M_ab ≠ M_ba`，这一点在 Day 1 的第 7 节已经从打印出来的约束里看过一次。

建模时的调用只有两行（[milp_scheduling.py](../../projects/02_optimization_models/opt_models/milp_scheduling.py) 的 `build_sequence_model`）：

```python
m_fs = pairs_m[(first.id, second.id)] if tight else m_loose
m_sf = pairs_m[(second.id, first.id)] if tight else m_loose
```

`tight=False` 时两个方向都用同一个 `m_loose` —— **这是 tight 与 loose 两个模型唯一的差别**：变量数、约束数、非零元数完全相同。

模型建好后，与 `M` 有关的三个数字会记进 `built.meta`：

```text
big_m_min / big_m_max / big_m_sum
  tight：对逐对界取最小值与最大值，sum = Σ_{(j,k)} M_jk
  loose：三个键都来自同一个 n·H（因此 min == max，sum = 2·C(n,2)·n·H）
```

这三个键的作用是让「松紧」变成可比较的数。把它们和变量数、约束数摆在一张表里，就能确认一件事：**tight 与 loose 的差别只在系数取值上，不在模型结构上**。

### 7.1 第 1–3 节在说什么

第 1 节的 `H = 14` 是 3 job 手算实例（Day 1 那个）的值，第 2 节及之后的 `H = 19` 是 4 job 实例的值 —— **同一个符号在不同实例上取值不同，读输出时必须先确认它在说哪个实例**。这也是为什么第 2 节的表里 `H - p_j` 一列是 `16/15/17/14` 而不是 Day 1 的 `11/12/10`。

第 3 节是全篇最值得反复读的一段：它把「合法」从一句形容词变成了 144 次可复核的不等式检验。注意表里 `J0-J2` 与 `J1-J2` 两行的 tight 值恰好等于所需值 `14`：**紧到没有余量也是合法的**（余量等于 0 意味着存在一个排程恰好把这个界顶满）。反过来，若某行的「实际 M」小于「需要的最大 M」，那一行就是 `否` —— 输出里没有任何一行是 `否`。

### 7.2 第 4 节在说什么

4a 是一台「音量旋钮」：`M` 从 0 调到 42，`M <= 8` 时模型一律 `INFEASIBLE`，`M >= 9` 时给出正确的最优值 1。两次失败的性质完全不同：

```text
M <= 8：模型不可行（响亮）—— 求解器明确说「没有可行解」，使用者会立刻去查
M = 9：第一次成功，因为 9 = H - r_C = 14 - 5 恰好是逐对界里最小的那个
```

`9` 这个数字不是巧合：`H - r_C` 就是「C 参与的那一对」所需的最小可行 `M`，而 C 是唯一有释放时间的 job。**当天平上唯一有 `r > 0` 的 job 恰好在最紧的那一对里时，逐对界与全局最小值会重合** —— 这也解释了为什么 4a 里出现的是一个整齐的台阶，而不是参差不齐的边界。

4b 才是今天真正的收获。它保留逐对 tight 界，只把 `('A','B')` 方向的 `M` 从 14 改成 4：

```text
报告 ΣTj = 3，真最优 = 1，求解器状态 OPTIMAL，独立验证器报错 0 次
```

三件事同时成立：**结果错了、没有任何地方报错、交出去的排程完全合法**。这就是「静默失败」。它的机制可以一句话说清：

> `M` 变小只会让可行域变小。模型的可行域是**真实可行域的子集**，所以模型永远不会给出比真最优更好的值 —— 它只有两种可能：报 `INFEASIBLE`（响亮），或者把真最优排程切掉、退而求其次（静默，目标值偏大）。

第 4 行则给出了一个反向的提醒：把 `('A','C')` 的 `M` 从 9 改成 1 什么也没有改变，因为最优排程里 `A` 与 `C` 的先后关系用不到那条被放松的约束。**「改小了一个 M」本身不说明任何事，必须落到「哪一对的哪一侧」上** —— 这正是必须逐对论证、逐对验证的原因。

### 7.3 这一段实验不能证明什么

以上实验只能证明**本实例上**两种 `M` 都没有切掉可行解（24 个排程全部检验过），以及**本实例上**把 `M` 取小会产生什么后果。它不能证明：

- 「tight 比 loose 更好」—— 合法性一样，好坏只能由搜索行为与松弛强度回答；
- 「`M_jk = H - r_k` 是唯一的合法取法」—— 它是**一个**可证明合法的取法，逐对最小可行 `M` 的下确界还可以更小（在本仓库的 8 job 实例上是 `[61, 66]`，而 tight 给的是 `[61, 69]`）。

## 10. 自测题

- Q1：为什么「`x = 1 ⇒ a'z <= b`」不能直接写进 LP？
- Q2：把 `x = 1 ⇒ s_k >= s_j + p_j` 写成 Big-M 形式，`M` 应该乘 `x` 还是 `1 - x`？为什么？
- Q3：`M_jk = H - r_k` 里的 `r_k` 是「先加工」还是「后加工」的释放时间？
- Q4：为什么 `M` 的取值可以用「被放松那一侧的最大松弛量」来刻画？这里的「最大」是在哪个集合上取的？
- Q5：为什么 `loose` 的 `n·H` 一定不小于任何逐对 `M_jk`？写出两行不等式。
- Q6：本模型的 `M_jk·(1 - x_jk)` 是乘积项吗？需要 McCormick 线性化吗？
- Q7：什么时候调度模型里会出现真正的乘积项？举一个例子。
- Q8：4a 实验里为什么 `M = 9` 是第一个成功的值？
- Q9：4b 实验里把 `('A','C')` 的 `M` 改小为什么没有影响？
- Q10：如果 `M` 取小了而模型给出偏大的目标值且验证器无报错，本仓库还有哪一道关卡能发现问题？

### 参考答案

- A1：该集合是两个分支的并集，一般是非凸的；LP 的可行域必为凸集，无法表达非凸集合，所以必须先引入二元变量再用 Big-M 抹掉一侧。
- A2：乘 `(1 - x)`。`x = 1` 时该式退化为要表达的逻辑（生效），`x = 0` 时右侧减掉 `M` 从而不起作用（放松）；乘 `x` 会让生效与放松的方向反掉。
- A3：后加工的那个（`M_jk` 里的下标 `k` 就是排在后面的那个 job）。4 job 实例上取值集合为 `{14, 17, 18, 19}`，四个值互不相同，正来自四个互不相同的 `r_k`。
- A4：因为约束要「在任何真实可行解上都不被切掉」，所以 `M` 只需覆盖真实可行域内该表达式可能取到的最大值；这个最大值在真实可行域上取，定义域越紧得到的 `M` 越小。
- A5：对任意 job `k` 有 `r_k >= 0`，故 `H - r_k <= H`，于是逐对界的最大值 `max_k (H - r_k) <= H`；又 `n >= 1` 故 `H <= n·H`。串联起来 `n·H >= max_k (H - r_k) >= M_jk`，即 `n·H` 是全体逐对界的一个上界，因而合法。
- A6：不是乘积项。`M_jk` 是常数，`M_jk·(1 - x_jk)` 关于变量是一次表达式；不需要 McCormick 线性化。
- A7：当「界本身含决策变量」时，例如用 `(H - s_j)` 当作放松量，就会出现 `s_j·x_jk`；本仓库用常数界绕开了它，time-indexed 模型用「二元变量自带时间下标」也绕开了它。
- A8：因为该实例里唯一 `r > 0` 的 job 是 `C`（`r_C = 5`），逐对界的最小值恰是 `H - r_C = 9`，它也是所有会用到的界里最小的那个。
- A9：最优排程里 `A` 与 `C` 的先后关系并没有用到那条被放松的约束（那一侧在最优解上不是紧的），所以改小它不改变可行域中与最优解相关的部分。
- A10：`_finish` 中的下界一致性检查：若 `best_bound > 独立重算的可行解目标值 + 1e-6`，直接判 `FAILED`。`M` 取小会让模型的界高于真实最优，一旦该值超过独立重算的可行解目标值就会被拦下；但若 `M` 只是略小（如 4b 的情形），这道关卡也不一定触发 —— 这是它仍然危险的原因。

## 11. 今日一句话总结

> **Big-M 的内容只有两句话：`M` 必须不小于「被放松那一侧在真实可行域上的最大松弛量」，而有效时间界给出了这个最大值的可证明上界；`M` 取小只有两种结局 —— 报 `INFEASIBLE` 的响亮失败，或者给出偏大目标值却全程无报错的静默失败。**
