## 2. 为什么 Day 1 要从 sequence 模型开始

Week 1 的全部主角是 LP：连续变量、可行域是多面体、最优解在极点上取到。LP 有一个它**做不到**的表达式 —— 析取。请看下面这句话：

```text
机器 M0 要么先加工 A 再加工 B，要么先加工 B 再加工 A。
```

它的两个分支各自都是线性的：

```text
分支一：C_B >= C_A + p_B      （A 在 B 之前）
分支二：C_A >= C_B + p_A      （B 在 A 之前）
```

但「要么……要么……」本身不是线性约束：

```text
{ C_B >= C_A + p_B } ∪ { C_A >= C_B + p_A }
```

这个并集画在平面上是一个非凸的「L 形」，而任何 LP 的可行域都是凸集。**LP 写不出非凸集合，这就是整数变量必须出场的唯一原因**。

今天要做的事，就是把这句话交回给求解器，代价是引入二元变量：

```text
Week 1  LP：连续变量，整数性靠矩阵结构（全幺模）白送
Week 2  MILP：整数性要向求解器索取，先付二元变量的代价
        Day 1  直接把「谁先谁后」写成二元变量、把析取写成 Big-M 不等式   ← 今天
        Day 2  把 Big-M 的合法性论证清楚（多小算够？取小了会怎样？）
        Day 3  用 LP relaxation 量出这个模型的松弛到底有多松
```

sequence 模型（也叫 disjunctive 模型、排序模型）是最贴近「车间里那句话」的写法，也是后面所有比较的基准：Day 2 在它身上讲线性化，Day 3 在它身上量松弛强度，Day 6 拿它和另一种 formulation 对拍。先把这一版写对，后面才有可比的基准。

## 3. 模型：三族变量与三类约束

### 3.1 定义（单机 sequence MILP）

**定义（单机 sequence 调度 MILP）**：给定 job 集合 `J`（每 job 恰好一道工序）、加工时间 `p_j`、释放时间 `r_j`、交期 `d_j`，以最小化总迟交 `ΣTj` 为目标：

```text
min   Σ_j T_j

s.t.  s_k >= s_j + p_j - M_jk·(1 - x_jk)      对每一对 j < k     (disjunctive)
      s_j >= s_k + p_k - M_kj·x_jk            对每一对 j < k
      T_j >= s_j + p_j - d_j                  对每个 j           (tardiness)
      s_j ∈ [r_j, H - p_j]   T_j ∈ [0, H]   x_jk ∈ {0, 1}
```

三族变量各自回答一个问题：

| 变量 | 含义 | 回答的问题 |
|---|---|---|
| `s_j` | 工序 `j` 的开工时刻 | 什么时候开始 |
| `x_jk`（`j < k`） | 二元，1 表示 `j` 排在 `k` 之前 | 谁先谁后 |
| `T_j` | 迟交量 | 迟到了多少 |

### 3.2 约束为什么是这个样子

**互斥约束**。以 `x_jk = 1`（`j` 先）为例：

```text
x_jk = 1  ⇒  s_k >= s_j + p_j - M_jk·(1 - 1) = s_j + p_j     ← 正是要的逻辑
x_jk = 0  ⇒  s_k >= s_j + p_j - M_jk                          ← 右边被减掉 M_jk，自动成立
```

所以 `M_jk` 的职责只有一个：当 `x_jk = 0`（这条约束「不该起作用」）时，把它放松到**永远不会切掉任何可行解**。第二族约束里的 `M_kj` 乘的是 `x_jk` 而不是 `1 - x_jk`，作用是反过来在 `x_jk = 1` 时把 «`j` 排在 `k` 之前» 的同侧约束放松。一句话概括：

> **每条 disjunctive 约束都有一个「生效方向」和一个「必须被放松的方向」，两个方向各自需要一个独立的 `M`。**

这一点在本实例里立刻能看出差别：`A` 的释放时间是 0，`C` 是 5，所以 `M_AC = H - r_C = 9` 而 `M_CA = H - r_A = 14` —— 同一个 job 对的两个方向，`M` 是不同的数。

**迟交约束**。`T_j >= s_j + p_j - d_j` 只给了下界，没有上界。这在最小化目标下是**充分**的：

> **结论（建模决策，非定理）**：当目标里 `T_j` 的系数为正、且 `T_j` 不出现在任何「需要它小」的约束中时，`T_j >= max(0, C_j - d_j)` 与「`T_j >= C_j - d_j` 加上变量下界 0」等价 —— 因为任何一处「多报的迟交」都会被目标函数压回去。

如果目标改成 `max(-T_j)`、或者把 `T_j` 用在一条 `T_j <= 5` 这样的约束里，这个论证立刻失效，必须把两支都写出来。**条件必须跟结论一起记**。

### 3.3 有效时间界 H（理论结论）

**理论结论**：对目标关于完工时间单调不减的问题（`Cmax`、`ΣCj`、`ΣwjCj`、`Lmax`、`ΣTj` 都是），存在一个最优排程，其所有完工时间都不超过

```text
H = max_j r_j + Σ_j p_j
```

证明是一段「把空隙填掉」的论证：

```text
取任一可行排程（按开工时间排好）。从左往右扫描：
  若机器此刻空闲、而某道未加工工序已释放 → 把它整体提前
  若机器此刻空闲、但所有未加工工序都没释放 → 只能空转，等待
提前只会让该工序及其后继的完工时间不变或更小，
所以每一步都不增加任何 C_j，也就不增加任何目标值。
扫完后机器的空转只可能发生在「等释放」上，空转总量 <= max_j r_j，
于是每道工序的完工时间 <= max_j r_j + Σ_j p_j = H。
```

这条界今天是三处地方的共同根据：

1. `s_j` 的变量上界 `H - p_j`（今天验证：`s_C ∈ [5, 10]`，`10 = 14 - 4`）；
2. `T_j` 的变量上界 `H`；
3. 两种 Big-M 的合法性（Day 2、Day 3 展开）。

## 4. 手算：3 个 job 的小实例

实例（本仓库 examples 与 tests 中的 `hand3`）：

| job | `r_j` | `p_j` | `d_j` |
|---|---|---|---|
| A | 0 | 3 | 4 |
| B | 0 | 2 | 2 |
| C | 5 | 4 | 10 |

`H = max(0, 0, 5) + (3 + 2 + 4) = 5 + 9 = 14`。

先手算最优值，**不看模型**：

```text
若想让 ΣT_j = 0，则 A 必须在 4 前完工、B 必须在 2 前完工、C 在 10 前完工。
B 的 p = 2 且 d = 2，只可能在 [0, 2) 加工（唯一可能）。
A 的 p = 3，最早只能在 B 之后开工，即 [2, 5)，完工时刻 5 > 4 → A 至少迟交 1。
C 的 r = 5，可以排在 [5, 9)，完工 9 <= 10，不迟交。
于是 ΣT_j >= 1，而排程 B[0,2) A[2,5) C[5,9) 恰好取到 1。
```

所以**真最优是 1，最优排程是 B → A → C**。这段推理没有用任何求解器，它就是第 7 节里用来对账的那把尺子。

再把 6 个加工顺序全部手算一遍（`start = max(机器空闲时刻, r_j)`，写成 `id[start,end)`）：

```text
顺序      时间线                              完工时刻        ΣT_j
A B C     A[0,3) B[3,5) C[5,9)        C_A=3  C_B=5  C_C=9    0+3+0 = 3
A C B     A[0,3) C[5,9) B[9,11)       C_A=3  C_C=9  C_B=11   0+0+9 = 9
B A C     B[0,2) A[2,5) C[5,9)        C_B=2  C_A=5  C_C=9    0+1+0 = 1   ← 最优
B C A     B[0,2) C[5,9) A[9,12)       C_B=2  C_C=9  C_A=12   0+0+8 = 8
C A B     C[5,9) A[9,12) B[12,14)     C_C=9  C_A=12 C_B=14   0+8+12 = 20
C B A     C[5,9) B[9,11) A[11,14)     C_C=9  C_B=11 C_A=14   0+9+10 = 19
```

手算表里带机器空转的行有三行：`A C B` 空转 `[3, 5)`、以 `C` 开头的两行各自空转 `[0, 5)`，全是「等释放」这一种。这不是巧合：`start = max(clock, r_j)` 已经把「能提前就提前」做完了，剩下的空转只可能发生在等释放上 —— 这正是第 3.3 节 `H` 的论证里被允许的那一种空转，所以 `C_j <= H` 依然成立。表里最小值 1 落在 `B A C`，与上段的下界论证一致。

## 5. 实现：模型在代码里长什么样

模型实现在 [milp_scheduling.py](../../projects/02_optimization_models/opt_models/milp_scheduling.py)。与今天直接相关的几块：

| 函数 | 职责 |
|---|---|
| `time_horizon(instance)` | 计算 `H = max_j r_j + Σ p` |
| `pair_big_m(instance, horizon)` | 返回逐对 `{(j, k): H - r_k}`（tight） |
| `loose_big_m(instance, horizon)` | 返回全局常量 `n * H`（loose） |
| `build_sequence_model(instance, objective_name, *, tight, relax=False, deadline=None)` | 真正建模型 |
| `build_model(instance, spec)` | 按 `spec["method"]` 分派三个注册方法 |
| `_finish(...)` | 把 `solver.Solve()` 的返回包装成 `SolveResult`（含独立复核） |

互斥约束的两条不等式在代码里就是两行 `solver.Add`：

```python
solver.Add(start[second.id] >= start[first.id] + p_first - m_fs * (1 - x))
solver.Add(start[first.id] >= start[second.id] + p_second - m_sf * x)
```

注意 `m_fs` 与 `m_sf` 是两个独立的数：`m_fs = H - r_second`，`m_sf = H - r_first`。同一个 job 对的两个方向，释放时间不同，界就不同。

**接入注册表**。三个方法名通过装饰器注册：

```python
@register("milp_tight", "单机 sequence MILP，逐对 tight Big-M（M_jk = H - r_k）")
def milp_tight(instance, spec) -> SolveResult: ...
```

`spec` 里今天用到的键：

| 键 | 作用 | 本日取值 |
|---|---|---|
| `objective` | 目标名，取自 `opt_common.bridge.M2_OBJECTIVES` | `total_tardiness` |
| `time_limit` | wall-clock 预算（秒） | `10.0` |
| `seed` | 记录用；CBC 通过 `pywraplp` 不暴露种子 | `0` |
| `root_lp` | 为 `True` 时只解 LP relaxation（Day 3 起使用） | 不用 |

`SolveResult` 是本仓库对「一次求解」的统一记账单：`status`、`objective`、`best_bound`、`schedule`、`build_time`、`solve_time`、`iterations`、`detail`。**建模时间与求解时间分开记**，因为 Day 6 要比较的两个 formulation 恰恰一个建模便宜、一个建模昂贵。

各字段在 `milp_tight` 上的来源：

| 字段 | 来源 | 本日实例取值 |
|---|---|---|
| `status` | `_SOLVER_STATUS → _M2_STATUS` 映射 | `OPTIMAL` |
| `objective` | **从解码后的排程重算**（不是求解器报的值） | `1` |
| `best_bound` | `solver.Objective().BestBound()` | `1` |
| `schedule` | `_decode(built)` 翻译 `end_expr` 与选机指示量 | `M0: OB[0,2) OA[2,5) OC[5,9)` |
| `build_time` | 建模开始到 `build_model` 返回 | `0.0005s` |
| `solve_time` | 仅 `solver.Solve()` 的 wall-clock | `0.0081s` |
| `iterations` | `solver.nodes()`，且 `iterations_kind = "branch_and_bound"` | `0` |
| `detail` | formulation 名、`big_m_min/max/sum`、变量数等元信息 | 见 `built.meta` |

其中 `objective` 取自「重算值」这一点很关键：交出去的每一个目标值都至少经过一次独立计算，**求解器报的值只作为 `detail["solver_objective"]` 留下痕迹，供对账用**。

## 6. 求解器的输出不等于证据

一个模型能跑出 `OPTIMAL` 只说明求解器认为自己找到了最优解。要把它变成可用的结论，本仓库用三道独立关卡：

```text
关卡一（约束可读）：把每条约束打印成一行式，人眼确认它等价于机器互斥。
关卡二（独立验证器）：schedule_errors(instance, schedule) 逐条检查
        —— 每道工序都在资格机器上、不重叠、不早于释放时间、precedence 满足。
关卡三（目标可重算）：用 M1 的 M2_OBJECTIVES 从排程重新算目标值，
        与求解器报的 objective 对齐；再检查 best_bound 不高于该值。
```

**关卡二与关卡三之所以有价值，是因为它们的计算路径与建模/求解完全无关**：它们只看 `Instance` 和 `Schedule` 两个数据结构，不看模型。关卡三在代码里落在 `_finish` 中：

```python
recomputed = float(M2_OBJECTIVES[built.objective_name](instance, schedule))
if best_bound > recomputed + 1e-6:
    return _no_solution(built, "FAILED", ...)   # 下界高于已验证可行解 → 模型有错
```

这条检查把「`OPTIMAL`」从一个自称升级成一件**可以被反驳的事**：一旦模型写错（例如 `M` 取小了），下界与独立重算的可行解目标值会发生矛盾，`_finish` 会直接判 `FAILED`，而不是把一个漂亮但错误的数字交出去。

### 7.1 怎么读这段输出

**第一处要读的是约束的符号。** 打印出来的第一行是

```text
-1*s_A +1*s_B -14*x_A_B >= -11
```

它不是我们写的那个形式，而是 `pywraplp` 整理后的等价形式。倒推一下：

```text
原始：s_B >= s_A + 3 - 14·(1 - x_A_B)
展开：s_B >= s_A + 3 - 14 + 14·x_A_B
移项：s_B - s_A - 14·x_A_B >= -11        ← 与打印结果一致
```

所以 `-14*x_A_B >= -11` 里的 `-11` 正是 `p_A - M_AB = 3 - 14`。**看懂这一步，`M` 在每条约束里的位置就不会再记错**：`M` 只跟二元变量在同一侧出现，且符号由「哪一侧被放松」决定。

**第二处要读的是 `M` 的两个方向不同。** 第 3、4 行是 job 对 `(A, C)`：

```text
-1*s_A +1*s_C -9*x_A_C >= -6        ← M_AC = 9 = H - r_C（C 是后者）
+1*s_A -1*s_C +14*x_A_C >= 4        ← M_CA = 14 = H - r_A（A 是后者）
```

`9 ≠ 14` 的来源只有一个：`r_C = 5` 而 `r_A = 0`。tight 的第一层「紧」就体现在这里。

**第三处要读的是 `nodes=0`。** 3 个 job 的实例对 CBC 来说太小：根节点的割平面与界就把它解完了，一次分支都没做。Day 4 会专门去看「有分支、有剪枝」的过程，Day 6 会看到 15 个 job 时 `nodes` 变成几百甚至上万。

**第四处要读的是最后一段。** `objective=1` 与第 4 节手算的 1 相同，`validate_schedule` 报错 0 条。至此这一段数字链可以接受：模型可读、求解结果可复算、排程过独立验证器。要强调的是，**这三件事没有一件是「求解器说它对」**。

### 7.2 与手算对账：三条互相独立的数字链

把第 4 节的手算与第 7 节的运行叠在一起看，同一个数字 1 有三条来源：

```text
链条一（手工下界）：ΣT_j >= 1，因为 B 只能 [0,2) 加工、A 最早 [2,5) 完工 5 > 4
链条二（模型最优值）：CBC 报 objective = 1，best_bound = 1，gap = 0
链条三（独立重算）：解码后的排程 B[0,2) A[2,5) C[5,9) 用 M1 目标函数重算 = 1
```

三条链的计算路径完全不同：链条一靠人脑推理，链条二靠 Cbc 2.10.12 的分支定界与割平面，链条三靠 M1 的 `total_tardiness`。三者一致时，我们才说「这个模型在这个实例上写对了」。**只跑出链条二是最常见的自欺方式** —— 它对倒过来的错误（模型过紧、切掉了真最优）毫无分辨力，Day 2 会给出一个具体的反例。

## 10. 自测题

- Q1：为什么 LP 写不出「机器一次只加工一道工序」？请用凸性给出理由。
- Q2：`x_jk` 与 `x_kj` 的关系是什么？本模型需要额外写一条 `x_jk + x_kj = 1` 吗？
- Q3：`H = 14` 在本实例里具体用在哪三个地方？
- Q4：为什么 `T_j` 的上界取 `H` 就够，不需要更精细的分析？
- Q5：把 `M_AB` 从 14 改成 8 会怎样？改成 16 呢？今天能确定结论的部分是什么？
- Q6：`build_sequence_model(..., tight=True)` 与 `loose=True` 的模型，变量数相同吗？约束数相同吗？
- Q7：`SolveResult.build_time` 与 `solve_time` 为什么要分开记？
- Q8：`_finish` 里 `best_bound > recomputed + 1e-6` 说明什么？为什么这个条件一定意味着模型有错？
- Q9：`milp_tight` 在并行机实例上会返回什么状态？为什么这是「如实拒绝」而不是缺陷？
- Q10：如果实例里某 job 的 `p_j = 0`，`H`、变量域、模型会不会出问题？请指出最脆弱的一处。

### 参考答案

- A1：互斥集合是两条半空间的并集，其形状是「L 形」，对两个分属不同分支的可行点取凸组合会落在两个分支之外，所以该集合非凸；LP 的可行域必为凸集，故无法精确表达。
- A2：本模型里 `x_jk` 与 `x_kj` 并非都出现，每对只建一个 `x`（`j < k` 时命名为 `x_j_k`），它的两条互补分支由两条 disjunctive 约束的 `M` 项方向区分；因此不需要额外写 `x_jk + x_kj = 1`（Day 7 会实验这条等式对松弛没有帮助）。
- A3：`s_j` 的上界 `H - p_j`、`T_j` 的上界 `H`、以及两种 Big-M 的推导（`M_jk = H - r_k`）。
- A4：因为 `T_j` 只受下界约束且目标系数为正，最小化会自己把它压到 `max(0, C_j - d_j) <= H`；上界只是为了给求解器一个有限盒子，不参与逻辑。
- A5：改成 8 会切掉可行解，模型要么 `INFEASIBLE`、要么给出偏大的目标值（Day 2 会逐对实验）；改成 16 仍然合法，但界更松。今天能确定的只有「14 与 16 都满足合法性所需的不等式」，至于哪个对搜索更快，必须由实验回答。
- A6：完全相同。`tight` 与 `loose` 只改变若干非零元的取值，变量数、约束数、非零元数一模一样（Day 3 的模型规模表给出一致的三列数字）。
- A7：因为两个 formulation 的成本结构不同：time-indexed 模型建模昂贵、搜索便宜，sequence 模型相反；合成一个数字会掩盖这个差异。
- A8：`best_bound` 是求解器给出的下界，`recomputed` 是独立验证器认可的可行解目标值；下界不可能严格高于一个可行解的目标值，所以出现该不等式说明模型表达与真实问题不一致，必须判 `FAILED` 而不是照常返回。
- A9：返回 `FAILED`，理由里写明只支持单机（行程理由含「单机」二字）；因为 sequence 模型的变量定义就是「同一台机器上谁先谁后」，多机与选机超出了它的定义范围，如实拒绝比硬套一个不正的模型更可信。
- A10：最脆弱的一处是「用加工时间推进时间轴」的那些地方：`p_j = 0` 时上界 `H - 0 = H` 仍然合法、模型也可行，但机器互斥会退化成「零长度工序可以插在任意位置」，于是排程的解读与验证器都必须允许 `start == end`；换到 time-indexed 模型（Day 5 展开）时，零长度工序只覆盖一个时间格点，容量约束的写法要单独核对。

## 11. 今日一句话总结

> **单机 sequence MILP 的全部内容就是三族变量与两类约束：用 `x_jk` 表达「谁先谁后」、用 Big-M 把析取写成两条线性不等式、用 `T_j` 把迟交变成目标里的线性项；而它的正确性不由求解器保证，由约束可读、独立验证器与目标可重算三件事共同保证。**
