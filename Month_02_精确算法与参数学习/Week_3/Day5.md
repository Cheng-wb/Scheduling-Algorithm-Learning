## 1. 先读状态，再读变量

求解器停止可能因为证明完成，也可能因为预算耗尽。状态码描述停止时得到的信息。它不是目标好坏的排行榜，也不代替业务校验。

| CP-SAT 状态 | 基本含义 | 如何处理 |
|---|---|---|
| OPTIMAL | 满足当前设置下的最优终止条件；纯可行性问题则已求解 | 读取解，并核查目标界和终止设置 |
| FEASIBLE | 找到可行解，但未完成最优性证明 | 可以交付校验后的解，保留差距 |
| INFEASIBLE | 已证明当前模型不可行 | 调查数据、约束和冲突 |
| UNKNOWN | 尚未获得可行解或不可行结论就停止 | 增加信息或预算，不能判为无解 |
| MODEL_INVALID | 模型未通过合法性验证 | 先修复模型表达或数值范围 |

基本状态定义见 [官方文档](https://developers.google.com/optimization/cp/cp_solver)。具体终止还应看本机版本、参数及 response；尤其设置了正的 gap limit 时，应报告实际 gap，避免把容差意义的终止写成严格零差距证明。

## 2. 解和界是两种可以分别存在的信息

最小化时，已知可行解给上界，求解器界给下界。即使还没有可行解，有时仍已有下界；反过来，规则启发式可以有解而不提供求解器下界。

只有实际存在解时才能读取变量。不能因为对象里有某个默认 objective 数字，就断言存在对应排程。应检查状态、解是否存在及独立验证结果。

## 3. 如何构造状态实验

可行小例：$x\in\{0,1\}$，最小化 x；不可行小例：同一域中同时要求 x=0 与 x=1；非法模型例子应使用确实不被 API 支持的表达或溢出，并查看验证错误。

“时间限制极短”不保证一定返回 UNKNOWN：小模型可能在限制前就解出。FEASIBLE 和 UNKNOWN 的出现依赖实例、版本与执行速度，所以不能把毫秒阈值当成固定语义。

## 4. 项目状态包装的边界

项目另有 FAILED、NOT_SOLVED 等工程状态，描述异常或未执行等情况。读包装词表时要区分项目自定义名称与 CP-SAT 官方枚举；不要仅凭名字推断为官方状态。

报告同时保留原始状态、统一状态、终止原因和是否有有效排程，能避免把异常、未知和不可行混成同一类“失败”。

## 5. 自测

1. FEASIBLE 的目标值能用于实际排程吗？通过独立校验后可以，但不能声称全局最优。
2. UNKNOWN 等于 INFEASIBLE 吗？不等于，前者缺乏结论。
3. 没有 objective 但有有效下界时怎样记 gap？空值；缺少上界，无法计算这一差距。
