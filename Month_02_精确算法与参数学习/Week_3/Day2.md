## 2. 为什么并行机是「选机」而不是「排序」

M1 把 `P||Cmax` 当成一个**排序**问题：给工序排一个顺序，然后按 LPT 规则依次把每道工序放到「当前负载最小的机器」上。这条路径很省事，但它有一个隐含的假设：

```text
排序 + 贪心分派  →  一个解。排序变了，解就变了。
```

Month 2 的视角不同。并行机问题的决策其实是两个：

```text
决策 1（指派）：每道工序放在哪台机器上          ← 组合决策，机器数 k 就有 k 个选项
决策 2（时间）：同一台机器上的工序怎么排先后    ← 连续决策，被 Cmax 目标压着走
```

「排序 + 贪心」是把决策 2 固定成「按某个优先级顺序」，然后顺着决策 1 走一条路。而精确模型要**同时**处理这两个决策——这正是 CP-SAT 的区间模型擅长的地方：

```text
决策 1  →  一组布尔 presence[工序][机器]
决策 2  →  时间变量 start / end 的域，与机器上的 AddNoOverlap
```

今天要建立的就是这套对应关系。它比 MILP 的写法更贴近调度语言：MILP 里「指派」要用 Big-M 把「选不选」与「时间先后」缝在一起，而 CP 里 `presence` 是原生的布尔，`AddNoOverlap` 是原生的约束，中间没有 Big-M 常数可以选择错。

## 3. 概念：选机 = 一组布尔 presence

### 3.1 定义（并行机模型的三条约束）

**定义（并行机区间模型）**：对每道工序 $o$ 与每台合格机器 $m$，建一个可选区间

```text
OptionalIntervalVar(start_o, p_o, end_o, presence[o][m])
```

再加上三条约束：

| 约束 | 写法 | 语义 |
|---|---|---|
| 恰好一个 | `AddExactlyOne(所有 presence[o][*])` | 工序 $o$ 恰好被一台机器加工 |
| 机器互斥 | `AddNoOverlap(落在机器 m 上的所有区间)` | 机器 $m$ 同一时刻只加工一个工序 |
| 时间一致 | `end_o = start_o + p_o` | 区间定义本身 |

注意一个设计细节：**同一个工序在所有机器上共享同一对 `start_o` / `end_o`**。这不是偷懒，而是语义上必须如此——工序在 M0 上开工的时刻就是它在 M1 上「假如被选中」的开工时刻，只有被选中的那个区间会真正占用时间。共享变量还顺带把「选机」与「定时」解耦：`AddExactlyOne` 只管选，`AddNoOverlap` 只管时间。

### 3.2 理论结论：为什么这样建是对的

三条可以放心使用的结论：

1. **可行性等价**：任何满足上述三条约束的赋值，去掉 `presence = 0` 的区间后就是一个合法的并行机排程（每道工序恰好一台机器、每台机器上的区间不重叠、时长正确）。反过来，任何合法排程都能读出一组满足约束的赋值。
2. **`presence` 的数量是精确的**：总数等于 `Σ_o |合格机器集合(o)|`。固定路由（每道工序只有一台合格机器）时，可选区间退化成必选区间，`presence` 数量为 0。
3. **`AddNoOverlap` 是析取约束的原生表达**：它的语义是「这些区间两两不重叠」，比用一组 Big-M 线性不等式表达的松弛紧得多。

第 1 条是本周所有模型的共同骨架：**建模正确性可以「双向验证」**——模型给的解用独立验证器查一遍（解 → 约束），约束的语义用调度定义校一遍（约束 → 解）。

### 3.3 与 MILP 写法的一个关键差别

同一件事在 MILP 里要写成：

```text
Σ_m x[o][m] = 1                                    指派：恰好一台
start[o][m'] >= end[o'][m] - M * (2 - x[o][m] - x[o'][m])   先后：Big-M 缝起来
```

两处代价：

1. **Big-M 常数**。`M` 取大了松弛松、取小了会切掉可行解，是 MILP 建模里最常见的错误来源之一。CP 的 `AddNoOverlap` 没有这个常数；
2. **变量数量的量级**。MILP 要为每个 (工序, 机器) 对都开一组时间变量，CP 的时间变量只有工序一份。

反过来说，MILP 有 `AddNoOverlap` 没有的东西——**LP 松弛与对偶界**。这个差别值得记账：今天先建立模型。

### 3.4 释放时间写进变量的下界

M1 的 `Instance` 里，释放时间挂在 **job** 上（`Job.release_time`），语义是「这个 job 的第一道工序不能早于 `r` 开工」。CP 模型把它写成变量的下界：

```python
start = model.NewIntVar(job.release_time * time_scale, horizon, f"start_{op.id}")
end = model.NewIntVar(job.release_time * time_scale + size, horizon, f"end_{op.id}")
```

两条设计考量：

1. **写进下界比写成约束更有效**。`Add(start >= r)` 与 `NewIntVar(r, horizon, ...)` 在语义上等价，但前者要等传播器去收，后者在建模阶段就已经把域限死了。CP 里**尽可能把信息放进域**，是让传播更早生效的标准手法；
2. **`end` 的下界是 `r + size`，不能写成 `r`**。因为 `end = start + size` 且 `start >= r`，所以 `end >= r + size` 是恒成立的——顺手写进去可以再省一轮传播。

还有一处容易漏：**release time 只约束 job 的第一道工序**。上面这段代码对 job 的**每一道**工序都取了 `job.release_time` 作为下界。这对本仓库的实例语义是一致的（M1 的 `release_time` 是 job 级的准备时间，整条链都要等它），但如果换成「每道工序各有自己的释放时间」，就必须改成读工序级的字段。**建模时把语义写清楚，比事后调参重要。**

## 4. 手算：两个实例的下界、LPT 与最优

### 4.1 实例 A：`p = [3, 3, 2, 2, 2]`，2 台机器

**下界**：

```text
最长工序 = 3
总工时   = 3 + 3 + 2 + 2 + 2 = 12
机器数   = 2
LB = max( 3, ceil(12 / 2) ) = max(3, 6) = 6
```

**下界可达**：把 2、2、2 放在一台机器上（负载 6），把 3、3 放在另一台（负载 6）：

```text
M0: 三个长度 2 的工序        负载 2 + 2 + 2 = 6
M1: 两个长度 3 的工序        负载 3 + 3     = 6
Cmax = 6 = LB   →   6 就是最优值
```

**LPT 在这里为什么得不到 6**：LPT 按长度降序放，每次放到当前负载最小的机器上：

```text
工序 3  →  M0（负载 3）        两台都是 0，取第一台
工序 3  →  M1（负载 3）        M1 负载 0 最小
工序 2  →  M0 还是 M1？都是 3，取第一台 → M0（负载 5）
工序 2  →  M1（负载 5）
工序 2  →  M0（负载 7）
结果：M0 = 7，M1 = 5   →   Cmax = 7 > LB = 6
```

**这就是「LPT 非最优的最小反例」**：它的失败只是因为在两个负载相等时固定选了 M0。LPT 的排序是对的（长任务先放），贪心分派在「平局」这一步上做了局部选择，而最优解需要把平局打破的方向反过来。

### 4.2 实例 B：`p = [8, 7, 6, 5]`，2 台机器

```text
最长工序 = 8
总工时   = 8 + 7 + 6 + 5 = 26
LB = max( 8, ceil(26 / 2) ) = max(8, 13) = 13
```

**LPT 这次达到下界**：

```text
8  →  M0（负载 8）
7  →  M1（负载 7）
6  →  M1（负载 7 最小）  →  M1 负载 13
5  →  M0（负载 8 最小）  →  M0 负载 13
Cmax = 13 = LB   →   最优
```

两个实例合起来说明一件事：**同一个启发式在同一类问题上的表现可以完全不同**。第一个实例里 LPT 差 1（6 → 7，相对差 16.7%），第二个实例里 LPT 正好命中下界。这也解释了为什么 Month 2 要做精确方法：**没有精确解，你无法知道某一次 LPT 的输出离最优有多远**——除非像实例 A 这样手算出下界。

### 4.3 「下界紧」是什么意思

`parallel_makespan_lower_bound` 给的是：

```text
LB = max( 最长工序, ceil(总工时 / 机器数) )
```

两条理由都很直接：任何工序都要占时间，所以 Cmax 不会小于最长工序；总工时要在机器之间分摊，所以 Cmax 不会小于平均负载。但这两条理由**没有考虑「工序不可拆分」**——把总工时平均分给 k 台机器，只有恰好能整除成合法分组时才可达。

```text
实例 A：12 / 2 = 6 恰好可分组（2+2+2 与 3+3）    →  LB 紧
实例 B：26 / 2 = 13 恰好可分组（8+5 与 7+6）     →  LB 紧
反例：  p = [3, 3, 3]，2 台机器
       LB = max(3, ceil(9/2)) = max(3, 5) = 5，但最优是 6（一台做两个 3，另一台做一个 3）
```

最后这条反例要记住：**`ceil(总工时 / 机器数)` 不是总能达到**。所以 M2 的三层参照体系里，这个下界只能作为「参考下界」（`reference_kind = lower_bound`），不能作为「最优值」使用。

## 5. 实现：约束构成与模型规模

### 5.1 四类约束的构成

`cpsat_parallel` 用的就是第 3.1 节的三件套，`prefer_fixed_route` 默认为 `False`。实测两个实例的模型规模（用 proto 逐条数约束种类）：

| 实例 | 整数变量 | 约束总数 | interval | exactly_one | no_overlap | lin_max |
|---|---|---|---|---|---|---|
| `p = [3,3,2,2,2]`，2 台 | 21 | 18 | 10 | 5 | 2 | 1 |
| `p = [8,7,6,5]`，2 台 | 17 | 15 | 8 | 4 | 2 | 1 |

逐列对上手算：

```text
实例 A：5 个工序、2 台机器
  整数变量 = 5 个 start + 5 个 end + 10 个 presence + 1 个 makespan = 21
  interval      = 10 = 工序数 x 机器数（每个 (工序, 机器) 对一个可选区间）
  exactly_one   = 5  = 工序数（每道工序一条）
  no_overlap    = 2  = 机器数（每台机器一条）
  lin_max       = 1  = makespan 取全部 end 的最大值

实例 B：4 个工序、2 台机器
  整数变量 = 4 + 4 + 8 + 1 = 17
  约束 = 8 + 4 + 2 + 1 = 15
```

两点值得注意：

1. **`exactly_one` 是每个工序一条，不是「每组 presence 一条」**——所以它随工序数线性增长，随机器数不变；
2. **`no_overlap` 是每台机器一条，与工序数无关**。这正是 `AddNoOverlap` 的价值：**约束条数与「需要互斥的区间对数」无关**，而 Big-M 写法要 `O(n²)` 条。10 个区间用 Big-M 表达互斥需要 45 条析取约束，CP 只需要 2 条 `no_overlap`。

代码里有两处细节：

```python
# 每台机器上只有一个区间时不加 NoOverlap（一条约束管一个区间没有意义）
if len(intervals) > 1:
    model.AddNoOverlap(intervals)
```

```python
# 只有一个合格机器时不必用 exactly_one，直接强制它成立
if len(presences) == 1:
    model.Add(presences[0] == 1)
else:
    model.AddExactlyOne(presences)
```

第二处看起来是优化，实际上更重要：**它保证了「单个合格机器」这种退化情形不会因为求解器的选择而产生意外**——整条路由都固定时，这条路径会被推到极致。

### 5.1 makespan 怎么写进目标

`makespan` 是「全部工序的最晚完工时刻」，在 CP 里用一个辅助变量加一条 `AddMaxEquality` 表达：

```text
Cmax 是一个整数变量，约束   Cmax = max(end_1, end_2, ..., end_n)
目标  Minimize(Cmax)
```

对应到求解器的约束类型就是上表里的那条 `lin_max`——**它正是「取最大值」这条语义的编码**。这一点和 MILP 不同：MILP 里 `Cmax >= end_k`（对所有 k）就够了，因为最小化会把它压下来；CP 里因为目标也是变量、传播需要双向信息，所以用 `AddMaxEquality` 同时给出上下两个方向的信息。

这个差别值得记一笔：**同一个「最大值」语义，在 LP/MILP 里写成一组单向不等式，在 CP 里写成一条双向的等式约束**。后者在传播上更强（`Cmax` 的上界能反过来压 `end_k` 的上界），代价是多一个变量。

其它四个目标（`total_completion_time` / `total_flow_time` / `total_tardiness` / `max_lateness`）都是 `end` 的线性组合，其中 `total_tardiness` 与 `max_lateness` 各需要一个辅助变量来做「取正部」：

```text
tardy_k >= end_k - d_k ，tardy_k >= 0      →  Minimize(Σ tardy_k)
late_k  >= end_k - d_k                     →  Minimize(max late_k)（可为负）
```

`weighted_completion_time` 还要多做一步整数化：权重是 `float`，而 CP-SAT 的目标系数必须是整数，所以权重乘 1000 取整（`WEIGHT_SCALE`），汇报时用一个 `objective_divisor` 除回来。**这一步不能省**——直接 `int(w)` 会把小于 1 的权重截成 0，让目标函数悄悄少掉一项。

## 6. 与 M1 的接口：独立验证器与三层参照

M2 不重新定义问题。`Instance` / `Schedule` / `Objective` / 独立验证器全部来自 M1（经 [bridge.py](../../projects/02_optimization_models/opt_common/bridge.py) 转出），所以「CP-SAT 的解」与「LPT 的解」是**同一把尺子量出来的**。

`validate_schedule` 检查的四件事：

```text
1. 每道工序恰好出现在排程里一次
2. 排程用的机器在该工序的 eligible_machine_ids 里
3. 同一台机器上的区间两两不重叠
4. start >= release_time，且 end = start + processing_time
```

**为什么求解器说 OPTIMAL 还不够**：求解器的 OPTIMAL 是「在这个模型上找到最优解」的声明，而模型的正确性是**建模者**的责任。如果建模时漏了一条 release 约束、或者把 `eligible_machine_ids` 接错，求解器会兴高采烈地告诉你「最优」，因为它在解一个错误的问题。

所以 M2 的纪律是：**求解器的状态与解的可信度是两件事**。每个返回的排程都要过一遍独立验证器——`OPTIMAL` 不等于「解一定可行」，它只保证「在这个模型上没有更好的解」。

三层参照体系也在今天第一次完整出现：

| 参照类型 | 来源 | 能说明什么 |
|---|---|---|
| 手算最优（代码里记 `hand_computed`） | 手算（实例 A 的 6、实例 B 的 13） | 最优值本身就是这个数 |
| 下界（只作旁证，代码里不占 `reference_kind` 的一档） | `parallel_makespan_lower_bound` | 最优值不会低于它；**不保证可达** |
| 同组最好 / 交叉复核（代码里记 `per_group` / `cross_checked`） | 跑批件按实例取组内最好值，或用另一种建模方式复核 | 只说明「至少有这么好」 |

本次实验里，实例 A 与实例 B 的参照都是 `hand_computed`，因为下界紧、而且手算给出了可达的排程。

## 7. 实验：`m2w3d2_parallel_machines`

对应脚本 [m2w3d2_parallel_machines.py](../../projects/02_optimization_models/examples/m2w3d2_parallel_machines.py)，在项目目录下运行：

```bash
python examples/m2w3d2_parallel_machines.py
```

脚本对两个实例各打印：模型规模（布尔数与约束数）→ M1 的 LB → LPT 的结果 → CP-SAT 的结果与时间线 → 独立验证器结论。实际输出：

```text
=== 1. LPT 非最优的最小反例 ===
实例 p=[3, 3, 2, 2, 2], 2 台机器
  模型规模：布尔 presence 10 个，CP-SAT 约束 18 条
  M1 下界 LB = 6（max(最长工序, ceil(总工时 / 机器数))）
  M1 parallel_lpt  -> Cmax = 7  （> LB）
  cpsat_parallel   -> Cmax = 6, 状态 OPTIMAL, bound = 6.0, 分支 96, 冲突 5
  建模 0.0008 s / 求解 0.0078 s
    M0: J2_O0[2,4], J3_O0[0,2], J4_O0[4,6]  负载 6
    M1: J0_O0[0,3], J1_O0[3,6]  负载 6
  独立验证器：通过（5 道工序）

=== 2. 下界紧的实例 ===
实例 p=[8, 7, 6, 5], 2 台机器
  模型规模：布尔 presence 8 个，CP-SAT 约束 15 条
  M1 下界 LB = 13（max(最长工序, ceil(总工时 / 机器数))）
  M1 parallel_lpt  -> Cmax = 13  （= LB，该实例上 LPT 已最优）
  cpsat_parallel   -> Cmax = 13, 状态 OPTIMAL, bound = 13.0, 分支 66, 冲突 3
  建模 0.0008 s / 求解 0.0034 s
    M0: J1_O0[6,13], J2_O0[0,6]  负载 13
    M1: J0_O0[0,8], J3_O0[8,13]  负载 13
  独立验证器：通过（4 道工序）

=== 3. 选机是一次「恰好一个」的决策 ===
每道工序在每台合格机器上各有一个 OptionalIntervalVar，
AddExactlyOne 保证其中恰好一个 presence 成立，AddNoOverlap 保证
同一台机器上的区间不重叠。LPT 用「长任务先放」的贪心做同一个决策，
CP-SAT 则在同一组布尔变量上搜索并给出最优性证明。
```

五处观察：

1. **第 4 节的手算与求解器完全一致**：实例 A 的 6、实例 B 的 13，两边的 `bound` 都等于目标值（`OPTIMAL` 的判据）。实例 A 的分组也和手算一致——三个长 2 的工序在同一台机器上（`M0` 负载 6），两个长 3 的在另一台（`M1` 负载 6）。
2. **LPT 的两个结果差在「平局怎么破」**：实例 A 里 LPT 得 7、比最优差 1（相对差 16.7%）；实例 B 里 LPT 得 13、正好命中下界。同一个启发式，表现完全不同。
3. **求解规模小得可以忽略**：两个实例的分支数分别是 96 与 66，冲突 5 与 3，求解时间 0.0078 s 与 0.0034 s。这个量级的问题是「用来看清机制」的，不是用来比性能的。
4. **`bound` 是求解器自己给的**：实例 A 的 `bound = 6.0` 来自 CP-SAT 的搜索推理，不是被 `objective` 填进去的。M2 的包装层有一条硬纪律——取不到界就写 `None`，**绝不拿目标值冒充下界**，因为那会让 gap 恒为 0、看起来「全都证明最优了」。
5. **验证器与求解器是两条独立的路径**：求解器给出排程，验证器按 M1 的语义逐条检查（工序唯一、机器资格、机器互斥、释放时间、时长）。两边都通过，才说明这个排程可信。

注意到脚本打印的时间线把每台机器的负载也算了出来（`负载 6` / `负载 13`）——这不是求解器给的，是脚本按排程自己加的。**自己按语义重算一遍，是核对任何求解器输出的通用手段**。

## 10. 自测题

不看上文回答：

- Q1：并行机调度的两类决策是什么？
- Q2：并行机 CP 模型要加哪三条约束？各自的语义是什么？
- Q3：为什么同一个工序在所有机器上共享同一对 `start` / `end`？
- Q4：实例 `p = [3,3,2,2,2]`、2 台机器的下界是多少？最优值是多少？
- Q5：LPT 在这个实例上得到几？失败在哪一步？
- Q6：`presence` 变量的总数怎么算？固定路由时是多少？
- Q7：`ceil(总工时 / 机器数)` 这个下界一定能达到吗？举一个反例。
- Q8：`AddNoOverlap` 与 Big-M 析取约束相比，约束条数上有什么优势？
- Q9：求解器返回 `OPTIMAL` 之后，为什么还要跑一遍 `validate_schedule`？
- Q10：M2 的包装层为什么坚持「取不到界就写 `None`」，而不是填目标值？

### 参考答案

- A1：指派（每道工序放哪台机器）与时间（同一台机器上的工序先后）。前者是组合决策，后者是连续决策。
- A2：`AddExactlyOne`（每道工序恰好被一台机器加工）、`AddNoOverlap`（每台机器同一时刻只加工一个工序）、`end = start + p`（区间定义）。
- A3：因为工序的实际开工时刻只有一个；共享变量让「选机」与「定时」解耦——`AddExactlyOne` 只管选、`AddNoOverlap` 只管时间，未被选中的区间不占用时间。
- A4：`LB = max(3, ceil(12/2)) = 6`，最优值也是 6（三个长 2 的放一台、两个长 3 的放另一台，两机负载都是 6）。
- A5：得到 7。失败在前两个长 2 的工序分派时，两台机器负载相等（都是 3），LPT 固定选了第一台，导致最后一个长 2 的工序被压到已经负载 5 的机器上。
- A6：等于 `Σ_工序 |合格机器集合|`；固定路由时为 0（可选区间退化成必选区间）。
- A7：不一定。反例 `p = [3,3,3]`、2 台机器：`LB = max(3, ceil(9/2)) = 5`，但最优是 6，因为 9 无法分成两个各不超过 5 的整数组合且每道工序不可拆。
- A8：`AddNoOverlap` 每台机器一条，条数与区间数无关；Big-M 写法要为每一对需要互斥的区间写一条，条数是 `O(n²)`。
- A9：求解器的 `OPTIMAL` 只声明「在这个模型上没有更好的解」，模型本身是否正确是建模者的责任。验证器按问题语义（工序唯一、机器资格、机器互斥、释放时间、时长）独立检查，能挡住建模错误。
- A10：因为把 `best_bound` 填成目标值会让 gap 恒为 0、看起来「全都证明最优了」，这是求解器实验里最严重的伪证据。没有可比的界就如实写 `None`。

## 11. 今日一句话总结

> **并行机调度的要害是「选机」与「定时」两个决策；`OptionalIntervalVar` + `AddExactlyOne` + `AddNoOverlap` 三件套把它们分别落在布尔变量与机器互斥上，没有 Big-M 常数也没有 `O(n²)` 条析取约束——而 LPT 在这个最小反例上差的那 1 个单位，正好说明了为什么必须有精确方法给出「离最优多远」的答案。**
