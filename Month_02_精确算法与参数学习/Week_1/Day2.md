## 2. 为什么 Day 2 要把问题交给求解器

Day 1 的结论是「最优解一定在极点上取到」。这条定理在二维很好用——画个图就能枚举。但它的可操作性随维数迅速消失：

```text
n 个变量      候选极点数量的上界 = C(m + n, n)，m 是约束条数
三产品算例     n = 3, m = 5   ->  C(8, 3)              =   56
再加 7 个产品  n = 10        ->  C(15, 10)             = 3003
一周排产       n = 200       ->  天文数字
```

所以 Day 1 的手算只能是**判据**，不能是**方法**。今天要接入的一环是：

```text
Day 1：  数学模型 → 极点枚举（只在小规模可行）→ 最优值
Day 2：  数学模型 → 求解器 → 最优解 + 对偶信息        ← 今天
```

接上这一环之后，「模型 → 数字」这条路就通了。但立刻会冒出新的问题：**求解器给的数字该怎么读、凭什么信**。这正是今天的全部内容——不是「怎么调用 `Solve()`」，而是：

```text
一句话：求解器负责算，你负责解释；解释不了的数字，等于没有算过。
```

今天先建立起四个读数量的直觉——至于「凭什么信」，那要靠一次独立复算来回答。

## 3. 概念：四个读数量

求解器返回的远不止「最优目标值」一个数。本仓库的 `solve_model` 一次抽出四组读数：

| 读数 | 位置 | 数学含义 | 业务读法 |
|---|---|---|---|
| `primal` | 变量 | `x_j` | 每个产品做多少 |
| `slack` | 约束 | `b_i - a_i'x` | 这条约束还剩多少余量 |
| `reduced cost` | 变量 | `rc_j = c_j - Σ_i a_ij y_i` | 这个产品要开工，单位利润得提高多少 |
| `shadow price` | 约束 | `y_i` | 这条约束多给一单位，目标能多多少 |

两组读数之间有一一对应的**互补关系**（今天先用，推导留到对偶那一层）：

```text
x_j > 0            ->  rc_j = 0          投产的产品不存在「补贴不足」
slack_i > 0        ->  y_i  = 0          没顶死的约束不值钱
```

这条「一正一零」的配对，是理解今天所有数字的钥匙。

### 3.1 `reduced cost` 的正负号约定

**本项目约定：`rc_j = c_j - Σ_i a_ij y_i`。** 这是 `pywraplp` 的约定，也是本仓库对拍时**验证过的**约定（第 7 节的实测里 `rc` 恒等式误差是 `0.000e+00`）。

在 `max` 问题里，互补松弛要求：

- 若 `x_j > 0`，则 `rc_j = 0`（变基变量）；
- 若 `x_j = 0`，则 `rc_j <= 0`（不投产的变量不能有「正的补贴」）。

一个负数 `rc_j < 0` 的读法是：**当前这个产品是「亏的」，亏 `|rc_j|` 元 / 件**。它要进基，单位利润至少要提高 `|rc_j|`。

### 3.2 为什么无解时必须给 `None`

`pywraplp` 在不可行时 `Objective().Value()` 返回 `0.0`。如果直接把它写进结果表，就会把「没有解」伪装成「解是 0」——这是数据管线里最危险的一类错误，因为它**不报错**。

本仓库的约定是：`objective`、`primal`、`dual`、`slack`、`max_constraint_residual` 在无解时全部是 `None`（或空字典），并且下游的检查函数（互补松弛、rc 恒等式、对偶可行）也返回 `None`——

```text
None 的语义：没有检查过 ≠ 检查通过
```

在不可行算例上，这条约定会把整组读数一起置空。

### 3.3 两个「量」的对称性

```text
primal 侧：x_j    配 slack_i        每行剩多少
dual   侧：y_i    配 reduced cost   每个变量亏多少
```

这两组量的对称性会在「原始—对偶对照表」里变得完全清晰；今天先把它们当成「两组独立的读数」记住即可。

### 3.4 状态码：先看状态，再看数字

求解器的状态码要翻译成词再看，别直接对着数字编程：

| 状态 | 码 | 含义 | 本轮检查里怎么用 |
|---|---|---|---|
| `OPTIMAL` | 0 | 找到最优解 | 可以读 `primal` 与 `dual` |
| `FEASIBLE` | 1 | 找到可行解，但没证明最优 | 可以读 `primal`，**不能**读 `dual` |
| `INFEASIBLE` | 2 | 没有最优解 | 所有读数给 `None` |
| `UNBOUNDED` | 3 | 目标无界 | 同上 |
| `ABNORMAL` | 4 | 求解过程异常 | 同上 |
| `NOT_SOLVED` | 6 | 还没求解 | 同上 |

有一条**实测限制**必须记住（用两个真实的小 LP 就能演示）：本环境的 GLOP 后端对**无界** LP 也返回状态码 2，即词表里的 `INFEASIBLE`；`UNBOUNDED`（3）一次也没出现过。所以

```text
状态 2 的正确读法：「没有最优解」
状态 2 的错误读法：「可行域为空」
```

要区分「不可行」与「无界」，必须另找证据：手算、加人工界、或换一个后端。这条限制在代码里以 `GLOP_STATUS_CAVEAT` 的形式随模块一起发布，实验记录里也留下了原始证据。

## 4. 手算：三产品算例的最优解

算例（`PRODUCTION_BASE`）：

```text
max  40 x_P1 + 30 x_P2 + 25 x_P3
s.t. 2 x_P1 +   x_P2 +   x_P3 <= 100      (cap_M)
       x_P1 + 2 x_P2 +   x_P3 <=  80      (cap_L)
       x_P1                  <=  40      (demand_P1)
                x_P2         <=  50      (demand_P2)
                         x_P3 <=  80      (demand_P3)
      x >= 0
```

比 Day 1 多了 `P3` 与三条需求上限。先猜「两条产能行顶死、`x_P2 = 0`」，解方程组：

```text
2 x_P1 + x_P3 = 100
  x_P1 + x_P3 =  80
相减：x_P1 = 20，代入得 x_P3 = 60
```

得到一个候选极点 `x = (20, 0, 60)`，目标值 `40*20 + 25*60 = 800 + 1500 = 2300`。三件事要逐个验证：

```text
1. 可行性：demand_P1  20 <= 40  ✓    demand_P2   0 <= 50  ✓    demand_P3  60 <= 80  ✓
2. 这个点是不是极点：两条产能行线性无关，是。
3. 它是不是**最优**：需要另一个证据——对偶可行 + 互补松弛。
```

**手算最优性证明**（这一步是今天的重点）：设两条产能行的影子价格为 `y_M`、`y_L`。由互补松弛，三条需求行都没顶死，所以它们的影子价格都是 0；两个投产变量 `x_P1`、`x_P3` 的 `reduced cost` 必须为 0：

```text
rc(P1) = 40 - (2 y_M + 1 y_L) = 0    ->   2 y_M + y_L = 40
rc(P3) = 25 - (1 y_M + 1 y_L) = 0    ->     y_M + y_L = 25
相减：y_M = 15，代入得 y_L = 10
```

得到 `y = (15, 10)`。检查对偶可行性（所有变量的 `rc <= 0`）：

```text
rc(P2) = 30 - (1 * 15 + 2 * 10) = 30 - 35 = -5  <= 0  ✓
rc(P1) = 0  ✓（基变量）           rc(P3) = 0  ✓（基变量）
y_M = 15 >= 0  ✓                  y_L = 10 >= 0  ✓
```

于是我们**手算证明**了 `(20, 0, 60)` 是最优解：它可行、它对应的对偶解可行、两者满足互补松弛。目标值 `40*20 + 30*0 + 25*60 = 2300`，对偶目标 `100*15 + 80*10 + 40*0 + 50*0 + 80*0 = 1500 + 800 = 2300`，两边相等——强对偶。

这条推理链是今天最重要的产出：**「最优」不是求解器说的，是可以被证明的**。求解器只是替我们把这个证明的候选值找出来。

### 4.1 为什么被挤掉的是 `P2`

`P2` 的单位利润是 30，比 `P3` 的 25 高，为什么反而不投产？因为资源不够用，要比的是**单位资源贡献**：

```text
按 M 算：P2 = 30 / 1 = 30 元每单位 M      P3 = 25 / 1 = 25 元每单位 M   -> P2 更强
按 L 算：P2 = 30 / 2 = 15 元每单位 L      P3 = 25 / 1 = 25 元每单位 L   -> P3 更强
```

单看某一个资源会得出相反的结论，所以要比的是**按影子价格折算后的总资源成本**：

```text
P2 的资源成本 = 1 * y_M + 2 * y_L = 15 + 20 = 35 > 30 = 单位利润   -> 亏 5
P3 的资源成本 = 1 * y_M + 1 * y_L = 15 + 10 = 25 = 25 = 单位利润   -> 刚好打平
```

这就是 `rc(P2) = -5` 的含义：`P2` 每做一件，按当前资源的影子价格算要「亏 5 元」。要让 `P2` 值得做，它的单位利润必须从 30 涨到 35——`35` 就是它的**盈亏平衡价**。

### 4.2 为什么这个算例不能靠手算枚举极点

Day 1 用「两条直线求交」枚举极点。三产品、五约束的算例里，候选极点数量的上界是「从 `m + n = 8` 条约束里任取 `n = 3` 条」：

```text
C(8, 3) = 56
```

要继续加快约束（例如再加几个产品、几道工序），这个数量会迅速爆炸；而且每算一个候选点都要解一个 3 × 3 线性方程组、再验证它是否可行——手算在 `n = 3` 就已经不划算了。这正是今天要把「找点」交给求解器的理由，而**手算仍然保留**，只不过角色变了：

```text
Day 1 的手算：方法（把所有极点找出来）
Day 2 的手算：判据（验证求解器给的这一个点确实最优）
```

本节那两组方程（解 `x` 与解 `y`）就是判据的全部内容：**解 `x` 用两条产能行、解 `y` 用两条 `rc = 0`，再用互补松弛收尾。**

## 5. 建模：`build_production_lp` 的约束命名与设计决策

对应文件 [lp_models.py](../../projects/02_optimization_models/opt_models/lp_models.py)。

### 5.1 约束命名与顺序

```text
cap_<资源>        每个资源一条，方向 <=
demand_<产品>     每个产品一条，方向 <=（只在 max_demand 非空时生成）
delivery_<产品>   每个产品一条，方向 >=（只在 min_delivery 非空时生成，且跳过 0）
```

两条设计决策值得记住：

1. **`max_demand` 为空时不生成需求行**：这是「这个算例没有需求上限」，不是「需求上限为 0」。填 0 会生成 `x_p <= 0`——一条把所有产品都禁掉的约束，语义完全不同。
2. **`min_delivery` 为 0 时跳过该行**：`x_p >= 0` 与变量自身的非负性完全重复，留着只会让对偶表多一条恒为 0 的行。但 `max_demand = 0` 是真约束（不许生产），所以不跳过。**同为 0，含义不同，处理方式也不同。**

### 5.2 名字是给对偶用的

这套命名约定不只是为了好看。以 `cap_M` 为例，它同时决定三件事：

```text
1. LPModel.rows 里的顺序       -> 结果表按同一顺序打印，diff 稳定
2. 求解器里的约束名             -> 出错时能直接对上是哪一条
3. 对偶变量的名字 y_cap_M       -> 「原始—对偶对照表」靠它自动生成
```

第 3 条是重点：**对偶变量不是「第 i 个影子价格」，而是「某一条具名约束的影子价格」**。名字一旦稳定，「谁是谁的对偶」就不需要靠位置索引去猜——对照表与对拍都直接建立在这条上。

另一条相关的约定是**顺序也属于接口**：`products`、`resources` 的元组顺序决定变量与约束的顺序，同一个 `ProductionData` 每次生成的模型逐位相同。确定性的要求不只是「结果一样」，还包括「打印出来的行序一样」——否则 `results.csv` 就没法用 diff 检查。

## 6. 实现：`solve_model` 与 `LPSolution`

### 6.1 `solve_model` 抽出的读数

```python
status = STATUS_NAMES.get(model.solver.Solve(), "UNKNOWN")   # 先把状态码翻译成词

# 只在 OPTIMAL / FEASIBLE 时才读值
primal[x]      <- variable.solution_value()
reduced_cost[x] <- variable.reduced_cost()
dual[row]      <- constraint.dual_value()
activity[row]  <- 本模块自己按系数重算（不读求解器）
slack[row]     <- row_slack(row, activity[row])
```

注意 `activity` 是自己算的：`pywraplp` 的 `Constraint` 根本没有 `activity()` 方法，而且即使有也不该抄——**约束是否被满足必须是一次独立复算**。`max_constraint_residual` 就是这条复算的结论，一切对拍都建立在它上面。

### 6.2 `LPSolution` 的字段

| 字段 | 类型 | 无解时 |
|---|---|---|
| `status` | `str` | 一定存在（如 `"INFEASIBLE"`） |
| `objective` | `float \| None` | `None` |
| `primal` / `dual` / `slack` / `activity` | `dict[str, float]` | `{}` |
| `reduced_cost` | `dict[str, float]` | `{}` |
| `dual_available` | `bool` | `False` |
| `max_constraint_residual` | `float \| None` | `None` |
| `has_solution` | 属性 | `False` |

`dual_available` 单独存在，是因为**对偶读数只在 `OPTIMAL` 时可信**：`FEASIBLE`（可行但没跑完）时原始解可用，对偶解没有意义。这个区分会反复用到。

### 6.3 一条数据流，从参数到结论

本周所有模型的形状都一样，只有 builder 不同：

```text
纯参数容器              builder                句柄            读数
ProductionData   ->  build_production_lp  ->  LPModel  ->  solve_model  ->  LPSolution
TransportData    ->  build_transportation_lp            （含求解器对象        （status / primal /
AssignmentData   ->  build_assignment_lp                 + 元数据）             dual / slack / 残差）
```

三条设计原则贯穿这条流：

1. **参数容器是纯数据**：`frozen`、可 `replace`，不持有求解器状态。敏感性实验靠 `with_capacity` / `with_profit` 生成几十个变体，而基线对象一个都没被改。
2. **builder 是纯函数**：同样的输入必然生成同样的模型。它不做业务假设（不加虚拟节点、不猜需求），遇到无法表达的情况抛 `ValueError`。
3. **读数只从 `LPSolution` 出**：调用方不需要再跟 `pywraplp` 打交道，也就不会有人绕过元数据、拿索引去猜「第 3 个变量是什么」。

### 6.4 三个常见错误

```text
错误 1：拿 == 比较浮点数。
        x_P1 是 39.999999999999986 还是 40.0，取决于求解过程；比较必须带容差。
错误 2：把 None 当成 0。
        「求解器没给出这个量」与「这个量是 0」是两件事，混起来会静默给出错误结论。
错误 3：在没有检查互补松弛的情况下宣布「最优」。
        状态码只说明求解器认为找到了最优解；它是不是这个模型的最优解，
        要靠可行性与最优性条件自己验一遍。
```

## 7. 实验：`m2w1d2_lp_production`

脚本打印六张表：参数 → 约束矩阵 → `primal` 与 `reduced cost` → 每行的 `activity` / `slack` / `y` → 两条手算恒等式 → 逐项 `rc` 符号核对，最后用 `assert` 把第 4 节的手算固化成检查。实际输出：

```text
== 1. 算例参数（先集合、后数值）==
产品集合 P = ['P1', 'P2', 'P3']
资源集合 R = ['M', 'L']
单位利润 profit = {'P1': 40.0, 'P2': 30.0, 'P3': 25.0}

demand_P2         0.0      1.0      0.0    <=      50.0

求解状态 OPTIMAL，目标值 2300

== 3. primal 解与 reduced cost ==
变量                x   reduced cost   解释
x_P1        20.0000       0.000000   手算 > 0，投产；rc = 0，它是基变量
x_P2         0.0000      -5.000000   手算 = 0，不投产；rc < 0 表示要它开工得先补贴
x_P3        60.0000       0.000000   手算 > 0，投产；rc = 0，它是基变量

== 4. 每行的 activity / slack / shadow price ==
行名             方向      右端项   activity     slack        y   解释
cap_M          <=    100.0   100.0000    0.0000  15.0000   顶死；放松 1 单位目标 +15
cap_L          <=     80.0    80.0000    0.0000  10.0000   顶死；放松 1 单位目标 +10

== 5. 手算核对 ==

dual   手算：b'y = 100*15 + 80*10 + 40*0 + 50*0 + 80*0 = 2300
两者相等，正是强对偶；求解器给的目标值是 2300。

== 6. reduced cost 的符号约定逐项核对 ==
rc(x_P1) = c_j - Σ a_ij y_i = 40 - 40 = 0；求解器报 0.000000
rc(x_P2) = c_j - Σ a_ij y_i = 30 - 35 = -5；求解器报 -5.000000
rc(x_P3) = c_j - Σ a_ij y_i = 25 - 25 = 0；求解器报 0.000000
全模型最大恒等式误差 = 0.000e+00

== 7. 断言 ==
primal、dual、reduced cost 三项手算值全部与求解器一致（容差 1e-9）。
```

四处要留意的细节：

1. **`rc` 恒等式误差是 `0.000e+00`（精确为 0）**，不是「很小」——因为 `rc = c_j - Σ a_ij y_i` 在求解器内部就是这个定义，两边算的是同一个浮点表达式。这**验证了符号约定的方向**，但不能证明求解器算对了。真正独立的检查是第 5 节那条 `c'x = b'y = 2300`。
2. **`x_P1` 与 `x_P3` 是精确的 `20.0000` / `60.0000`，不像 Day 1 那样带尾巴。** 浮点噪声的大小取决于求解过程，**不能假设每次都有或都没有**。所以比较永远用容差，永远不用 `==`。
3. **三条需求行的 `y` 都是 `0`，但它们的 `slack` 各不相同（20 / 50 / 20）。** 「影子价格为 0」不区分「差一点点就顶死」和「完全用不上」——这个区分要靠 `slack`，两条信息合起来才能确定敏感性区间。
4. **`cap_M` 的影子价格 15 元 / 单位 M、`cap_L` 是 10 元 / 单位 L。** 这是业务上最有用的两个数字：如果外购一单位 M 的价格低于 15 元，就值得买。

## 10. 自测题

不看上文回答：

- Q1：本仓库约定的 `reduced cost` 定义式是什么？在 `max` 问题里它的符号要求是什么？
- Q2：`x_P2 = 0` 且 `rc(P2) = -5`，这句话翻译成业务语言是什么？
- Q3：三条需求行的影子价格都是 0，是否说明这三条约束「没用」？为什么？
- Q4：`activity` 与 `slack` 的关系是什么？等式行的 `slack` 是多少？
- Q5：为什么无解时 `objective` 必须是 `None`？直接写 0 会掩盖什么错误？
- Q6：`dual_available` 为 `False` 时，哪些检查函数会返回 `None`？为什么这样设计？
- Q7：`max_demand = 0` 与 `max_demand` 为空，语义差别是什么？
- Q8：为什么 `min_delivery = 0` 的行会被跳过，而 `max_demand = 0` 不会？
- Q9：脚本里 `rc` 恒等式误差精确为 0，这能证明什么、不能证明什么？
- Q10：`cap_M` 的影子价格是 15，如果你能以 12 元 / 单位外购 M，应该买吗？边界在哪里？

### 参考答案

- A1：`rc_j = c_j - Σ_i a_ij y_i`；`max` 问题里要求 `rc_j <= 0`（基变量取 0）。
- A2：按当前资源的影子价格核算，`P2` 每做一件要亏 5 元；要让 `P2` 值得做，它的单位利润要从 30 提高 5 元到 35。
- A3：不能这样读。影子价格为 0 只说明「在当前解处放松一单位不改变目标」。它可能还有余量（`slack > 0`），也可能刚好顶死但没有替代方案。要判断「有没有用」，得看 `slack`。
- A4：`slack = b - a'x`（`<=` 行），`activity = a'x`；等式行的 `slack` 恒为 0，因此等式行上的互补松弛 `slack * y = 0` 自动成立、不携带信息。
- A5：因为 `pywraplp` 在不可行时 `Objective().Value()` 返回 `0.0`，写成 0 就把「没有解」伪装成「解为 0」，而且不报错。`None` 的语义是「这个方法不提供这个量」。
- A6：互补松弛、`rc` 恒等式、对偶可行三个检查都返回 `None`——它们的输入依赖对偶解。设计理由是「没有检查过不等于检查通过」，不能用 0 冒充「已检查且通过」。
- A7：`max_demand = 0` 是一条真约束「这个产品不许生产」；`max_demand` 为空是「这个算例没有需求上限」，对应的行根本不会生成。
- A8：`min_delivery = 0` 生成的行是 `x_p >= 0`，与变量自身的非负性完全重复；而 `max_demand = 0` 生成的是 `x_p <= 0`，与 `x_p >= 0` 合起来禁掉该产品，是实质约束。
- A9：能证明「本仓库读到的 `reduced cost` 与 `pywraplp` 的定义方向一致」；不能证明求解器算对了——那需要独立的交叉验证（如 `c'x = b'y` 与手算顶点）。
- A10：应该买，前提是**在这个解的邻域内**：每多一单位 M 目标增加 15 元，成本 12 元，净赚 3 元。但影子价格只在基不变的区间内有效（实测区间是 `cap_M ∈ [80, 120]`），超出这个范围要重新求解。

## 11. 今日一句话总结

> **求解器给的不是「答案」而是四个读数：`primal` 说做什么、`slack` 说哪里还松、`reduced cost` 说要补贴多少才值得做、`shadow price` 说哪一单位资源最值钱；而「最优」这件事要靠「对偶可行 + 互补松弛」证明，不能靠求解器自述。**
