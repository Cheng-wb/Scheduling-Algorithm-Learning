## 2. 为什么 Day 6 要专门做一次对拍

前五天的结论都建立在一句话上：**「求解器说 OPTIMAL」**。今天是这一周里唯一一天**不信任求解器**的日子：

```text
Day 2  求解器说 OPTIMAL，我读它的输出
Day 3  求解器说 OPTIMAL，我用手算核对了一个数
Day 4  求解器说 OPTIMAL，我另建了一个对偶模型交叉验证
Day 5  求解器说 OPTIMAL，我在网格上核验了影子价格的区间
Day 6  求解器说什么先放一边：我用五条独立的量自己算一遍   ← 今天
```

为什么必须做，而且要**五条**：

```text
原始可行性  告诉我「这个解是不是真的可行」          —— 求解器说 OPTIMAL 不等于解可行
互补松弛    告诉我「这个解是不是真的最优」          —— 可行离最优还有一步
rc 恒等式   告诉我「我的公式符号有没有写反」        —— 这一类错误不会影响可行性
对偶可行性  告诉我「对偶解本身站不站得住」          —— 和上一条是两个独立的方向
对偶目标    告诉我「强对偶的等式在数值上成立吗」    —— 这是唯一一条用到第二个模型的核对
```

五条里有四条**不构造第二个模型**，这意味着它们能在「模型只写了一半」的情况下仍然工作。这是工程上重要的冗余：**同一个结论用不同的路径去验，才能算验过。**

知识链的位置：

```text

Day 6  为整个对拍定下容差          ← 今天
Day 7  把这些检查整理成复盘清单
```

## 3. 概念：五条核对量

### 3.1 定义

**定义（约束残差）**：设 `x` 是一个自称可行解，第 `i` 条约束的活动值为 `a_i'x`。

```text
等式行 i： 残差 = |a_i'x - b_i|
<= 行 i：  残差 = max(0, a_i'x - b_i)      （越界量，不越界就是 0）
>= 行 i：  残差 = max(0, b_i - a_i'x)
约束残差 = 所有行的残差取最大值
```

**定义（互补松弛违反量）**：

```text
max( max_j |x_j · rc_j| ,  max_{i 是不等式行} |slack_i · y_i| )
```

**定义（`rc` 恒等式误差）**：

```text
max_j | rc_j - ( c_j - Σ_i a_ij y_i ) |
```

**定义（对偶可行性违反量）**：

```text
max( y 的符号条件违反量， max_j max(0, c_j - Σ_i a_ij y_i) )
```

**定义（相对 gap）**：

```text
|primal - dual| / max(1, |primal|)
```

### 3.2 四条要对齐的纪律

1. **重算而不是读取**：约束残差必须从 `x` 与模型系数**重新算**，不能用 `LPSolution.slack`（那是求解器算的）。重算才有独立价值。
2. **分方向**：`<=` 行的「越界量」不能写成 `|a_i'x - b_i|`——那会把「没顶死」误判成错误。只有 `>=` 行与等式行参与可行性判定。
3. **互补松弛只统计不等式行**：等式行的 `slack` 恒为 0，乘积恒为 0，不影响 `max`，但也别把它列出来充数。
4. **`None` 而不是 0**：当求解器没给出最优解时，这些量要么无法计算、要么毫无意义。**返回 `None` 是有信息量的答案（「没有检查过」），返回 0 是伪造的通过。**

### 3.3 容差的三条性质

```text
1. 容差不是「越小越好」：小于实测噪声的阈值只会把浮点尘埃判成错误；
2. 容差必须能被解释：本仓库默认 1e-9 —— 比实测噪声宽约 4 个数量级，
   比求解器自带的可行性容差（1e-8 量级）严一个数量级；
3. 容差是**事后对拍**用的尺子，不是用来放宽求解器的参数。
```

第 3 点尤其重要：把对拍容差调大让它「通过」是把尺子锯短，不是把零件做好。求解器的容差是它内部判定可行性的门槛，两者服务的目的不同，不能混用。

### 3.4 为什么是「五条」而不是「一条大的检查」

一个自然的想法是写一个 `check_all(model, solution) -> bool`，把五个量加权求和、超过阈值就报错。**不要这么做**，理由是取证：

```text
1. 五种错误的表现完全不同：
   符号约定写反 -> rc 恒等式非零，但残差与互补松弛都可能正常；
   解不可行     -> 残差非零，其余可能全对；
   解可行但非最优-> 互补松弛非零，其余全对（Day 4 的 y = (20, 10) 就是这样）。
2. 加权求和会抹掉「是哪一条错了」这个信息，而修复动作完全取决于它是哪一条。
3. 五条里四条不需要第二个模型，一条需要；合并之后就必须每次都构造对偶模型，
   慢的那部分会拖累快的那部分。
```

**一条检查的价值在于它能被单独解释**；不能被单独解释的检查，出错时只能整段重写。

## 4. 手算：四个场景的核对值

### 4.1 `prod_2d`（2 变量 2 约束）

Day 1 手算过 `x = (40, 20)`、目标 2200。核对值：

```text
约束残差：cap_M 活动 2*40 + 20 = 100 = rhs 100 -> 残差 0
          cap_L 活动  40 + 2*20 = 80  = rhs  80 -> 残差 0
互补松弛：x_P1 = 40 且 rc_P1 = 0 -> 乘积 0
          x_P2 = 20 且 rc_P2 = 0 -> 乘积 0
          两条产能行 slack = 0 -> 乘积恒为 0
rc 恒等式：rc_P1 = 40 - (2*(50/3) + 1*(20/3)) = 40 - 40 = 0    ✓
          rc_P2 = 30 - (1*(50/3) + 2*(20/3)) = 30 - 30 = 0    ✓
对偶可行：y_M = 50/3, y_L = 20/3 都 >= 0；两条对偶约束取等（不是严格大于）；
          所以对偶可行违反量 = 0（允许取等！）
```

**最后一条是最容易写错的地方**：对偶可行性是 `Σ a_ij y_i >= c_j`，**取等是允许的**。把判据写成「严格大于」会把这些取等的算例全部误判。

### 4.2 `transport_base` / `assign_base`

两个网络模型的解全是整数，`c`、`A`、`b` 都是小整数，所以：

```text
理论上：互补松弛与 rc 恒等式是精确的等式；
实测：  在本环境里三张表的对应列都是 0.000e+00 —— 因为整数运算在
        浮点里是精确的（小整数与其乘积都能被 double 精确表示）。
```

**这一条不能推广到一般 LP**：`prod_2d` 的解是 `(40, 20)`（恰好整数），但它的对偶解是 `50/3`，于是互补松弛列出现了 `2.368e-13`。**分数一出现，噪声就出现**——这就是为什么容差必须按最坏情况而不是最好情况定。

### 4.3 不可行算例

`prod_infeasible` 里两条约束：

```text
demand_P2:   x_P2 <= 50
delivery_P2: x_P2 >= 60
```

两式相加立刻得到 `0 <= -10`，可行域为空。**这是手算出来的证据，不是状态码给的**——第 7 节的陷阱正好说明为什么必须自己算。

## 5. 实现：五条核对放在哪里

对应文件 [lp_models.py](../../projects/02_optimization_models/opt_models/lp_models.py)（函数：`row_slack`、`complementarity_rows`、`max_complementarity_violation`、`max_reduced_cost_identity_error`、`dual_feasibility_violation`、`duality_gap`）。

### 5.1 返回 `None` 的分支

```python
def max_complementarity_violation(model, solution):
    if not solution.dual_available:
        return None
    ...
```

`solution.dual_available` 只在该解状态为 `OPTIMAL` 时为真。这一条判断把「没法检查」与「检查通过」彻底分开——**`None != 0`，这是本周贯穿全程的纪律**（Day 2 的 `LPSolution`、Day 6 的核对函数、Day 7 的复盘表都用同一套约定）。

### 5.2 为什么要另建一个对偶模型

把原始目标抄一遍再和原始目标比，结果永远是 0——那是**同义反复**，不是核对。本仓库的做法：

```python
dual_model = build_dual(model)          # 用对偶表机械生成
dual_solution = solve_model(dual_model)  # 独立求解一次
gap = abs(solution.objective - dual_solution.objective)
```

这样 `gap` 是**两次独立求解**之间的差，它同时验证了三件事：对偶表翻译正确、`build_dual` 实现正确、强对偶在数值上成立。**一项核对能同时覆盖三条结论，才值得放进取证流程。**

### 5.3 检查器必须被「反向验证」过

一条只会在正确输入下返回 0 的检查器**什么都没证明**。第 7 节的第 7 项专门喂了一个已知错误的输入：

```text
y = {'cap_M': 20.0, 'cap_L': 10.0}
```

这个点满足对偶可行性（违反量 0），但互补松弛违反量是 `4.000e+02`——检查器抓到了它。**先证明检查器会报警，再看它没报警的结论。**

### 5.4 这些核对在测试里怎么用

`tests/test_lp_models.py` 里有两条测试直接把这些核对当断言用：

```python
def test_numerical_invariants_on_every_model(name, model):   # 参数化：四个核心模型
    ...  # 断言五条核对量都在 TOLERANCE 以内

def test_status_code_alone_is_not_a_proof():
    ...  # 断言「状态不是 OPTIMAL」时核对函数返回 None，而不是 0
```

**测试与被测代码共享同一套核对函数，这在一处是危险、在另一处是必要的**：危险的是「用被测代码证明被测代码」；这里必要的是，核对函数本身已经被 `test_complementary_slackness_hand_pairs_on_production_base` 用手算的配对值单独验过。顺序不能反：

```text
先用手算验核对函数（Day 4 的 2D 算例：已知 x、rc、slack，眼睛能看出的配对）
再用核对函数验模型（Day 6 的四个场景）
```

这也是本周唯一一处「自己验自己」的地方——它被允许存在，是因为它前面有一道手算闸门。

## 6. 状态码陷阱与不可行记录

### 6.1 GLOP 的一个实测事实

```text
min -x, x >= 0        （可行、无下界）    -> 状态 INFEASIBLE
min y, y >= 1, y <= 0 （真的可行域为空）  -> 状态 INFEASIBLE
```

两个在数学上完全不同的情形拿到同一个状态码。所以：

```text
INFEASIBLE 只能读作「没有最优解」，不能读作「可行域为空」。
```

要区分两者只能另找证据：手算、加人工界（把无界变量夹住再看是否有解）、或换一个后端。本仓库把这条限制记在 `GLOP_STATUS_CAVEAT` 常量里，让读到这个状态的人第一眼就看到限定语。

**这条是实验观察，不是 GLOP 的规格说明**：它是在本环境（`ortools 9.15.6755`）实测出来的；换版本时应当重跑探针再下结论。

### 6.2 不可行算例的正确记录方式

```text
状态 INFEASIBLE -> objective = None、primal = {}、dual = {}、slack = {}
                   max_constraint_residual = None、互补松弛检查 = None
```

把 `objective` 记成 `0` 会造出一行「看起来很成功」的假数据；记成 `None` 才逼着下游回答「这一行到底该怎么解释」。这和 M1 里「`bound` 必须诚实、没有 `Schedule` 就不许假装有」是同一条纪律的两次应用。

```text
取一个**对偶可行但不是最优**的 y = {'cap_M': 20.0, 'cap_L': 10.0}：
  对偶可行违反量 = 0.000e+00（符号条件与对偶约束都满足，所以它是 0）
  互补松弛违反量 = 4.000e+02（x_P1 = 40 而 rc_P1 = -10，乘积不为 0，被抓到）
  与原始最优目标的差 = 600
这条反例说明：对偶可行是「必要条件」，光有它还不够；
互补松弛才是把「可行」推进到「最优」的那一步。

== 8. 断言 ==

```

七处要留意的细节：

1. **第 2 节的 `prod_2d` 有 `4.547e-13` 的 gap，其他三个是 0**：因为 `prod_2d` 的对偶解含 `50/3`、`20/3` 这样的分数，而 `transport_base` / `assign_base` 的全整数数据在浮点里是精确的。**噪声不是「求解器不好」，而是「问题里有分数」。**
2. **`prod_base` 的 `互补松弛` 列是 `2.132e-13`，比 `prod_2d` 的 `2.368e-13` 略小**：两个都是分数引起的噪声，量级一致。容差必须按**最大**的那个定，不能按平均值定。
3. **第 3 节探针的 `1e-13` 一栏「通过 2 个、未通过 prod_2d、prod_base」**：这一栏是整份笔记里最重要的一行数据——它把「阈值越严越好」这个直觉直接推翻了。**判据：阈值必须大于被测量的实测噪声。**
4. **探针只回答一半的问题**：它能回答「多严算太严」，不能回答「多松算太松」。后半个问题要靠第 7 节的反例——**喂一个已知错误的输入，看检查器会不会报警**。两半合起来才构成对容差的完整论证。
5. **第 4 节的浮点尾巴 `39.999999999999986`**：这说明「求解器给的极点」不是精确的 `(40, 20)`。脚本用 `Fraction(Decimal(str(round(x, 12))))` 把它舍入成精确有理数再重算目标，得到**精确的 2200**——这一步的意义是证明「尾巴是表示误差，不是模型误差」。**结论不能反过来说**：不是所有 1e-14 的尾巴都可以忽略，只有当「舍入后代回原模型仍然可行」时才成立（本算例残差为 0）。
6. **第 5 节的两个探针都是真的跑出来的**：脚本用 `pywraplp` 现建两个小模型再求解。**不要凭印象说「求解器会区分不可行与无界」**——本环境的实测结果是它不区分。
7. **第 7 节反例的三个数字**：`对偶可行违反量 = 0.000e+00`、`互补松弛违反量 = 4.000e+02`、`与原始最优目标的差 = 600`。三个数字连起来读：**一个满足对偶可行性的点，离开最优还差 600**。这就是 Day 4 里「弱对偶给出上界、强对偶才给出等式」的数值化身。

## 10. 自测题

不看上文回答：

- Q1：约束残差该怎么算？`<=` 行为什么不能取绝对值？
- Q2：互补松弛违反量检查的是可行性还是最优性？
- Q3：`rc` 恒等式误差在检查什么？它能发现哪一类错误、不能发现哪一类？
- Q4：「另建 dual 模型独立求解」比「抄一遍原始目标」多验证了什么？
- Q5：默认容差 `1e-9` 的两条依据是什么？
- Q6：为什么不能把容差定成 `1e-13`？
- Q7：如何验证一个检查器「足够严」？探针只能回答哪一半问题？
- Q8：`INFEASIBLE` 状态应该怎么读？为什么不能读成「可行域为空」？
- Q9：不可行算例为什么要把 `objective` 记成 `None` 而不是 `0`？
- Q10：求解器给的解带 `1e-14` 的尾巴，怎么判断它是表示误差还是模型误差？

### 参考答案

- A1：按 `A x` 重算活动值再与右端项比较；`<=` 行只关心越界量 `max(0, 活动值 - 右端项)`，取绝对值会把「没顶死」误判成错误。
- A2：最优性。互补松弛是「可行 + 互补松弛 = 最优」这一定理里的后半步，一个可行但非最优的点乘积不为 0。
- A3：检查 `rc_j = c_j - Σ_i a_ij y_i` 这个符号约定有没有写反；能发现约定错误，不能发现「对偶模型本身翻译错了」（那要靠强对偶的 gap）。
- A4：多验证了「对偶表翻译正确、`build_dual` 实现正确、强对偶在数值上成立」三条；抄目标只是同义反复。
- A5：比本环境实测噪声（约 `2e-13`）宽约 4 个数量级；比求解器自带可行性容差（`1e-8` 量级）严一个数量级。
- A6：`1e-13` 小于等于实测噪声上限，会把浮点尘埃判成错误（探针实测该阈值下 4 个场景有 2 个失败）。
- A7：喂一个已知错误的输入，看它是否报警（本仓库用「对偶可行但非最优」的 `y` 反例）；探针只能回答「多严算太严」，回答不了「多松算太松」。
- A8：读作「没有最优解」。因为 GLOP 对「可行但无界」与「真不可行」返回同一个码。
- A9：`None` 表示「没有检查过」，是诚实的未知；`0` 会伪装成「检查通过」，把未知变成假数据。
- A10：把它舍入成精确有理数再代回原模型重算：若可行性残差为 0 且目标值不变，则是表示误差；否则要当模型问题查。

## 11. 今日一句话总结

> **「求解器说 OPTIMAL」不是证据，五条独立核对才是：约束残差管可行性、互补松弛把可行推进到最优、`rc` 恒等式管符号约定、对偶可行性管对偶解本身、另建对偶模型独立求解管强对偶——容差 `1e-9` 的依据是「比实测噪声（约 `2e-13`）宽、比求解器容差严」，探针只能说明多严算太严，还得喂一个已知错误的输入证明检查器真的会报警；无法判断的字段一律写 `None`，不写 `0`。**
