## 2. 为什么 Day 3 要体检「数值」和「不可行」

前两天的技巧（对称破缺、冗余约束、初解、固定）都在往模型里**加东西**。加东西有一个共同的副作用：**系数开始变得不是一个量级**。这件事平时看不见，等到求解器报 `MODEL_INVALID`、或者在容差附近给出矛盾结论时才暴露。所以工程流程里必须有两件「求解器不会替你做」的事：

```text
第一件：体检模型自己的数值条件
        方程的系数从 1 跨到 10^6 时，任何浮点求解器都会开始丢有效数字。
        这件事与「模型对不对」无关，与「模型好不好解」有关。

第二件：当模型不可行时，回答「为什么」
        求解器只会回一句 INFEASIBLE。它不会说「是 J000 和 J001 的交期打架」，
        更不会说「是你的模型漏了一条机器约束」。
```

两件事今天各占一半，它们共享同一个出发点：**读数据而不是读日志**。`scaling_report` 完全不解方程，它只把实例里的系数收集起来算比值；`diagnose_infeasibility` 虽然要调用求解器，但每一步都写成可以独立核对的「重解 + 比对状态」，而不是「相信求解器的自述」。

知识链的位置：

```text
Week 2 Day 3   Big-M 的紧/松两种取法          「M 取多少」
Day 3（今天）   量化跨度、检查缩放不变性        ← 今天前半
Week 3 Day 5   五个状态各自的含义              「INFEASIBLE 说什么」
Day 3（今天）   从 INFEASIBLE 走到极小冲突集    ← 今天后半
```

## 3. 定义：跨度、缩放不变性、冲突集

### 3.1 定义

**定义（系数跨度 `span`）**：模型中**最大系数绝对值**与**最小非零系数绝对值**的比值。本模块把它写成

```text
span = coefficient_max / coefficient_min
```

其中系数集合包含加工时间、释放时间、交期与 `horizon`。注意它是**比值**，没有量纲。

**定义（缩放不变性）**：设实例 `I'` 由 `I` 的全部时间数据乘一个正因子 `f` 得到（`p' = f·p`、`r' = f·r`、`d' = f·d`）。若某个指标在 `I` 与 `I'` 上取值相同，就称该指标是缩放不变的。

**理论结论**：`span` 是缩放不变的。因为 `coefficient_max` 与 `coefficient_min` 同时乘 `f`，比值不变。而 `horizon`、`coefficient_max` 这类**绝对量**会随 `f` 线性放大。

**定义（冲突集 / IIS）**：设给定一组假设 `A`（本模块里每条假设是「作业 `j` 按时完工」）。若 `A` 同时成立会导致不可行，则 `A` 的一个子集 `C` 若本身不可行、且 `C` 去掉任意一个元素后都可解，就称 `C` 是一个**极小冲突集**（irreducible infeasible subset，IIS）。

### 3.2 充分 ≠ 极小

CP-SAT 提供 `SufficientAssumptionsForInfeasibility()`，它返回的是**充分**冲突集：

| 性质 | 充分冲突集 | 极小冲突集（IIS） |
|---|---|---|
| 保证「同时成立会导致不可行」 | 是 | 是 |
| 保证「每个元素都必要」 | **否** | 是 |
| 保证唯一 | **否** | **否**（可以有多个极小集） |
| 依赖求解器内部传播痕迹 | 是 | 否（由重解验证） |
| 换 `seed` / 换设备是否稳定 | 可能变 | 稳定（一旦算出） |
| 代价 | 一次求解 | 多次重解 |

模块注释把这条差别写成一句判准：

```text
SufficientAssumptionsForInfeasibility() 返回的是**充分**冲突集，不是最小集，
也不是唯一原因。它依赖求解器内部的传播痕迹，换个 seed 或换台机器可能给出
不同的超集。所以本模块一律再做一遍删除过滤。
```

### 3.3 删除过滤（deletion filtering）

把充分冲突集收缩成极小集的算法只有几行，但每一步都要重解：

```text
minimal = list(reported)          # 从充分冲突集出发
cursor = 0
while cursor < len(minimal):
    trial = minimal 去掉第 cursor 个元素
    求解 trial
    if trial 仍然 INFEASIBLE:
        第 cursor 个元素不必要  →  把它永久移除（minimal 变短）
    else:
        cursor += 1              # 它不是多余的，保留，往后看
```

三点必须记住：

1. **每次尝试都要重解一次模型**，这是删除过滤的全部代价来源。
2. 循环里 `minimal` 会变短，因此 `cursor` 不总是自增——**移动的是窗口，不是索引**。
3. 收缩完之后还要**验证**：IIS 单独求解必须不可行（`still_infeasible`），IIS 去掉任意一个元素必须可解（`irreducible`）。没有这两条，`minimal` 只是一个「碰巧没被删掉」的集合。

### 3.4 求解次数可以提前算出来

驱动脚本记录的 `solves` 不是随机数，它有一个干净的结构（以本次三个 slack 为例，删除过滤没有真的删掉任何元素）：

```text
求解次数 = 1（首次，全部假设） + reduction_steps（删除过滤的尝试次数）
         + 1（IIS 复核）      + |minimal|（逐条去一验证）
         = 2|minimal| + 2
```

实测三组：`|minimal| = 1 / 2 / 3` → `solves = 4 / 6 / 8`，与上式逐项吻合。**这条结构决定了成本上限**：想诊断一个 20 个作业的实例，光验证就要 40 次以上求解，每次还可能撞到时间上限。成本纪律与时间上限这两件事，在这里接上了头。

## 4. 手算：三个 slack 下为什么不可行、为什么冲突集在变大

实验实例是 `seed=82, jobs=6, machines=1`，数据如下（`r` / `p` / `d` 都是生成器给出的原交期）：

| Job | `rj` | `pj` | `dj`（原） |
|---|---:|---:|---:|
| J000 | 7 | 5 | 14 |
| J001 | 2 | 10 | 17 |
| J002 | 2 | 9 | 15 |
| J003 | 7 | 14 | 28 |
| J004 | 3 | 4 | 9 |
| J005 | 2 | 18 | 29 |

诊断用的交期不是原交期，而是 `deadlines_with_slack` 造出来的旋钮：

```text
d_j = r_j + ceil(slack * p_j)
```

三档 slack 对应的交期：

```text
slack = 0.5:  J000=10  J001=7   J002=7   J003=14  J004=5   J005=11
slack = 1.0:  J000=12  J001=12  J002=11  J003=21  J004=7   J005=20
slack = 2.0:  J000=17  J001=22  J002=20  J003=35  J004=11  J005=38
```

### 4.1 `slack = 0.5`：单个作业自己就做不到

```text
J000: r = 7, p = 5  →  最早完工 r + p = 12
      交期 d = 7 + ceil(0.5 * 5) = 7 + 3 = 10
      12 > 10  →  J000 单独一个作业就不可能按时完工
```

所以极小冲突集是**一个元素**：`{J000}`。注意这条结论完全不依赖别的作业——它是「单个假设自我矛盾」，与机器、与排序都无关。手算与求解器给出的 `('J000',)` 一致。

### 4.2 `slack = 1.0`：两个作业的交期把机器夹住

```text
J000: r = 7, p = 5, d = 7 + 5 = 12   →  必须正好在 [7, 12] 加工（长度 5 的窗口也是 5）
J001: r = 2, p = 10, d = 2 + 10 = 12 →  必须正好在 [2, 12] 加工（长度 10 的窗口也是 10）
```

两个窗口 `[7, 12]` 与 `[2, 12]` 在单机上重叠，所以 `{J000, J001}` 不可行。同时：

```text
J000 单独：可解（排在 [7,12]）
J001 单独：可解（排在 [2,12]）
```

两个元素都必要，所以 `{J000, J001}` 是一个极小冲突集，与实测的 `('J000', 'J001')` 一致。

### 4.3 `slack = 2.0`：要三个作业才逼出矛盾

```text
J000: r=7, p=5,  d=17  →  窗口 [7, 12]（长度 5 在 [7,17] 内，最早开 7）
J002: r=2, p=9,  d=20  →  窗口 [2, 11]（长度 9 在 [2,20] 内，最早开 2）
J004: r=3, p=4,  d=11  →  窗口 [3, 7] （长度 4 在 [3,11] 内，最早开 3）
```

逐对检查都可行：

```text
{J000, J004}:  J004 3-7，J000 7-12          → 都对得上（12 <= 17）
{J000, J002}:  J002 2-11，J000 11-16        → 都对得上（16 <= 17）
{J002, J004}:  J004 3-7，J002 7-16          → 都对得上（16 <= 20）
```

三个一起就不可行：

```text
若 J002 先做：占 2-11，则 J004 的窗口 [3,7] 被占满，J004 无法按时；
若 J004 先做：占 3-7，则 J000 最早 7 开工占 7-12，J002 只能 12 起，21 完工 > 20；
其余排列只会更晚。
```

所以 `{J000, J002, J004}` 是一个极小冲突集，与实测一致。**三个 slack 下的冲突集大小 1 → 2 → 3 逐级变大**，原因可以手算看出来：slack 越宽，每个作业的「可用窗口」越宽，单个作业或两个作业的自我矛盾就不成立了，需要更多作业共享一台机器才逼出矛盾。

### 4.4 「极小」不等于「唯一」

手算已经能构造出另一个候选：`{J001, J002, J004}` 三个作业在 slack=2.0 下是否也不可行？手工试排（`J002` 2-11、`J001` 需 10 单位且 `d=22`、`J004` 需 4 单位且 `d=11`）：

```text
J004 3-7 → J002 7-16 → J001 16-26  > 22   ✗
J002 2-11 → J001 11-21 (<= 22 ✓) → J004 无处安放（窗口 [3,7] 已过）✗
```

这个集合同样不可行，而且逐对检查也可行——它**也是**一个极小冲突集。所以必须写清楚：

```text
删除过滤给出的是「一个」极小冲突集，不是「唯一」的极小冲突集。
它具体给出哪一个，取决于充分冲突集的元素顺序与遍历顺序。
```

这是 IIS 的标准性质，不是本模块的缺陷。**诊断报告必须写成「这组假设一起冲突」，而不是「冲突的原因就是这几个作业」。**

## 5. 实现：三个函数与两条容错

对应文件 [diagnostics.py](../../projects/02_optimization_models/opt_models/diagnostics.py)。

### 5.1 `scaling_report`：只读数据

```python
coefficients = [op.processing_time ...] + [job.release_time ...] + [job.due_date ...] + [horizon]
positive = [abs(v) for v in coefficients if v]
span = max(positive) / min(positive)
big_m_span = max(big_m.values()) / min(positive)
```

两个设计决定值得说明：

1. **`horizon` 也进系数集合**。它是变量的上界，直接决定「时间变量」这一族的系数尺度；把它算进去，`tight_model_span` 才等于 `horizon / min p` 这个可解释的式子。
2. **Big-M 的数值只读调用 Week 2 的函数**（`loose_big_m` / `pair_big_m`），本模块自己的模型不使用 Big-M。跨周调用写在一层 `try` 里，取不到就**如实留空并记一条 note**，而不是编一个数：

```python
except Exception as exc:
    notes.append(f"未取到 Week 2 的 Big-M 数值：{type(exc).__name__}: {exc}")
```

### 5.2 `rescale_instance`：整数是硬约束

```python
if factor <= 0:
    raise ValueError(...)
def apply(value):
    product = value * factor
    rounded = round(product)
    if abs(product - rounded) > 1e-9:
        raise ValueError(f"factor {factor} turns integer data into {product}")
    return int(rounded)
```

三点：

- **先整体检查、再构造**。示例里先对所有 `r` / `d` / `p` 跑一遍 `apply`，全部合法才真正 `replace` 出新的 `Instance`；否则会出现「缩放到一半才抛错」的半个实例。
- **只缩时间数据**：`r`、`p`、`d`。机器、工序、资格集合原样保留。
- **1e-9 的容差**用来吸收 `0.1 × 3 = 0.30000000000000004` 这类浮点噪声，同时仍然拒绝真正的分数结果。

### 5.3 `diagnose_infeasibility`：五步流程

```text
1. 每个作业一个布尔 on_time_j，用 AddAssumption(on_time_j) 强制它在本次求解中为真；
   on_time_j 为真时约束 C_j <= d_j。
2. 求解：可行 → 返回排程（并且过 M1 的独立验证器）；不可行 → 进入第 3 步。
3. 取 SufficientAssumptionsForInfeasibility() 作为**充分**冲突集。
4. reduce_conflict=True 时做删除过滤，得到 IIS。
5. 验证：IIS 单独求解必须不可行；IIS 去掉任一元素必须可解。
```

四个「失败也要留痕」的分支，每个都写清了不同的失败语义：

| 分支 | 状态 | 含义 |
|---|---|---|
| 交期没给全（有作业不在 `deadlines` 里） | `FAILED` | 假设集合本身不完整，不猜 |
| 求解器返回非 `OPTIMAL` / `FEASIBLE` / `INFEASIBLE` | `UNKNOWN` | 连「哪组约束冲突」都还不能断言 |
| `INFEASIBLE` 但求解器没归咎任何假设 | `INFEASIBLE` | 不可行与这批假设无关，先检查模型本身 |
| 有解但排程过不了独立验证器 | `FAILED` | 求解器自称可行不算 |

第三条分支特别值得记：它把「**假设集合导致的不可行**」与「**模型自身就不可行**」分了开来。没有这条判别，任何一个 `INFEASIBLE` 都会被顺手写成「作业交期打架」，而真正的原因可能是模型写错了。

### 5.4 诊断结论能说什么、不能说什么

模块把三条边界直接写进返回值的 `notes`（示例脚本会把它们逐条打印出来）：

```text
SufficientAssumptionsForInfeasibility() 只保证「充分」，不保证最小、也不保证唯一；
    换 seed 或换设备可能给出不同的超集。
不可行可能来自建模错误而不是数据；求解器不会替你区分这两者。
IIS 是「关于这组假设集合的极小」，不在假设集合里的约束不参与最小化。
```

第三条最容易被忽略：如果「机器数量」本身写错了（比如实际有两台机器，模型里只有一台），最小化的对象里**不包含**这条信息，所以诊断结果会指向「作业之间交期打架」。**报告里必须写清假设集合的含义，读者才知道这个 IIS 是关于什么说的。**

## 6. 实测读数：三件必须一起看的事

### 6.1 `span` 是比值，所以缩放不变

```text
factor = 1     horizon = 67    最大系数 = 67    span = 33.5   big_m_span = 201.0
factor = 10    horizon = 670   最大系数 = 670   span = 33.5   big_m_span = 201.0
factor = 100   horizon = 6700  最大系数 = 6700  span = 33.5   big_m_span = 201.0
```

`horizon` 与最大系数随因子线性放大（67 → 670 → 6700），`span` 一动不动。这条观察的用处很实际：

```text
看到「最大系数 6700」不能说明模型差 —— 那可能只是你选了「分」而不是「秒」做时间单位。
看到「span = 33.5」才可以开始讨论数值条件 —— 它与单位选择无关。
```

### 6.2 松模型的跨度比紧模型大 6 倍

```text
tight_model_span = 33.5      （= horizon 67 / 最小非零系数 2）
big_m_span       = 201.0     （= 最大 Big-M 402 / 最小非零系数 2）
比值             = 6.0
```

三个数的来源都可以手算核对：

```text
最小非零系数 = 2                （实例里最小的 r_j）
horizon      = max_j r_j + Σp   = 7 + 60 = 67
loose Big-M  = n * horizon      = 6 * 67   = 402          （Week 2 的全局常量界）
pair  Big-M  = horizon - r_k    ∈ {67-7, 67-2} = {60, 65}  （Week 2 的逐对界）
```

所以 `203` 这个差距不是「Big-M 不好」，而是一件事的量化：**松模型里同一组约束既有 2，也有 402**，比值越大，单纯形里的比值与松弛误差越容易吃掉有效数字。Week 2 的结论（`tight_model_span` 与 `big_m_span` 都见诸 `scaling.json`）在这里被量成了两个数。

### 6.3 观测到的冲突集在变大，但「冲突」是相对假设说的

```text
slack = 0.5   INFEASIBLE   极小冲突集 = ('J000',)                 求解次数 = 4
slack = 1.0   INFEASIBLE   极小冲突集 = ('J000', 'J001')          求解次数 = 6
slack = 2.0   INFEASIBLE   极小冲突集 = ('J000', 'J002', 'J004')  求解次数 = 8
```

三档**全部不可行**，但原因不同（第 4 节手算）：slack=0.5 是单作业自我矛盾，slack=2.0 要三个作业共享机器才矛盾。这带来一句必须记住的话：

```text
「冲突」不能脱离「相对哪组假设」单独讲。
slack 变了，能各自达标的作业集合变了，冲突集自然跟着变。
```

另外，示例脚本对 slack=2.0 仍不可行专门打印了一句提醒：单机上每个作业只有 2 倍自身工时的交期，而它必须等前面所有作业做完——**可行的临界点要靠实验找，不能靠直觉断言**；本实验三档都没找到可行点，这是一个观察，而不是「临界点不存在」的结论。

### 6.4 删除过滤的代价

`solves` 从 4 → 6 → 8 的上升全部来自 |极小集| 的上升（第 3.4 节的结构式）。如果实例扩到 20 个作业、时间上限放到 30 秒，光验证就要几十次求解——**这正是把一个会话实例跑成「安静地跑很久」的原因**（驱动脚本 docstring 的原话）。所以本模块的示例与驱动一律用 **6 作业 + 3 秒预算**。

对应脚本 [m2w4d3_diagnostics.py](../../projects/02_optimization_models/examples/m2w4d3_diagnostics.py)，在项目目录下运行：

```bash
python examples/m2w4d3_diagnostics.py
```

脚本分五段：系数跨度体检、三档缩放、把交期压到 0 构造不可行、把冲突诊断出来、用 slack 旋钮扫描。实际输出：

```text
== 1. 系数跨度：Big-M 是主要来源 ==
  jobs=6 operations=6 machines=1
  horizon（有效时间界）        = 67

  同一组约束里既有 1（时间）又有 M（排序），比值越大数值条件越差。

== 2. 缩放：把时间数据整体乘一个因子 ==
    factor   horizon      最大系数    span(比值)  big_m_span
       1.0        67        67        33.5       201.0
      10.0       670       670        33.5       201.0
     100.0      6700      6700        33.5       201.0
  绝对量级（horizon、最大系数）随因子线性放大，
  而 span 是比值，**缩放不变**——所以看 span 才看得出模型的固有数值结构，
  看绝对系数只会看到你选了多大的时间单位。

== 4. 求解器不会替你区分「数据错」和「模型错」==
  - SufficientAssumptionsForInfeasibility() 只保证「充分」，不保证最小、也不保证唯一；换 seed 或换设备可能给出不同的超集。
  - 不可行可能来自建模错误而不是数据；求解器不会替你区分这两者。
  - IIS 是「关于这组假设集合的极小」，不在假设集合里的约束不参与最小化。
```

四处读数要留意：

1. **最小非零系数是 2 而不是 1**：本例里最小的加工时间是 4、最小的释放时间是 2，所以 `coefficient_min = 2`。若实例里恰好出现 `p = 1`，`span` 会更大——**`span` 对数据里的最小值极其敏感**，这也是为什么要用比值而不是最大值来谈数值条件。
2. **`pair_min = 60` 与 `pair_max = 65` 的差来自释放时间**：`M_jk = H - r_k`，`r_k` 取 7 时得 60、取 2 时得 65。这两个数不是「Big-M 的取值」，而是**逐对** Big-M 的最小与最大；`big_m_span` 用的是 `pair_max` 之上的 `loose`（402），因为松模型里出现的是全局常量。
3. **交期压到 0 的诊断只用了 0.01 秒**：因为 `{J000}` 是单元素冲突，删除过滤一次尝试就收敛。**冲突越小，诊断越便宜**——这是一个反直觉但很实用的观察。
4. **`irreducible` 与 `still_infeasible` 两个验证字段在脚本里没有逐条打印**，但它们保存在 `ConflictReport.verification` 里。想核对「去一可解」除了 `J000` 之外还有哪些组合，要读这个字段（本实验三档的 `drop_one_status` 全部是 `OPTIMAL` / `FEASIBLE`）。

**测试覆盖情况（如实记录）**：本模块的验证现在在 `tests/test_diagnostics.py` 里，共 **16 个测试函数**，覆盖三处曾经没有回归测试的地方：`scaling_report` 的 span 计算（`test_span_is_a_ratio_and_therefore_scale_invariant` 断言 span 在缩放 10 倍 / 100 倍后不变，而 horizon 线性放大）、`rescale_instance` 的整数与结构保持、以及删除过滤的循环（`test_minimal_conflict_is_verified_irreducible` 断言 IIS 整体不可行且去掉任一元素即可行；`test_diagnosis_is_bounded_by_the_time_limit` 断言求解次数是作业数的常数倍而非爆炸式增长）。另外还覆盖了三条失败分支：假设集合缺作业时直接 `FAILED`、预算小到无法判定时返回 `UNKNOWN` 而**不**声称有冲突集、可行时不报冲突且返回排程过独立验证器。整个文件在 1.2 秒内跑完——**测试本身的速度就是纪律**：删除过滤会对冲突集反复重解，实例一大就会失控。

**曾经**这是一处明确的缺口：`scaling_report` 的 span 计算、`rescale_instance` 的整数检查、删除过滤的循环这三处都没有回归测试。现在这三处都已补齐（见上），所以本节保留这段记录是为了说明**缺口是怎么被发现和关闭的**——先如实写进「未完成清单」，再补测试，而不是一开始就默认它已被覆盖。

## 10. 自测题

不看上文回答：

- Q1：`span` 的定义是什么？为什么它比「最大系数」更能说明数值条件？
- Q2：把实例整体放大 100 倍，`horizon`、`span`、`big_m_span` 各怎么变？
- Q3：`tight_model_span = 33.5` 与 `big_m_span = 201.0` 的差距来自哪里？
- Q4：充分冲突集与极小冲突集差在哪一条性质上？
- Q5：删除过滤的每一步代价是什么？为什么它不能用在大会话实例上？
- Q6：`slack = 0.5` 时为什么 `{J000}` 一个作业就构成冲突？
- Q7：`slack = 1.0` 时 `{J000, J001}` 为什么是极小集？两个元素各自为什么必要？
- Q8：`solves` 与 `|minimal|` 在本实验里的结构式是什么？
- Q9：为什么说「极小冲突集」不唯一？这对报告的措辞有什么要求？
- Q10：求解器报 `INFEASIBLE` 但没归咎任何假设时，说明什么？

### 参考答案

- A1：`span = 最大系数 / 最小非零系数`，是比值而非绝对量级；绝对量级会被时间单位选择放大或缩小，比值才反映模型的固有数值结构。
- A2：`horizon` 放大 100 倍；`span` 不变（分子分母同乘 100）；`big_m_span` 也不变。
- A3：来自 Big-M 的引入——松模型的最大系数是 `n·horizon = 402`，紧模型的最大系数是 `horizon = 67`，而两者的最小非零系数都是 2，于是比值相差 6 倍。
- A4：极小性。充分冲突集只保证「一起成立会不可行」，不保证每个元素都必要，也不保证唯一。
- A5：每尝试去掉一个元素就要重解一次；`solves` 随极小集大小线性增长（本实验 `2|minimal| + 2`），大会话实例上单次求解就可能撞到时间上限。
- A6：因为 `d = r + ceil(0.5·p) = 7 + 3 = 10` 小于任何加工的完工时间 `r + p = 12`，这个假设自我矛盾，与机器和排序无关。
- A7：`J000` 的可加工窗口是 `[7, 12]`，`J001` 的是 `[2, 12]`，在单机上重叠；各自单独可解，所以两个都必要。
- A8：`solves = 1（首次）+ reduction_steps + 1（IIS 复核）+ |minimal|（去一验证）`，本例中删除过滤没有真的删掉元素，故 `solves = 2|minimal| + 2`，取值 4 / 6 / 8。
- A9：同一个不可行假设集合可以有多个极小冲突集（本实验第 4.4 节手算了另一个候选）。所以报告只能写「这组假设一起冲突」，不能写「冲突的原因就是这几个作业」。
- A10：说明不可行不是由这批假设造成的，很可能是模型本身不可行（或约束写错），应当先去检查模型，而不是继续解释交期。

## 11. 今日一句话总结

> **`span` 是最大系数与最小非零系数的比值，所以缩放不变、能反映模型的固有数值结构（紧模型 33.5，Big-M 模型 201.0，差 6 倍）；而当模型不可行时，求解器只能给出相对某组假设的充分冲突集，删除过滤把它收缩成极小集（slack 0.5/1.0/2.0 下 `J000` → `J000\|J001` → `J000\|J002\|J004`），代价是每试一次就重解一次——冲突只在「相对这组假设」的意义上成立，而「数据错」与「模型错」它不会替你区分。**
