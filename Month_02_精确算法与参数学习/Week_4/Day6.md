## 2. 为什么今天才做比较

前五天各做了一件事，但都还缺一个终点：**这些手段到底在什么情况下该用哪一个**。今天补上。

比较是实验里最容易糊弄的一环。四种典型的糊弄法：

```text
① 不同预算：启发式 0.002 秒解出 46，MILP 5 秒解出 39 ——「启发式快 2500 倍」
   （快是因为它根本没在解同一个问题：它给的是可行解，不是最优性证明）
② 不同实例：拿 A 实例的 CP-SAT 对照 B 实例的 MILP
③ 只看目标值：不看状态 —— 把 FEASIBLE 的 968 与 OPTIMAL 的 903 并列成「903 更好」
④ 只看 gap：把不同 formulation 的 gap 横向排序（今天会看到这是错的）
```

真正能写进报告的比较，必须钉死四条：

```text
同一个 Instance 对象   —— 不是「同规模」，是同一个实例（同 seed、同数据）
同一个 objective       —— ΣT 与 Cmax 之间没有可比性
同一个 time_limit      —— 同预算，否则就是「谁跑得久谁好」
同一个验证器           —— 每一行都过 M1 的 schedule_errors
```

Day 4 说过「解出 X」必须带预算，今天把这句话升级成：

> **「方法 A 比方法 B 好」必须带实例、目标、预算与状态四项限定词。**

## 3. 概念：三种「更好」与两种「差多远」

### 3.1 定义（三种「更好」）

```text
更好（可行解质量）    objective 更小 —— 只要状态在 FEASIBLE_STATUSES 里就有意义
更好（可信度）        在预算内被证明最优 —— 只有 status == "OPTIMAL" 算数
更好（代价）          wall_time 更小 —— 但要先确认前面的可比性都成立
```

三者**可以互相矛盾**，今天就会看到三种矛盾各一次：

| 矛盾 | 今天的实测 |
|---|---|
| 解更差但界更紧 | `parallel_24`：`milp_alt` gap 0.4293 < `cpsat_parallel` 0.6620，但目标 74 > 71 |
| 证明最优但更慢 | `parallel_12`：`milp_alt` 证明最优用 2.236 秒，`cpsat_parallel` 只用 0.047 秒 |
| 更快但不提供证明 | 所有启发式行：0.001～0.002 秒，`gap` 恒为 `None` |

### 3.2 定义（相对 gap 的可比范围）

```text
gap = (objective - best_bound) / max(1, |objective|)
```

`gap` 是一个**双端受影响的量**：目标值变差会推高它，界变紧也会推高它（分子里的界变小）。所以：

```text
同一个方法随预算变化      gap 可比（界单调不降，目标值单调不增）
同一实例的不同方法之间    gap **不可比** —— 两个 bound 来自不同的松弛，
                         「更小的 gap」可能只是「更紧的界 + 更差的解」
```

`parallel_24` 就是这条纪律的现成反例（见第 7 节）。跨方法排序只能用 `objective`，且必须与 `status` 一起写。

### 3.3 定义（参考值分档）

「最好」需要一个参照。月末批次的 `opt_experiments/benchmark.py` 用三档参考值，可信度依次下降：

```text
档 1  optimum            M1 的独立枚举器给出的真最优（只对单工序小实例可行）
档 2  proven_by_solver   某个求解器在预算内证明的最优（可信，但依赖求解器正确）
档 3  best-known         本批次见过的最好可行解（只是估计，不是证明）
```

今天脚本里打印的「本实例最好可行解来自 X」属于**档 3 的说法**——它没有说 X 是最优，只说在这张表里它最小。这一点必须在报告里写清，否则读者会默认它是档 1。

## 4. 手算：同一实例、同一预算，界能差多少

拿 `single_20`（`seed=70`，20 作业单机，ΣT，预算 5 秒）上的两行做算术。两行的 `objective` 分别是 `968` 与 `903`，界分别是 `65.5` 与 `903.0`：

```text
界之比       903.0 / 65.5 = 13.8 倍
界之间的相对差 (903.0 - 65.5) / 903.0 = 0.927 → 92.7%
```

也就是说：同一个实例、同一个目标、同一个 5 秒预算——

```text
序列 MILP（milp_tight）   5 秒后界停在 65.5，连最优值 903 的一个零头都没到
时间索引 MILP（milp_alt）  0.98 秒就把界推到 903，并证明它就是最优
```

再核对 `milp_tight` 的 gap：

```text
gap = (968 - 65.5) / max(1, 968) = 902.5 / 968 = 0.93233 → 0.9323 ✓
```

**这条算术与 Week 2 的结论连成一条线**：Week 2 测到「loose/tight 两种 Big-M 的根 LP 界都是 0」——Big-M 的松紧不改变根界。今天进一步看到：即使给了 5 秒的搜索预算，把界从 0 推到 65.5 已经是序列模型的极限，而**换 formulation（时间索引）**一步就把界推到最优值。

```text
Big-M 的松紧 → 影响系数规模与搜索路径
formulation 的结构 → 决定界的量级
```

这是本月最值钱的一条结论之一，值得在月末汇总时重申。

## 5. 实现：比较脚本的四条纪律

对应脚本 [m2w4d6_selection_matrix.py](../../projects/02_optimization_models/examples/m2w4d6_selection_matrix.py)（93 行）。它的结构本身就是纪律的载体：

```python
TIME_LIMIT = 5.0                      # ① 全局唯一预算，不逐个方法调

CASES = (
    ("single_12 (ΣT, 已可解)", generate_instance(51, jobs=12, machines=1),
     "total_tardiness", ["heur_spt", "milp_tight", "milp_alt"]),
    ...
)

r = get(name)(inst, {"objective": objective, "time_limit": TIME_LIMIT, "seed": 0})   # ② 同一 spec
diagnostics = validate_result(inst, r)                                              # ③ 每行都验证
winner = min(results, key=lambda item: item[1].objective or float("inf"))           # ④ 只比目标值
```

四处设计意图：

1. **预算提到模块级常量**：`TIME_LIMIT = 5.0` 只出现一次，杜绝某一组方法用了不同预算。
2. **`spec` 逐字段对齐**：`objective` 随实例走（单机 ΣT、并行机 Cmax），`time_limit` 与 `seed` 三组一致。
3. **每行都过 `validate_result`**：结果表的最后一列是「通过 / 拒绝」，不是一个装饰性列——它是 Day 5 那条纪律（求解器的声明不算数）在执行层的落地。
4. **排序键只取 `objective`**：不掺 `gap`、不掺耗时。理由见第 3.2 节。

### 5.1 一条已知局限（如实记录）

`min(results, key=lambda item: item[1].objective or float("inf"))` 这一行有一个**潜在缺陷**：Python 里 `0.0` 是假值，所以当某个方法的 `objective == 0.0` 时，`0.0 or float("inf")` 会给出 `inf`，该方法会被排到**最后**。

- 这次运行**没有触发**：四组实例的目标值是 39 / 46 / 71 / 74 / 75 / 532 / 543 / 903 / 968，没有 0。
- 但 `makespan` 与 `ΣT` 都可能合法地取 0（所有作业交期宽松、或没有作业），所以这是一个真实存在的隐患，正确的写法是显式判 `None`。
- 本仓库的 `opt_experiments/benchmark.py` 没有这个问题（它用 `min(float(r["objective"]) for r in solved)`，先过滤掉 `None`）。

笔记记录它，是因为这正是一个好的自查点：**用 `or` 给 `None` 兜底时，顺带把合法的 0 也兜进去了**。

### 5.2 比较前的自查清单

在把任何一张跨方法表贴进笔记之前，逐条过一遍：

```text
□ 表里的每一行都写明了实例（含 seed）与 objective 吗？
□ 所有行的 time_limit 相同吗？（启发式那一列写「不使用预算」而不是留空）
□ 每一行都有状态列吗？（没有状态的目标值只是一半信息）
□ 有界的方法都填了界，没有界的方法都写 None（而不是 0）了吗？
□ 「最好可行解来自谁」与「谁证明了最优」是两句话吗？
□ 表外有没有一句话说明这只是本批实例的观察？
```

六条里最容易漏的是第 2 条与第 6 条。**第 2 条**漏了会出现「启发式 0.002 秒」被误读成「快 2500 倍」；**第 6 条**漏了会把摘要写成规律。这两条的写法都已经在第 6 节的输出里出现：脚本第一行就声明了共同预算，最后一行就声明了不能外推。

## 7. 读数：五条结论与两条警告

### 7.1 结论一：formulation 结构支配界（本日头条）

`single_12` 与 `single_20` 上，`milp_alt`（时间索引）在 **1 秒内**证明最优（0.749 / 0.980 秒，`gap = 0.0000`），而 `milp_tight`（序列 + 逐对 tight Big-M）给了 5 秒仍停在 `gap 0.8984 / 0.9323`。第 4 节已经把界差算成 13.8 倍。

注意这两行的差距**不是 Big-M 松紧造成的**——`milp_tight` 用的已经是紧的那种 Big-M（`pair_big_m = H - r_k`）。差距来自**变量结构**：时间索引模型的不等式直接给出「时间格上的容量」约束，根界天然强；序列模型的不等式是析取式的大 M 表达，松弛后几乎不提供信息。

### 7.2 结论二：预算内的精确方法不保证优于规则解

`single_12` 上 `milp_tight` 给 543，而 `heur_spt` 给 532 —— **精确方法更差**。`single_20` 上也是 968 对 903。这不是 bug：5 秒不够 CBC 在弱松弛的序列模型上搜出比 SPT 更好的解。

所以正确表述是：

```text
「在这两组实例、5 秒预算下，milp_tight 的最好可行解不如 heur_spt」
而不是「MILP 不如启发式」，更不是「milp_tight 这个方法不好」。
```

### 7.3 结论三：启发式「碰巧等于最优」不能写成「SPT 最优」

`heur_spt` 在 `single_12` 给 532、在 `single_20` 给 903，而 `milp_alt` 独立证明了这两个值就是最优值。看起来像是「SPT 对 ΣT 最优」——**这个结论是错的**：

- M1 的 CE-02 已经给出反例（EDD 给 4、最优为 3），规则解不保证最优；
- 本仓库的测试集里有专门的 `single_edd_trap_instance` 用来钉死这一点；
- 这里只是**两个实例上的巧合**，样本量 2，且都是随机生成的实例。

诚实的写法：「本次两组实例上 `heur_spt` 的目标值恰好等于已证明的最优」。

### 7.4 结论四：选择矩阵随实例族翻转

`parallel_12`（12 作业 3 机，能解完）与 `parallel_24`（24 作业 3 机，解不完）给出的答案完全不同：

| 维度 | `parallel_12` | `parallel_24` |
|---|---|---|
| 最好可行解 | 39（三方并列） | 71（`cpsat_parallel`） |
| 证明最优 | 3 个方法都证明了 | **无** |
| 谁最快 | `cpsat_parallel` 0.047 s | ── |
| `cpsat_parallel` vs `milp_alt` | 并列（39 = 39） | 71 vs 74，CP-SAT 胜 |

同一类实例，只把规模从 12 加到 24，胜负就反过来了。这条实测把一句话钉死：**选择矩阵必须带规模条件**，写「并行机用 CP-SAT」是不完整的，要写「并行机、规模小、需要最优性证明时 CP-SAT 与时间索引 MILP 都行；规模上去了 CP-SAT 的可行解更好」。

### 7.5 结论五：`wall_time` 会超过预算

四行里 `wall_time > 5.0` 的有三行：`5.033`、`5.063`、`5.530`。差额是**建模时间**（因为预算只管 `solve_time`）：

```text
single_12 milp_tight  wall 5.033 - 5.0 ≈ 0.033 s 建模
single_20 milp_tight  wall 5.063 - 5.0 ≈ 0.063 s 建模
parallel_24 milp_alt  wall 5.530 - 5.0 ≈ 0.530 s 建模   ← 时间索引模型在 24 作业上
```

最后一行值得单独记住：**时间索引模型在 24 作业上的建模开销已到预算的 10% 量级**，而求解器超限的少量开销也混在差额里，所以 `0.530` 是**上界**。这正好回收 Day 4 的纪律：只记一个总耗时，就会出现「配了 5 秒却跑了 5.53 秒」这种无法解释的行。

### 7.6 警告一：`gap` 不能跨方法排序

`parallel_24` 那两行是现成的反例：

```text
cpsat_parallel  目标 71  界 24.0  gap 0.6620   ← 解更好，gap 更大
milp_alt        目标 74  界 42.2  gap 0.4293   ← 解更差，gap 更小
```

如果按 `gap` 排序，会得出「`milp_alt` 更好」的结论——但它的可行解比 CP-SAT 差 3 个单位。`gap` 更小只说明 `milp_alt` 对自己的剩余空间估计得更紧（它的界 42.2 远高于 CP-SAT 的 24.0），**不代表解更好**。

正确的读法：**跨方法看 `objective` 与 `status`，`gap` 只在同一方法随预算变化时纵向看**。

### 7.7 警告二：0.05 秒级的差异不要过度解读

`cpsat_parallel 0.047 s` vs `cpsat_symmetry 0.155 s`（都是 OPTIMAL 39）：看起来对称破缺把时间拖慢了 3 倍。但这发生在**不到 0.2 秒**的尺度上，机器的负载抖动就足以解释这个量级；更重要的解释是——实例太小（12 作业），两边的搜索都短到被**建模与传播开销**支配，破缺加进去的额外约束反而增加传播成本。这与 Day 1 的诚实负结论一致（小实例上破缺的冲突数上升、耗时上升）。**不要**把这个单点读成「对称破缺有害」——它只说明「这个小实例上没收益」。

### 7.8 选择矩阵（由实测归纳）

把四组实测与前几天的手段实验合起来，得到下面这张表。**每一行都带条件**，没有不带条件的推荐：

| 情形 | 推荐 | 依据（本日或本周的哪一条实测） |
|---|---|---|
| 规模小、必须**保证最优** | MILP（时间索引优先）或 CP-SAT | `single_12` / `single_20` 上 `milp_alt` 均在 1 秒内 `OPTIMAL` |
| 单机、排序型、目标含迟交 | 序列 MILP 建模最直接，但**界弱**；有预算压力就换时间索引 | 同一实例上界 65.5 vs 903、耗时 5 秒未证明 vs 0.98 秒证明 |
| 并行机、只看 `Cmax`、规模不大 | CP-SAT 的区间 + `AddNoOverlap` 最自然 | `parallel_12` 上 0.047 秒证明最优 |
| 多工序 / JSP 型 | CP-SAT 的 precedence + 每机器 `NoOverlap` | Week 3 的模型，本日未重复测 |
| 大规模、预算内搜不完 | 先给规则可行解，再让精确方法在剩余预算改进；`gap > 0` 是常态 | `parallel_24` 上三种精确方法都未证明最优 |
| 只要一个能用的解、且要快 | 启发式；但**它没有 `bound`**，不要与精确方法并列 `gap` | 所有启发式行 `gap = None`、0.001～0.002 秒 |
| 需要可复现的对照实验 | 固定 `workers = 1`、固定 `seed`、逐次记预算 | Day 4 的 3 秒档抖动（1519 / 968 / 968） |

强化手段（对称破缺、冗余约束、warm start、前缀固定）不在这张表的「推荐」列，因为 Day 1 与 Day 2 的消融给出的结论是：**它们不改变最优值，且在这批实例上没有观察到收益**（破缺推高冲突数、前缀固定封顶在初解）。要写进选择矩阵的只能是「在什么条件下可能有益，本批实例没测出来」，不能写成推荐。

### 7.9 这张矩阵的有效期：重测协议

选择矩阵不是知识，是**这一批实测的摘要**。换实例、换预算、换机器都要重测。重测的最小协议：

```text
① 改什么      只改一个维度（预算，或规模，或实例族），其余全部不动
② 改哪里      TIME_LIMIT 常量；CASES 里的 generate_instance 参数；方法列表
③ 记什么      状态 / 目标 / 界 / gap / iterations / build_time / solve_time
               / wall_time / seed_value / time_limit —— 十列，一列都不能少
④ 判什么      先看「验证」列是否全通过；再看「证明最优」的集合有没有变；
               最后才比较目标值
⑤ 写什么      「在 X 实例、Y 目标、Z 秒预算下，A 的最好可行解小于 B」
               —— 不写「A 比 B 好」
⑥ 存哪里      新的产物目录（不给非空目录写东西），metadata 里记下参数与来源哈希
```

最小改动量：**两处**（`TIME_LIMIT` 与实例参数），加一次重跑。如果一次重测需要改三处以上，说明实验条件没有抽出来，应当先重构再测。

不看上文回答：

- Q1：四条公平性条件是什么？缺一条会怎样？
- Q2：「更好」有哪三种含义？它们为什么可能互相矛盾？
- Q3：`single_20` 上 `milp_tight` 的界 65.5 与 `milp_alt` 的界 903 说明了什么？
- Q4：为什么 `gap` 不能用于跨方法排序？给出实测反例。
- Q5：`wall_time` 为什么会超过 `time_limit`？差额里是什么？
- Q6：`heur_spt` 在两组实例上都等于最优，为什么不能写成「SPT 对 ΣT 最优」？
- Q7：`parallel_12` 上三个方法都证明了最优，选哪个？依据是什么？
- Q8：`parallel_24` 上「在预算内证明最优的方法：无」意味着什么？该怎么做？
- Q9：脚本里 `item[1].objective or float("inf")` 有什么潜在问题？
- Q10：`cpsat_symmetry` 比 `cpsat_parallel` 慢 3 倍，能得出「对称破缺有害」吗？

### 参考答案

- A1：同一个 `Instance` 对象、同一个 `objective`、同一个 `time_limit`、同一个独立验证器。缺一条，比较就可能变成「谁跑得久谁好」或「谁的问题更简单谁好」。
- A2：可行解质量（`objective`）、可信度（是否 `OPTIMAL`）、代价（`wall_time`）。三者由不同机制决定，可以互相矛盾——解更差但界更紧、证明最优但更慢、更快但不提供证明。
- A3：同一个实例、同一目标、同一预算下，换 formulation（序列 → 时间索引）把界从 65.5 推到 903（最优值），差距约 13.8 倍，说明 formulation 的**结构**而非 Big-M 的松紧决定界的量级。
- A4：因为 `gap` 同时受目标值与界影响，不同方法的界来自不同松弛。反例：`parallel_24` 上 `cpsat_parallel`（71 / 界 24.0 / gap 0.6620）解更好但 gap 更大，`milp_alt`（74 / 界 42.2 / gap 0.4293）解更差但 gap 更小。正确排序依据是 `objective` + `status`。
- A5：因为 `time_limit` 只管 `solve_time`，`wall_time = build_time + solve_time`。差额里是建模时间（求解器超限的少量开销也混在其中，所以差额是建模时间的上界）。
- A6：那是两个随机实例上的巧合；M1 的 CE-02 已给出反例证明规则解不保证最优，`single_edd_trap_instance` 就是为此存在的。正确写法是「本次两组实例上恰好等于已证明的最优」。
- A7：看目的——要最快就用 `cpsat_parallel`（0.047 秒）；三者都 `OPTIMAL 39`，所以解质量无差别。若还要考虑建模成本与后续扩展（多工序、资源），CP-SAT 侧的表达更自然。
- A8：意味着 5 秒预算下没有任何方法同时给出一个解并证明它最优；此时应先用规则给可行解、再让精确方法在剩余预算里改进，并把 `gap > 0` 当作常态如实报告。
- A9：Python 里 `0.0` 是假值，目标值为 `0.0` 的方法会被当成 `None` 处理、被排到最后。本次运行的实例目标值都非 0，所以没触发。
- A10：不能。差异出现在不到 0.2 秒的尺度上，且实例小到由建模与传播开销支配；它只说明「这个小实例上没收益」，与 Day 1 的负结论一致，不构成「有害」的普遍结论。

## 11. 今日一句话总结

> **同实例同预算的四组实测给出了一张带条件的矩阵：时间索引 MILP 在单机 12/20 作业上用不到 1 秒证明最优（界 903 对序列模型的 65.5，差 13.8 倍），而 24 作业并行机上 CP-SAT 的可行解更好（71 对 74）却 gap 更大（0.6620 对 0.4293）——所以跨方法只能按 `objective` 与 `status` 排序，`gap` 只在同一方法内纵向看，而 `heur_spt` 这两次「恰好等于最优」只是巧合，不是「SPT 最优」。**
