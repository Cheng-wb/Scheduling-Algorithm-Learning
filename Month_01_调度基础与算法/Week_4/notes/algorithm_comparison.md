## 1. 评测对象与问题条件

算法评测需要同时回答：解的质量如何、计算成本多大、随机结果是否稳定。一次运行得到较小目标值，并不足以说明某种方法普遍更好。

实验采用单机、不可抢占、释放时间为零的任务排列问题，统一最小化总延期：

\[
T_j=\max(C_j-d_j,0),\qquad f(S)=\sum_j T_j.
\]

| 方法 | 初始解与搜索方式 |
| --- | --- |
| FCFS | 保留同时到达任务的输入顺序 |
| SPT | 按加工时间升序排列 |
| EDD | 按交期升序排列 |
| SPT + LS | SPT 起点，Swap 邻域，Best Improvement |
| Multi-start | 多个随机排列，分别运行相同的 LS，保留最好结果 |
| SPT + SA | SPT 起点，随机 Swap，概率接受差解 |

SPT 作为 **Baseline**，表示比较的参照方法，不代表最优解。SPT 对无释放时间约束的单机总完工时间具有最优性，EDD 对最大 lateness 具有最优性；这些结论不能直接用于总延期目标。

## 2. Objective 与 Metric

Objective 决定搜索时如何比较候选解。Metric 用于描述结果，可以同时报告多项指标，但不会自动参与搜索决策。

实验以总延期为 Objective，另外报告 Makespan、平均完工时间和最大 lateness。由于所有任务同时可用、排程连续加工，各排列的 Makespan 都等于总加工时间，不能据此区分总延期质量。

相对 SPT 的绝对改善与改善率为：

\[
\Delta f=f_{SPT}-f_{algorithm},\qquad
Improvement=\frac{f_{SPT}-f_{algorithm}}{f_{SPT}}\times100\%.
\]

负改善表示结果比基准更差；基准值为零时，保留绝对改善，相对改善率显示 `N/A`。

## 3. 统一输入、结果与调用接口

同一对照组使用完全相同的任务、目标函数、解码器和合法性检查。每个算法获得任务列表的副本，`Job` 为不可变对象，避免某个算法改变后续算法的输入。

`experiments/benchmark.py` 将不同接口适配为：

```python
solver(jobs, decode, score) -> result
```

`run_algorithm()` 负责计时、实际目标调用计数和最终结果复核，搜索模块继续接收解码器与目标函数，不依赖实验报表。

| 结果字段 | 含义 |
| --- | --- |
| algorithm / instance | 算法名、实例标识 |
| instance_seed / algorithm_seed | 实例与算法随机种子 |
| objective / solution | 最终总延期、任务排列 |
| runtime / evaluations | 秒数、实际目标函数调用次数 |
| iterations / restarts | 算法自身迭代数、总起点数 |
| improvement / improvement_rate | 相对 SPT 的绝对与相对改善 |
| status / error / stop_reason | 运行状态、错误信息、停止原因 |

正常结果标为 `OK`；运行异常标为 `ERROR`；排程、分数或计数复核失败标为 `INVALID`。失败值不填零、不参与质量统计，同时保留失败数量。

## 4. Runtime、评价次数与公平预算

使用 `perf_counter()` 测量从初始化到搜索结束的时间，包括规则排序、随机初始解生成、排程解码、搜索中的校验和目标计算；最终报表复核与文件写入不计入。计时反映当前实现和运行环境的成本，并非纯算法理论复杂度。

评价次数通过包装目标函数实际累计，并与算法内部计数交叉核对：

- 规则：初始排程评价一次。
- 单次 LS：一次初始评价，加全部邻居评价，包括最后一次无改进扫描。
- Multi-start：所有起点的初始评价和邻居评价之和。
- SA：一次初始评价，加每个候选邻居的评价，无论是否接受。

LS 的 Iterations 是成功更新次数，SA 的 Iterations 是候选评价次数，Multi-start 另有起点数。因此相同 Iterations 不等于相同计算量。

Runtime Budget 限制实际运行时间，但受硬件、负载与实现开销影响。Evaluation Budget 限制目标调用次数，更容易复现搜索工作量，但不同规模下一次评价的成本不同，也不包括全部其他开销。

本实验统一计数口径，**未实现硬时间预算或硬评价预算**。LS 的更新上限和 SA 的候选上限不是统一预算，结果仅表示给定配置的质量与成本。后续等预算实验需要在每次评价前检查剩余预算，并保留预算耗尽前的最好解。

## 5. 随机性与稳定性

Instance Seed 控制任务数据；Algorithm Seed 控制随机起点、邻居与接受决策。固定实例、改变算法种子，才是在观察同一问题上的算法稳定性。

对成功运行的目标值统计 Best、Mean、Worst 与样本标准差：

\[
\bar f=\frac1k\sum_{i=1}^k f_i,\qquad
s=\sqrt{\frac{\sum_{i=1}^k(f_i-\bar f)^2}{k-1}}.
\]

最小化问题中 Best 取最小值、Worst 取最大值。只有一次成功运行时，代码约定 Std 为零，这不提供稳定性证据。多个种子均得到相同结果，也不能证明全局最优。

## 6. 实验配置与结果

任务加工时间均匀取整数 `[1,20]`，交期取 `[20,150]`，释放时间均为零。实例种子为 42。LS 使用 Swap + Best，最多接受 1000 次更新；Multi-start 使用 20 个随机起点；SA 初温 100、降温率 0.95、最低温度 `1e-6`、候选上限 1000。

### 固定 20 任务对照

随机算法种子为 42。以下为一次实际运行，耗时随环境变化。

| 方法 | 总延期 | 改善率 | 评价次数 | 耗时 / s |
| --- | ---: | ---: | ---: | ---: |
| FCFS | 811 | -96.37% | 1 | 0.0005 |
| SPT | 413 | 0.00% | 1 | 0.0003 |
| EDD | 358 | 13.32% | 1 | 0.0003 |
| SPT + LS | 296 | 28.33% | 1521 | 0.3412 |
| Multi-start | 260 | 37.05% | 61580 | 13.6915 |
| SPT + SA | 284 | 31.23% | 361 | 0.0824 |

Multi-start 得到此组最小总延期，但成本最高。SA 比单次 LS 的目标值更小、评价更少，这是当前实例与种子下的结果，不能推导为普遍优越性。SA 在 360 次候选评价后触及温度停止条件，未用满 1000 次上限。

### 固定实例，算法种子 0～4

| 方法 | 成功数 | Best | Mean | Worst | Std | 平均评价次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Multi-start | 5/5 | 260 | 260.00 | 260 | 0.00 | 59794 |
| SPT + SA | 5/5 | 271 | 289.60 | 310 | 14.81 | 361 |

这组配置下 Multi-start 的五次结果一致，SA 存在可见波动。应联合查看均值、离散程度与成本，而不是只挑随机算法最好的一次。

### 问题规模对照

| 任务数 | SPT 总延期 | LS 总延期 | SA 总延期 | LS 评价次数 | SA 评价次数 | LS 耗时 / s | SA 耗时 / s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 69 | 0 | 0 | 136 | 361 | 0.0277 | 0.0812 |
| 20 | 413 | 296 | 284 | 1521 | 361 | 0.3412 | 0.0824 |
| 30 | 1702 | 1520 | 1536 | 7396 | 361 | 2.7948 | 0.1287 |

Swap 一层邻域有 `n(n-1)/2` 个候选，LS 的完整扫描随规模增长更贵；SA 的候选数量相同，但每次解码与评价成本仍随任务数增长。10 任务上的零总延期达到非负目标的下界，因此可确认最优。

不同规模使用同一随机序列的前缀，交期范围固定。规模增加同时提高了任务拥挤程度，因此这不是只改变规模、保持难度不变的实验。每个规模也只有一个实例，不能据此拟合普遍的运行时间规律。

## 7. 实验入口与记录

在仓库根目录运行：

```powershell
python "projects/search_lab/experiments/algorithm_comparison.py"
```

入口依次执行统一算法对照、五种子稳定性统计、10/20/30 任务规模实验。终端按列宽对齐文本与数字，不打印完整搜索轨迹。

每次运行在 `results/day6_时间戳/` 保存：

- `config.json`：参数、种子、目标、数据范围和运行环境。
- `instances.json`：实际任务属性。
- `runs.csv`：各实验组的逐次结果、排列、指标与停止原因。
- `summary.csv`：随机算法的成功数与统计汇总。

完全相同的实例、算法、种子和配置复用同一次测量；统计仅使用稳定性组，不把跨组重复展示当作独立样本。复现实验应同时保留这些文件与对应代码版本。

统一 Runner、输入与日志为后续项目整合提供基础。扩展 Benchmark 时可增加独立实例、明确的统一预算和结果可视化，继续保持数据、搜索与评价分离。
